# verify — 교차 검증 실행

이 스킬은 **절차의 정본**이다. 규칙(리뷰어 구성, 평가 영역 5종, 확정 기준, 중요도 정의, 결과 파일·backlog 형식, 기록 금지 사항)의 정본은 [교차 검증 계약](../../../docs/workflow/REVIEW.md)이며 여기서 중복 기술하지 않는다. 규칙과 이 문서가 어긋나면 계약이 이긴다.

너는 이 절차에서 **조정자**다. 독립 리뷰를 산출하지 않는다. 네가 혼자 발견한 것은 확정 발견이 아니다.

## 1. 대상 확정

1. 대상 task를 정한다. 인자로 task ID를 받았으면 그것, 없으면 `docs/execution/phases/index.jsonl`의 현재 `in_progress` task다. 수동 전체 스캔이면 대상은 코드베이스 전체다.
2. 기준 커밋을 정한다. 그 task의 handoff(`docs/execution/runs/<task-id>/handoff.md`)에 적힌 기준 커밋을 쓰고, 없으면 현재 `HEAD`의 전체 SHA-1 40자를 쓴다.
3. 리뷰 대상 파일 목록을 모은다(`git diff --name-only <기준 커밋>`와 미추적 파일). 수동 전체 스캔이면 대상 디렉터리 목록으로 대신한다.
4. 관련 spec ID와 승인된 RADIO(`docs/execution/radio/<task-id>-radio.md`) 경로를 모은다.

여기까지가 **두 리뷰어에게 똑같이 전달할 대상 정보**다.

## 2. 리뷰어 2자 병렬 호출

두 리뷰어를 **병렬로** 호출한다. 전달하는 것은 1단계의 대상 정보와 평가 영역 5종뿐이다. 너의 의견·발견·결론·점수는 어느 쪽에도 전달하지 않는다.

| 리뷰어 | 호출 |
| --- | --- |
| `opus` | `subagent_type: "reviewer"`로 [`reviewer` 에이전트](../../agents/reviewer.md)를 띄운다 |
| `codex` | `codex exec -s read-only -C <저장소 경로> -o <결과 파일> -` 로 실행하고 지시문을 표준 입력으로 넣는다(모델 미지정). `-s read-only`는 리뷰어의 쓰기를 실행 환경에서 막는 필수 플래그다 |

두 결과는 모두 리뷰어 결과 JSON이다.

```json
{"findings":[{"title":"","severity_candidate":"","area":"","description":"","file":""}],"scores":{},"score_rationale":{}}
```

- 리뷰어는 도구가 읽기 전용이라 명령을 실행하지 못한다. `git diff --name-only <기준 커밋>`처럼 실행이 필요한 사실 자료는 **네가 실행해 대상 정보에 담아** 전달한다. 사실 자료만 주고 판단은 주지 않는다.
- 회수한 텍스트에서 마지막 JSON 블록만 파싱한다. 파싱에 실패하면 그 리뷰어에게 **형식만 다시** 요구한다. 네가 대신 채우지 않는다.
- Codex CLI를 쓸 수 없으면 독립 Opus 서브 에이전트 2자(`opus`·`opus-2`)로 대체한다. 두 인스턴스는 같은 `reviewer` 에이전트이며 식별자는 네가 기록할 때 구별한다. 검증을 건너뛰거나 네가 리뷰어 자리를 대신하지 않는다. 대체 사유는 결과 파일의 `participants_note`에 적는다.

## 3. 결과 병합

1. 두 결과를 한자리에 모은다. 같은 결함을 가리키는 발견은 하나로 병합한다(같은 파일·같은 원인이면 표현이 달라도 같은 발견이다).
2. 각 발견에 임시 `id`를 붙이고 **상대 리뷰어에게 되물어** 인정 또는 반박을 받는다. 두 리뷰어가 이미 같은 결함을 낸 병합 발견은 되묻지 않고 전원 인정으로 본다.
3. 되묻는 단계에서도 너의 판단을 얹지 않는다. 발견의 제목·설명·파일 경로만 그대로 전달하고, 상대의 점수는 전달하지 않는다.

되묻기는 같은 리뷰어 인스턴스를 이어서 쓴다. `opus`는 그 서브 에이전트에 메시지를 보내고, `codex`는 `codex exec resume --last -o <결과 파일> -`로 이어간다(`resume`은 `-s`·`-C`를 받지 않으므로 저장소 디렉터리에서 실행한다).

전달 형식과 회수 형식은 다음과 같다. 회수한 텍스트에서도 마지막 JSON 블록만 읽는다.

```text
[<id>] <제목> (파일: <경로>)
<설명>
```

```json
{"verdicts":[{"id":"","agree":true,"severity_candidate":"critical|high|medium|low","reason":""}]}
```

- 답이 빠진 항목이 있으면 그 항목만 다시 요구한다. 무응답을 인정으로도 반박으로도 해석하지 않는다.
- 반박에 근거가 없으면 근거를 요구한다. 근거 없는 반박으로는 발견이 기각되지 않는다.

## 4. 확정과 중요도 판독

- **참여 리뷰어 전원**이 인정한 발견만 확정한다. 한쪽만 주장한 발견은 기각하고 결과 파일에도 backlog에도 남기지 않는다. 판단이 갈린 사실 자체가 중요하면 해당 task의 handoff 미결 사항에 적는다.
- 확정 발견마다 중요도(`critical`·`high`·`medium`·`low`)를 판독한다. 정의는 계약이 소유한다. 리뷰어의 `severity_candidate`가 갈리면 **더 높은 쪽**을 택하고 사유를 `description`에 적는다.
- 확정 발견에 `id`를 `F-01`부터 순번으로 붙이고 `agreed_by`에 인정한 리뷰어를 적는다.

## 5. 최종 영역 점수 판정

- 5개 영역 점수는 **네가** 판정한다. 리뷰어 점수의 산술 평균을 그대로 쓰지 않는다.
- 근거는 **확정 발견**과 각 리뷰어의 영역 평가다. 기각된 발견은 점수의 근거로 쓰지 않는다.
- 영역마다 판정 근거 한 줄을 `score_rationale`에 남긴다. 판단 재료가 없던 영역은 100점을 주되 그 사실을 근거에 명시한다.

## 6. 기록

- task 검증: `docs/execution/reviews/<task-id>-review.json`
- 수동 전체 스캔: `docs/execution/reviews/scan-<YYYY-MM-DD>-review.json` (`task_id` 대신 `scope: "full-scan"`)

`total`은 5개 영역 점수의 산술 평균을 반올림한 정수다. 파서가 검증하므로 어긋나면 대시보드에 형식 오류로 뜬다. `participants`에는 실제 리뷰를 산출한 리뷰어 2자만 적는다(조정자 `main`은 넣지 않는다).

`medium`·`low` 확정 발견은 [backlog](../../../docs/execution/reviews/backlog.md)에 한 줄씩 누적한다. 비밀값·토큰·개인정보와 그대로 악용 가능한 payload는 결과 파일·backlog·보고 어디에도 적지 않는다.

## 7. 에스컬레이션

| 중요도 | 처리 |
| --- | --- |
| `critical` | 해당 task를 `blocked`로 전환하고 결정 신호·handoff를 기록한 뒤 즉시 사용자에게 보고한다 |
| `high` | 즉시 사용자에게 보고하되 개발 루프는 계속한다 |
| `medium`·`low` | backlog에 누적하고 개별 보고하지 않는다 |

검증은 읽기 전용이다. 이 절차 안에서 코드를 고치지 않는다. 수정은 결과를 받은 뒤 개발 단계에서 한다. 리뷰 결과를 근거로 현재 task의 승인 범위를 넓히지 않는다.
