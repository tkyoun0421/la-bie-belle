## 기본 자세

명령형으로 쓴다. "~하면 좋습니다"가 아니라 "~한다".

**이유를 같이 적는다.** 이게 가장 크게 갈리는 지점이다. 모델은 이유를 알면 안 적힌 상황에서도 맞게 판단하지만, 규칙만 받으면 규칙 밖에서 무너진다. 대문자 MUST와 NEVER를 쌓는 건 이유를 안 적었다는 신호다. 그런 줄을 발견하면 지우지 말고 왜 그게 중요한지로 바꿔 쓴다.

**한 사례에 맞추지 않는다.** 스킬은 몇 번이 아니라 수천 번 쓰인다. 개발하는 동안에는 시나리오 두세 개만 반복해서 보니까 거기에 맞춰 조건을 덧대기 쉬운데, 그렇게 만든 스킬은 그 세 개 밖에서 쓸모가 없다. 잘 안 풀리는 자리가 있으면 조건을 더하는 대신 설명 방식 자체를 바꿔본다. 시도 비용이 싸고 가끔 훨씬 나은 걸 찾는다.

**초안을 쓰고 다시 본다.** 한 번에 완성하려 하지 말고, 쓴 뒤에 새로 읽으며 안 쓰이는 줄을 뺀다.

## 출력 형식을 못 박는 법

형식이 정해져 있으면 템플릿을 통째로 박는다. 말로 설명하는 것보다 짧고 어긋나지 않는다.

```markdown
## 리포트 구조
항상 이 형식을 그대로 쓴다:
# [제목]
## 요약
## 발견
## 권고
```

## 예시를 넣는 법

애매한 자리에는 입력과 출력을 짝지어 보여준다. 규칙 세 줄보다 예시 하나가 잘 통할 때가 많다.

```markdown
## 커밋 메시지 형식
**예시 1**
입력: JWT 토큰으로 사용자 인증을 붙였다
출력: feat(auth): implement JWT-based authentication
```

## 안 되는 것

**Windows 경로.** 항상 슬래시로 쓴다 — `scripts/helper.py`. 역슬래시는 그대로 안 통한다.

**선택지 나열.** "pypdf를 써도 되고 pdfplumber를 써도 되고 PyMuPDF도 있다"는 결정을 모델에게 떠넘긴 것이다. 기본값 하나를 정해주고, 그게 안 되는 조건에서만 대안을 알려준다.

**시간에 묶인 서술.** "2025년 8월 이전에는 ~"처럼 쓰면 시간이 지나면서 틀린 문장이 된다. 옛 방식이 꼭 필요하면 "예전 방식" 절로 따로 접어둔다.

**용어 흔들기.** 같은 것을 API endpoint라고 했다가 URL이라고 했다가 route라고 하면 모델이 다른 것으로 읽는다. 하나를 골라 끝까지 쓴다.

**모델에게 떠넘기기.** 스크립트 안에서 에러를 그냥 흘려보내고 모델이 알아서 처리하기를 기대하지 않는다. 예상되는 실패는 스크립트가 명시적으로 다룬다.

**근거 없는 상수.** `REQUEST_TIMEOUT = 30`처럼 숫자만 있으면 나중에 아무도 못 고친다. 왜 30인지 주석으로 남긴다.

**설치돼 있다고 가정.** "PDF 라이브러리를 쓴다" 대신 `pip install pypdf`를 적는다.

**MCP 도구 이름 줄이기.** 서버 이름을 붙인 전체 이름(`ServerName:tool_name`)으로 적는다. 프리픽스가 없으면 도구를 못 찾을 수 있다.

**참조를 깊게 쌓기.** SKILL.md에서 모든 참조 파일에 바로 닿게 한다. 한 겹 더 들어가면 모델이 거기까지 안 간다.

## 스크립트를 넣을 때

`scripts/`에 있는 코드는 컨텍스트에 안 실리고 그냥 실행된다. 그래서 결정적이고 반복되는 일은 지침으로 설명하는 것보다 스크립트로 넣는 편이 싸고 정확하다.

넣을지 판단하는 신호는 하나다. **시나리오를 여러 개 돌려봤는데 매번 비슷한 헬퍼를 새로 짜고 있다면** 그건 스크립트로 뺄 자리다. 한 번 써서 넣어두면 다음부터 아무도 다시 안 짠다.

## 해서는 안 되는 스킬

스킬은 설명된 대로만 동작해야 한다. 사용자가 설명을 읽고 예상하지 못할 일을 스킬이 몰래 하면 안 된다.

악성 코드, 익스플로잇, 무단 접근이나 데이터 유출을 돕는 스킬은 만들지 않는다. 요청이 그런 쪽이면 거기서 멈춘다. "XYZ 역할로 연기한다" 같은 건 문제없다.
