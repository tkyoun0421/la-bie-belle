## 평가를 먼저 만든다

Anthropic 문서는 이렇게 못 박는다 — "There is not currently a built-in way to run these evaluations." 돌려주는 도구가 없으니 직접 설계한다.

그리고 **긴 지침을 쓰기 전에** 만든다. 순서가 반대면 무엇이 부족한지 모르는 채로 줄을 쌓게 되고, 나중에 그중 어느 줄이 일하고 있는지 가릴 방법이 없다.

1. 스킬 없이 대표 과제를 시켜본다. 어디서 무너지는지 본다
2. 그 구멍을 겨냥한 시나리오를 셋 이상 쓴다
3. 스킬 없는 상태의 결과를 기준선으로 남긴다
4. 최소한의 지침만 쓴다
5. 돌려보고 고친다

시나리오는 실제 사용자가 할 법한 말로 쓴다. 추상적인 한 줄이 아니라 파일 이름, 컬럼 이름, 사정 설명이 들어간 구체적인 요청이어야 한다.

## 시나리오 형식

```json
{
  "skills": ["pdf-processing"],
  "query": "이 PDF에서 텍스트를 전부 뽑아서 output.txt로 저장해줘",
  "files": ["test-files/document.pdf"],
  "expected_behavior": ["...", "...", "..."]
}
```

`expected_behavior`는 객관적으로 확인되는 것만 적는다. 글의 문체나 디자인 품질처럼 사람이 봐야 아는 것에 억지로 항목을 붙이면, 통과하든 말든 아무것도 알려주지 않는 검사가 된다. 그런 스킬은 사람이 결과를 직접 보고 판단하는 편이 낫다.

## 돌리는 법

시나리오마다 둘을 같이 돌린다 — 스킬을 준 실행과 안 준 실행. 나중에 몰아서 하지 말고 한꺼번에 띄운다.

- **새 스킬을 만드는 중이면** 기준선은 "스킬 없음"이다
- **있는 스킬을 고치는 중이면** 기준선은 고치기 전 버전이다. 편집하기 전에 스킬 디렉터리를 복사해두고 그 복사본을 기준선으로 쓴다

결과는 반복 회차별로 나눠 쌓는다. 회차를 덮어쓰면 좋아졌는지 나빠졌는지를 못 본다.

```
<skill-name>-workspace/
├── iteration-1/
│   ├── <시나리오-이름>/
│   │   ├── with_skill/outputs/
│   │   └── without_skill/outputs/
│   └── ...
└── iteration-2/
```

디렉터리 이름은 `eval-0` 대신 무엇을 보는 시나리오인지 알 수 있게 짓는다.

**Haiku와 Sonnet과 Opus에서 다 돌려본다.** 큰 모델에서만 되는 지침은 실제로는 반쯤 깨진 지침이다.

## 반복 루프

1. 결과를 사람에게 보여주고 피드백을 받는다
2. 피드백을 일반화해서 스킬을 고친다 — 그 사례에만 맞는 땜질은 넣지 않는다
3. 기준선까지 포함해 전부 다시 돌린다
4. 이전 회차와 나란히 놓고 본다

멈추는 조건은 셋 중 하나다. 사용자가 만족하거나, 지적할 게 안 남거나, 더 고쳐도 나아지지 않는다.

**결과만 보지 말고 기록을 읽는다.** 모델이 헛도는 자리가 보이면 그렇게 만든 지침을 지우고 다시 돌려본다. 스킬을 짧게 유지하는 가장 확실한 방법이다.

## 트리거를 따로 평가한다

본문이 좋아도 안 불리면 소용없다. 트리거는 별도로 잰다.

질문 스무 개를 만든다. 걸려야 하는 것 8~10개, 안 걸려야 하는 것 8~10개.

```json
[
  {"query": "사용자가 실제로 칠 법한 요청", "should_trigger": true},
  {"query": "다른 요청", "should_trigger": false}
]
```

질문은 구체적이어야 쓸모가 있다. 경로, 파일 이름, 컬럼 이름, 회사 이름, 사정 설명이 들어가고 길이도 제각각이며 오타나 반말이 섞여도 된다.

- 나쁘다 — "데이터 정리해줘", "PDF에서 텍스트 뽑아줘"
- 좋다 — "부장님이 방금 xlsx 파일 보내줬는데 다운로드 폴더에 'Q4 sales final FINAL v2.xlsx' 이런 이름으로 있어. 이익률을 퍼센트로 보여주는 컬럼 하나 추가해달래. 매출이 C열이고 원가가 D열인 것 같은데"

**걸려야 하는 쪽**은 같은 의도를 여러 말투로 담는다. 스킬 이름이나 파일 형식을 직접 말하지 않는데도 명백히 이 스킬이 필요한 경우, 드문 용례, 다른 스킬과 겹치지만 이쪽이 이겨야 하는 경우를 넣는다.

**안 걸려야 하는 쪽**은 아슬아슬한 것일수록 값을 한다. 키워드는 겹치는데 실제로는 다른 게 필요한 요청, 이 스킬이 다루는 영역을 스치지만 다른 도구가 맞는 상황이 그렇다. PDF 스킬의 반대 사례로 "피보나치 함수 짜줘"를 넣는 건 아무것도 검사하지 않는다.

질문 세트는 사용자에게 먼저 확인받는다. 질문이 나쁘면 거기서 나온 description도 나쁘다.

Anthropic 공식 `skill-creator` 플러그인에는 이 루프를 자동으로 도는 스크립트(`scripts/run_loop.py`)가 들어 있다. 설치돼 있으면 그걸 쓰고, 없으면 위 절차를 손으로 돌린다.

## 스킬이 불리는 원리

Claude는 스킬 목록에서 이름과 description만 보고 열어볼지 정한다. 그런데 **혼자 쉽게 처리되는 일에는 스킬을 안 꺼낸다.** "이 PDF 읽어줘" 같은 한 단계짜리 요청은 description이 아무리 잘 맞아도 안 걸린다 — 기본 도구로 되는 일이기 때문이다.

그래서 평가 질문도 스킬을 볼 만한 무게가 있어야 한다. "파일 X 읽어줘"로는 description의 좋고 나쁨을 가리지 못한다.
