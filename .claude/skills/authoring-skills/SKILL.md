# 스킬 저술

스킬은 Claude가 특정 일을 만났을 때만 꺼내 읽는 지침 묶음이다. 잘 만든 스킬은 둘을 한다. 필요한 순간에 정확히 불려 나오고, 불려 나온 뒤에 컨텍스트를 적게 먹는다.

이 둘은 서로 다른 문제다. 불리는 쪽은 `description` 한 줄이 정하고, 먹는 양은 본문을 어떻게 쪼갰느냐가 정한다. 그래서 작업도 두 갈래로 나뉜다.

## 먼저 물을 것

지금 대화에 이미 재료가 있을 때가 많다. 사용자가 "방금 한 거 스킬로 만들자"고 하면 대화 기록에서 먼저 뽑아낸다 — 쓴 도구, 단계 순서, 사용자가 중간에 잡아준 것, 입력과 출력 형식. 빈 자리만 사용자에게 묻고, 넘어가기 전에 확인을 받는다.

빈 자리를 채우는 질문은 넷이다.

1. 이 스킬이 있으면 Claude가 무엇을 하게 되나
2. 언제 불려야 하나 — 사용자가 어떤 말을 할 때인가
3. 결과물 형식은 무엇인가
4. 검증할 테스트가 필요한가

넷째는 스킬 성격이 정한다. 파일 변환, 데이터 추출, 코드 생성, 고정된 절차처럼 결과를 객관적으로 확인하는 스킬이면 테스트가 값을 한다. 글의 문체나 디자인 취향처럼 사람이 봐야 아는 스킬이면 억지로 붙이지 않는다. 성격에 맞는 기본값을 먼저 제안하고 결정은 사용자에게 남긴다.

경계 사례, 입출력 형식, 예시 파일, 성공 기준, 의존성을 먼저 물어 정리한다. 여기가 덜 정리된 채로 초안을 쓰면 나중에 통째로 다시 쓰게 된다.

## 어디에 두는가

| 범위 | 경로 |
|---|---|
| 개인 | `~/.claude/skills/<skill-name>/SKILL.md` |
| 프로젝트 | `.claude/skills/<skill-name>/SKILL.md` |
| 플러그인 | `<plugin>/skills/<skill-name>/SKILL.md` |

디렉터리 이름과 `name` 필드를 맞춘다. 기존 스킬을 고칠 때는 디렉터리 이름과 `name`을 그대로 둔다 — `-v2` 같은 걸 붙이면 사용자가 설치해둔 스킬과 별개 스킬이 되어버린다.

## 프론트매터

표준 스펙에서 필수는 `name`과 `description` 둘뿐이다.

```yaml
---
name: processing-pdfs
description: PDF에서 텍스트와 표를 뽑고, 양식을 채우고, 문서를 합친다. PDF 파일을 다루거나 사용자가 PDF·양식·문서 추출을 언급할 때 쓴다.
---
```

제약은 지키지 않으면 로딩이 막히는 종류다.

- `name` — 최대 64자, 소문자와 숫자와 하이픈만, XML 태그 금지, `anthropic`과 `claude`는 예약어라 못 쓴다
- `description` — 비면 안 되고 최대 1,024자, XML 태그 금지

이름은 동명사꼴이 낫다(`processing-pdfs`, `analyzing-spreadsheets`). `helper`나 `utils`나 `tools`처럼 무엇을 하는지 안 알려주는 이름은 피한다.

Claude Code 로컬 스킬은 `allowed-tools`, `model`, `disable-model-invocation` 같은 필드를 더 받는다. 반면 claude.ai 업로드와 Skills API는 여섯 개(`name`, `description`, `allowed-tools`, `compatibility`, `license`, `metadata`)만 받고 나머지는 에러로 막는다. **배포처에 따라 허용 필드가 다르다** — 전체 목록과 각 필드가 하는 일은 `references/frontmatter.md`에 있다. 로컬 밖으로 내보낼 스킬을 만들 때 반드시 읽는다.

## description이 트리거를 정한다

스킬은 이름과 description만 항상 컨텍스트에 올라가 있다. Claude는 그 한 줄만 보고 이 스킬을 열어볼지 정한다. 본문이 아무리 좋아도 여기서 안 걸리면 스킬은 없는 것과 같다.

**3인칭으로 쓴다.** description은 시스템 프롬프트에 그대로 박히기 때문에 시점이 섞이면 탐색이 흔들린다.

- 좋다 — "Excel 파일을 처리하고 리포트를 만든다"
- 나쁘다 — "제가 Excel 파일 처리를 도와드립니다", "이걸로 Excel을 처리할 수 있습니다"

**무엇을 하는지와 언제 쓰는지를 둘 다 담는다.** "언제"에 해당하는 말은 전부 여기 들어가고 본문에는 남기지 않는다. 본문은 이미 불려 나온 뒤에야 읽히니까 트리거에 기여하지 못한다.

**조금 밀어붙인다.** Claude는 스킬을 덜 부르는 쪽으로 기운다. 그래서 "대시보드를 빠르게 만드는 법"보다 "대시보드를 빠르게 만드는 법. 사용자가 대시보드나 데이터 시각화나 사내 지표를 언급하면, 대시보드라는 말을 직접 안 써도 이 스킬을 쓴다"가 실제로 더 잘 걸린다.

**모호한 말은 트리거가 안 된다.** "문서 관련 작업을 돕는다", "데이터를 처리한다", "파일로 뭔가 한다" 같은 문장은 어느 대화에나 반쯤 걸려서 결국 아무 데도 안 걸린다.

## 본문 구조 — 세 겹으로 나눈다

스킬은 세 단계로 로딩된다. 이걸 알고 쪼개야 컨텍스트를 아낀다.

| 단계 | 언제 실리나 | 비용 |
|---|---|---|
| 이름 + description | 항상 | 스킬당 100 토큰 안팎 |
| SKILL.md 본문 | 스킬이 걸렸을 때 | 5천 토큰 미만 |
| 묶음 파일 | 필요할 때만 | 열기 전까지 0 |

디렉터리 구성은 성격대로 나눈다.

```
skill-name/
├── SKILL.md          (필수)
├── scripts/          실행할 코드. 컨텍스트에 안 실리고 그냥 돌아간다
├── references/       필요할 때 읽는 문서
└── assets/           결과물에 들어가는 파일 — 템플릿, 아이콘, 폰트
```

규칙 셋을 지킨다.

- **SKILL.md는 500줄 아래로.** 한계에 가까워지면 계층을 하나 더 만들고, 어느 파일을 언제 읽어야 하는지 SKILL.md에서 분명히 가리킨다
- **참조는 한 겹만.** SKILL.md에서 모든 참조 파일로 바로 닿게 한다. SKILL.md가 A.md를 가리키고 A.md가 다시 B.md를 가리키는 구조는 만들지 않는다
- **100줄 넘는 참조 파일에는 목차를 단다**

여러 갈래를 지원하는 스킬은 갈래별로 파일을 나눈다. 그래야 Claude가 해당하는 하나만 읽는다.

```
cloud-deploy/
├── SKILL.md          (절차 + 어느 갈래인지 고르기)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

## 본문을 쓰는 법

명령형으로 쓴다. 그리고 **왜 그래야 하는지를 같이 적는다.** 대문자 MUST와 NEVER를 쌓는 대신 이유를 설명하면 모델이 안 적힌 상황에서도 맞게 판단한다. 대문자 강제어를 여러 개 쓰고 있다면 그건 이유를 안 적었다는 신호다.

출력 형식이 정해져 있으면 템플릿을 통째로 박고, 애매한 자리에는 입력과 출력을 짝지은 예시를 넣는다. 예시가 규칙 세 줄보다 잘 통할 때가 많다.

특정 예시에만 맞는 지침은 피한다. 스킬은 몇 개 사례가 아니라 수천 번 쓰이는 물건이라, 한 사례를 고치려고 조건을 덧대면 나머지가 망가진다.

안 되는 것 목록과 상세 패턴은 `references/writing.md`에 있다. 초안을 쓴 뒤와 고치기 전에 읽는다.

## 검증

Anthropic 문서에는 이렇게 적혀 있다 — "There is not currently a built-in way to run these evaluations." 평가를 돌리는 빌트인 도구가 없어서 직접 설계한다.

**긴 문서를 쓰기 전에 평가를 먼저 만든다.** 무엇이 부족한지 모르는 채로 지침을 쌓으면 필요 없는 줄이 늘어난다.

1. 스킬 없이 대표 과제를 시켜본다. 어디서 무너지는지 본다
2. 그 구멍을 겨냥한 시나리오를 셋 이상 쓴다
3. 스킬 없는 상태의 결과를 기준선으로 남긴다
4. 최소한의 지침만 쓴다
5. 돌려보고 고친다

시나리오 형식과 채점, 반복 루프는 `references/evaluation.md`에 있다.

넘기기 전 점검:
- 시나리오 셋 이상을 만들었나
- Haiku와 Sonnet과 Opus에서 다 돌려봤나
- 실제 사용 상황으로 확인했나

## 이미 있는 스킬을 고칠 때

고칠 때는 결과가 아니라 기록을 본다. 결과만 보면 왜 그렇게 됐는지가 안 보인다.

- **피드백을 일반화한다.** 특정 사례에만 맞는 땜질이나 빡빡한 금지 조항 대신, 걸리는 자리가 있으면 설명 방식 자체를 바꿔본다
- **안 쓰이는 줄을 뺀다.** 기록을 읽고 모델이 헛도는 자리를 찾아, 그렇게 만든 지침을 지우고 다시 돌려본다
- **되풀이되는 작업은 스크립트로 뺀다.** 시나리오 셋이 전부 비슷한 헬퍼를 각자 새로 짰다면 그건 `scripts/`에 넣으라는 신호다. 한 번 써두면 다음부터 아무도 다시 안 짠다

description이 문제일 때는 본문을 건드려도 안 낫는다. 안 불리는 증상이면 description부터 고친다.

## 마지막 점검

- `name`이 64자 아래, 소문자·숫자·하이픈만, 디렉터리 이름과 같다
- `description`이 3인칭이고, 무엇을 하는지와 언제 쓰는지를 둘 다 담고, 1,024자 아래다
- SKILL.md가 500줄 아래고, 참조 파일이 전부 SKILL.md에서 한 번에 닿는다
- 경로를 전부 슬래시(`/`)로 썼다
- 시나리오 셋 이상으로 돌려봤다
- 설명된 대로만 동작한다 — 사용자가 예상 못 할 일을 스킬이 하지 않는다

## 참조 파일

- `references/frontmatter.md` — 필드 전체 목록, 배포처별 허용 필드 차이
- `references/writing.md` — 본문 작성 패턴과 안 되는 것 목록
- `references/evaluation.md` — 평가 시나리오 설계와 반복 루프
