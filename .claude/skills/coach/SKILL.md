# coach — 레이어별 점검과 개선 제안

**이 스킬은 코드 결함을 찾지 않는다.** 그건 [verify](../verify/SKILL.md)의 전체 스캔 몫이다. coach가 보는 것은 **일하는 방식 자체가 어디서 막히고 어디서 새는가**다. 게이트가 헛돌거나, 문서가 코드를 못 따라가거나, backlog가 쌓이기만 하거나, 특정 레이어에 결합이 몰리는 것 — 이런 것들이다.

훅도 주기 실행도 두지 않는다. **언제 돌릴지는 언제나 사람이 정한다.** 결과는 파일로 남고 대시보드 코칭 페이지가 표시한다.

## 1. 기준 확정

1. 기준 커밋은 현재 `HEAD`의 전체 SHA다.
2. 실행 날짜(`YYYY-MM-DD`)를 정한다 — 결과 파일 이름에 쓴다.
3. 사용자가 축을 지정했으면 그 축만 본다. 지정이 없으면 다섯 축 전부다.

## 2. 축별 조사

축마다 **읽기 전용 서브 에이전트 하나**를 띄운다. 서브 에이전트에는 도구를 `Read`·`Grep`·`Glob`로 제한하고, 파일을 고치거나 커밋하지 말라고 명시한다. 다섯을 한 번에 띄워 병렬로 돌린다.

| 축 | 무엇을 보나 | 주로 읽을 곳 |
| --- | --- | --- |
| L1 협업 | 워크플로 마찰, 게이트가 막지 못한 사고, 재봉인·수정 라운드 빈도, 에이전트 계약과 실제 운영의 어긋남 | `docs/workflow/`, `.claude/agents/`, `docs/execution/runs/*/handoff.md`, `docs/execution/retrospective/cases.md` |
| L2 제품 문서 | PRD·DOMAIN·DECISIONS의 미결·모순, 결정이 코드에 반영 안 된 곳 | `docs/product/` |
| L3 표준 | ADR의 상태(제안만 되고 안 닫힌 것), DEVELOPMENT 규칙 중 강제되지 않는 것 | `docs/standards/` |
| L4 실행 증거 | backlog 적체와 그 나이, flaky 테스트, 교차 검증 점수 추세, 회고 제안 중 방치된 것 | `docs/execution/reviews/`, `docs/execution/retrospective/proposals.md`, CI 이력 |
| L5 코드 | FSD 레이어별 결합·중복·크기 쏠림, 세그먼트 규칙 위반 근처, 테스트 없는 구역 | `src/`, `config/fsd.json`, `tests/` |

각 서브 에이전트에게 요구할 것은 **관찰과 근거**다. 축마다 최대 5건, 각 건에 `파일:줄` 또는 문서 절 인용을 붙이게 한다. 고치는 방법을 길게 쓰게 하지 않는다 — 한 줄이면 된다.

## 3. 병합과 중요도 판정

다섯 축의 결과를 모아 **전체에서** 상위 10개 내외를 고른다. 축마다 두 개씩 억지로 배분하지 않는다 — 한 축에서 다섯이 나올 수도 있다.

중요도는 [REVIEW.md](../../../docs/workflow/REVIEW.md)의 정의를 그대로 쓴다: `critical` · `high` · `medium` · `low`. 그 문서와 어긋나면 그쪽이 이긴다.

같은 원인에서 나온 여러 관찰은 하나로 묶는다. 겹치는 제안을 개수만 늘려 적지 않는다.

## 4. 결과 기록

`docs/execution/coaching/<YYYY-MM-DD>-coach.md`에 쓴다. 대시보드가 이 형식을 읽는다.

```md
# <YYYY-MM-DD> 코칭 결과

- 기준 커밋: <sha>
- 조사한 축: L1, L2, L3, L4, L5

## critical
- <제안 한 줄> | <근거 경로>

## high
- <제안 한 줄> | <근거 경로>

## medium
- ...

## low
- ...
```

- `## <중요도>` 제목과 `- ` 항목 형식을 지킨다. 대시보드가 이 두 가지로 파싱한다.
- 해당 중요도에 항목이 없으면 그 절은 쓰지 않는다.
- 같은 날 두 번 돌리면 뒤엣것이 앞엣것을 덮는다. 남기고 싶으면 파일명 뒤에 구분을 붙인다.

기록 뒤 `pnpm dashboard`를 돌려 코칭 페이지를 갱신한다.

## 5. 보고와 그 뒤

사용자에게는 중요도순 목록과 각 항목의 근거 위치만 보고한다.

**제안을 task로 만드는 것은 사용자 승인이 있을 때만 한다.** 승인이 나면 기획 인터뷰로 넘어가고, `index.jsonl` 등록은 승인 이후다. 제안 자체는 승인이 아니다.

`docs/execution/reviews/backlog.md`에는 넣지 않는다 — backlog는 교차 검증이 발견한 코드 결함의 자리이고, 코칭 결과는 `coaching/` 폴더가 소유한다.
