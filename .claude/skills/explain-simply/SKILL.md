# 쉽게 설명하기

설명이 어렵게 나왔을 때 다시 쓰는 방법이다. 내용을 빼는 게 아니라 **읽는 데 드는 힘을 줄인다.**

대화에서 하는 설명에만 쓴다. 화면에 나가는 문안은 [writing.md](../../../docs/2-design/design-system/writing.md)가 정본이고, 코드 주석과 커밋 메시지와 문서는 각자 규칙이 따로 있다.

## 원칙 넷

**1. 한 문장에 한 가지만 담는다.**

원인과 결과와 조건이 한 문장에 다 들어가면 두 번 읽어야 한다. 끊어서 순서대로 놓는다.

**2. 어려운 단어를 일상어로 낮춘다.**

기술 용어가 그 자리에 꼭 필요한 게 아니면 아는 말로 바꾼다.

| 쓴다 | 안 쓴다 |
| --- | --- |
| 설정값 | 환경 변수 |
| 에러를 낸다 | 예외를 던진다 |
| 안 지나간다 | 통과하지 못한다 |
| 못 쓴다 | 사용이 불가하다 |
| 조용히 넘어간다 | 암묵적으로 무시된다 |

**3. 비유를 쓰지 않는다.**

"열쇠 없이 문 앞에 선 것과 같다" 같은 문장을 쓰지 않는다. 비유는 이해를 돕는 것처럼 보이지만, 읽는 사람이 비유와 실제를 맞춰보는 일을 한 번 더 해야 한다. 무엇이 실제로 일어나는지를 그대로 말하는 쪽이 짧고 정확하다.

**4. 코드에 있는 이름은 건드리지 않는다.**

함수 이름, 파일 경로, 명령어, 에러 문구는 원문 그대로 둔다. 그래야 저장소에서 찾을 수 있다. 설명하는 말만 쉽게 쓴다.

## 예시

**어렵게 쓴 것**

> `?? ""`가 env 누락을 빈 문자열로 삼킨다. 그러면 `getUser()`가 실패하고 `getCurrentUser`가 null을 돌려주니, 화면은 "로그인하지 않았습니다"를 그린다.

**쉽게 쓴 것**

> 설정값이 없을 때 에러를 안 낸다. 빈 값을 대신 넣고 그냥 간다.
>
> 그래서 로그인이 안 되는데 화면은 멀쩡해 보인다.

바뀐 것은 셋이다. 문장을 넷에서 셋으로 끊었고, "누락"과 "삼킨다"를 없앴고, 결과를 마지막 줄에 따로 뒀다. `getUser()`와 `getCurrentUser`는 이 설명에서 몰라도 되는 이름이라 뺐다 — 어디를 고칠지 말할 때는 다시 넣는다.

## 안 하는 것

- **내용을 빼지 않는다.** 어려워서 지우는 게 아니라 쉽게 말한다. 중요한 사실이 빠지면 실패다.
- **틀리게 말하지 않는다.** 쉽게 만들려다 사실이 어긋나면 안 쓰느니만 못하다. 정확하게 쓸 방법이 없으면 어려운 채로 두고 그 사실을 말한다.
- **길이를 늘리지 않는다.** 풀어 쓴다고 문장을 더 붙이면 읽는 힘이 되레 는다. 쉬운 말은 대개 더 짧다.
- **가르치려 들지 않는다.** "쉽게 말하면", "즉", "다시 말해" 같은 앞말을 붙이지 않는다. 그런 말이 붙으면 앞 문장이 실패했다는 뜻이고, 문장만 하나 는다. 그냥 쉬운 문장으로 시작한다.
