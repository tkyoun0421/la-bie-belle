# Spec

기능 하나가 어떻게 동작하는지다. 이 파일이 유일한 정본이고 Epic이 여기를 링크한다.

`/doc`을 지나지 않고 여기로 들어왔으면 `/doc`으로 다시 시작해라. 경로도 소유권도 브랜치도 라우터가 갖는다.

## 모으기

라우터가 넘긴 인용에서 이 기능이 닿는 도메인 어휘와 그것을 묶는 결정 기록을 확인해라. 도메인 용어의 이름을 바꾸거나 수락된 ADR과 부딪히는 스펙은 제안이 아니라 결함이다.

대화와 저장소가 이미 쥐고 있는 것에서 종합해라. 기능이 아예 논의되지 않았다면 `interview` 스킬을 먼저 불러라.

## 무게는 인수 조건이 진다

스펙의 나머지는 맥락이다. Dev가 슬라이스를 자르는 기준도, 리뷰어가 검사하는 것도 번호 매긴 Given / When / Then 목록이다.

각 조건은 그 자체로 검증 가능하고, 내부 상태가 아니라 관찰되는 결과를 말하며, 경로 하나를 덮는다. "예약이 저장되고 손님에게 메일이 간다"는 둘로 쪼갠다 — 따로 실패하기 때문이다.

행복한 경로를 덮었다고 목록이 끝난 게 아니다. 잘못된 입력, 다른 사람의 동작과의 충돌, 실패한 외부 호출, 빈 결과 — 각각이 조건을 갖거나 범위 밖에 이름으로 적힌다.

## 쓰기

도메인 어휘는 `docs/domain/`이 정의한 그대로 쓰고, 정의를 다시 적지 말고 도메인 파일을 링크한다.

파일 경로도 코드 조각도 넣지 않는다. 예외는 산문보다 정확하게 결정을 담는 형태 — 상태 기계나 스키마 — 이고, 그것도 결정에 필요한 만큼만 남긴다.

## 발행

Issue가 PR보다 먼저다.

1. `gh-issue-generator` — `[Epic]` Issue. `.github/ISSUE_TEMPLATE/epic.yml`이 묻는 칸을 그대로 채운다. 무엇을 만드나는 지금 어떻게 되어 있고 이 작업이 끝나면 무엇이 가능해지는지 한 문단, 무엇이 달라지나는 사용자가 겉으로 보는 변화를 항목으로, 이번에 하지 않는 것은 범위 밖으로 민 것이다. 상세 명세 칸에 스펙 파일 경로를 넣어라. 인수 조건은 그 파일에 두고 복사하지 않는다. 담당 칸은 Dev다 — 슬라이스를 자르는 것이 Dev이기 때문이다. 라벨을 붙이고 카드를 보드에 올린다.
2. `gh-pr-generator` — 스펙 파일의 PR. Epic을 참조한다.

## 이미 있는 스펙을 고칠 때

정정은 Issue 본문이 아니라 파일로 간다. merge된 스펙이 바뀌는데 그에 대해 이미 열린 슬라이스가 있으면 PR 본문에 적어라 — 어느 슬라이스의 발밑이 움직였는지 Dev가 알아야 한다.
