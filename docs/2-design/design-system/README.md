# 디자인 시스템

디자인과 퍼블리싱 규칙은 여기가 정본이다. 산출물 문서도 이 디렉터리에 쌓인다.

## 문서 지도

무엇이 어디 있는지는 이 절이 정본이다. 새 문서가 생기면 여기에 한 줄을 더한다.

- [tokens.md](tokens.md) — 모든 값의 정본. 팔레트, 역할 토큰, 타이포 스케일, 스페이싱과 브레이크포인트, 라운딩과 그림자, 모션, 대비 검증. `src/app/globals.css`가 여기서 나온다
- [foundation/color.md](foundation/color.md) — 적응형 2계층이 왜 필요한지, 층 셋, 브랜드 색을 아끼는 규칙, 경고색 제약, 차트와 일러스트가 색을 쓰는 법
- [foundation/typography.md](foundation/typography.md) — 스케일과 굵기를 쓰는 법, Wanted Sans, 숫자 정렬, 큰 숫자
- [foundation/spacing-shape.md](foundation/spacing-shape.md) — 여백 리듬, 폭, 라운딩, 면 나누기, 그림자
- [foundation/motion.md](foundation/motion.md) — 언제 움직이고 언제 안 움직이는지, 접근성, 무엇으로 움직이나, 스켈레톤
- [writing.md](writing.md) — 화면에 나가는 한국어 규칙
- [components.md](components.md) — 컴포넌트별 역할 토큰 표
- [illustration.md](illustration.md) — 그림이 서는 자리와 안 서는 자리, 3D 오브젝트의 결과 프롬프트 틀, 장면 목록, 토스페이스 사용 규칙, 승인 절차

화면 문서는 소유 영역의 `screens/`에 있다 — [업무 영역 지도](../modules/README.md#영역-지도). 화면 문서를 쓰는 틀은 [설계 안내](../README.md#화면-문서)가 소유한다.

## 두 축

**값은 tokens.md에만 적는다.** hex와 oklch, 픽셀 수치, 밀리초, 대비비, 폰트 굵기 숫자가 전부 여기 해당한다. 다른 문서는 토큰 이름으로 가리키고 값을 옮겨 적지 않는다. 같은 값이 두 곳에 적히면 바꿀 때 한 곳을 놓치고, 그때부터 문서 둘이 서로 다른 말을 하는데 어느 쪽이 맞는지 아무도 모른다.

**지도는 README에만 건다.** 어떤 문서가 무엇을 담는지는 위의 문서 지도 절에만 적는다. 다른 문서는 자기 안에 문서 목록을 두지 않는다. 값을 가리키는 `tokens.md` 링크와 근거 한 곳을 짚는 링크는 지도가 아니라서 예외다. 같은 파일의 제목으로 가는 목차도 지도가 아니다 — 긴 페이지 문서는 첫 구분선 위에 2단계 제목 목차를 둔다. 지도가 여러 곳에 적히면 문서가 늘거나 이름이 바뀔 때 한 곳을 놓치고, 그때부터 문서들이 없는 파일을 가리킨다.

`CLAUDE.md`가 저장소 전체에 쓰는 방식과 같다.

## 작성법

**용도·작성 시점:** 화면에 공통으로 적용할 시각·문안 기준이 생기거나 바뀔 때 갱신한다. 값과 사용법의 소유권은 [두 축](#두-축)이 정한 대로다.

**필요한 입력:** 실제 화면의 적용 사례, 대비·터치·가독성 확인 결과, 기존 토큰 값.

**복사용 틀과 절별 질문:**

| 문서 | 본문 틀 | 세부 작성 방법 |
| --- | --- | --- |
| `tokens.md` | 기존 표·절·생성기 입력 형식 유지 | 값은 여기서만 바꾼다. 토큰의 의미·용도·테마 대응과 검증 근거를 확인한다. 틀 통일을 위해 파서가 읽는 표를 재구성하지 않는다 |
| `foundation/color.md` | 사용 목적 → 선택 기준 → 조합 예시 → 제약·예외 | 배경·글자·강조의 역할 조합과 대비 확인 방법을 쓴다. 실제 색값은 토큰 참조로 둔다 |
| `foundation/typography.md` | 정보 위계 → 역할별 사용 → 숫자·줄바꿈 → 예외 | 제목·본문·보조 정보의 토큰과 선택 이유를 적고 실제 화면 길이로 점검한다 |
| `foundation/spacing-shape.md` | 묶음과 간격 → 면·경계 → 크기·형태 → 예외 | 같은 그룹과 다른 그룹의 구분, 터치 영역, 라운딩과 면을 나누는 조건을 토큰으로 설명한다 |
| `foundation/motion.md` | 목적 → 시작·종료 조건 → 사용 토큰 → 움직임 축소·예외 | 무엇이 바뀌었음을 알리는 모션인지부터 적는다. 시간·이징 값은 토큰을 참조한다 |
| `components.md` | 컴포넌트별 용도 → 변형·상태 → 구성·역할 토큰 → 입력·접근성 → 사용 예·예외 | 정상·비활성·로딩·실패 상태를 대조한다. 화면마다 새 조합을 만들기 전에 기존 컴포넌트로 표현 가능한지 본다 |
| `writing.md` | 문체·용어 → 상황별 문장 구조 → 좋은 예·고칠 예 → 금지·예외 | 행동·성공·실패·권한 제한을 구별한다. 실패 문장은 현재 상황과 가능한 다음 행동을 알려준다. 화면별 최종 문구는 화면 문서가 소유한다 |
| `illustration.md` | 목적 → 3D 스타일 → 해상도와 파일 → 프롬프트 틀 → 장면 목록 → 토스페이스 → 승인 절차 | 장면은 화면 문서의 상태 표에서 센다. 같은 장면은 한 장으로 묶고 파일 이름을 첫 열에 둔다. 결을 바꾸는 것은 공통 문장이고 장면 줄은 사물만 적는다 |

**검토 기준:** 새 기준을 실제 화면에 적용해 판정할 수 있는가. 토큰 값이 여러 문서에 생기지 않았는가. 화면만의 예외를 공통 기본값으로 넓히지 않았는가. 현재 규칙과 부딪힌 자리는 적용 범위와 결정 근거를 남긴다.

## 순서

구현과의 앞뒤는 [roadmap](../../1-plan/roadmap.md#순서의-이유)이 정본이다 — 1차는 화면 디자인을 전부 끝낸 뒤 구현한다. 그리다 만나는 미정은 착수 전 인터뷰로 닫고, 그때까지는 페이지 문서의 「아직 안 정한 것」에 산다.

디자인 시스템을 먼저 만들고 페이지별 디자인을 다음에 만든다. 시안 방향 같은 결정은 사람이 내리고, 문서 전개만 subagent에 스폰한다.

## 퍼블리싱

조각은 우리가 만든다. 설치해서 쓰는 조각 모음이 없으니([ADR-011](../adr/ADR-011-expo-native-app.md)) 만드는 순간부터 [components.md](components.md)의 토큰을 쓴다. 기능 화면은 그 조각을 가져다 짜는 일이고, 퍼블리싱은 그 위에서 여백과 상태를 문서에 맞추는 일이다. 화면 구조를 다시 짜지 않는다.

e2e 테스트는 화면에 보이는 글자와 접근성 이름으로 화면을 잡는다. 스타일에 기대지 않으니 여백과 색을 고쳐도 테스트는 그대로 통과해야 한다. 퍼블리싱이 e2e를 깨뜨렸다면 구조를 건드렸다는 뜻이다.

## 검수 루프

퍼블리싱 검수는 자동으로 돈다. 검수 스폰은 합격 여부와 지적 목록을 구조화해 리턴한다.

지적마다 이 디렉터리의 조항을 인용해야 반려가 성립한다. 인용할 조항이 없으면 그건 취향이지 반려가 아니다.

반려가 2회를 넘으면 루프를 멈추고 사람이 판정한다. 대개 디자인 문서가 모호한 탓이다.
