# 2-design — 설계

## 역할

설계의 전체 그림이 이 파일이다. 갈래마다 정본은 하나다. 배치의 근거는 [ADR-009](adr/ADR-009-design-modules-and-stage-links.md)다.

**목표 설계다.** 코드가 여기 적힌 대로 돼 있다고 읽지 않는다. 지금 코드와 다른 자리는 영역 design의 「코드와의 차이」 표가 목표 조항·확인한 코드·차이·전환 작업으로 든다. 본문 절은 목표만 적는다. 그것을 옮기는 task는 [`docs/backlog.md`](../backlog.md)에 있다. 문서를 코드에 맞추려고 목표를 지우지 않는다.

### 갈래의 경계

한 화면을 셋이 나눠 적는다. 계정 상태와 권한 같은 업무 규칙은 그 영역의 `modules/<영역>/README.md`, 어느 화면에서 어느 화면으로 가는지는 그 화면 문서의 「화면 상태와 흐름」 절과 전역 경로를 든 `system/navigation.md`, 화면 안의 구성·문안·모션은 같은 화면 문서다. 셋이 다른 말을 하면 자기 갈래가 아닌 쪽이 따라온다 — 화면 문서가 업무 정책을 다시 정의하지 않고 규칙을 링크한다.

공통 원칙과 영역별 적용도 가른다. `system/` 넷은 전체가 지키는 원칙을, 각 `design.md`는 자기 캐시 키·무효화·재시도 예외 같은 적용만 적는다. 공통 무효화 표와 영역별 무효화 표를 둘 다 유지하지 않는다 — 변경을 일으킨 행위의 design이 전체 갱신 대상을 든다. system 문서가 영역 상세를 요약할 때는 원문 링크와 관계만 적는다. 예외를 허용할 때는 공통 조항에도 대상과 이유를 함께 기록한다.

여러 영역이 같은 저장 구조를 쓰면 소유 문서도 하나다. `requests`·`request_candidates`의 공통 구조와 `respond_request`의 공통 계약은 schedule design이 소유하고, swap design은 이를 참조해 교대의 추가 조건·행위·결과만 적는다.

## 입력과 산출물

작성법 하나는 「용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준」 순서다. 모든 문서에 공통인 규칙은 [문서 지도](../README.md#참조와-작성-규칙)가 소유하고, `design-system/`의 작성법은 [디자인 시스템 안내](design-system/README.md#작성법)가 든다.

새로 쓰는 문서와 통합하는 문서의 기준이다. 옮기기만 한 문서는 기존 절을 유지한다. 해당하지 않는 절은 두지 않고, 내용이 없는 파일을 새로 만들지도 않는다.

작성법은 [업무 규칙](#업무-규칙) · [기술 설계](#기술-설계) · [공통 설계](#공통-설계) · [화면 문서](#화면-문서) · [spec](#spec) · [ADR](#adr) 여섯이다. `4-test/evidence/`·`5-deploy/releases/`·`6-maintain/incidents/`의 절 순서는 그 단계 README가 든다.

### 업무 규칙

`modules/<영역>/README.md`의 작성법이다.

**용도·작성 시점:** 업무 용어·판정·책임이 생기거나 바뀔 때 쓴다.

**필요한 입력:** 제품 요구와 사용자 결정.

**복사용 틀:**

```markdown
# <업무 영역>

## 책임과 범위
<이 영역이 판정하는 것. 다른 영역이 판정하는 것은 소유 링크>

## 용어
| 용어 | 업무에서의 뜻 | 혼동하는 개념과의 차이 |
| --- | --- | --- |
| <용어> | <정의> | <구별 기준> |

## 업무 규칙
### <규칙 ID>
<규칙 이름. 누가 어떤 조건에서 무엇을 할 수 있거나 해야 하나>

- 예외와 경계: <허용·거부·보류가 갈리는 조건>
- 이유와 근거: <이 판정이 필요한 이유와 결정 근거>

## 상태 전이
| 이전 상태 | 사건·행위자 | 허용 조건·규칙 참조 | 다음 상태 | 거부 시 결과 |
| --- | --- | --- | --- | --- |

## 판정 예시
| 규칙 | 입력·이전 상태 | 사건 | 기대 판정·이후 상태 | 사례의 이유 |
| --- | --- | --- | --- | --- |

## 다른 영역과의 계약
| 상대 영역 | 제공·기대하는 사실 | 소유 조항 | 바뀔 때 확인할 곳 |
| --- | --- | --- | --- |

## 아직 안 정한 것
<질문별 영향·담당·필요 근거·결정 시점>
```

**절별 질문:**

업무 규칙에는 `### ACC-001`처럼 제목 자체가 식별자인 고정 ID를 붙인다. 접두는 영역(ACC·SCH·SWP·ATT·PAY·NTF), 번호는 문서 순서다. 제목 다음 문단이 규칙 문장이다. 링크는 `#acc-001`이고 제목이 아니라 ID를 가리키니 규칙 이름이 바뀌어도 참조가 끊기지 않는다. 모든 설명 문장을 형식화하지는 않는다 — 규칙이라 부를 문장에만 붙인다. 용어 절과 「아직 안 정한 것」에는 붙이지 않는다.

규칙 문장 쓰기 — 행위자 → 전제 → 행위 → 판정 → 예외 순으로 확인한다. 「적절히 막는다」 대신 무엇을 막고 기존 상태가 어떻게 남는지 쓴다. 보존 기간·시각 경계·권한은 근거를 확인하며 DDL이나 함수 이름으로 업무 정의를 대신하지 않는다. 「해당하지 않는 절은 두지 않는다」는 규칙 안의 두 불릿에도 적용된다 — 근거가 예외와 경계나 이유와 근거 한쪽만 주면 그 불릿만 둔다.

두 불릿의 경계도 가른다. 규칙 문장이 낳는 결과의 서술은 「예외와 경계」에 두고, 「이유와 근거」에는 왜 그렇게 정했는지와 근거 링크만 남긴다 — 「거절했다는 기록도 남는다」 같은 문장이 결과 쪽이다. 규칙에 딸린 산문·표·목록·예시 문단은 두 불릿 뒤에 그대로 둔다. 불릿 안으로 억지로 접지 않는다.

규칙 문장이 원래 절 제목에 기대던 것이거나 제목 자체였으면 제목 낱말을 주어로 붙이거나 「표제 — 규칙 문장」 꼴로 쓴다. 뜻을 더하지 않는다.

용어 표의 「혼동하는 개념과의 차이」는 원문이 대비를 말할 때만 채우고 아니면 `—`다. `—`가 대부분이어도 된다.

상태 전이 표는 이 영역이 판정하는 상태만 든다. 다른 영역의 상태를 바꾸는 행위는 「다른 영역과의 계약」 표로 보낸다. 상태 전이와 판정 예시 표 앞에는 도입 산문 한 문단을 둘 수 있다.

판정 예시 만들기 — 정상 사례를 하나 고른 뒤 결과가 뒤집히는 축을 찾는다. 수치가 있으면 경계 직전·동일·직후, 권한이면 본인·타인과 허용·금지 역할, 상태면 허용 전이·금지 전이·중복 사건을 검토한다. 실제로 판정이 달라지는 사례만 표에 남긴다. 모르는 기대값은 테스트로 고정하지 않고 미정으로 돌린다. 「규칙」 칸이 규칙이 아니라 용어에 기대면 `#용어` 링크를 적는다.

**검토 기준:** 같은 입력에 판정 하나가 나오는가. 상태 전이가 규칙과 모순되지 않는가. 다른 영역이 내부 테이블을 알아야 업무 계약을 이해하는 구조는 아닌가.

### 기술 설계

`modules/<영역>/design.md`의 작성법이다.

**용도·작성 시점:** 합의한 업무 규칙을 데이터·호출·실행 동작으로 연결할 때 쓴다.

**필요한 입력:** 업무 규칙, 공통 설계, 실제 마이그레이션·타입·코드.

**복사용 틀:**

```markdown
# <업무 영역> 기술 설계

## 참조 규칙
<적용 업무 규칙과 system 조항 링크. 영역별 예외가 있으면 해당 절>

## 소유 데이터
<소유 테이블·관계·제약의 의미, 실제 스키마·생성 타입 위치>
<자기 캐시 키와 읽기 범위. 공유 데이터는 소유 영역 링크>

## 행위별 구현 계약
### <행위 이름>

- 규칙: <이 행위가 실현하는 업무 규칙 링크>
- 입력·전제: <진입점·인자·필요 상태·시각 기준>
- 읽고 쓰는 데이터: <대상·변경 필드·원자적으로 처리할 범위>
- 권한: <인증·행 단위 접근·서버 측 강제 위치>
- 처리와 경쟁: <순서·중복 호출·동시 변경·재시도 처리>
- 결과와 실패: <반환·오류·저장 여부·부분 성공 또는 복구>
- 캐시 갱신: <성공·실패 때의 무효화·직접 갱신·복원 대상>

## UI 연결
<행위가 시작되는 화면과 결과를 보여주는 화면·상태 링크>

## 코드와의 차이
| 목표 조항 | 확인한 코드와 Git 기준점 | 차이 | 전환 작업·검증 근거 |
| --- | --- | --- | --- |

## 아직 안 정한 것
<기술 선택의 질문. 업무 판단이면 업무 규칙의 질문 링크>
```

**절별 질문:**

design의 「행위별 구현 계약」은 같은 행위를 중심으로 **입력·전제 / 읽고 쓰는 데이터 / 권한 / 처리와 경쟁 / 결과와 실패 / 캐시 갱신**을 함께 적는다. 데이터·API·런타임이라는 세 개의 큰 절에 같은 행위를 다시 흩어놓지 않는다. 소유 데이터 절은 관계·제약과 스키마 위치를 설명하고 전체 DDL을 복사하지 않는다. 실제 스키마와 타입은 마이그레이션과 생성 타입이 정본이고, 문서는 업무 규칙의 실현 방식과 선택 근거를 설명한다.

화면의 상태는 정상·빈 상태·로딩·실패·권한 제한·성공 직후를 확인한다. 화면의 로딩 모양은 화면 문서, 언제 데이터를 읽거나 재시도하는지는 design이 소유한다.

행위별로 쓰기 — 화면의 사용자 행동 또는 시스템 사건 하나를 고른다. 입력부터 저장·응답·화면 갱신까지 따라가며 위 여섯 항목을 채운다. 데이터·API·런타임별로 같은 행위를 다시 나누지 않는다. 실패에는 「요청 실패」만 쓰지 말고 서버 저장 여부를 알 수 있는지, 재호출하면 중복되는지도 구별한다.

「해당하지 않는 절은 두지 않는다」가 여기도 적용된다 — 행위 아래 여섯 불릿도 원문이 말한 것만 둔다. 행위 하나가 함수 여럿을 부르면 `| 함수 | 누가 | 하는 일 |` 표를 「입력·전제」 불릿 앞에 둘 수 있다. 행위 `###` 아래에 `####`를 두지 않는다 — 긴 「처리와 경쟁」은 불릿 아래 하위 불릿으로 내린다.

소유권 쓰기 — 스키마 전체를 복사하지 않고 제약이 업무 규칙을 어떻게 보장하는지 설명한다. `requests`·`request_candidates`의 공통 계약은 [갈래의 경계](#갈래의-경계)가 정한 대로 schedule이 소유하고 swap은 추가 조건만 쓴다. 다른 영역 캐시까지 갱신하는 행위는 그 행위의 계약에 전체 갱신 대상을 적고 캐시 정의는 소유 영역을 링크한다.

**검토 기준:** 허용 UI를 우회한 요청도 권한이 지켜지는가. 두 요청이 겹치거나 응답이 끊겼을 때 결과를 설명할 수 있는가. 설계 목표와 현재 코드의 차이를 진행 상태와 혼동하지 않았는가. 「코드와의 차이」를 절 이름으로 통일한다.

### 공통 설계

`system/` 네 문서의 작성법이다.

**용도·작성 시점:** 여러 영역이 함께 따라야 하는 결정이 있을 때 갱신한다. 공통 문서를 만들기 위해 영역별 사례를 일반화하지 않는다. 한 영역만의 예외는 영역 design에 쓰고 공통 조항에는 예외의 대상·이유·링크를 남긴다.

**필요한 입력:** 영역별 규칙과 design, 그 결정을 낳은 ADR.

**복사용 틀과 절별 질문:**

| 문서 | 본문 틀 | 절별 작성 방법 | 검토 기준 |

공통 조항 하나의 틀은 다음과 같다. 기본값의 실제 수치나 정책은 기존 근거로 채운다.

```markdown
### <공통 조항 이름 또는 고정 ID>

- 적용 범위: <어느 호출·데이터·화면에 적용하나>
- 기본 계약: <조건과 결과, 호출자와 제공자의 책임>
- 이유: <해결하는 문제와 선택 근거>
- 예외: <영역·이유·예외 계약 링크, 없으면 해당 없음>
- 구현 참조: <코드·설정의 원천. 아직 없으면 전환 작업>
```

본문 틀의 `##` 이름과 공통 조항 이름이 같으면 `###`을 만들지 않고 조항 본문을 `##` 바로 아래 둔다 — 앵커 `-1` 충돌을 막는다.

「구현 참조」는 실존하는 코드·설정 경로만 적는다. 아직 없으면 「아직 없음 — 」 뒤에 [`backlog.md`](../backlog.md)의 전환 작업 ID를 잇는다.

미정은 `## 예외·미정` 아래 `### 아직 안 정한 것`을 두고 그 안에서 `#### Q-01`이다. `#아직-안-정한-것` 앵커가 그래야 산다.

### 화면 문서

**용도·작성 시점:** 화면 동작·구성·문안·모션이 새로 생기거나 바뀔 때 문서와 짝 시안을 함께 갱신한다.

**필요한 입력:** 업무 규칙, 행위별 기술 계약, 전역 탐색, 디자인 시스템.

**복사용 틀:**

```markdown
# <화면 또는 흐름 이름>

## 목적과 진입
<사용자 목적·진입 계기·나갈 때의 결과. 경로·역할 조건은 navigation 링크>

## 참조 기준
<업무 규칙 / design의 행위 / navigation / 공통 시각·문안 조항>

## 화면 상태와 흐름
| 상태 | 진입 조건·계기 | 보이는 내용 | 가능한 행동 | 다음 상태·목적지 |
| --- | --- | --- | --- | --- |

## 짜임과 토큰
<위에서 아래의 정보 순서, 컴포넌트·역할 토큰, 작은 화면·키보드·포커스 처리>

## 문안
| 상태·위치 | 최종 문구 | 가변값·표기 조건 |
| --- | --- | --- |

## 모션
<시작·종료 상태 / 공통 토큰 / 움직임 축소 시 표현>

## 예외와 미정
<범위 밖 / 공통 기준과의 충돌·판단 / 아직 결정하지 않은 상태>
```

**절별 질문:**

`screens/` 아래에 쌓는다 — 한 영역의 화면은 `modules/<영역>/screens/`, 여러 영역에 걸치는 화면은 `system/screens/`다. 파일 하나가 흐름 하나를 담고 그 안에서 화면마다 절을 나눈다. 화면 절은 넷으로 쪼갠다 — 짜임, 색과 글자와 여백, 문안, 모션. 그 뒤에 안 담은 것과 규칙과 부딪힌 자리와 아직 안 정한 것을 파일 단위로 붙인다.

상태 표 채우기 — 「보이는 내용」 칸은 버튼·카드·안내 줄 같은 구성 요소 이름만 적고 화면에 나오는 문구는 「문안」 표가 소유한다. 정상·빈 상태·로딩·실패·권한 제한·성공 직후를 한 번씩 검토한다. 각 상태에서 사용자가 할 수 있는 행동을 따라 다음 상태를 쓴다. 입력 보존·중복 누름·닫기·뒤로 가기·재진입 때문에 결과가 달라지는 경우도 추가한다. 한 표에 모든 상태 조합을 늘어놓지 말고 실제로 다른 표현이나 행동이 필요한 경우를 남긴다.

「구성 요소 이름만」은 상태 표에만 적용된다 — 짜임 안의 표가 문구를 들면 그대로 둔다. 상태별 표시 규칙은 「짜임과 토큰」 아래 둔다. 「값이 없을 때」 같은 것이 그것이다. 원문이 진입 조건을 안 정한 상태는 지어내지 않고 「아직 안 정한 것」의 Q-nn으로 보낸다.

**엣지 케이스까지 전부 그린다.** 정상 흐름만 그린 화면은 절반이다. 빈 상태, 실패, 상한, 잠금, 재진입처럼 드물게 나오는 상태도 화면마다 그린다. 그리다가 아직 못 정한 상태가 나오면 비워두지 말고 「제안」이라 밝혀 그리고 결정을 요청한다. 문서에 없는 상태는 구현자가 즉석에서 메우게 되는데, 그 즉석 판단은 검수 루프가 인용할 조항이 없다.

**해피 패스는 끝까지 그린다.** 버튼을 누르는 데서 멈춘 화면도 절반이다 — 동작이 성공한 직후의 모습(무엇이 닫히고, 무슨 표시가 남고, 사용자가 다음에 무엇을 보는가)까지가 해피 패스다. schedule-worker의 교대·취소가 「보낸 뒤」 없이 봉인될 뻔한 것이 이 조항의 계기다.

문안 쓰기 — 상태 표가 쓰는 최종 문구는 문안 절에서 소유한다. 상태 표는 그 문구를 위치나 항목명으로 가리킨다. 문안 절 안에서는 표가 최종 문구의 정본이고, 그 문구를 고른 이유는 표 아래 산문으로 둔다. 실패 원인마다 다음 행동이 다르면 문구도 구별한다. 아직 행동 정책이 없으면 임의로 「다시 시도」를 넣지 않는다. 읽기·재시도 시점은 design, 기다리는 동안 보이는 모습은 화면 문서가 정한다.

원문 산문에만 든 최종 문구는 문안 표로 옮긴다. 행을 새로 만드는 게 아니라 이동이고 글자는 그대로다 — 「자리 — 문구」 꼴 목록이 그것이다. 근거를 대며 문구를 인용하는 산문은 인용을 남기고 표가 그 문구를 소유한다. 동작은 정해졌는데 문안이 없는 상태는 상태 표에 행을 두고, 문안 표의 그 행 「최종 문구」 칸에 「미정 — Q-01」 링크를 적는다.

모션 값이 다른 절에 살면 「모션」 절은 그 자리를 가리키는 한 줄만 둔다. 값은 한 자리에만 산다.

「규칙과 부딪힌 자리」는 비워두지 않는다. 화면을 그리다 보면 디자인 시스템의 조항과 어긋나는 자리가 반드시 나오고, 그때 조항을 고칠지 그 화면만 예외로 둘지가 갈린다. 어느 쪽이든 판단과 근거를 남겨야 다음 사람이 같은 자리를 다시 판단하지 않는다.

읽는 사람이 답을 얻어야 하는 것은 셋이다. 무엇이 어디 놓이는가, 어떤 토큰을 쓰는가, 화면에 무슨 글자가 나오는가. 왜 그렇게 정했는지를 같이 적어야 나중에 바꿀 때 근거를 다시 캐지 않는다.

첫 파일이 [modules/account/screens/login.md](modules/account/screens/login.md)고 뒤따르는 화면은 이 틀을 따른다.

「참조 기준」은 파일마다 하나다.

앵커가 갈리지 않게 절마다 이름을 달리한다 — `###`과 그 아래 `####` 모두다. 「화면 상태와 흐름」의 `###`은 `<화면>`, 나머지 셋은 `### <화면> 짜임`·`### <화면> 문안`·`### <화면> 모션`이고, 「짜임과 토큰」 안의 색·글자·여백과 모양도 `#### <화면> 색`처럼 화면 이름을 앞에 단다. 원문이 색과 글자를 한 표로 묶었으면 `#### <화면> 색과 글자` 하나로 둔다. 부모 절과 이름이 겹치는 `#### 짜임`은 두지 않고 본문으로 둔다. 화면이 하나뿐인 파일도 같은 꼴로 맞춘다. 여러 화면이 함께 쓰는 절은 화면 이름을 못 다니 그대로 두고, 그 파일 안에서 이름이 겹치지 않는지 확인한다.

파일 제목과 화면 이름이 같은 파일은 「화면 상태와 흐름」에 `### <화면>`을 두지 않고 표를 바로 둔다 — 여기서도 `-1` 앵커를 막는 것이고, 「짜임과 토큰」·「문안」·「모션」의 `### <화면> 짜임` 꼴은 그대로다. 파일 머리에 목차를 두지 않는다. 절 이름 규칙이 앵커를 준다.

시안 만들기 — `<화면>.md`와 `<화면>.sian.html`을 같은 폴더에 둔다. 파일 첫 주석에는 문서 경로와 토큰이 정본이라는 점을 적는다. 화면 상태 표와 비교할 수 있도록 시안에도 상태 이름을 표시한다. 확정되지 않은 표현은 「제안」으로 구별한다. 문서에서 변경한 상태를 시안에서도 확인하고 문서에 없는 동작이 나타나면 소유 문서로 돌린다. 새 시안 메타데이터 형식이나 HTML 생성기는 추가하지 않는다.

**시안 HTML을 문서 옆에 같이 커밋한다.** `dashboard.md` 옆에 `dashboard.sian.html`을 둔다. 사람이 보고 고르는 데 쓴 그 파일 그대로다.

문서만 넘기면 새는 것이 있다. 이징 곡선, 겹치는 타이밍, 화면 여럿을 나란히 놓고 보는 눈 같은 것들이다. 글로 옮겨 적을 수는 있지만 옮겨 적는 순간 값이 두 곳에 살고, 그다음부터 어느 쪽이 맞는지 아무도 모른다. 파일을 그대로 두면 값은 한 곳에 있고 구현자가 직접 연다.

**시안은 참고고 정본이 아니다.** 값은 [design-system/tokens.md](design-system/tokens.md)에, 짜임과 문안은 화면 문서에 있다. 시안과 그 둘이 어긋나면 그 둘이 이긴다. 시안 파일 맨 위에 그 말을 주석으로 박아둔다.

시안은 포맷 검사에서 뺀다. 손으로 만든 산출물이라 prettier가 다시 줄을 나누면 사람이 고른 그 모습이 아니게 된다. `.prettierignore`에 자리가 있다.

**시안의 CSS를 앱으로 옮기지 않는다.** [디자인 시스템의 퍼블리싱](design-system/README.md#퍼블리싱)이 정한 대로 shadcn/ui와 Tailwind 위에 토큰을 갈아끼운다. 시안은 눈으로 보는 것이지 복사할 코드가 아니다.

**검토 기준:** 버튼을 누른 뒤 성공·실패의 끝까지 그려졌는가. 적용되는 라이트·다크와 작은 화면에서 글자·터치·포커스를 확인할 수 있는가. 지적마다 근거 조항을 연결할 수 있는가.

### spec

기능만 들어온다. 사용자에게 보이는 동작이 새로 생기거나 달라지는 task가 기능이다. 리팩터링·문서·토큰·검사 같은 비기능 task는 실행 방향이 정해지면 [`3-build/plans/`](../3-build/plans/)에 task 문서를 둔다. 여러 단계에 걸친 변경 방향의 검토는 [proposals](../proposals/README.md)가 맡는다.

제안이 채택되면 영향을 받는 기획·설계 정본을 먼저 갱신하고 필요한 구현 계획을 쓴다. 중요한 선택과 근거는 ADR에 남긴다. 제안의 채택은 기능 spec의 승인을 대신하지 않는다([ADR-008](adr/ADR-008-proposals-and-implementation-plans.md)).

**용도·작성 시점:** 사용자 문제와 적용할 설계가 정리되어 이번 기능의 범위를 승인받을 때 쓴다. 설계가 덜 된 곳을 spec 안의 별도 정책으로 채우지 않는다.

**필요한 입력:** intent와 이번에 적용하는 업무 규칙·기술 설계·화면 문서.

**복사용 틀:**

```markdown
---
status: draft
sources:
  - ../../1-plan/intent/<task>.md
  - ../modules/<영역>/README.md#<규칙-id>
  - ../modules/<영역>/design.md#<행위-앵커>
  - ../modules/<영역>/screens/<화면>.md
---

# <이번 기능에서 바뀌는 사용자 동작>

## 요구
<intent의 문제와 연결한 이번 구현 범위>

## 설계 참조
<각 입력에서 이번에 적용하는 부분과 제외하는 부분. 규칙 본문은 링크>

## 완료 조건
### AC-01

- 전제: <사용자·상태·입력>
- 행동: <사용자 또는 시스템이 하는 일>
- 관찰 결과: <화면·반환·저장 상태로 확인할 결과>
- 근거: <적용 설계 조항 링크>

## 범위 밖
<인접 기능 중 이번 승인에 포함하지 않는 것>

## 승인 근거
<승인 전에는 승인 기록 없음>
```

**절별 질문:**

한 파일은 넷으로 선다.

- **요구** — 왜 이 task인지, 사용자에게 무엇이 달라지는지
- **설계** — 정본 중 이번에 구현하는 자리를 링크로 가리키고, 정본이 안 정한 것을 이 task에서 어떻게 정했는지만 적는다. 정본을 풀어 옮기지 않는다 — 정본이 바뀌면 spec이 낡는다
- **완료 조건** — 무엇이 되면 끝인지. `AC-01` 같은 식별자로 참조할 수 있다
- **범위 밖** — 이 task가 안 하는 것

정본이 앱 전체가 늘 지키는 것이라면 spec은 task 하나의 문서다. 구현 순서·파일 배치·리스크는 [`3-build/plans/`](../3-build/plans/)가 맡는다. 승인된 과거 spec·완료 plan은 당시 기록을 보존한다.

완료 조건 쓰기 — 요구 하나마다 어떤 결과를 보면 끝인지 묻는다. 「잘 동작한다」「설계대로 만든다」로 끝내지 않는다. 하나의 조건이 하나의 판정으로 통과·실패할 수 있게 나누고 정상·거부·경계 사례를 필요한 만큼 적는다. 파일 변경 목록과 테스트 명령은 plan으로 보낸다. 테스트가 참조할 때는 spec 경로와 `#ac-01`을 함께 쓴다.

승인 기록 쓰기 — 승인한 사람, 날짜, 실제 승인 메시지·리뷰·기록의 참조, 검토한 Git 기준점, 승인 범위와 제한을 적는다. 대상 spec뿐 아니라 `sources`의 내용을 그 시점에 재현할 수 있어야 한다. 커밋 전 승인이라면 기준 커밋과 검토한 고정 diff·PR revision을 함께 연결한다. 움직이는 브랜치 이름이나 `HEAD`만 쓰지 않는다. 승인 근거가 없는 상태에서 `approved`로 채우지 않는다.

입력 변경 검토 — 승인 이후 요구나 입력 설계가 달라지면 이전 승인 기준과의 차이·영향 AC·기존 승인 범위 충족 여부를 남긴다. 기존 사용자 결정이 충분하면 그 근거를 연결하고, 범위가 새로 넓어지면 필요한 승인을 받는다. 단순 링크 이동과 제품 요구 변경을 같은 것으로 처리하지 않는다. 완료된 과거 spec의 승인 내용은 현재 틀에 맞춰 다시 쓰지 않는다.

#### sources

spec과 plan은 frontmatter `sources`에 입력 문서를 적는다. 작성 파일 기준의 상대 경로다. 파일명이 작업 슬러그라 같은 ID를 frontmatter에 다시 적지 않는다.

```yaml
---
status: draft
sources:
  - ../../1-plan/intent/<task>.md
  - ../modules/attendance/README.md#att-003
  - ../modules/attendance/design.md
---
```

spec은 intent와 이번에 적용하는 설계 조항을, plan은 대응 spec을 든다. 여기서 역참조를 계산하니 별도의 수기 연결표를 두지 않는다. 기준을 고치는 PR은 그것을 `sources`로 든 spec·plan과 관련 테스트를 같은 PR에서 고치거나, 영향이 없는 이유를 남기거나, 전환 작업을 연결한다. 승인된 spec의 `sources`가 달라지면 승인 범위가 달라지는지 검토하고 필요한 재승인을 받는다. 승인 근거 절은 검토한 Git 기준점과 승인 범위를 기록한다.

### ADR

**용도·작성 시점:** 영역 경계·플랫폼·접근 방식처럼 중요한 선택을 확정했을 때 쓴다. 검토 중인 대안은 proposal이나 해당 설계의 미정에 둔다.

**필요한 입력:** 비교한 대안과 그 비용, 결정의 근거가 된 사용자 판단.

**복사용 틀:**

```markdown
# ADR-<번호> — <선택을 드러내는 제목>

<결정 날짜와 근거. 이전 결정을 바꾸면 해당 ADR 링크>

## 배경과 제약
<무엇이 문제였고 어떤 조건을 지켜야 했나>

## 대안과 선택
<검토한 대안 / 비교 기준 / 선택 / 받아들이는 비용>

## 적용과 결과
<영향받는 정본·작업 링크 / 얻는 것 / 남는 제약>

## 재검토 조건
<어떤 사실이 바뀌면 다시 판단할 것인가>
```

**절별 질문:** 선택의 이유와 비용이 핵심이다. 상세 현재 정책은 소유 설계로 보내고 ADR에는 이유를 보존한다. 이후 결정이 바뀌면 새 ADR에서 이전 것을 참조하고 이전 문서에 후속 결정 링크를 추가한다. 이미 확정된 결정의 역사를 최신 설명으로 덮어쓰지 않는다.
