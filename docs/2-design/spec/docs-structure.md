# 문서 구조 개선 — 검토 계획

2026-09-14 문서 구조 검토에서 나온 일곱 개선안을 적용하기 위한 초안이다. 목표는 문서를 읽는 사람이 현재 결정, 구현 상태, 다음 작업을 같은 뜻으로 이해하게 만드는 것이다.

현재의 `1-plan`~`6-maintain` 구분과 `domain`·`architecture`·`design-system` 구분을 유지한다. 변경 범위는 문서 간 불일치 해소, 상태 표시, 작업 연결, 탐색, 기록 절차다.

이 파일은 변경안과 완료 조건을 검토하는 문서다. 작성만으로 제안이 승인되거나 기존 규칙이 바뀌지는 않는다. [3-build 안내](../../3-build/README.md)가 승인된 spec의 구현 계획만 받으므로, 승인 전 검토안은 이곳에 둔다.

## 검토할 변경 요약

| 번호 | 우선순위 | 변경 | 기대 결과 |
| --- | --- | --- | --- |
| 1 | 높음 | 서로 다른 결정을 설명하는 문서 동기화 | 어떤 문서를 먼저 읽어도 같은 동작을 이해한다 |
| 2 | 높음 | 목표 설계와 구현 상태 구별 | 예정된 기능이나 명령을 이미 있는 것으로 오해하지 않는다 |
| 3 | 높음 | backlog와 handoff 역할 정리 | 다음 작업과 선행 조건을 보드에서 찾는다 |
| 4 | 중간 | 문서 입구와 디자인 색인 보완 | 처음 온 사람도 필요한 문서에 도달한다 |
| 5 | 중간 | spec과 구현 계획의 경계 명확화 | 완료 조건을 복제하지 않고 구현 계획을 쓴다 |
| 6 | 중간 | 긴 문서의 내부 목차 허용 | 화면별 절로 바로 이동한다 |
| 7 | 중간 | CHANGELOG 갱신 책임 명시 | 회차 로그와 변경 색인이 함께 유지된다 |

## 1. 서로 다른 결정을 설명하는 문서 동기화

### 확인한 문제

[로그인 문서의 승인 대기](../design-system/pages/login.md#승인-대기)는 차단된 사람이 로그인 화면에서 멈춘다고 설명한다. 같은 문서의 「아직 안 정한 것」에는 차단 화면 위치가 미정이다. 반면 [flows의 진입 판정](../architecture/flows/README.md#앱을-열면)은 차단된 사람을 `/blocked`로 보낸다.

[handoff의 열린 결정](../../handoff.md#열린-결정)에도 이 불일치와 관리자 홈 뒤로 버튼의 문서 불일치가 남아 있다. 발견은 기록됐지만 관련 정본의 갱신까지 끝나지 않았다.

### 변경안

- 계정 상태와 권한의 업무 규칙은 `domain`, 화면 간 목적지는 `architecture/flows`, 화면 안의 구성·문안·모션은 `design-system/pages`가 맡는다는 경계를 명시한다.
- 파일 수정 시각만으로 어느 쪽이 맞는지 고르지 않는다. 승인된 결정의 근거를 확인하고 관련 문서를 같은 변경에서 맞춘다.
- 먼저 차단 진입과 관리자 홈 뒤로 동작을 맞춘다. 차단 화면의 시각 설계가 아직 없으면 목적지는 확정됐고 화면 설계는 남았다고 구분한다.
- 화면 이동을 설명하는 페이지 문서는 해당 flows 절에 연결한다. 시안의 화면이나 문안이 바뀌어야 하는 경우에는 페이지 문서 변경과 시안 갱신·감사를 함께 계획한다.
- 미정의 답이 정해지면 그 항목의 정본을 갱신하고 handoff에서 미정 표기를 제거한다. 별도 결정 목록을 새로 만들지 않는다.

### 변경 대상과 완료 기준

대상은 [설계 안내](../README.md), [flows 안내](../architecture/flows/README.md), [디자인 시스템 안내](../design-system/README.md), 관련 페이지 문서·시안, `handoff.md`다.

- [ ] 차단된 사용자의 목적지와 관리자 홈의 뒤로 동작에 상반된 설명이 없다.
- [ ] 목적지 확정과 화면 설계 미완료가 구별돼 있다.
- [ ] 변경된 화면 설명이 정본으로 연결되며, 필요한 시안 갱신·감사 결과가 남는다.

## 2. 목표 설계와 구현 상태 구별

### 확인한 문제

[API 문서의 타입 생성 설명](../architecture/api/README.md#읽기)은 `pnpm types`와 CI의 타입 차이 검사가 있는 것처럼 쓰여 있다. 현재 [package.json](../../../package.json)과 [CI 설정](../../../.github/workflows/ci.yml)에는 그 명령과 검사가 없다.

[계정 데이터 모델](../architecture/data-model/account.md#프로필-신원)은 목표 구조와 기존 마이그레이션의 차이를 설명하지만, 이런 구분이 아키텍처 전체에 일관되게 적용돼 있지는 않다. [계정 런타임](../architecture/runtime/account.md#게이트는-세션만-판정은-클라이언트가)의 클라이언트 판정도 handoff에서는 후속 구현 대상으로 기록돼 있다.

### 변경안

- `architecture/README.md`에 이 문서군이 목표 설계를 담으며 구현 여부는 연결된 backlog task에서 확인한다는 안내를 둔다.
- 현재 코드와 다른 설명에는 필요한 곳에만 `현재 구현`·`목표 설계`·`연결 작업`을 짧게 적는다. 모든 문단에 상태 필드를 붙이지 않는다.
- 타입 생성, 프로필 신원 분리, 개인정보 표 분리, 승인 게이트 이동과 `proxy` 전환을 우선 대상으로 삼는다.
- spec의 `status: draft | approved`는 기존 승인 의미를 유지한다. `approved`를 구현 완료로 해석하지 않고, 작업 진행 상태는 backlog가 관리한다.
- 문서를 현실에 맞춘다는 이유로 목표 설계를 지우거나, 문서를 맞추려고 이 작업에서 기능을 구현하지 않는다.

### 변경 대상과 완료 기준

대상은 [아키텍처 안내](../architecture/README.md), `data-model`·`api`·`runtime`의 해당 문단, `backlog.md`다.

- [ ] 아직 없는 명령·CI 검사·스키마·인증 흐름이 현재 동작으로 읽히지 않는다.
- [ ] 미구현 설명에서 실제 후속 task로 이동할 수 있다.
- [ ] 기존 승인 게이트의 상태 값과 의미가 바뀌지 않는다.

## 3. backlog와 handoff 역할 정리

### 확인한 문제

[handoff의 다음 첫 수](../../handoff.md#다음-첫-수)는 데이터 task부터 구현한다고 적었다. 하지만 [backlog의 다음](../../backlog.md#다음)에는 선행 데이터 task를 기다리는 대시보드만 있다. 다음 행동이 보드 밖에 있는 상태다.

handoff에는 회차의 상세 설명, 여러 영역의 미정, 상시 개발 주의사항도 함께 쌓여 있다. 새 세션이 당장 해야 할 일을 찾기 위해 넓은 범위를 읽어야 한다.

### 변경안

- 데이터 작업을 보드에 등록한다. 초기 분해 후보는 Edge Function import 확인, 계정 데이터 구조 전환, 인증 진입 전환, 데이터 타입 생성 절차다. 실제 task 경계와 의존관계는 관련 설계를 읽고 확정한다.
- 대시보드가 기다리는 근무표·출근 기록·급여 계산·알림의 의존관계를 보드에 드러낸다. 아직 완료 조건을 못 정한 작업은 착수 가능한 작업으로 표시하지 않는다.
- handoff는 현재 상태 요약, 다음 task 링크, 당장 그 task를 막는 결정, 이번 회차에 특별히 필요한 주의사항에 집중한다.
- 미정의 본문은 해당 정본에 남기고 handoff에는 필요한 항목의 링크와 다음 작업에 미치는 영향만 적는다.
- 상시 규칙은 기존 담당 문서나 정의문으로 옮긴다. 예를 들어 테스트 실행 주의사항은 테스트 안내로, 시안 재생성 관련 사항은 디자인 시스템 문서로 보낸다. 옮길 때 목적지의 기존 설명과 먼저 합친다.
- `session-recorder`가 미해결 항목을 매번 통째로 이어 붙이지 않도록 handoff 작성 규칙도 함께 고친다. 새 task의 범위와 완료 조건은 총괄이 정한다는 기존 경계는 유지한다.

### 변경 대상과 완료 기준

대상은 `backlog.md`, `handoff.md`, 필요한 후속 task의 draft spec, 기존 정본 문서, [session-recorder 정의문](../../../.claude/agents/session-recorder.md)이다.

- [ ] handoff의 다음 작업이 backlog의 실제 항목과 연결돼 있다.
- [ ] 대시보드의 선행 작업과 착수 불가 사유를 보드에서 확인할 수 있다.
- [ ] 옮긴 미정·주의사항의 내용이 보존되고 원래 자리에서 목적지를 찾을 수 있다.
- [ ] handoff에 과거 회차의 상세 설명과 상시 규칙을 중복해서 유지하지 않는다.

## 4. 문서 입구와 디자인 색인 보완

### 확인한 문제

현재 루트 `README.md`가 없다. 저장소 전체 문서 지도는 [CLAUDE.md](../../../CLAUDE.md#문서-지도)에 있다.

[디자인 시스템 지도](../design-system/README.md#문서-지도)에는 페이지 문서 12개 중 7개가 빠져 있다. 누락된 파일은 `approvals.md`, `members.md`, `payroll.md`, `profile.md`, `qr.md`, `stats.md`, `wages.md`다.

### 변경안

- 루트 `README.md`를 추가한다. 프로젝트 소개, 최소 실행 절차, 문서 지도·handoff·backlog로 가는 링크를 담는다.
- 저장소 전체 문서 지도의 정본은 CLAUDE.md에 유지한다. README에 전체 폴더 목록을 복제하지 않는다.
- 실행 절차에는 실제 존재하는 명령과 필요한 준비만 적는다. 미구현 명령은 넣지 않는다.
- 디자인 시스템 지도에 빠진 페이지 7개를 추가한다. 페이지 문서와 시안이 같은 이름으로 나란히 놓인다는 기존 규칙을 따른다.
- 파일 이동과 새로운 문서 사이트 도입은 이번 범위에 넣지 않는다.

### 변경 대상과 완료 기준

대상은 새 루트 `README.md`와 `design-system/README.md`다.

- [ ] 루트에서 실행 방법과 기존 문서 지도에 도달할 수 있다.
- [ ] 디자인 페이지 문서 12개가 지도에 모두 연결된다.
- [ ] 새 링크가 실제 파일과 절을 가리키며, 전체 문서 지도는 중복되지 않는다.

## 5. spec과 구현 계획의 경계 명확화

### 확인한 문제

[3-build 안내](../../3-build/README.md)는 “이 계획만 읽고 intent와 spec을 안 열어도 구현할 수 있어야 한다”고 요구한다. 완료 조건과 도메인 규칙을 다른 정본에서 관리하는 원칙과 함께 적용하면 계획에 내용을 복제할 여지가 있다.

### 변경안

- 해당 문장을 “계획과 연결된 정본을 읽으면 구현할 수 있어야 한다”로 바꾼다.
- spec은 요구·범위·완료 조건을 담고, plans는 변경 파일·작업 순서·리스크·검증 방법·정본 링크를 담도록 안내한다.
- plans가 spec의 완료 조건을 참조해 검증 방법을 설명하는 것은 허용한다. 완료 조건이나 업무 규칙을 별도의 원문으로 재정의하지 않는다.
- 신규 기능의 intent·spec·plan은 기존 같은 슬러그 규칙으로 연결한다. 각 문서가 다음 단계로 넘어갈 때 이전 단계 링크를 확인한다.
- 과거 완료 task의 누락된 intent나 plan을 형식상 채우지 않는다. 승인 전에 결정을 더 받아야 하는 신규 task부터 연결을 적용한다.

### 변경 대상과 완료 기준

대상은 [설계 안내](../README.md)와 [3-build 안내](../../3-build/README.md)다. 승인 게이트와 파일 이름 규칙은 [ADR-005](../adr/ADR-005-sdlc-stage-folders-and-artifact-chain.md)가 정한 것을 따른다.

- [ ] spec과 plan에 무엇을 적을지 안내만 읽고 구별할 수 있다.
- [ ] spec을 복제해야만 충족할 수 있는 계획 작성 규칙이 없다.
- [ ] 신규 task의 연결을 확인할 방법이 안내되고, 완료된 기록은 소급해서 만들어지지 않는다.

## 6. 긴 문서의 내부 목차 허용

### 확인한 문제

검토 시점에 관리자 근무표 문서는 957줄, 대시보드는 850줄, 로그인은 648줄이다. [디자인 시스템의 지도 규칙](../design-system/README.md#두-축)은 다른 문서에 목차나 문서 목록을 두지 못하게 한다. 문서 목록의 중복을 막는 규칙이 같은 파일 안의 탐색까지 막고 있다.

### 변경안

- 여러 문서의 목록은 README가 관리한다는 규칙을 유지하고, 같은 파일의 제목으로 이동하는 내부 목차를 허용한다.
- 첫 적용 대상은 [관리자 근무표](../design-system/pages/schedule-admin.md), [대시보드](../design-system/pages/dashboard.md), [로그인](../design-system/pages/login.md)이다.
- 목차는 주요 화면·흐름에 해당하는 2단계 제목을 중심으로 만든다. 모든 세부 제목을 나열하지 않는다.
- 기존 제목과 앵커를 유지한다. 파일 분할, 제목 개명, 본문 대규모 재작성은 이번에 하지 않는다.
- 목차만 추가한 경우 시안의 외형을 바꿀 이유는 없다. 1번 변경으로 화면 설명이 달라진 경우에는 그 변경 범위에 따라 시안을 갱신한다.

### 변경 대상과 완료 기준

대상은 `design-system/README.md`와 위 페이지 문서 세 개다.

- [ ] 문서 목록과 내부 목차의 차이가 규칙에 명시돼 있다.
- [ ] 긴 문서 세 개에서 주요 화면 절로 바로 이동할 수 있다.
- [ ] 추가한 앵커 링크가 모두 유효하고 기존 외부 참조가 유지된다.

## 7. CHANGELOG 갱신 책임 명시

### 확인한 문제

[CHANGELOG](../../CHANGELOG.md)의 최신 행은 2026-09-12다. [2026-09-14 회차 로그](../../log/2026-09-14.md)는 아키텍처 PR #315~#318을 기록하지만 변경 색인에는 해당 행이 없다.

[session-recorder 정의문](../../../.claude/agents/session-recorder.md)은 로그·backlog·handoff·관찰 로그를 다루며 CHANGELOG 갱신 절차는 명시하지 않는다.

### 변경안

- 회차 마감 담당에 CHANGELOG 갱신을 추가한다. 이미 읽는 merge된 PR을 근거로 날짜·변경 한 줄·PR 링크를 기록한다.
- 날짜는 실제 merge 날짜를 쓴다. 회차 로그의 날짜만 보고 추정하지 않는다.
- 중복 여부는 PR 번호로 확인한다. 상세 이유는 기존 로그와 PR에 남기고 CHANGELOG에는 변경 요약만 둔다.
- 우선 9월 13~14일 로그가 참조하는 merge된 PR과 색인을 대조해 누락을 채운다. 이 범위 이전의 전체 이력 복원은 별도로 판단한다.
- PR을 조회할 수 없는 경우 검증되지 않은 날짜를 채우지 않고 미확인 범위를 작업 결과에 남긴다.
- 갱신 누락을 막는 새 CI 검사는 이번에 추가하지 않는다. 담당 절차를 명시한 뒤에도 누락이 반복되는지 기존 관찰 로그로 확인한다.

### 변경 대상과 완료 기준

대상은 `CHANGELOG.md`와 `session-recorder` 정의문이다.

- [ ] 마감 담당의 입력·작업·결과에 CHANGELOG가 포함된다.
- [ ] 지정한 회차 범위의 PR이 실제 merge 날짜와 함께 중복 없이 기록된다.
- [ ] 최신 변경이 위에 있고, 각 행에서 해당 PR을 열 수 있다.

## 권장 작업 순서

| 묶음 | 수행 항목 | 함께 검토할 것 |
| --- | --- | --- |
| A. 작성 기준 정리 | 5번, 6번의 목차 규칙, 1·2·3번의 역할과 상태 표시 규칙 | 기존 정본 원칙·spec 승인 의미를 유지하는지 |
| B. 현재 문서 동기화 | 1번 불일치 해소, 3번 보드 정리, 2번 미구현 설명 연결, handoff 축약 | 결정 근거와 후속 task가 실제로 연결되는지, 옮긴 내용이 보존되는지 |
| C. 탐색과 기록 마감 | 4번, 6번 목차 적용, 7번 | 색인 누락·깨진 링크·변경 기록 누락이 없는지 |

각 묶음에서 규칙과 그 규칙을 적용한 문서는 함께 검토한다. 새 기능의 구현이나 데이터 마이그레이션은 이 계획에서 만든 후속 task의 별도 spec과 계획으로 진행한다.

## 검증 방법과 작업 종료 조건

검토 당시 기존 `docLinkViolations`와 `docMapViolations` 함수를 실행한 결과는 각각 0건이었다. 이는 상대 링크와 지도에 적힌 경로의 검증 결과다. 색인에서 빠진 파일, 의미가 다른 문장, 설명된 기능의 구현 여부까지 증명하지는 않는다.

| 검사 | 확인할 내용 |
| --- | --- |
| 기존 문서 검사 | `tests/lint/doc-links.test.ts`, `doc-map.test.ts`, `legacy-doc-paths.test.ts`로 링크·지도 경로·금지된 과거 경로를 확인한다 |
| 색인 대조 | `pages/*.md` 실제 목록과 디자인 시스템 지도를 비교한다 |
| 의미 검토 | 차단·뒤로 동작과 현재/목표 설명을 연결된 문서 및 코드와 대조한다 |
| 작업 연결 | handoff → backlog → 해당 spec이 이어지고 선행 조건이 보존됐는지 확인한다 |
| 기록 대조 | 지정한 회차 범위의 merge된 PR과 CHANGELOG를 대조한다 |
| 저장소 기본 검사 | 문서 변경에도 요구되는 `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`를 통과한다 |

루트 README의 링크는 현재 `docs/` 중심 링크 검사 범위 밖이므로 별도로 확인한다. 검사 범위를 넓히거나 문서 색인 자동 검사를 추가하는 일은 이 계획의 필수 변경에 포함하지 않는다.

일곱 항목의 완료 기준과 위 검증을 충족하면 작업을 끝낸다. 계획에서 다룬 정리 때문에 원래 내용이 사라지거나 정본이 둘로 늘어나지 않았는지 마지막으로 diff를 검토한다.

## 검토 시 판단할 범위

| 판단할 것 | 이 초안의 제안 | 영향 |
| --- | --- | --- |
| 문서 입구 | 루트 README를 추가하고 전체 지도는 CLAUDE.md에 유지 | 입구 파일 하나가 추가된다 |
| handoff 범위 | 다음 작업에 필요한 요약과 링크에 집중 | 상시 주의사항을 해당 정본으로 옮긴다 |
| 상태 관리 | spec은 승인, backlog는 진행 상태, architecture는 현재와 목표의 차이 | 기존 승인 훅을 바꾸지 않는다 |
| 목차 적용 | 같은 파일의 내부 목차 허용, 긴 페이지 세 개부터 적용 | 기존 목차 금지 규칙을 좁힌다 |
| 변경 기록 보정 | 9월 13~14일 회차 범위부터 대조 | 과거 전체 이력 복원으로 범위를 넓히지 않는다 |

이 계획은 문서의 구조와 유지 절차를 다룬다. 폴더 재편, 앱 기능 구현, DB 전환, 배포·운영 문서 채우기, 문서 사이트 구축, 새 자동 검사 도입은 별도 작업이다.
