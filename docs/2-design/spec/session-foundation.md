# 세션 기반

로그인한 사람이 누구인지를 서버와 브라우저 양쪽에서 읽고, 토큰이 만료되기 전에 갱신하는 층을 만든다. 화면은 안 만든다.

`docs/plan.md`의 task "세션 기반을 깐다"의 명세다. 승격 기준은 [ADR-002](../adr/ADR-002-sdd-ddd-tdd.md)에 있다 — 완료 조건이 여섯이고 예외 규칙이 셋이라 여기로 뺐다.

## 왜 먼저인가

`docs/2-design/domain/account.md`가 프로필을 "로그인한 계정에 딸린 앱 안의 사람"으로 정의한다. 로그인이 없으면 프로필도 승인도 없다. 계정 영역의 나머지 task가 전부 이 위에 선다.

지금 저장소에는 세션을 다루는 코드가 한 줄도 없다. `@supabase/ssr`이 없고 미들웨어도 없다. 클라이언트를 만드는 자리는 integration 테스트 헬퍼 안에만 있다.

## 용어

`docs/2-design/domain/account.md`가 정본이다. 이 명세는 셋만 쓴다.

- **프로필** — 구글 계정 하나에 하나. 로그인하는 순간 트리거가 만든다
- **승인 시각** — 비어 있으면 아직 승인 전
- **가입 승인** — 교대 승인과 다른 것이다. 이 task는 둘 다 판정하지 않는다

## 완료 조건

1. `@supabase/ssr`로 브라우저용과 서버용 클라이언트를 각각 만드는 자리가 있다. 서버용은 Server Component와 Route Handler에서 다 쓸 수 있다.
2. 서버에서 지금 로그인한 사람을 읽는다. 로그아웃 상태면 사람 대신 빈 값이 온다.
3. 미들웨어가 요청마다 세션 토큰을 갱신하고 새 쿠키를 응답에 심는다. 한 시간짜리 토큰이 만료돼도 사용자가 다시 로그인하지 않는다.
4. 로그아웃 Route Handler가 있다. 부르면 쿠키가 지워지고 그다음 요청에서 빈 값이 온다. 화면 없이 e2e가 직접 부를 수 있는 통로다.
5. e2e가 로컬 Supabase에 사용자를 만들고 그 세션을 브라우저에 심는 헬퍼가 있다.
6. `/`가 로그인한 사람의 **이메일 주소를 그대로** 드러낸다. 로그아웃 상태면 로그인하지 않았다는 문구가 뜬다.

조건 6이 이메일인 이유는 가짜 통과를 막기 위해서다. "로그인됨" 같은 문구만 띄우면 아무 쿠키나 심어도 통과한다. 그 세션에만 있는 값이 화면까지 나와야 세션이 정말 서버까지 닿았다는 증거가 된다. 실제 화면에 이메일을 노출하겠다는 뜻이 아니라, 발판이라서 로그인 화면 task에서 걷어낸다.

## 예외 규칙

**미들웨어는 정적 자원을 건너뛴다.** `_next/static`, `_next/image`, 파비콘, 이미지 확장자가 붙은 경로다. 안 그러면 이미지 한 장마다 토큰 갱신이 돌아 느려진다.

**서버에서는 `getUser()`만 믿는다.** `getSession()`은 쿠키를 그대로 돌려줄 뿐이라 위조된 쿠키를 걸러내지 못한다. `getUser()`는 Supabase에 물어보고 온다. 서버 코드에서 `getSession()`을 쓰지 않는다.

**승인 여부로 막지 않는다.** 이 task는 로그인만 본다. 승인 전 사람도 로그인은 된다 — `account.md`가 "승인 전에도 본인은 자기 프로필을 읽고 고친다"고 정해뒀다. 무엇을 막을지는 다음 task의 몫이다.

`getSession()` 금지는 테스트가 아니라 lint로 막는다. 코드가 어떤 메서드를 불렀는가는 정적인 사실이라, 요청마다 위조 쿠키를 만들어 확인하는 것보다 lint가 싸고 확실하다. 이미 있는 하우스 규칙들과 같은 자리에 둔다.

## 안 하는 것

- 로그인 화면과 구글 버튼. 화면 없이 기반만 깐다. 로그아웃은 화면이 아니라 Route Handler라서 이번에 들어간다
- 구글 OAuth 콜백 처리. 버튼이 있어야 검증이 되니 로그인 화면 task와 같이 간다
- 승인 대기 화면, 관리자 승인, 대기 목록
- 역할·차단·퇴사 컬럼. 필요해지는 task에서 마이그레이션을 더한다

## 어떻게 검증하나

구글은 자동화된 브라우저를 막는다. e2e가 진짜 구글 로그인 화면을 거칠 수 없다.

그래서 테스트는 로컬 Supabase에 사용자를 만들고 그 세션 쿠키를 브라우저에 직접 심은 채 화면을 돈다. 로그인 뒤의 흐름은 이 방식으로 전부 검증된다. "구글 버튼을 누르면 구글로 간다"는 한 조각만 자동 검증 밖에 남고, 그건 로그인 화면 task에서 사람이 손으로 본다.

로컬 Supabase에는 `[auth.external.google]` 설정이 아예 없다. 이메일 가입만 켜져 있고 지금 integration 테스트가 그걸 쓴다. 이 task는 그 상태를 그대로 두고, 세션을 심는 길만 새로 낸다.

## 걸릴 것

`tests/integration/supabase.ts`의 `createSignedInUser()`가 사용자를 만들기만 하고 치우지 않는다. 한 번 돌 때 여럿이 로컬 DB에 쌓이고, `supabase/config.toml`이 IP당 5분에 서른 번으로 가입을 막는다. e2e가 세션을 심으려면 사용자를 또 만들어야 해서 이 한도에 더 빨리 닿는다.

지금 막히지는 않지만 계정 task를 여러 회차 돌리면 닿는다. `docs/handoff.md`의 열린 결정에 있다.
