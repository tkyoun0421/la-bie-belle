# ADR-008 — 검토 제안과 실행 계획을 구별한다

2026-09-14에 정했다. [ADR-005](ADR-005-sdlc-stage-folders-and-artifact-chain.md)의 단계 구성을 유지하고, 여러 단계에 걸친 변경 방향을 검토하는 문서를 `docs/proposals/`에 둔다. 채택된 변경의 실행 방법은 `docs/3-build/plans/`에 둔다.

## 배경과 선택

문서 구조 개선 제안서를 비기능 문서라는 이유로 `3-build/plans/`에 두었다. 아직 어떤 변경을 할지 검토하는 내용인데 구현 계획으로 분류돼, 기획·설계를 고칠 방향이 이미 정해진 것처럼 읽혔다. 사용자 문제를 발견하는 `1-plan/intent/`에 둘지, 별도 자리를 만들지도 검토했다.

`intent/`는 제품 기능·이슈의 디스커버리와 spec 입력이라는 역할을 유지한다. 제품·설계·작업 방식의 변경 방향을 여러 단계에 걸쳐 검토할 자리는 단계 밖의 `proposals/`로 분리한다. 폴더와 작성 기준을 하나 더 관리하는 비용으로, 변경 방향의 검토와 결정 이후의 실행을 구별한다.

## 적용

작성 형식과 상태의 정본은 [proposals/README.md](../../proposals/README.md)다. 제안이 채택되면 영향을 받는 기획·설계 정본을 먼저 갱신하고, 필요한 구현 계획과 backlog 작업을 연결한다. 중요한 선택은 ADR로 남기고, 제안서는 당시 검토 근거로 보존한다. 한 제안의 일부만 채택되면 항목별로 결과를 적어 나머지가 함께 승인된 것으로 읽히지 않게 한다.

제안의 채택은 기능 spec의 승인을 대신하지 않는다. 기능의 intent→spec→plan 사슬과 spec 승인 관문은 유지한다. 방향이 분명한 작은 수정에는 제안서를 의무로 만들지 않는다. 관찰 기록은 계속 `observations/`에 두고, 변경 방향을 따로 검토할 때 제안서를 연결한다.

현재 [문서 구조 후속 제안](../../proposals/docs-structure-followup.md)은 새 자리로 옮긴다. 보관 위치의 결정과 그 문서에 담긴 개선 항목의 채택은 별개다. 이미 완료된 `3-build/plans/` 문서는 당시 작업의 기록으로 남긴다.
