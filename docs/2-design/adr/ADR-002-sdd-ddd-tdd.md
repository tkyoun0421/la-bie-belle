# ADR-002 — SDD와 DDD와 TDD

2026-08-25에 정했다.

## 결정

셋을 순서로 묶는다. 도메인 용어를 먼저 고정하고, 그 용어로 명세를 쓰고, 명세에서 실패하는 테스트를 뽑고, 그다음 구현한다.

셋 다 전부를 끌어오지 않는다. ADR-001이 이미 막고 있는 자리는 그대로 두고, 비어 있는 자리만 채운다.

## 순서

task 하나가 지나는 길이다.

1. 용어 — 새 개념이 나오면 `docs/2-design/domain/`에 한 뜻으로 박는다
2. 명세 — 무엇이 되면 완료인지를 그 용어로 쓴다
3. 테스트 — `test-planner`가 명세에서 리스크를 뽑고 writer 둘이 실패하는 테스트를 쓴다
4. 구현 — `implementer`가 빨간불을 초록불로 바꾼다

앞 단계를 건너뛰고 뒤로 갈 수 없다. 반대로 뒤에서 앞을 고칠 때는 앞 문서를 먼저 고친다. 구현하다 명세가 틀린 걸 발견하면 명세를 고치고 테스트를 다시 뽑는다. 코드에서 슬쩍 바꾸지 않는다.

## 명세가 사는 곳

기본은 `docs/plan.md`의 완료 조건이다. task 대부분은 한두 문장이면 끝난다.

규칙이 얽히면 `docs/2-design/spec/<task>.md`로 뺀다. 승격 기준은 둘 중 하나만 걸려도다.

- 완료 조건이 세 문장을 넘어간다
- 예외 규칙이 둘 이상이다

승격하면 `plan.md`의 완료 조건 자리에는 spec 파일 링크와 한 줄 요약만 남긴다. 같은 내용을 두 곳에 쓰지 않는다.

spec 파일은 총괄이 쓴다. 결정이 담기기 때문이다.

## 도메인을 어디까지 가져오나

셋만 쓴다.

**용어 정본.** 근무·포지션·배정·예식 같은 말을 `docs/2-design/domain/`에 한 뜻으로 박는다. 문서와 코드와 화면 문구가 같은 말을 쓴다. 뜻이 다르면 이름을 다르게 짓는다.

**규칙의 자리.** 도메인 규칙은 `entities/`에만 산다. `features`와 `screens`와 `shared`에 규칙을 두지 않는다. ADR-001의 "`.tsx`는 더미 UI다"가 UI 쪽을 막고, 이 조항이 나머지를 막는다.

**컨텍스트 경계.** 같은 말이 자리에 따라 다른 뜻이면 경계를 긋고 이름을 나눈다. 근무표에서 근무는 예정된 배정이고 급여에서 근무는 정산된 실근무다. 이런 자리를 `docs/2-design/domain/`에 적어둔다.

aggregate와 value object와 repository와 domain event는 쓰지 않는다. 근무자 수십 명이 쓰는 앱에서는 보일러플레이트가 기능보다 많아진다. 실제로 불변식을 못 지켜 사고가 나면 그때 넣는다.

## 컨텍스트는 폴더가 아니다

경계는 `docs/2-design/domain/`에만 산다. `src/` 아래에 컨텍스트 폴더를 만들지 않는다.

FSD는 레이어 밑에 슬라이스가 평평하게 놓이는 구조다. 그 위에 컨텍스트 폴더를 한 겹 끼우면 ADR-001의 배치가 깨지고 훅의 경로 판정도 어긋난다. 경계는 이름 짓기를 안내하는 문서로 두고, 파일은 FSD 그대로 놓는다.

## TDD와 맞닿는 곳

TDD 자체는 ADR-001이 정했다. 여기서 더하는 것은 테스트의 출처 하나다.

테스트는 명세에서 나온다. `test-planner`에게 넘기는 입력은 완료 조건이거나 spec 파일이고, 대화 요약이 아니다. 명세에 없는 단언이 테스트에 있으면 명세가 빈 것이니 명세를 먼저 채운다.

## 함께 정한 것

**세 이름을 새 절차로 만들지 않는다.** SDD와 DDD는 지금 흐름에 이름을 붙이고 빈 자리 둘(용어 정본, 명세 승격)을 채우는 선까지다. 새 subagent도, 새 훅도 만들지 않는다.

**`docs/2-design/domain/`는 PRD와 같이 자란다.** 지금은 코드가 없어 박을 용어도 없다. PRD를 확정할 때 처음 채우고, 이후 새 개념이 나올 때마다 더한다.

**훅으로 막지 않는다.** 용어가 어긋나거나 규칙이 `features`로 새는 것을 기계가 판정하기 어렵다. `pr-diff` 감사와 총괄 리뷰가 받는다. 이 길로 위반이 main에 들어오면 증축 규칙대로 그때 훅을 단다.

## 남는 위험

승격 기준이 사람 판단이다. 세 문장 안에 우겨넣으면 spec 파일이 안 생긴다. 완료 조건이 읽기 어려워지면 그게 신호다.

컨텍스트 경계를 코드보다 먼저 긋는다. 틀린 자리에 그을 위험이 있다. 문서에만 두고 폴더로 굳히지 않는 이유가 이것이다. 틀리면 문서 한 줄을 고치면 된다.

용어 정본과 코드 사이를 잇는 장치가 없다. `docs/2-design/domain/`를 고치고 코드 이름을 안 바꿔도 아무도 안 막는다.
