# ADR-005 — SDLC 단계 폴더와 artifact chain

2026-09-04에 정했다.

## 결정

`docs/`를 SDLC 단계 폴더로 재편한다. Plan→Design→Build→Test→Deploy→Maintain 여섯이 `1-plan/`부터 `6-maintain/`까지 번호 폴더로 선다. 기능마다 intent→spec→plan 사슬을 만들고, spec 승인 없이 구현을 시작하지 못하게 훅으로 막는다.

원본은 Anthropic의 AI-native SDLC 플레이북이다. 진단은 기획과 설계의 부실 — 완료 조건 한두 줄이 설계를 대신해 왔다. 처방이 설계 먼저, 구현 나중이다.

## 새 배치

```
docs/
  handoff.md            유지 — 세션 스냅샷, 단계 무소속
  backlog.md            plan.md 개명 — 기능 목록·상태·우선순위·사슬 링크만
  CHANGELOG.md          신설 — 무엇이 언제 바뀌었는지의 시간순 색인
  log/                  유지 — 회차 서사, 왜가 여기 있다
  1-plan/               prd.md, scenarios.md, roadmap.md, metrics.md, intent/
  2-design/             domain/, architecture/, design-system/, adr/, spec/
  3-build/              plans/ — 기능별 구현 계획
  4-test/               strategy.md — 테스트 층 배정 기준
  5-deploy/             자리만 — 배포가 다가오면 채운다
  6-maintain/           자리만 — 운영이 시작되면 채운다
```

intent·spec·adr·plans는 전용 하위 폴더로 관리하고 그 안에 기능 슬러그 단위 파일을 쌓는다. 단계 폴더 바닥에 낱장을 두지 않는다.

메타 문서 넷(handoff·backlog·CHANGELOG·log)은 어느 단계에도 안 속해서 루트에 남는다. 언제 읽느냐의 답이 "항상"인 문서다.

## 파일 이름

소문자 kebab-case가 기본이다. 예외는 셋뿐이다 — `README.md`와 `CHANGELOG.md`와 `ADR-NNN-*.md`는 생태계 표준이 대문자라 그대로 둔다.

사슬 파일은 같은 슬러그로 잇는다. `1-plan/intent/dark-mode.md`가 생기면 spec과 plans의 파일도 `dark-mode.md`다. 슬러그 하나로 세 단계를 오간다.

기능 브랜치도 같은 슬러그를 쓴다 — `feat/<슬러그>`. spec 승인 게이트 훅이 브랜치 이름에서 슬러그를 읽어 그 spec의 승인을 확인한다. `feat/`가 아닌 브랜치(문서·리팩터링·수리)는 게이트 밖이다.

## 사슬

기능 하나가 지나는 길이다. 같은 슬러그가 세 파일을 잇는다.

1. `1-plan/intent/<슬러그>.md` — 디스커버리 인터뷰 산출물. 왜 만들고 무엇을 원하는지
2. `2-design/spec/<슬러그>.md` — 요구와 설계와 완료 조건. 프론트매터 `status`가 승인 마크다
3. `3-build/plans/<슬러그>.md` — 바꿀 파일, 순서, 리스크

관문은 spec→구현 한 마디만이다. 승인 안 된 spec의 기능으로 `src/`를 고치면 훅이 막는다. intent→spec에는 관문이 없다 — intent는 태관과의 인터뷰가 낳는 문서라 쓰이는 순간 이미 태관이 봤다. 여기에 ADR-001의 TDD 훅이 이어져 사슬이 완성된다: spec 승인 → 실패 테스트 → 구현.

spec은 기능마다 의무다. ADR-002의 승격 기준(세 문장, 예외 둘)은 이 결정으로 대체된다 — 완료 조건은 이제 항상 spec에 산다.

## 증축 규칙 예외

CLAUDE.md 증축 규칙은 상처가 생긴 자리에만 짓는다고 정했다. 이번 개편은 예외로 선검사를 단다 — 라우터와 실제 폴더의 일치, 구 경로 잔존, spec 승인 게이트가 그것이다. 예방이 아니라 확인된 위험의 방어다. 조사에서 경로 하드코딩 세 곳과 정의문 여섯이 이동에 깨질 것을 미리 확인했다. 규칙 자체는 그대로 둔다.

## 범위 밖

셋을 이번에 안 한다. 잊은 게 아니라 미룬 것이다.

- 배포 플랫폼 선택 — 정보가 없어 결정 품질이 안 나온다. 배포가 다가오면 ADR로 정한다
- CI eval — 운영 중인 제품이 전제다
- 자율 유지보수(알림이 에이전트를 깨워 스스로 intent를 쓰는 것) — 같은 이유다

## 이행

자족 PR 여섯으로 나른다. 각 PR이 혼자 CI 초록이어야 한다 — 문서 이동과 그 경로를 참조하는 코드 갱신은 같은 PR에 탄다.

1. 골격 — 폴더·README·CHANGELOG·이 ADR·라우터 갱신
2. design-system 이사 + 경로 하드코딩 세 곳 갱신
3. domain·adr·spec·prd 이사 + 정의문 갱신
4. plan.md→backlog.md 전환 + 완료 조건의 spec 이사
5. spec 승인 훅 + 라우터 일치·구 경로 잔존 검사
6. 신설 기획 문서 뼈대

CLAUDE.md 문서 지도는 매 PR에서 실제 자리를 따라간다. 신구 혼재 기간에도 지도는 거짓말하지 않는다.

## 남는 위험

이름이 두 겹이다. 전역 backlog.md와 기능별 `3-build/plans/`가 다 계획이라 불릴 수 있다. 보드는 무엇을 할까의 목록이고 plans는 어떻게 만들까의 순서다 — 섞이면 이 조항을 가리킨다.

정의문 갱신 누락이 조용히 깨진다. 구 경로를 참조하는 정의문은 이사 PR에서 같이 고치지만, 빠뜨린 자리는 다음 스폰이 헛짚을 때야 드러난다. 5번 PR의 구 경로 잔존 검사가 이 구멍을 막는다.

단계 폴더는 한 문서가 여러 단계에 걸칠 때 자리가 애매하다. 그럴 땐 만든 단계가 아니라 정본을 찾을 단계에 둔다 — 그래서 adr이 전부 `2-design/`에 있다.
