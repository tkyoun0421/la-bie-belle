# Matcher: gate 원장

슬라이스를 구현하거나 그 완료를 판정할 때 읽는다.

완료를 주장이 아니라 증거로 가른다. 세션이 "다 됐다"고 말하는 것과 명령이 실제로 초록으로 끝나는 것은 다른 사실이다. 원장은 뒤쪽만 센다.

## 어디에 사는가

원장은 `.gates/<slice>.md`다. 슬라이스 하나에 파일 하나이고 `.gitignore`에 들어 있다. 추적되지 않지만 `config/ownership.json`에는 네 역할 모두의 목록에 들어 있다 — 소유 가드는 git이 아니라 경로를 보고 판정하므로 registry에 없으면 아무도 원장을 쓰지 못한다.

추적하지 않는 이유는 수명이 브랜치보다 짧아서다. 슬라이스가 merge되면 그 원장이 가리키던 작업은 끝난다.

**끝난 원장은 지운다.** 브랜치를 지울 때 함께 지워라. 남겨 두면 그 worktree의 모든 종료를 계속 막는다. 서브에이전트가 돌아올 때마다 끝난 작업의 `CHECK:`가 지금 체크아웃된 트리에서 다시 돈다.

**PR을 열 때 원장 전문을 PR 본문에 올린다.** 요약이 아니라 `CHECK:`까지 그대로다. 거기가 정본이다. 로컬 파일은 작업 중 상태를 담는 자리일 뿐이다. 리뷰어는 PR 본문에서 원장을 읽는다.

## 무엇이 gate가 되나

기계가 돌려 통과 여부를 가를 수 있는 것만이다. 사람이 눈으로 보는 절차는 원장이 아니라 `[Slice]` Issue의 확인 방법 칸이 받는다. 두 자리는 겹치지 않는다.

| 자리 | 담는 것 | 누가 판정 |
|------|---------|-----------|
| `[Slice]` Issue 확인 방법 | 직접 눌러 보는 순서, 상태·반응형·접근성 | 사람 |
| `.gates/<slice>.md` | 명령과 기대 출력 | `scripts/gate-check.py` |

디자인 슬라이스는 실행 gate가 거의 나오지 않는다. 원장 없이 간다.

## 형식

```markdown
# Gates: 예약 취소 — Slice #142

- [ ] G1: 스펙 3.2
  CHECK: pnpm vitest run src/reservation/cancel
  EXPECT: 8 passed
  EVIDENCE: pending

- [ ] G2: 스펙 3.4 — 취소 마감이 지난 예약은 거절한다
  CHECK: pnpm vitest run src/reservation/cancel-deadline
  EXPECT: 3 passed
  EVIDENCE: pending
```

gate 제목은 인수 조건 **번호를 참조한다**. 조건 본문을 옮겨 적지 마라. 명세의 유일한 정본은 `docs/specs/` 아래 파일이다. 옮겨 적은 순간 원장이 두 번째 사본이 된다. 번호만으로 무엇인지 떠오르지 않으면 짧은 꼬리말을 붙여도 되지만 조건을 다시 쓰지는 않는다.

파서 규칙은 좁다.

- gate는 `- [ ] ID: 제목`이나 `- [x] ID: 제목`으로 시작한다. id는 파일 안에서 유일해야 한다
- `CHECK:`, `EXPECT:`, `EVIDENCE:`는 gate 아래로 들여쓴다. 들여쓰지 않으면 오류다
- 속성은 gate 줄 **바로 다음 줄부터 끊기지 않고** 이어진다. 사이에 빈 줄이나 주석이 들면 오류다
- 같은 속성을 gate 하나에 두 번 쓰지 않는다
- gate마다 `CHECK:`와 `EXPECT:`가 둘 다 있어야 한다. 하나만 있으면 오류이고 둘 다 없는 수동 gate도 오류다. 둘 중 하나라도 비어 있으면 오류다 — 빈 기대는 무엇에나 걸려 gate가 아무것도 재지 않는다
- `EVIDENCE:`는 gate당 한 줄이다. 빠뜨리면 검사가 넣어 준다
- `EXPECT:`는 부분 문자열이다. `/패턴/플래그` 형태로 쓰면 정규식이고 플래그는 `i`, `m`, `s`만 받는다
- 코드 펜스 안의 줄은 세지 않는다. 원장 안에 형식 예시를 적을 자리다. 열린 펜스가 닫히지 않은 채 파일이 끝나면 오류다 — PR 본문에서 원장을 옮겨 붙이다 여는 펜스가 딸려오면 그 아래 gate가 통째로 사라지기 때문이다
- gate가 하나도 없는 원장은 오류다. 빈 원장은 ALL MET이 아니다

형태가 어긋난 줄은 무시되지 않고 오류가 된다. 검사가 그것을 잡는 길은 둘이다.

하나는 **인접**이다. 속성이 자기 gate 바로 아래에 없으면 사이에 무엇이 끼었다는 뜻이라 오류가 난다. 다른 하나는 **의심**이다. 어느 규격에도 맞지 않는 줄에 gate의 재료 — `CHECK:` 같은 속성 이름이나 `[ ]` 꼴의 짧은 대괄호 상자 — 가 실려 있으면 줄의 어느 자리에 있든 오류다. 검사는 줄을 유니코드 호환 분해(NFKD)로 펼친 뒤 서식·결합·제어 부류의 문자를 통째로 걷어 내고 본다. 합성이 아니라 분해가 먼저인 것이 요점이다 — 결합 부호가 앞 글자와 합쳐져 다른 글자가 되기 전에 걷힌다. 그래서 대소문자·불릿 문자·전각 글자·전각 콜론과 콜론 닮은꼴·전각 대괄호·글자 사이에 끼운 제로폭이나 방향 표식이나 결합 부호·줄 앞의 인용 부호 `>`나 보이지 않는 공백을 전부 가리지 않는다.

의심이 어긋난 모양을 하나하나 세지 않는 것이 요점이다. 어긋나는 모양은 끝이 없지만 재료 없는 gate는 없다. 블록이 검사를 지나치려면 줄마다 속성 이름과 상자가 다 지워져야 하는데 그때는 삼킬 gate가 남아 있지 않다. 대신 원장 산문에는 제약이 둘 생긴다 — 속성 이름 뒤에 콜론을 달거나(`typecheck:`처럼 영문 낱말의 꼬리인 것만 산문으로 본다. 한글·숫자·밑줄에 붙은 것은 잡는다), 안이 세 글자 이하인 대괄호를 쓰면 줄 어디에 있어도 의심에 걸린다. 산문은 그 두 가지를 피해서 써라.

이 방어의 경계도 적어 둔다. 다른 문자 체계의 닮은꼴 글자로 재료 자체를 갈아 끼우는 것 — 키릴 문자로 쓴 CHECK, 대괄호 닮은꼴 괄호 — 은 기계가 다 셀 수 없다. 그건 `CHECK:`를 약하게 고치는 것과 같은 부류이고 방어선도 같다. PR 본문에 실린 원장을 리뷰어가 읽는다.

## 판정

실행 gate는 조건 둘이 함께 참일 때만 충족이다.

1. 프로세스가 종료 코드 `0`으로 끝난다
2. `EXPECT:`가 표준 출력과 표준 에러를 합친 것에 걸린다

실패한 프로세스는 에러 문구에 기대 표식이 섞여 있어도 통과하지 못한다. 타임아웃, 셸 실행 실패, 없는 명령도 실패다. 기본 제한 시간은 120초이고 `--timeout`으로 바꾼다.

**상자가 채워졌는데 증거가 `pending`이면 미충족이다.** 증거는 검사가 쓰지 사람이 쓰지 않는다.

## 명령

```
python3 scripts/gate-check.py --status      # 파싱하고 보고만 한다. 아무것도 돌리지 않는다
python3 scripts/gate-check.py --run         # 미충족 gate를 돌리고 증거를 채운다
python3 scripts/gate-check.py --reverify    # 충족된 것까지 전부 다시 돌린다
```

`--timeout <초>`로 제한 시간을, `--cwd <경로>`로 명령이 도는 자리를 바꾼다. `--hook`과 `--subagent`는 훅이 쓰는 모드다. 손으로 부르지 않는다.

경로를 넘기지 않으면 `.gates/` 아래를 전부 읽는다. 종료 코드는 충족이면 0, 미충족이 남으면 1, 원장이 깨졌으면 2다.

`--status`를 재검증으로 착각하지 마라. 그건 파일에 적힌 것을 읽을 뿐이다. 돌아온 작업을 받을 때는 `--reverify`를 쓴다.

## 누가 무엇을 쓰나

`CHECK:`와 `EXPECT:`는 슬라이스를 던지는 쪽이 쓴다. worker는 `EVIDENCE:`만 채운다.

판정 기준을 쓴 손과 통과시킬 손을 가르는 것이 요점이다. 자기 PR을 자기가 리뷰하지 않는다는 규칙이 같은 축에 서 있다. worker가 `CHECK:`를 고쳐야 할 만큼 기준이 틀렸다면 그건 구현이 아니라 보고할 일이다.

## 포기

불가능한 gate를 조용히 지우지 마라. 원장 아무 자리에 한 줄을 남긴다. gate 정의보다 위여도 된다. 다만 들여쓰지는 마라 — 들여쓴 줄은 gate의 속성 자리라서 오류가 난다.

```
ABANDON: G3 결제 사업자 계정이 아직 없어 실제 승인 경로를 못 돈다
```

사유는 비울 수 없고 없는 id를 가리키면 오류다. 포기한 gate는 미충족으로 세지 않지만 보고에서 사라지지도 않는다. PR 본문과 완료 보고가 그것을 그대로 나른다. 요청받은 산출물이 통째로 포기됐다면 그 작업은 완료가 아니다.

한 슬라이스가 통째로 막히는 것은 포기가 아니라 Blocked다. `docs/rules/matchers/blocked.md`를 봐라.

## 훅

`.claude/hooks/gate-guard.sh`가 `Stop` 훅으로 걸린다. 세션이 끝나려 할 때 `.gates/` 아래를 읽는다.

- 원장이 없으면 통과시킨다. 강제 범위를 정하는 것이 이 조건이다
- 미충족 gate가 남았으면 막는다
- 원장이 깨졌으면 막는다. 통과가 아니라 차단이다

이 훅은 명령을 돌리지 않고 파일에 적힌 것만 읽는다. 종료할 때마다 셸이 도는 것을 막으려는 것이다.

증거를 만드는 것은 짝이 되는 훅이다. `.claude/hooks/gate-verify.sh`가 `SubagentStop`으로 걸려, 서브에이전트가 돌아올 때마다 원장의 실행 gate를 전부 다시 돌리고 결과를 덮어쓴다.

**이것이 증거 위조를 무의미하게 만드는 자리다.** 상자와 증거를 손으로 써넣어도 훅이 명령을 다시 돌린다. 실제로 통과하지 않으면 상자가 그 자리에서 비워진다. 위조를 막을 방법은 없다 — 같은 기계, 같은 권한이다. 대신 위조가 남지 못하게 한다.

훅이 덮는 것은 `EVIDENCE:`뿐이다. `CHECK:`를 약하게 고쳐 놓으면 다시 돌려도 초록으로 돌아온다. 그 자리의 방어선은 사람이다 — PR 본문에 실린 원장에서 리뷰어가 `CHECK:`를 읽는다. 상태 파일 `.gates/.hook-state.json`을 지우면 해제 횟수도 처음으로 돌아간다. 로컬 훅을 끄거나 `--no-verify`로 커밋하는 것과 같은 부류다. 그래서 마지막 판정은 언제나 리뷰에 있다.

원장이 없으면 이 훅도 아무것도 하지 않는다.

## 해제

**새로 충족된 gate 없이** 여섯 번 연속으로 막히면 일곱 번째는 통과시킨다. 채울 수 없는 gate 하나가 세션을 영원히 붙잡는 것을 막는 장치다.

세는 기준은 직전 값이 아니라 그 세션이 이제까지 도달한 최고치다. 그래야 gate 둘이 번갈아 통과하며 충족 수가 오르내려도 카운터가 계속 오른다. 직전 값과 견주면 오르내림이 매번 카운터를 되돌려 세션이 영원히 갇힌다.

해제는 조용히 일어나지 않는다.

- 원장에 `RELEASED: <사유와 미충족 목록>` 줄이 남는다. PR 본문에 실려 리뷰어가 본다
- 해제는 **세션당 한 번**이다. 그 뒤로 미충족이 남으면 계속 막는다

그 자리에서 할 일은 `ABANDON:`에 사유를 남기는 것이지 여섯 번 버티는 것이 아니다. 상태는 `.gates/.hook-state.json`에 세션별로 앉고 역시 추적하지 않는다.

## 정직하게 실패하는 gate를 써라

검사는 네가 선언한 명령이 무엇을 재는지 모른다. 한국어 제목과 셸 코드가 같은 것을 말하는지는 사람만 안다.

```markdown
- [ ] G1: 청구서가 맞아떨어진다
  CHECK: node -e "console.log('ok')"
  EXPECT: ok
```

형식은 멀쩡하고 의미는 없다. 아래를 지켜라.

- 제목이 말하는 산출물이나 측정을 명령이 직접 읽게 해라
- 성공 표식은 모든 단언을 통과한 뒤에만 찍는다. 중간에 찍힌 표식은 실패를 덮는다
- 부재를 확인하는 gate는 믿기 전에 통과할 것이 확실한 대조군에 먼저 돌려 실패하는지 봐라. 없는 파일이나 틀린 경로도 부재처럼 보인다
- 브리프에서 받은 숫자를 그대로 `EXPECT:`에 옮기지 마라. 그 숫자를 원천에서 다시 재는 명령을 써라
- 증거는 결정적인 한 줄이면 된다. 로그 전체를 원장에 붙이지 마라
