# PR이 커서 자동 리뷰가 diff를 한 줄도 못 읽었다

PR #507이 변경 파일 300개를 넘었다. 자동 리뷰가 「판정: 확인 필요」를 달고 못 본 곳을 네 가지로 적었는데, 그중 첫째가 **diff 전문을 하나도 못 읽었다**다.

## 무엇이 막혔나

- `gh pr diff`가 HTTP 406을 돌려준다 — GitHub이 파일 300개 넘는 PR의 diff를 안 내놓는다
- 파일 목록 API는 앞 100개에서 끊긴다
- PR 브랜치를 `git fetch`로 가져오는 길은 워크플로 권한이 막는다

그래서 리뷰가 확인한 것은 읽은 100개의 **추가·삭제 줄 수**와 저장소 전체 시크릿 검색뿐이다. 「삭제 줄이 주석뿐인가」·「테스트 단언이 약해지지 않았나」·「동작이 바뀐 줄이 없나」는 전부 못 봤다.

## 리뷰가 놓친 것이 실제로 하나 있었다

`src/shared/ui/DragAndDrop.tsx` 삭제다. 리뷰는 「읽은 100개 중 삭제로 표시된 파일은 없다」고 적었고 그 말은 맞았다 — 그 파일이 101번째 뒤에 있었다. 삭제 자체는 plan이 적어 둔 걸음이라 문제가 아니었지만, **리뷰가 봤어야 할 종류의 변경이 눈 밖에 있었다**.

## 기계가 대신할 수 있나

할 수 있다. PR의 변경 파일 수를 CI가 세서 상한을 넘으면 경고를 달면 된다. 상한 값은 리뷰가 막히는 선(300)이 아니라 사람이 한 번에 읽을 수 있는 선이어야 하고, 그 선이 몇인지는 아직 모른다.

**갈라서 올리는 길도 기계가 재지는 못한다.** 이 task는 AC 열다섯이고 묶음 열이 직렬로 돌았다 — 묶음마다 PR을 열었으면 열 번 리뷰를 받았겠지만, 그 묶음들이 같은 `eslint.config.mjs`와 같은 카탈로그 표를 고쳐서 PR끼리 충돌한다. 끊는 자리를 정하는 것은 사람의 판정이다.

## 지금 한 것

로컬에서 `git diff main...HEAD`로 리뷰가 못 본 넷을 직접 확인해 PR에 코멘트로 답했다. 삭제 줄 347개가 전부 주석인 것, 삭제 파일 하나가 의도된 것, 총괄 문서 접촉이 셋인 것, 고친 버그 둘에 짝 테스트가 온 것이다. **총괄이 리뷰의 눈을 대신한 셈이고 그것이 마찰이다** — 자동 리뷰를 둔 까닭이 총괄이 안 봐도 되게 하려는 것이었다.
