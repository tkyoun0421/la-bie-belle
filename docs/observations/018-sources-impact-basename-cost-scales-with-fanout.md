# 「영향 확인」 게이트가 파일 하나당 이름을 다 세게 만든다

## 일

PR #406이 `navigation.md`와 `components.md`처럼 여럿이 `sources`로 드는 문서 둘을 건드렸다. 그 둘을 받는 spec·plan이 서른한 개고, 게이트(`tests/lint/sources-impact.ts`)는 PR 본문에서 바뀐 각 문서의 basename을 문자열로 찾는다. 산문으로 「전수 확인했다」고만 적으면 그 이름이 하나도 안 나와서 막힌다.

통과하려면 서른한 개를 바뀐 입력 다섯 갈래로 묶어 각 파일 이름을 본문에 글자로 적어야 했다 — 판정 자체(영향 없음)는 짧게 끝나는데, 그것을 검사가 읽게 쓰는 절이 PR 본문에서 가장 길었다. 판정이 쉬운데 표현 비용이 판정 난이도가 아니라 팬아웃(그 문서를 받는 문서 수)에 비례해서 커진다.

## 고침

셋 중 하나다. 팬아웃이 큰 문서(`navigation.md`·`components.md`류)는 받는 쪽 서른한 개 전부를 basename으로 요구하는 대신, 「영향 없음」 판정을 문서 단위로 한 번만 적어도 통과하게 검사를 완화한다. 아니면 받는 문서를 입력 갈래로 묶어 적는 지금 방식을 검사가 인식하는 형식(예: 갈래 제목 + 하위 목록)으로 못박아 다음 사람이 같은 구조를 반복 발명하지 않게 한다. 아니면 그대로 두고 「팬아웃 큰 문서를 건드리는 PR은 본문이 길어진다」를 알려진 비용으로 남긴다.

## 원칙

영향 확인의 어려움은 판정(닿는가 안 닿는가)에 있는데, 검사가 요구하는 것은 표현(이름을 얼마나 나열하는가)이다. 판정이 쉬운 변경도 팬아웃이 크면 표현 비용만으로 본문이 길어진다.
