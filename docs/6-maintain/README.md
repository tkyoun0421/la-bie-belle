# 6-maintain — 운영

## 역할

아직 백지다. 운영 중인 배포가 없다. 첫 출시 준비 task가 배포 문서와 같이 채운다 — 운영이 시작된 뒤가 아니다. 첫 운영 전에 서야 하는 최소는 장애를 확인하는 자리, 대응 담당, 복구 뒤 확인 방법이다. 지표는 측정을 만들기 전에 집계 기준(분모·기간·수집 대상)이 [metrics.md](../1-plan/metrics.md)에 선다.

다룰 것: 모니터링, 인시던트 절차, 운영 지표.

미뤄둔 것: CI eval, 알림이 에이전트를 깨워 스스로 intent를 쓰는 자율 유지보수. 근거는 ADR-005의 범위 밖 절에 있다.

## 문서 지도

| 문서 | 답하는 질문 |
| --- | --- |
| [`monitoring.md`](monitoring.md) | 무엇을 어디서 보고 어떤 신호일 때 대응을 시작하나 |
| [`response.md`](response.md) | 누가 어떤 순서로 대응하고 복구를 무엇으로 확인하나 |
| [`metrics.md`](metrics.md) | 기획이 정의한 지표를 무엇으로 수집하고 어떻게 집계하나 |
| `incidents/` | 어떤 장애가 언제 무엇에 영향을 줬고 어떻게 끝났나. 첫 기록이 생길 때 만든다 |

## 입력과 산출물

작성법 하나는 「용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준」 순서다. 모든 문서에 공통인 규칙은 [문서 지도](../README.md#참조와-작성-규칙)가 소유한다.

### monitoring·response·metrics

**용도·작성 시점:** 첫 운영 전에 관측·대응·측정 방법을 작성한다. 실제 담당·도구·경보 기준은 출시 준비 작업에서 확인한다. 사건 기록을 채우기 위해 가상의 운영 사건을 만들지 않는다.

**복사용 틀과 절별 질문:**

| 문서 | 본문 틀 | 절별 작성 방법 | 검토 기준 |
| --- | --- | --- | --- |
| `monitoring.md` | 관측 대상 → 확인 위치·방법 → 신호 해석 → 담당·주기 → 누락·미정 | `신호 / 확인 위치·질의 / 정상 기준의 근거 / 대응을 시작할 조건 / response 링크` 표. 앱·DB·푸시 같은 의존성별로 사용자가 겪는 문제와 신호를 연결한다 | 담당자가 이상 여부를 판단하고 필요한 로그를 찾을 수 있는가 |
| `response.md` | 분류와 담당 → 초기 확인 → 완화 → 복구 확인 → 기록·후속 | 영향 파악·담당 연결·완화·복구 확인을 실제 순서로 쓴다. 각 단계에 전제·행동·확인 결과·다음 분기를 둔다. 되돌리는 명령은 deploy/procedure를 링크한다 | 담당·중단 조건·지원 요청 경로가 있고, 복구를 사용자 동작으로 확인하는가 |
| `metrics.md` | 기획 지표 참조 → 수집 원천 → 집계 구현 → 검증 → 측정 주기·담당 → 한계 | 아래 틀로 이벤트·쿼리·작업을 기획의 정의에 대응한다. 정의를 다시 만들지 않는다 | 분모·기간·누락 처리가 기획 정의와 같고, 수집하지 않는 값을 측정한 것처럼 쓰지 않았는가 |

```markdown
### <기획 지표의 이름>

- 정의: <1-plan/metrics.md의 해당 절 링크>
- 수집 원천: <이벤트·테이블·수기 기록, 발생·수집 시각>
- 집계 구현: <쿼리·스크립트 위치, 매개변수, 실행 방법>
- 정의와의 대응: <분자·분모·기간·제외 조건을 구현한 위치>
- 검증: <알려진 작은 표본의 기대 집계와 실제 값>
- 주기와 담당: <언제 누가 실행·검토하고 결과를 어디에 두나>
- 한계: <누락·중복·지연·관측 불가능한 항목과 보완 작업>
```

**측정 방법 쓰기:** 먼저 기획의 집계 정의가 결정되었는지 본다. 그다음 결과를 손으로 셀 수 있는 작은 가짜 표본을 만들고 쿼리 결과와 비교한다. 푸시를 보냈다는 기록이 사용자의 수신을 뜻하는지처럼 관찰한 사실과 추정도 구별한다. 관찰할 수 없는 지표를 다른 지표로 조용히 대체하지 않는다.

### incident

**용도·작성 시점:** 장애가 발생했을 때 확인한 사실부터 적고 대응 중에 보완한다. `<date>-<incident>.md`는 작업 ID·릴리스 ID와 별개이며 관련 기록을 링크한다.

**복사용 틀:**

```markdown
# <발생일> — <장애 이름>

## 영향과 발생 시각
<영향 사용자·기능 / 최초 영향·발견 시각과 시간대 / 아직 모르는 범위>

## 관련 릴리스
<릴리스·커밋·변경 사항. 관련성이 미확인이라면 그 사실>

## 확인 사실
| 시각 | 관찰한 사실 | 근거 | 남은 가설·확인 방법 |
| --- | --- | --- | --- |

## 대응·복구 확인
| 시각·담당 | 실행한 조치 | 실제 결과·근거 | 다음 판단 |
| --- | --- | --- | --- |

## 원인과 후속 작업
<확인한 원인과 근거, 또는 미확인 / 재발 조건 / 후속 task·정본 변경 링크>
```

**절별 질문:** 장애 중에는 사실·가설·조치를 시간순으로 쓴다. 복구 후 원인을 설명하고 미확인 추정을 확정 원인으로 바꾸지 않는다. 제품 요구 변경은 intent, 절차 문제는 해당 운영 문서와 비기능 plan, 작업 방식의 반복 마찰은 observation으로 연결한다. incident 본문에서 이후의 진행 상태를 별도로 관리하지 않는다.
