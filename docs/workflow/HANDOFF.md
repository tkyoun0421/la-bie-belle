# handoff 계약

- 상태: Accepted
- 기준일: 2026-08-03
- 관련 결정: [ADR-0013](../standards/adr/0013-project-layer-structure.md)
- 관련 문서: [운영 계약](WORKFLOW.md)

## 목적

세션이 끊겨도 다음 세션이 처음부터 다시 설명받지 않고 이어갈 수 있게 한다. handoff는 "지금까지 무엇이 확정됐고, 무엇이 안 정해졌고, 다음에 무엇을 하는가"를 한 파일에서 읽게 하는 인계 기록이다.

인터뷰와 하네스 실행은 **같은 포맷**을 쓴다. 형식이 같아야 사람과 도구가 단계와 무관하게 같은 방식으로 읽을 수 있다.

## 기록 시점

[운영 계약](WORKFLOW.md)의 5단계 경계마다 기록한다.

| 시점 | 기록 주체 | 위치 |
| --- | --- | --- |
| 기획 승인 직후 | 인터뷰 | `docs/execution/runs/interviews/<날짜-주제>.md` |
| RADIO 승인 직후 | 인터뷰 | `docs/execution/runs/interviews/<날짜-주제>.md` |
| 개발 단계 종료 | 하네스 실행 | `docs/execution/runs/<task-id>/handoff.md` |
| 검증 단계 종료 | 하네스 실행 | `docs/execution/runs/<task-id>/handoff.md` |
| 리팩토링 종료·완료 보고 | 하네스 실행 | `docs/execution/runs/<task-id>/handoff.md` |
| `blocked` 안전 중단 | 하네스 실행 | `docs/execution/runs/<task-id>/handoff.md` |

- task 단위 handoff는 파일 하나를 유지하고 단계별 기록을 **아래로 덧붙인다**. 이전 기록을 덮어쓰거나 지우지 않는다.
- 인터뷰 handoff의 `<날짜-주제>`는 `2026-08-03-project-structure`처럼 `YYYY-MM-DD-<영문-주제>` 형식을 쓴다.
- 세션이 비정상 종료돼 handoff가 없으면, 다음 세션은 작업을 이어가기 전에 현재 상태를 확인하고 handoff부터 복원한다.

## 최소 필드

모든 handoff는 다음 7개 항목을 가진다. 해당 없으면 항목을 지우지 말고 `없음`이라고 쓴다.

| 필드 | 의미 | 비고 |
| --- | --- | --- |
| 작업 식별자 | task ID 또는 인터뷰 주제 | task는 `P0-T30` 형식 |
| 현재 단계 | 기획 / 설계 / 개발 / 검증 / 리팩토링 | 종료한 단계와 다음 단계를 함께 적는다 |
| 확정된 사실 | 사용자 승인이나 검증으로 확정된 내용 | 추측·해석과 섞지 않는다 |
| 미결 사항 | 아직 정해지지 않았고 결정이 필요한 것 | 누가 결정하는지와 반환할 단계를 적는다 |
| 다음 행동 | 다음 세션이 바로 시작할 수 있는 구체적 행동 | "검토한다" 같은 모호한 표현을 쓰지 않는다 |
| 증거·산출물 경로 | 만든 파일, 실행 로그, 검증 결과의 경로 | 저장소 기준 상대 경로 |
| 기준 시각 | 이 기록을 작성한 시각 | `YYYY-MM-DD` 또는 ISO 8601 |

## 작성 규칙

- 확정된 사실과 미결 사항을 반드시 분리한다. 정해지지 않은 것을 정해진 것처럼 쓰지 않는다.
- 미결 사항은 임의로 결정해 채우지 않는다. 결정이 필요하면 결정 주체와 반환할 단계를 적는다.
- 승인 사실을 기록할 때는 승인자와 승인일을 함께 적는다. 다만 handoff는 승인의 정본이 아니다. 정본은 `docs/execution/phases/index.jsonl`이다.
- 개인정보, 토큰, 비밀값을 남기지 않는다. 실패는 안전한 요약과 경로로만 기록한다.
- 한국어로 쓴다. task ID, 파일 경로, 상태값, check ID 같은 기계 판독 식별자는 원래 형식을 유지한다.
