# 3-build — 구현

## 역할

구현 규칙의 정본은 CLAUDE.md와 ADR-001이다. 여기는 실행 방향이 정해진 task의 완료 조건과 구현 방법이 산다. 변경 방향 자체를 검토하는 제안의 자리는 [proposals](../proposals/README.md)다([ADR-008](../2-design/adr/ADR-008-proposals-and-implementation-plans.md)).

`plans/<슬러그>.md`는 두 갈래다.

- **기능의 구현 계획** — spec이 승인된 기능만 들어온다. 바꿀 파일, 작업 순서, 리스크, 검증 방법, 정본 링크를 적는다. 완료 조건과 업무 규칙은 spec과 `2-design/`이 정본이라 여기 다시 적지 않는다 — 참조해서 검증 방법을 설명하는 것은 된다
- **비기능 task 문서** — 리팩터링·문서·토큰·검사처럼 spec이 없고 실행 방향이 정해진 task. 완료 조건과 작업 순서를 한 파일에 적고 `backlog.md`의 행이 여기를 링크한다

제안에서 이어진 task는 채택된 항목과 갱신된 정본을 링크한다. 채택 전의 대안 비교와 판단 근거는 제안서에 남긴다. 방향이 분명한 작은 수정은 별도 제안서 없이 여기서 계획할 수 있다. 완료된 과거 계획은 당시 작업의 기록이므로 소급 이동하지 않는다. 대신 머리에 「완료된 작업의 당시 계획이다」 한 줄과 완료 기록 링크를 단다 — 본문은 그대로 두고, 그 뒤 바뀐 규칙은 링크된 정본이 말한다.

## 문서 지도

| 문서 | 답하는 질문 |
| --- | --- |
| [`plans/`](plans/) | 승인된 기능과 비기능 task를 어떤 순서로 만들고 무엇으로 검증하나 |

## 입력과 산출물

작성법 하나는 「용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준」 순서다. 모든 문서에 공통인 규칙은 [문서 지도](../README.md#참조와-작성-규칙)가 소유한다.

### 구현 계획

**용도·작성 시점:** 승인된 기능 spec 또는 방향이 정해진 비기능 task를 실제 변경 순서로 전개할 때 쓴다.

계획을 쓰는 일 자체가 task일 수 있다. 준비가 필요한 구현은 plan이 선 뒤에야 `backlog.md`에서 `ready`가 되고, 그 전에는 「plan을 쓴다」 행이 `ready`, 구현 행이 `blocked`다.

**필요한 입력:** 승인된 spec 또는 채택된 제안 항목, 저장소에서 확인한 기존 구현·테스트·설정. 저장소에서 확인하고 나서 파일과 명령을 적는다.

**복사용 틀:**

```markdown
---
sources:
  - ../../2-design/spec/<task>.md
---

# <작업 이름> — 구현 계획

## 입력 명세·기준
<승인된 spec / 관련 설계 / 확인한 코드와 Git 기준점>

## 변경 파일
| 파일·영역 | 바꿀 책임 | 참조 완료 조건·규칙 |
| --- | --- | --- |

## 구현 순서
1. <관련 실패 테스트와 실패 확인>
2. <그 테스트를 통과시킬 구현>
3. <영향받는 문서·생성물·주변 동작 확인>

## 리스크·전환·되돌리기
<영향받는 사용자·데이터 / 전환 전제·순서 / 실패 시 되돌리는 단위와 한계>

## 검증 방법
| 완료 조건·규칙 참조 | 깨질 수 있는 것 | 테스트 층·위치 또는 수동 시나리오 | 명령·환경 | 확인할 결과 |
| --- | --- | --- | --- | --- |
```

**절별 질문:**

비기능 plan — `sources`에는 실제 입력 정본·채택된 제안 항목을 넣는다. spec과 intent를 억지로 만들지 않는다. 「입력 명세·기준」 뒤에 「완료 조건」을 추가하고 `AC-01` 같은 식별자로 직접 판정 가능하게 쓴다. 기능 plan은 spec의 AC를 참조하며 복사하지 않는다.

구현 순서 쓰기 — 변경 파일을 나열하는 데서 끝내지 않고 선행 이유를 적는다. 규칙·동작이 달라지면 실패 테스트→구현 순서를 유지한다. 문서만 고치는 작업은 관련 기존 문서 검사로 확인하며 형식만 베끼는 새 테스트를 만들지 않는다. 구조 전환이면 읽기·쓰기의 호환 기간과 되돌릴 수 없는 지점을 따로 확인한다.

검토 방법 쓰기 — 먼저 AC별 실패 위험을 찾고 그 위험을 관찰할 수 있는 테스트 층을 고른다. 테스트 경로가 아직 없으면 예정임을 밝힌다. 실제 실행 결과는 CI·PR·특수 evidence로 연결하며 계획한 명령을 실행한 것처럼 적지 않는다.

층 선택과 완료 판정은 [strategy](../4-test/strategy.md), 검증 표의 작성·검토는 [4-test 안내](../4-test/README.md#작업별-검증-표), 명령·환경은 [execution](../4-test/execution.md)을 따른다. 새 작업과 활성 작업에 적용하고 완료된 과거 계획은 소급 변경하지 않는다.

**검토 기준:** 구현자가 계획과 참조 문서로 착수할 수 있는가. 기술 선택이 새 사용자 동작을 만들면 설계·spec으로 돌렸는가. 비기능 task의 완료 조건과 준비 작업의 산출물이 분명한가. 준비 task가 다른 작업의 plan을 산출하는 경우 그 경로를 그대로 링크한다.

계획과 그것이 링크하는 정본을 읽으면 구현할 수 있어야 한다. 그게 안 되면 계획이 빈 것이다.
