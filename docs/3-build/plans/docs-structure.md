## 8. spec 폴더를 기능만으로 좁힌다

### 문제

`spec/` 아홉 중 기능은 셋이고 나머지는 리팩터링·토큰·문서·검사·디자인 결정이다. ADR-005:44는 spec을 「요구와 설계와 완료 조건」이라 적었는데 실제 파일은 완료 조건 서너 줄뿐이다. 이 문서 자체도 229줄짜리 검토 보고서로 spec 자리에 있었다.

### 변경

- spec은 기능만. 절은 요구·설계·완료 조건·범위 밖. 설계 절은 정본을 링크로 가리키고 이 task만의 결정을 적는다. 규칙은 [설계 안내](../../2-design/README.md#spec)에 있다.
- 비기능 spec 여섯(doc-links · sdlc-gate · shadow-tokens · supabase-client-entry · session-foundation · dashboard-design)과 이 문서를 `3-build/plans/`로 옮긴다. backlog·plan·검사 코드의 링크를 따라 고친다. 로그와 관찰 보관함은 당시 기록이라 안 고친다.
- 새 형식은 `spec/dashboard.md`부터 적용한다. 완료된 `login-screens.md`는 안 건드린다.

### 완료 기준

- [x] `spec/`에 기능 spec만 남는다.
- [x] 옮긴 문서를 backlog 행이 링크하고 `pnpm test`의 링크·경로 검사가 통과한다.
- [x] spec 형식 규칙이 설계 안내에 있다.
- [x] `spec/dashboard.md`를 새 형식으로 세우는 일은 대시보드 task가 착수할 때 한다 — `backlog.md` 「대기」의 그 행에 적었다.

## 5. spec과 구현 계획의 경계를 적는다

### 문제

`3-build/README.md`가 「이 계획만 읽고 intent와 spec을 안 열어도 구현할 수 있어야 한다」고 요구했다. 완료 조건은 spec에, 업무 규칙은 정본에 두는 원칙과 같이 놓으면 계획에 내용을 베끼게 된다.

### 변경

- 그 문장을 「계획과 그것이 링크하는 정본을 읽으면 구현할 수 있어야 한다」로 바꾼다.
- plans는 두 갈래다 — 기능의 구현 계획(바꿀 파일·순서·리스크·검증·정본 링크), 비기능 task 문서(완료 조건 + 순서). [3-build 안내](../README.md)가 적는다.
- 과거 task의 빈 intent·plan은 소급해서 안 만든다. 신규 task부터 사슬을 잇는다.

### 완료 기준

- [x] 안내만 읽고 spec에 적을 것과 plan에 적을 것을 가른다.
- [x] spec을 베껴야 채워지는 계획 규칙이 없다.

## 6. 긴 문서의 내부 목차를 허용한다

### 문제

`pages/schedule-admin.md`·`dashboard.md`·`login.md`가 600~950줄인데 [디자인 시스템의 두 축](../../2-design/design-system/README.md#두-축)이 「다른 문서는 자기 안에 목차나 문서 목록을 두지 않는다」고 막는다. 이 규칙은 값과 지도가 여러 문서에 흩어지면 바꿀 때 일부만 바뀌는 사고를 막으려 세운 것이다([log](../../log/2026-08-26-4.md)). 같은 파일 안 제목으로 가는 목차는 그 사고와 무관하다.

### 변경

- 규칙을 좁힌다 — 문서 목록은 README에만, 같은 파일의 제목으로 가는 내부 목차는 된다.
- 위 세 문서에 2단계 제목 중심의 목차를 단다. 제목·앵커·본문은 안 바꾼다. 파일 분할은 안 한다 — 시안이 문서 하나에 짝이라 나누면 시안 규칙까지 흔들린다.
- 목차만 더한 문서는 시안을 안 건드린다.

### 완료 기준

- [x] 문서 목록과 내부 목차의 차이가 규칙에 있다.
- [x] 세 문서에서 주요 화면 절로 바로 간다.
- [x] 더한 앵커가 전부 유효하고 바깥 참조가 안 깨진다.

## 1. 상반된 설명을 맞춘다

### 문제

`pages/login.md` 293행은 차단된 사람이 로그인 화면에서 멈춘다고 적고, 646행 「아직 안 정한 것」은 차단 화면 자리를 미정으로 둔다. [flows](../../2-design/architecture/flows/README.md#앱을-열면)는 `/blocked`로 보낸다. 관리자 홈 앱바의 뒤로도 `profile.md`와 `schedule-admin.md`가 다르다. 둘 다 flows를 따른다.

### 변경

- 경계를 설계 안내에 적는다 — 계정 상태와 권한 규칙은 `domain`, 화면 간 목적지는 `architecture/flows`, 화면 안 구성·문안·모션은 `design-system/pages`.
- `login.md` 293행을 `/blocked`로 보낸다고 고친다. 차단 화면의 시각 설계는 아직 없다 — 646행 항목을 「목적지는 정해졌고 화면은 남았다」로 바꿔 `login.md`에 둔다. flows가 그 화면을 `login.md`가 그린다고 적어서다.
- `schedule-admin.md` 앱바에 뒤로를 더한다. `profile.md`가 정본이다.
- `schedule-admin.md`의 시안을 `sian-writer`가 따라가고 `sian-auditor`가 본다. `login.md`는 화면에 보이는 것이 안 바뀌어 시안을 안 건드린다.
- handoff의 두 항목을 지운다.

### 완료 기준

- [x] 차단 목적지와 관리자 홈 뒤로에 상반된 설명이 없다.
- [x] 목적지 확정과 화면 설계 미완이 구별돼 있다.
- [x] 시안이 갱신되고 감사 결과가 PR에 남는다.

## 3. backlog와 handoff의 역할을 나눈다

### 문제

[handoff의 다음 첫 수](../../handoff.md#다음-첫-수)는 데이터 task부터라는데 [backlog의 다음](../../backlog.md#다음)에는 그 task를 기다리는 대시보드만 있다. handoff에는 열린 결정 서른 하나와 상시 주의 서른 줄이 쌓여 새 세션이 당장 할 일을 찾으려면 다 읽어야 한다.

### 변경

- 데이터 task를 보드에 올린다. 후보는 Edge Function import 스파이크, 계정 데이터 구조 전환, 인증 진입 전환, 타입 생성 절차다. 경계와 의존은 `architecture/`를 읽고 정한다.
- 대시보드가 기다리는 근무표·출근 기록·급여 계산·알림을 보드에 이름으로 드러낸다. 완료 조건이 없는 것은 착수 가능으로 안 표시한다.
- handoff는 넷만 담는다 — 지금 상태 요약, 다음 task 링크, 그 task를 막는 결정, 이번 회차에만 필요한 주의. 상시 주의는 `4-test/README.md`(훅·검사·실행)와 `5-deploy/README.md`(CI·의존)로 간다.
- 열린 결정과 주의는 셋으로 가른다. 정본이 있으면 그 문서의 「아직 안 정한 것」으로, 할 일이면 backlog 행으로, 정의문·훅의 마찰이면 `observations/`로. 셋 다 아니면 handoff에 남긴다. 옮길 때 목적지의 기존 문장과 먼저 합친다.
- `session-recorder` 정의문의 handoff 작성 규칙을 위 넷으로 고친다. 새 task의 범위와 완료 조건은 총괄이 정한다는 경계는 그대로다.

### 완료 기준

- [x] handoff의 다음 작업이 backlog의 실제 행과 이어진다.
- [x] 대시보드의 선행 작업과 착수 불가 사유가 보드에 있다.
- [x] 옮긴 항목이 원래 내용을 잃지 않고, handoff에 상시 규칙이 남아 있지 않다.

## 2. 목표 설계와 구현 상태를 구별한다

### 문제

[api 문서의 읽기](../../2-design/architecture/api/README.md#읽기)는 `pnpm types`와 CI의 타입 diff 검사가 있는 것처럼 적었는데 `package.json`과 `ci.yml`에 없다. [계정 데이터 모델](../../2-design/architecture/data-model/account.md#프로필-신원)은 목표와 기존 마이그레이션의 차이를 적었지만 다른 문서는 그렇지 않다. [아키텍처 안내](../../2-design/architecture/README.md)는 이 문서군이 목표인지 현재인지 말하지 않는다.

### 변경

- 아키텍처 안내에 한 줄 — 이 문서군은 목표 설계고, 구현 여부는 링크된 backlog 행이 말한다.
- 현재 코드와 다른 문단에만 `현재 구현`·`목표 설계`·`연결 작업`을 짧게 적는다. 우선은 타입 생성, 프로필 신원 분리, 개인정보 표 분리, 승인 게이트 이동과 `proxy` 전환.
- spec `status`의 뜻은 그대로다. `approved`는 구현 완료가 아니다.
- 문서를 현실에 맞추려고 목표를 지우지 않고, 문서를 맞추려고 기능을 구현하지 않는다.

### 완료 기준

- [x] 없는 명령·검사·스키마·인증 흐름이 현재 동작으로 안 읽힌다.
- [x] 미구현 문단에서 backlog 행으로 간다.

## 7. CHANGELOG 갱신을 마감 담당에 맡긴다

### 문제

[CHANGELOG](../../CHANGELOG.md)가 #306에서 멈췄고 그 뒤 PR 열넷이 없다. 있는 행도 틀렸다 — #303·#305·#306의 merge 날짜는 09-13인데 09-12로 적혔다. [session-recorder 정의문](../../../.claude/agents/session-recorder.md)에 CHANGELOG가 없다. `sdlc-gate`는 이 검사를 「상처가 나면 그때 단다」고 미뤄뒀다.

### 변경

- 정의문에 CHANGELOG를 더한다 — 이미 읽는 merge PR로 날짜·변경 한 줄·PR 링크. 날짜는 `git log --date=short`의 merge 날짜다.
- 표의 첫 행(#229)부터 지금까지 merge된 PR 전부를 git에서 다시 뽑는다 — 검사가 로그의 모든 PR을 보니 두 회차만 채우면 그 사이 빈 번호가 걸린다. 기존 행의 문구는 두고 날짜만 git으로 바로잡는다. #229 앞 이력은 안 건드린다.
- 로그의 PR 번호와 CHANGELOG를 대조하는 검사를 `tests/lint/`에 단다.

### 완료 기준

- [x] 정의문의 입력·작업·결과에 CHANGELOG가 있다.
- [x] #229부터의 PR이 merge 날짜와 함께 중복 없이 있다.
- [x] 로그에 있는 PR이 CHANGELOG에 없으면 `pnpm test`가 실패한다.

## 검증

- `pnpm lint` · `pnpm format:check` · `pnpm typecheck` · `pnpm test`. 링크·지도·옛 경로 검사가 여기 든다.
- 묶음마다 diff에서 본다 — 옮긴 문장이 사라지지 않았는지, 정본이 둘로 늘지 않았는지.
