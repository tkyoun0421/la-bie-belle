# 4-test — 검증

## 역할

완료 조건에서 검증할 리스크를 찾고, 실행 결과로 그 조건을 충족했는지 판단하는 단계다. 제품 규칙과 완료 조건은 입력 문서가 소유하고, 여기는 검증 기준·실행 방법·결과 기록을 소유한다. 테스트 코드의 위치와 TDD는 [ADR-001](../2-design/adr/ADR-001-fsd-layout-and-tdd-guard.md)을 따른다.

## 문서 지도

| 문서 | 답하는 질문 |
| --- | --- |
| [`strategy.md`](strategy.md) | 리스크를 어느 층(unit·integration·e2e) 또는 수동 검증에 배정하고 무엇으로 완료를 판단하나. `test-planner`의 참조 정본 |
| [`execution.md`](execution.md) | 어떤 전제에서 무슨 명령을 돌리고, 훅과 문서 검사가 무엇을 막고, 실패하면 어디를 보나 |
| `evidence/` | CI 결과만으로 근거가 남지 않는 검증을 무엇으로 확인했나. 첫 기록이 생길 때 만든다 |

## 입력과 산출물

작성법 하나는 「용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준」 순서다. 모든 문서에 공통인 규칙은 [문서 지도](../README.md#참조와-작성-규칙)가 소유한다.

1. 기능은 승인된 spec, 비기능 작업은 plan의 완료 조건과 연결된 업무 규칙·설계를 읽는다.
2. `test-planner`가 [strategy](strategy.md)에 따라 검증 표를 만든다. 총괄이 기존 plan의 「검증 방법」에 반영하고 해당 행을 writer에게 넘긴다.
3. writer가 실패를 확인하고 구현 뒤에는 [execution](execution.md)에 따라 관련 검사와 필요한 전체 검사를 실행한다.
4. PR에는 검증한 커밋·변경분, 명령과 결과, 해당 완료 조건을 지키는 테스트 또는 CI 실행 링크를 남긴다. 수동 검증이 있으면 evidence를 연결한다.

실행 전 계획은 plan, 자동 검증 결과는 PR·CI, 별도로 필요한 실제 검증 기록은 evidence에 둔다. 기능마다 별도 테스트 계획 문서를 만들지 않는다. 작업 상태는 [backlog](../backlog.md)가 소유한다.

### strategy·execution

**용도·작성 시점:** 검증 기준을 바꿀 때는 `strategy.md`, 실행 환경·명령·문제 해결이 바뀔 때는 `execution.md`를 갱신한다. 개별 기능마다 전략 문서를 만들지 않는다.

**복사용 틀과 절별 질문:**

| 문서 | 본문 틀 | 절별 작성 방법 |
| --- | --- | --- |
| `strategy.md` | 리스크와 층 배정 → 대역·실제 의존성 경계 → 판정 예시와 AC 연결 → 수동 검증 조건 → 완료 판정 | `리스크 / 이를 관찰할 층 / 실제로 통과해야 하는 경계 / 이유` 표. [층 선택 기준](strategy.md#리스크와-층-배정)으로 배정하고 같은 위험을 여러 층에서 검사할 때는 추가로 잡는 실패를 밝힌다 |
| `execution.md` | 실행 전제 → 명령·환경 → 훅·문서 검사 → 실패 진단 → 결과 찾기 | 아래 실행 항목 틀로 로컬·CI의 차이, 필요한 서비스·빌드 순서, 통과 기준, 결과 위치를 적는다. 실패한 명령의 증상·확인 위치·복구 순서를 묶는다 |

```markdown
### <검증 명령 또는 절차 이름>

- 전제: <작업 위치·도구·서비스·데이터 상태>
- 실행: <저장소에서 확인한 실제 명령>
- 정상 결과: <종료 코드와 확인할 산출물·검사 내용>
- 실패할 때: <증상 → 확인 위치 → 조치 → 재검증>
- 근거 위치: <CI 실행 결과·리포트 등>
```

테스트 층 선택은 `test-planner`와 strategy에서 따로 유지하지 않는다. ADR-003은 선택의 이유를 보존하고 현재 배정 기준은 strategy에 모은다. 테스트 코드의 위치와 TDD는 ADR-001을 유지한다. 형식이 맞는 것과 동작이 맞는 것은 각각 문서 검사와 실제 테스트로 확인한다.

### 작업별 검증 표

**용도·작성 시점:** 새 작업과 활성 작업의 검증 방법을 계획할 때 기존 plan 안에 쓴다. 완료된 과거 계획은 소급 변경하지 않는다.

**필요한 입력:** spec 또는 비기능 plan의 완료 조건, 연결된 규칙·설계, 기존 코드·테스트. 고정 ID가 있으면 해당 조항을 링크하고, 없는 과거 spec에 ID를 소급 발급하지 않는다.

**복사용 틀:** [3-build의 검증 방법](../3-build/README.md#구현-계획)과 같은 표다.

```markdown
| 완료 조건·규칙 참조 | 깨질 수 있는 것 | 테스트 층·위치 또는 수동 시나리오 | 명령·환경 | 확인할 결과 |
| --- | --- | --- | --- | --- |
| <spec 또는 비기능 plan의 조항 링크> | <구체적인 실패> | <unit·integration·e2e·수동 / 경로 또는 절차> | <실행 명령·필요한 환경> | <관찰할 결과> |

- 배정하지 않은 것: <시나리오와 이유. 없으면 없음>
- 막힌 것: <모호한 조건·환경 제약·필요한 결정. 없으면 없음>
```

**절별 질문:** 완료 조건을 다시 정의하지 않고 구체적인 실패와 검증 방법을 연결했는가. 수동 검증이면 초기 상태·기기·절차가 있는가. 예정 테스트 경로는 예정이라고 밝혔는가.

**검토 기준:** 선택한 방법이 그 실패를 실제로 잡는가. 여러 층에 같은 시나리오가 있으면 각 층이 추가로 잡는 실패가 있는가. 계획한 기대 결과를 실제 통과 결과로 적지 않았는가.

### evidence

**용도·작성 시점:** 실기기·외부 서비스 등 CI 결과만으로 근거가 남지 않는 검증을 실행했을 때 쓴다. 실행 전 계획은 plan에 두고 사건 없는 evidence는 생성하지 않는다.

파일은 `evidence/<task>.md`로 만들며 task는 해당 spec 또는 plan과 같은 슬러그다. 재검증은 새 일시·기준점으로 덧붙이고 기존 결과를 구별한다.

**복사용 틀:**

```markdown
# <task> — 검증 기록

## 검증 대상과 Git 기준점
<spec AC 또는 비기능 plan AC 링크 / 검증한 커밋·변경분 / 실행 일시·검증자>

## 환경·기기
<로컬·스테이징 등 / OS·기기·앱 버전 / 설치·권한·연결 상태>

## 명령·시나리오
<초기 데이터·이전 상태 → 실행 단계 → 기대 결과. 사용한 실제 명령>

## 결과·증거
| AC·시나리오 | 실제 결과 | 판정 | 증거 위치 |
| --- | --- | --- | --- |

## 미해결 항목
<실패·미실행의 이유 / 차단되는 범위 / 후속 작업>
```

**절별 질문:** 기대 결과와 실제 결과를 분리한다. 환경이 없어 못 했다면 `미실행`으로 기록한다. 결과 표의 판정은 `통과 / 실패 / 미실행`으로 충분하며 작업 상태와 구별한다. 스크린샷·녹화·로그는 어떤 AC를 뒷받침하는지 연결하고 공개 저장소에 필요한 가짜 데이터 기준을 따른다.

**검토 기준:** 다른 사람이 같은 기준점과 환경에서 재현할 수 있는가. 이미지 한 장으로 확인하지 못하는 저장·권한·재시도까지 통과로 넓히지 않았는가. 코드가 바뀌었다면 이전 evidence가 이번 변경에도 유효한지 영향 범위를 확인했는가.

## 다음 단계로 넘기는 조건

검증은 [완료 판정](strategy.md#완료-판정)에 따라 출시 대상으로 삼을 수 있는 결과와 남은 제한을 확인한다. 필요한 검증의 실패·미실행을 드러내고, 남은 제한은 그것이 막는 범위와 처리 방법을 적어 넘긴다.
