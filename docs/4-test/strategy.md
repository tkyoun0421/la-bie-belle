# 테스트 전략

리스크를 어느 층(unit·integration·e2e)에 배정하는지의 기준이다. 선택의 이유는 [ADR-003](../2-design/adr/ADR-003-supabase-and-integration-tests.md#테스트-층)이 보존한다.

## 층을 고르는 법

리스크마다 그것을 확실히 잡는 가장 싼 층을 고른다. 아래 층이 못 잡을 때만 위로 올린다.

**unit** — 계산, 변환, 업무 규칙, 검증 로직, 상태 전이, 도메인 불변식, 정렬, 정규화, 중복 제거, 결정적인 에러 동작. 앱을 띄우지 않고 확인되는 것들이다.

**integration** — 실제 Postgres를 거쳐야만 드러나는 것. RLS 정책, 스키마 제약, 트랜잭션 경계, 여러 행이 맞물린 조회, `dals`가 DB와 주고받는 계약. 근거는 `docs/2-design/adr/ADR-003-supabase-and-integration-tests.md`에 있다.

**e2e** — 사용자 여정, 인증 전환, 라우팅과 내비게이션, 화면에서 서버까지 이어지는 동작, 새로고침이나 이동 뒤에도 남는 상태, 여러 층이 맞물려야 드러나는 회귀.

업무 규칙의 경우의 수를 e2e로 훑지 않는다. 그건 unit 몫이다.

## integration을 고르는 기준

한 질문으로 판정한다. **DB를 가짜로 바꿔도 이 테스트가 여전히 무언가를 지키나?**

지킨다면 unit이다. 아무것도 안 지키게 된다면 integration이다. 가짜 DB를 넣는 순간 사라지는 검증이 바로 이 층의 몫이다.

integration으로 보내는 것.

- 규칙이 앱 코드 밖에 사는 것. RLS 정책은 SQL에 있어 TypeScript 테스트로는 닿지 않는다.
- DB가 거절해야 정답인 것. 유니크 제약, 외래 키, not null, 체크 제약.
- 여러 행이나 여러 테이블이 맞물려야 답이 나오는 조회와 집계.
- 실패했을 때 어디까지 되돌아가는지가 중요한 것. 트랜잭션 경계.
- 권한에 따라 같은 질의가 다른 결과를 내는 것.

integration으로 보내지 않는 것.

- 순수 계산. 급여 가산율을 곱하는 규칙은 DB가 없어도 확인된다. unit이다.
- 화면을 거쳐야 하는 여정. e2e다.
- DB를 지나가기는 하지만 판정이 앱 코드에 있는 것. 그 판정은 unit으로 잡고, 통로가 실제로 이어지는지만 integration 하나로 덮는다.

한 리스크를 unit과 integration에 나눠 배정하지 않는다. 계산은 unit이 잡고 DB 경계는 integration이 잡는다. 둘은 서로 다른 리스크다.

## 중복을 만들지 않는다

한 시나리오를 다른 층에 또 배정하기 전에 묻는다. **이 층이 아래 층은 못 잡는 어떤 실패를 더 잡나?** 답이 안 나오면 배정하지 않는다.

unit이 이미 가격 선택 순서를 지키고 있다면 같은 순서를 확인하는 e2e를 더하지 않는다. 다만 그 결과가 화면까지 살아서 도착하는지가 따로 위험하면 그건 다른 리스크다.
