# 테스트 전략

리스크마다 그 실패를 확실히 잡는 가장 저렴한 검증 방법을 고른다. 목표는 결함 발견과 회귀 차단이며, 커버리지 비율이나 테스트 개수를 목표로 삼지 않는다. `test-planner`와 writer가 함께 읽는 현재 선택 기준이다.

## 입력

기능은 승인된 spec, 비기능 작업은 plan의 완료 조건이 기준이다. 연결된 업무 규칙·설계와 현재 코드를 함께 읽는다. 코드가 아직 없어도 계획할 수 있다. 완료 조건이나 정책이 모호하면 짐작해 단언을 만들지 말고 해당 소유 문서의 결정이 필요하다고 적는다.

검증 계획은 [README의 작업별 검증 표](README.md#작업별-검증-표)로 기존 plan에 남긴다. 테스트 코드 위치와 TDD는 [ADR-001](../2-design/adr/ADR-001-fsd-layout-and-tdd-guard.md), DB 검증의 이유와 사용자 세션 원칙은 [ADR-003](../2-design/adr/ADR-003-supabase-and-integration-tests.md)을 따른다. [훅이 요구하는 짝 테스트](execution.md#훅)는 계획에 포함한다. 훅 최소선이 검증 전체를 대신하지는 않는다.

## 리스크와 층 배정

| 깨질 수 있는 것 | 검증 방법 | 실제로 확인하는 경계 |
| --- | --- | --- |
| 계산·변환·검증·상태 전이·정렬·정규화가 틀림 | unit | 앱과 DB를 띄우지 않고 입력에 대한 결과를 확인 |
| RLS·제약·SQL 함수·트랜잭션·여러 행이 맞물린 조회가 틀림 | integration | 로컬 Supabase의 실제 Postgres와 사용자 세션을 거쳐 결과 확인 |
| 화면·인증·라우팅·서버 연결 또는 화면을 옮기거나 앱을 다시 연 뒤 상태가 끊김 | e2e | 앱을 띄워 사용자 여정을 실행하고 관찰 가능한 결과 확인 |
| 실제 기기·외부 서비스·시각적 검수에서만 확인할 수 있음 | 수동·실기기 | 해당 기기·서비스·설치 상태에서 절차를 실행하고 결과 기록 |

업무 규칙은 집행되는 위치를 본다. 앱의 순수 계산은 unit, SQL 함수나 DB 제약이 집행하는 규칙은 integration이다. 업무 규칙의 모든 경우의 수를 e2e에 복제하지 않는다.

### integration을 고르는 질문

**DB를 가짜로 바꾸면 지키려는 검증이 사라지는가?** RLS, 유니크·외래 키·not null·체크 제약, DB의 조회·집계, 트랜잭션의 되돌림, 권한별 결과 차이는 사라지므로 integration이다. `dals`의 DB 계약도 여기서 검증한다.

DB 응답을 받은 뒤 앱 코드가 하는 판정은 unit으로 확인한다. 그 응답을 실제 DB에서 받을 수 있는지는 별도의 integration 리스크다. 앱을 띄워야 하는 여정은 e2e로 배정한다. DB 대역을 쓸 수 있다는 이유만으로 화면 여정을 unit으로 내리지 않는다.

### 이 저장소의 배정 예

아래는 연결된 규칙에서 도출한 배정 예다. 구현 여부와 테스트 실행 결과를 뜻하지 않는다. 해당 작업의 완료 조건이 서면 그 조건을 참조하는 검증 표로 구체화한다.

| 근거 | 깨질 수 있는 것 | 배정과 통과 판단 |
| --- | --- | --- |
| [계정의 개인정보 분리](../2-design/modules/account/design.md#개인정보는-표를-가른다) | 승인된 근무자가 다른 사람의 개인정보를 읽음 | integration — 실제 서로 다른 사용자 세션으로 본인·관리자의 허용과 다른 근무자의 거부를 확인 |
| [계정 함수](../2-design/modules/account/design.md#첫-진입과-게이트) | `ensure_profile()`을 다시 호출해 자기 프로필이 중복 생성됨 | integration — 같은 사용자로 반복 호출한 뒤 자기 프로필이 하나임을 확인 |
| [사진 변경 계약](../2-design/modules/account/design.md#개인정보는-표를-가른다) | `update_my_photo()`가 남의 사진을 바꾸거나 본인 변경을 막음 | integration — 본인 변경 결과와 다른 사람·관리자의 남의 사진 변경 거부 및 값 보존을 확인 |
| [급여 읽기](../2-design/modules/payroll/design.md#급여는-계산한다) | 입력 근무 기록과 시급에 대한 계산이 틀림 | unit — 확정된 급여 규칙의 예시·경계값으로 계산 결과를 확인 |
| [로그인 화면 완료 조건](../2-design/spec/login-screens.md#완료-조건) | 로그인 상태별 화면 진입이 끊김 | e2e — 세션·승인 상태를 준비하고 해당 화면까지 도착하는지 확인 |

계정의 검증 연결은 [account-data plan](../3-build/plans/account-data.md)·[auth-entry plan](../3-build/plans/auth-entry.md)을 참고한다. 위 사례는 현재 코드·테스트와 대조해 계획을 세우는 예다. 프로필 폼 같은 새 작업에서는 완료 조건을 입력으로 기존 DB 계약의 회귀와 새 폼의 입력·제출·실패 흐름을 구별해 배정한다. 작업 순서와 상태는 [backlog](../backlog.md)가 소유하며 완료된 과거 계획은 소급해서 다시 쓰지 않는다.

## 대역과 실제 의존성

- unit의 대역(mock)은 인증·시간·네트워크 등 외부 경계에 둔다. 내부 함수의 호출 순서나 private 상태보다 입력과 관찰 가능한 결과를 단언한다.
- integration은 실제 DB에 붙는다. 권한을 검증할 호출은 사용자 세션 또는 명시적인 비로그인 클라이언트로 실행한다. service role key로 RLS를 우회하지 않는다.
- 로컬 Postgres 직결 헬퍼는 테스트의 초기 상태 준비에 쓰는 기존 방식이다. 권한을 검증할 동작을 그 헬퍼로 대신 실행하지 않는다. 데이터 준비·정리의 현재 한계는 [execution](execution.md#테스트-데이터)에 있다.
- e2e에서 기기 API를 대역으로 바꾸면 그 조건에 대한 앱 반응만 검증한다. 실제 권한 요청·기기 동작·외부 서비스 성공까지 확인한 것으로 넓히지 않는다.
- 세션을 심어 화면으로 바로 들어가는 헬퍼가 통과해도 구글 로그인 버튼부터 OAuth 완료까지 성공했다는 뜻은 아니다. 지금 [세션 헬퍼](../../tests/e2e/support/session.ts)는 쿠키로 심고, Expo로 옮기면 SecureStore로 바뀐다([ADR-011](../2-design/adr/ADR-011-expo-native-app.md)).

## 중복과 버그

같은 시나리오를 다른 층에 배정하기 전에 **그 층이 추가로 잡는 실패가 무엇인지** 적는다. 답이 없으면 추가하지 않는다. 계산 정확성과 계산 결과가 화면까지 도착하는지는 서로 다른 리스크다.

버그는 확실히 재현할 수 있는 가장 낮은 층에 실패 테스트를 배정한다. 층 사이 연결이 원인일 때만 위층 검증을 더하고, 수정 뒤에도 회귀 테스트를 남긴다. 버그 하나에 unit·integration·e2e를 하나씩 기계적으로 추가하지 않는다.

## 수동 검증

CI가 해당 환경을 재현하지 못하거나 완료 조건이 사람의 검수를 요구하면 수동 검증을 배정한다. 실행 전에는 plan에 초기 상태·기기·절차·기대 결과를 적고, 실행 뒤에는 [evidence 작성법](README.md#evidence)에 따라 결과를 남긴다.

- 구글 로그인 전체 성공 경로는 현재 자동 검증 밖이다([당시 로그인 구현 계획](../3-build/plans/login-screens.md#안-담은-것)). 실제 OAuth 환경에서 따로 확인한다.
- 뒤로 가기 손짓과 앱을 나갔다 돌아오는 흐름은 실기기에서 본다. 시뮬레이터 확인을 실기기 확인과 같은 증거로 취급하지 않는다 — 특히 권한 물음과 푸시는 시뮬레이터가 실제와 다르게 답한다.
- 시각적 검수는 해당 [화면·디자인 기준](../2-design/design-system/README.md)을 근거로 판단한다. 화면 이미지로 저장·권한·재시도까지 통과 판정을 넓히지 않는다.

## 완료 판정

1. 작업의 완료 조건마다 검증 방법과 실제 결과를 연결한다. 배정하지 않은 시나리오는 이유를 남기고, 완료 조건 자체를 생략하지 않는다.
2. 새 동작·버그 수정은 관련 실패를 확인한 뒤 구현한다. 기존 구현에서 이미 통과하면 그 사실을 기록하고 억지로 실패시키지 않는다. 환경 기동 실패와 제품 동작의 실패는 [실패 진단](execution.md#돌릴-때)에 따라 구별한다.
3. [현재 CI 검사](execution.md#ci와-결과-위치)와 작업에 필요한 검증이 통과해야 한다. 필요한 검증이 실행되지 않았으면 완료를 증명하지 못한 것이다. 재시도로 통과한 경우에도 최초 실패와 남은 불안정성을 드러낸다.
4. 결과에 검증한 커밋·미커밋 변경분·환경·명령 또는 절차를 연결한다. 이후 변경이 영향을 주면 해당 검증을 다시 실행한다.
5. `통과 / 실패 / 미실행`을 구별한다. 실패·미실행은 이유와 완료를 막는 범위, 후속 작업을 남긴다. 제품 정책의 미정은 소유 문서에서 해결한다.
