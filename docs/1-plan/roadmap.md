# 로드맵

큰 순서가 산다. 어떤 기능 묶음이 어떤 차례로 어떤 릴리스가 되는가다. task 하나의 순서는 `../backlog.md`의 「다음」이 담고, 여기는 묶음 단위만 담는다.

2026-09-06 태관 인터뷰로 채웠다. 시나리오(`scenarios.md`)의 장면 번호를 판정 기준이 가져다 쓴다.

## 틀

| 릴리스 | 담는 것 | 빼는 것 | 판정 기준 |
| ------ | ------- | ------- | --------- |

- **담는 것** — 이 릴리스에 들어가는 기능 묶음, 이름으로
- **빼는 것** — 다음으로 미루는 것, 이유 한 줄
- **판정 기준** — 이 릴리스를 내보내도 된다고 판정하는 조건

## 릴리스 목록

| 릴리스 | 담는 것 | 빼는 것 | 판정 기준 |
| ------ | ------- | ------- | --------- |
| 1차 | 계정(가입·승인), 근무표(신청 생성·휴무 제출·확정·강제 변경·보기), 출근 인증(위치·QR·지각), 급여 예상, 알림(승인·확정·전날·직전) | 교대 — 요청 흐름이 복잡하고 수기로 버틸 수 있다. 관리자 공지·통계 — 없어도 첫 실사용이 선다 | 장면 1·2·3·4·6이 e2e로 통과하고, 실기기(iOS PWA 포함)에서 푸시와 위치 인증이 확인된다 |
| 2차 | 교대 전 흐름과 교대 알림, 관리자 공지, 관리자 통계 | — | 장면 5가 e2e로 통과한다 |

## 순서 규칙

1차는 화면 디자인을 전부 끝낸 뒤에 구현한다. 계획과 설계가 꼼꼼히 선 다음에 코드를 만들고, 그리다 만나는 미정은 착수 전 인터뷰로 정한다(태관, 2026-09-07).

그리는 순서는 관리자 근무표 제작·확정부터다(태관, 2026-09-07). 제일 크고 복잡한 화면을 먼저 뚫으면 근무표 구조가 거기서 확정되고, 근무자의 근무표 보기가 그 구조를 따라온다. 나머지 화면의 순서는 그리면서 정한다.
