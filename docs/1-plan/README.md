# 1-plan — 기획

## 역할

왜 만드는지와 무엇을 만들지가 산다.

사슬의 첫 고리가 여기다: `intent/<슬러그>.md` → `2-design/spec/<슬러그>.md` → `3-build/plans/<슬러그>.md`. 근거는 ADR-005에 있다.

`intent/`는 제품 기능·이슈에서 어떤 사용자 문제를 풀려는지 기록한다. 문서 구조나 작업 방식처럼 여러 단계에 걸친 변경 방향을 검토할 때는 [proposals](../proposals/README.md)를 쓴다. 구분의 근거는 [ADR-008](../2-design/adr/ADR-008-proposals-and-implementation-plans.md)이다.

## 문서 지도

| 문서 | 답하는 질문 |
| --- | --- |
| [`prd.md`](prd.md) | 제품 요구. 왜 만드는지와 무엇을 안 하는지까지다 |
| [`scenarios.md`](scenarios.md) | 사용자 시나리오. 인물과 상황 단위의 이야기 |
| [`roadmap.md`](roadmap.md) | 우선순위와 릴리스 단위 |
| [`metrics.md`](metrics.md) | 성공 지표의 정의 |
| [`intent/`](intent/) | 기능·이슈별 디스커버리 산출물. 인터뷰가 낳고, spec의 입력이 된다 |

## 입력과 산출물

작성법 하나는 「용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준」 순서다. 모든 문서에 공통인 규칙은 [문서 지도](../README.md#참조와-작성-규칙)가 소유한다.

### prd·roadmap·scenarios·metrics

**용도·작성 시점:** 제품 목적·범위·지표가 새로 정해지거나 바뀔 때 쓴다. 아래 순서를 문서별 최소 틀로 삼는다. 전부 새로 만들 필요는 없고 기존 파일에서 이번에 바뀌는 제품 판단을 갱신한다.

**필요한 입력:** 사용자 인터뷰와 관찰, 현재 수단과 손실, 이미 합의된 릴리스 순서.

**복사용 틀과 절별 질문:**

| 문서 | 본문 틀 | 그 아래에 쓸 내용과 작성 방법 | 검토 기준 |
| --- | --- | --- | --- |
| `prd.md` | 제품 목적 → 대상 사용자 → 현재 문제와 근거 → 제품 범위 → 범위 밖 → 제약·미정 | 사용자별 현재 수단과 손실을 먼저 적는다. 기능 묶음은 해결할 문제와 연결하고 계산·권한 상세는 설계를 링크한다 | 기능마다 누구의 문제인지 말할 수 있고, 목표와 비범위가 충돌하지 않는가 |
| `roadmap.md` | 릴리스 목록 → 순서의 이유 → 재검토 조건 | `릴리스 / 담는 묶음 / 미루는 묶음과 이유 / 출시 판정의 참조` 표. 순서는 사용자 가치·의존 관계로 설명한다. 개별 task 상태는 backlog로 보낸다 | 릴리스 범위가 PRD와 맞고, 선행 관계를 설명할 수 있는가 |
| `scenarios.md` | 장면별 누가 → 언제·계기 → 하려는 일 → 현재 어려움 → 성공·실패 뒤 모습 → 관련 설계 | 가상 인물의 구체 장면으로 쓴다. 사용자가 결과를 확인하는 순간까지 적고 상세 버튼 배치는 화면 문서로 보낸다 | 화면 이름을 몰라도 사용자의 목적과 끝나는 상태가 이해되는가 |
| `metrics.md` | 지표별 정의 → 측정 이유 → 집계 기준 → 목표선과 근거 → 결정할 항목 | 아래 측정 틀로 분모·분자·기간·제외 대상을 정한다. 수집 쿼리는 운영 metrics로 보낸다 | 같은 원자료를 두 사람이 집계해 같은 값이 나오는가 |

장면 번호처럼 이미 참조되는 식별자는 보존한다. 새 표기법을 위해 기존 번호를 바꾸지 않는다. 숫자 정책이 필요하면 원문을 링크하고 장면의 숫자는 그 규칙의 사례임을 밝힌다.

```markdown
### <지표 이름>

- 정의와 이유: <무엇을 세며 어떤 제품 판단에 쓰나>
- 집계 단위: <사람·근무·요청 중 무엇인가>
- 분자 / 분모: <비율일 때 각각의 포함 조건. 비율이 아니면 집계식>
- 기간과 시각 기준: <기간 경계·시간대·어느 사건 시각인가>
- 제외·중복·누락: <취소·재시도·데이터 없음의 처리>
- 목표선과 근거: <합의된 값, 또는 미정과 결정 시점>
- 측정 방법: <운영 metrics의 해당 절 링크, 아직 없으면 준비 작업>
```

**검토 기준:** [성공 지표](metrics.md)의 목표선은 운영 첫 달 이후 결정한다. 틀에 빈칸이 있다는 이유로 목표 숫자를 채우지 않는다.

### intent

**용도·작성 시점:** 새 기능·이슈의 사용자 문제를 확인할 때 쓴다.

**필요한 입력:** 인터뷰·관찰·시나리오가 입력이며 기술 구현안부터 고르지 않는다.

**복사용 틀:**

```markdown
# <사용자가 해결하려는 일>

## 사용자 문제
<누가 어떤 상황에서 무엇을 못 하는가. 확인한 근거와 날짜>

## 사용자 장면
<계기 → 현재 행동과 어려움 → 원하는 끝. 기존 장면은 링크>

## 기대 결과
<사용자가 확인할 변화와 그 변화가 필요한 이유>

## 제약·범위 밖
<기기·운영·일정 등 확인된 제약 / 이번에 풀지 않을 문제>

## 열린 질문
<문제·범위의 미정. 설계 미정은 그 소유 문서를 링크>

## 연결 설계
<관련 업무·공통·화면 설계 링크와 이번에 결정이 필요한 부분>
```

**절별 질문:** 사용자가 말한 해결안에서 그 이유를 확인해 문제와 기대 결과를 분리한다. 인터뷰 사실과 작성자의 가설을 구별하고, 화면·업무 결정이 확정되면 설계에 올린 뒤 링크한다. 기존 [관리자 근무표 intent](intent/schedule-admin.md)의 상세 화면 결정처럼 이미 기록된 내용은 결정 근거로 보존하되 현재 화면 계약의 원천으로 중복 사용하지 않는다.

**검토 기준:** 설계자가 무엇을 결정해야 하는지 알 수 있는가. 문제를 「화면을 만든다」로만 적지는 않았는가. 결과를 바꿀 열린 질문은 승인 전에 답하거나 범위에서 명시적으로 제외할 수 있는가.

## 다음 단계로 넘기는 조건

기획은 사용자 문제·범위와 미정의 영향을 확인한다. 남은 미정은 그 미정이 막는 범위와 처리 방법을 적어 넘긴다.
