# 2026-10-14 — Expo 앱에 로그인 화면이 서고 시스템 테마가 OS 다크를 따른다

PR 다섯(#572~#576)이 돈 회차다. 어제 발견한 구멍, 곧 Expo 앱의 `/login`이 `NotBuiltYet` 한 줄이던 자리에 구글 로그인 화면과 흐름이 섰다. 그 뒷정리 중에 테마가 「시스템」일 때 다크 기기가 라이트로 남을 수 있다는 문제가 라이브러리 소스에서 나왔고 같은 날 고쳤다. 둘 다 코드와 단위 테스트는 초록이지만 기기로는 아직 못 봤고, Supabase 허용 목록 두 줄은 사람 손이 남았다.

## 정본 빈칸을 먼저 메우고 구현했다

구현 전에 문서를 먼저 낸 것은 login.md가 웹 시절 문장을 들고 있어서다(#572). `/auth/callback` 페이지로 이동하는 흐름은 앱에서는 안 맞는다. 앱 안 창을 열고 돌아오는 흐름으로 바꿨고, 로그인 상태 표에 「고르는 중」「돌아온 뒤」「실패」 세 행을 더했다. 돌아온 뒤에도 스피너가 없다는 것과 실패 줄의 자리를 모션 절에 적었다. 실패 문안 「로그인하지 못했어요. 다시 눌러 주세요」는 「제안」으로 넣었다. 문안은 `writing.md`가 정본이라 총괄이 확정하기 전까지 제안으로 둔다.

구글 토큰이 「지금 코드가 직접 그린 버튼이라 남아 있다」는 문장은 사실과 달라 걷었다. 그런 코드가 없었다. 구현(#573)이 `tokens.md` 9절의 구글 버튼 소절과 `globals.css`의 `vendor-google`·`color-google`을 지우면서 이 문장의 자리가 완전히 사라졌다. 생성기는 9절에 표가 없어도 던지지 않게 되었다.

등장 모션은 계획에서 떼어 `login-entrance-motion` 행으로 뒀다. 저장소에 움직임 줄이기 설정을 읽는 손이 없고, reanimated의 `ReduceMotion.System`은 애니메이션을 통째로 꺼서 「이동만 빼고 밝기는 남긴다」와 다르다. 이 판단이 서기 전에 로그인 화면을 붙잡아 두는 것보다 화면을 먼저 세우는 쪽을 골랐다. 행은 `candidate`로 남는다.

## 로그인 흐름은 lib · service · controller로 갈랐다

`signInWithGoogle.lib.ts`가 `signInWithOAuth({ skipBrowserRedirect })` → `openAuthSessionAsync` → `handleAuthCallback`을 잇고 실패 이유를 `start_failed`·`cancelled`·`missing_code`·`exchange_failed` 넷으로 나눈다. `expo-web-browser`와 돌아올 주소는 기본값으로 늦게 읽고 테스트가 주입한다. service는 로그인이 끝나면 `decideEntry`까지 가서 `decided`·`cancelled`·`failed`로 알리고, controller `useLoginScreen`은 `decided`면 `replace`, `failed`면 실패 줄을 낸다. 취소는 실패 줄을 안 낸다. 창을 닫은 사람에게 「하지 못했어요」를 보이면 안 된다.

버튼 톤은 `dark:` 변형으로 고른다. 라이트에는 Dark 자산, 다크에는 Light 자산이고, 둘을 다 그리고 `dark:hidden`·`hidden dark:flex`로 하나만 보인다. theme.store가 넣은 색 체계를 나머지 토큰과 같은 미디어 쿼리가 읽으니 화면 색과 버튼 톤이 어긋날 수 없다. 대안은 스토어를 `.tsx`에서 직접 읽는 것이었는데 AsyncStorage가 components 테스트에서 터져서 버렸다.

실패 줄은 안내 문구를 투명하게 남겨 그 높이를 쓴다. 시안의 `min-height: 2줄`을 RN에서 임의값 없이 맞추는 방법이고, 실패가 떠도 버튼이 안 움직인다. service의 `isPending`은 누른 순간 참이 되게 로컬 상태로 잡았다. react-query의 `isPending`은 알림이 다음 틱에 와서, 곧바로 실패하는 경우엔 한 번도 참으로 렌더되지 않는다.

`BrandMark`는 `shared/ui`에 섰다. 규칙 19가 화면 파일의 `rounded-`·`bg-`를 막아서 화면에 둘 수 없었다. `auth/callback` 딥링크는 `+native-intent.ts`가 `/login`으로 돌린다. 안드로이드에서 복귀하는 순간 Expo Router가 그 경로를 먼저 읽어 not-found가 번쩍일 수 있어서다. 판정은 `nativeIntent.policy.ts`에 있다.

받은 테스트에 손댄 자리가 셋이다. 대상이 서서 `TS2578`이 난 여섯 파일의 `@ts-expect-error` + `await import`를 걷었다. `signInWithGoogle.lib.test.ts`에는 `expo-constants` 모킹 한 줄을 더했다. lib가 `authRedirect.utils`를 거쳐 그 모듈을 당기고, logic 프로젝트에서 모킹이 없으면 스위트가 안 뜬다. `generateGlobalsCss.test.ts`는 9절 픽스처를 표 없는 꼴로 바꿨다. 단언은 안 바꿨다.

## 뒷정리에서 시스템 테마 문제가 나왔다

시안의 구글 버튼 치수가 자산과 안 맞았다(#574). 189:40이라 적었는데 실제 자산은 iOS 188×44, Android 180×40이라 높이 48px에서 각각 약 205px, 216px이다. `login.sian.html`을 자산에 맞췄다. `components.md`에는 구현이 세운 `BrandMark` 절을 더했다.

같은 PR의 `system-theme-follows-os` 행은 구현을 읽다가 나왔다. 테마가 「시스템」이면 `colorScheme.set(null)`을 부르는데 react-native-css의 미디어 쿼리는 관찰값을 `"dark"`와 그대로 비교한다. 관찰값은 `Appearance` 변경 이벤트가 와야 채워지니, 켤 때 이미 다크인 기기는 이벤트가 없어 라이트로 남을 수 있다. 라이브러리 소스로 확인했고 기기로는 못 봤다.

고침(#575)은 시스템일 때 `Appearance.getColorScheme()`을 직접 읽어 `light`나 `dark`로만 넣는 것이다. 그러면 반대 방향이 새로 열린다. react-native-css는 모듈이 로드될 때 `Appearance.addChangeListener(e => colorScheme.set(e.colorScheme))`를 걸어서, 이 리스너가 혼자 있으면 OS가 바뀌는 순간 사용자가 고른 밝게·어둡게가 덮인다. `followOsColorScheme`가 같은 이벤트에서 고른 테마로 다시 적용한다. 이기는 쪽은 등록 순서로 정해진다. react-native-css의 리스너는 모듈 평가 때, 우리 것은 첫 렌더 뒤 `useEffect`에서 걸리고, RN의 `EventEmitter`는 `Set`에 담아 넣은 순서대로 부르며 `emit` 직전에 `state.appearance`를 갱신한다. 그래서 우리 리스너가 마지막에 불리고 새 값을 읽는다. 이 순서는 소스를 읽어 확인한 것이고 기기 확인이 남았다.

`ThemeColorScheme`에서 `null`을 뺀 것도 이 고침의 일부다. 타입이 `null`을 허용하는 한 같은 실수가 다시 들어올 수 있다.

## react-native 대역이 구현에 안 닿았다

writer가 `themeStorage.lib.test.ts`에 `jest.unstable_mockModule("react-native", …)`로 `Appearance` 대역을 두고 「대상이 없어 빨갛다」고 돌려줬는데, 구현이 서자 `Appearance.getColorScheme is not a function`으로 죽었다(#575, 관찰 #576). jest `logic` 프로젝트는 babel에 `platform: "web"`을 넘기고 `babel-plugin-react-native-web`이 구현의 `import { Appearance } from "react-native"`를 `react-native-web/dist/exports/Appearance`로 바꾼다. 테스트의 대역이 그 import에 닿지 않는다. 구현자가 저장소 선례(`openPhone.lib.test.ts`)대로 실제 모듈을 import해 `Object.assign`으로 갈아 끼웠고, `stores` 아래는 `react-native` import가 `house/native-sdk-segment`로 막혀 `tests/setup/appearance.ts`의 `stubAppearance`를 새로 뒀다. 단언은 그대로다.

관찰 072는 `unit-test-writer` 정의문과 `execution.md`를 고치자고 열려 있다. 한 번 본 것이라 증축 문턱(세 번째)에는 못 미친다.

## 검증은 단위까지다

#573 기준으로 `pnpm lint`·`typecheck`·`format:check`·`test`(logic 468 스위트 3910건, components 10 스위트 47건)와 `pnpm bundle`(두 플랫폼 모두 `assets/google/*.svg` 넷이 번들에 든다)이 통과했다. #575 뒤 `pnpm test`는 468 스위트 3929건이다. `pnpm tokens:css` 재실행 diff는 0이다. `pnpm e2e`는 기기 빌드가 없어 못 돌렸다.

`pnpm test:integration:run`은 94건 가운데 92건이 통과했다. 실패 둘(`getPayrollMonth`·`getWageRates`)은 로컬 DB의 `wage_rates`가 14606행까지 쌓여 `max_rows = 1000`에 잘린 것이고 이 회차의 코드와 무관하다. CI는 깨끗한 DB라 안 난다. 로컬에서 풀려면 `supabase db reset`이 필요한데 로컬 데이터를 지우는 일이라 사람이 정한다.

남은 수동 확인은 handoff가 든다. 구글 왕복의 네 계정 경우, 안드로이드 복귀 때 not-found, 라이트·다크에서 버튼 톤, 시스템 테마 둘이다. iOS Expo Go는 SDK 57을 못 띄워 개발 빌드가 필요하다.

## 값이 드러난 자리

**구현자가 라이브러리 소스를 읽어 반대 방향을 잡았다.** 행이 가리킨 처방(`system`일 때 `getColorScheme()`을 넣는다)만 적용했으면 앱을 켤 때의 문제는 풀리지만, OS 설정을 바꾸는 순간 react-native-css의 리스너가 사용자가 고른 밝게·어둡게를 덮는다. 등록 순서와 `emit` 순서를 파일과 줄로 확인하고 `followOsColorScheme`를 둔 것이 그 자리를 막았다.

**구현자가 대역이 안 닿는 원인을 변환기에서 찾았다.** `react-native`가 mock됐는데도 `getColorScheme`이 없다는 에러를 모킹 문제가 아니라 babel 플러그인 변환으로 짚었다. 모킹을 이리저리 바꿨으면 시간이 더 들었을 자리다.

**시안 치수가 자산과 대조됐다.** 189:40은 어느 자산과도 안 맞았다. 자산의 실제 비율로 고치지 않았으면 시안이 구현과 어긋난 채 정본으로 남는다(#574).

**곧바로 실패하는 경로의 `isPending`이 잡혔다.** react-query 값을 그대로 쓰면 실패가 즉시 오는 경로에서 버튼이 눌림 상태로 한 번도 렌더되지 않는다. 누름부터 settle까지 로컬 상태로 잡았다(#573).
