# 2026-09-14 (2) — 문서 구조 계획 여덟 항목이 다 들어간다

PR 넷(#321, #322, #323, #324)으로 `docs/3-build/plans/docs-structure.md`의 여덟 항목이 순서대로 처리된다. 시작은 #320이다 — 직전 회차 마감 뒤 spec 폴더에 229줄짜리 검토 보고서(`docs-structure.md`)가 들어왔는데, 그 자체가 spec 폴더의 뜻과 어긋났다. spec은 완료 조건이 승인된 기능이 사는 자리인데, 문서 구조 개선은 승인할 기능이 아니라 검토 항목 목록이었다.

## spec을 기능만으로 좁힌다 (#321)

spec 절은 요구·설계·완료 조건·범위 밖 넷을 담는다. 「설계」 절은 정본을 링크로 가리키고 그 task만의 결정을 적는다 — 정본을 풀어 옮기면 architecture 문서와 내용이 겹치고, 정본이 바뀔 때 spec이 낡는다. ADR-005 44·49행이 이미 같은 말을 하고 있어 ADR은 손대지 않았다.

비기능 task는 승인할 기능이 없으니 spec을 안 쓴다. `3-build/plans/`에 task 문서를 쓰고 backlog 행이 그걸 가리키는 쪽으로 갔다. 비기능 spec 여섯(doc-links·sdlc-gate·shadow-tokens·supabase-client-entry·session-foundation·dashboard-design)을 `plans/`로 옮겼다. 지우는 안도 있었지만 기록을 남기는 쪽을 택했고, 새 폴더를 만들지 않고 이미 있는 `plans/`에 얹었다. 옮긴 여섯은 `status` 프론트매터를 뺐다 — 게이트(`sdlc-gate`)는 `spec/`만 읽으므로 남겨두면 검사 대상에서 조용히 빠지는 게 아니라 애초에 그 검사와 무관해진다.

`docs-structure.md`도 이 PR에서 여덟 항목짜리 task 문서로 다시 썼다. 8번(spec 좁히기)과 5번은 이 PR로 끝났고 나머지 여섯이 남았다.

## 목차, 차단 목적지, 관리자 홈 뒤로 (#322)

긴 문서에 내부 목차(같은 파일 안 제목 목차)를 허용했다. `design-system/README.md`의 「문서 목록 금지」는 그대로 두고 목차만 풀었다 — 그 규칙의 출처(`log/2026-08-26-4.md`)가 막던 건 값과 지도의 중복이지 한 파일 안의 제목 나열이 아니다.

`login.md`의 차단된 사람 목적지(`/blocked`)와 관리자 홈 앱바(뒤로·「관리자」·브랜드 마크)를 정본에 맞춰 정리했다. `sian-auditor`가 관리자 홈 앱바는 문서와 일치한다고 확인했고, 별개로 `.backic`의 svg 크기(20px, 문서는 28px)와 닿는 면(44px 미달) 어긋남을 잡았다 — 모든 시안이 같은 컴포넌트를 재사용해서 이번 변경 범위를 넘는 저장소 전체 문제로 보고 후속 행(backlog 후보)으로 넘겼다.

## 루트 README, 디자인 지도, CHANGELOG (#323)

루트 `README.md`를 새로 세웠다. 폴더 목록은 CLAUDE.md가 정본이라 베끼지 않고, 실제 있는 명령의 실행 절차와 handoff·backlog 링크만 담았다.

`design-system/README.md`의 문서 지도에 페이지 문서 일곱(payroll·profile·approvals·members·wages·stats·qr)이 빠져 있었다. 이건 이미 상처가 난 자리고 기계가 대신할 수 있는 검사라 `tests/lint/design-map.ts`를 새로 달았다 — `pages/*.md`가 지도에 없으면 `pnpm test`가 실패한다. 애초 검토 계획 초안은 이 검사를 「안 단다」였는데, 상처의 존재와 기계 대체 가능성 둘 다 갖췄다고 보고 증축 규칙 기준으로 뒤집었다.

CHANGELOG는 더 크게 손봤다. #229부터 지금까지 merge된 PR 92건으로 표를 다시 뽑았다. 원래 계획은 최근 두 회차만 채우는 거였는데, 새로 단 검사(`tests/lint/changelog.ts`)가 로그가 가리키는 모든 PR을 표에서 찾다 보니 그 사이 빈 번호(#243~#299)가 걸렸다. 부분만 채우면 검사가 못 통과해서 범위를 표의 시작까지 넓혔다. 기존 14행은 문구를 그대로 두고 날짜만 git merge 날짜로 고쳤다 — #301~#306이 로그 날짜보다 실제로 하루씩 앞서 merge돼 있었다.

CHANGELOG를 채우는 절차 자체를 `session-recorder` 정의문에 박았다 — 회차의 merge PR 전부를 git 날짜로 표에 더한다는 절이다. 관찰 010(CHANGELOG가 2026-09-04에서 멈춰 있다)이 이 PR로 닫혔다 — 정의문에 담당 주체가 없으면 문서가 안 채워진다는 그 관찰의 원칙대로, 담당을 명시하는 쪽으로 갔다.

## backlog·handoff 재편과 architecture 현재 상태 표기 (#324)

`backlog.md`에 「대기」(완료 조건 없음, 선행 조건만 적음)와 「후보」(작은 할 일) 절을 새로 세웠다. 데이터 task 넷을 「다음」에, 대시보드 선행 넷을 「대기」에 놓아 지금 뭘 잡을 수 있는지와 뭘 기다려야 하는지를 갈랐다.

`handoff.md`는 106줄에서 30줄로 줄었다. 절을 지금 상태·다음 첫 수·막는 결정·주의 넷으로 고정하고, 쌓여 있던 열린 결정 51건과 주의 29건을 각각 갈 곳으로 보냈다 — 정본에 이미 있는 내용은 지웠고(배웠다는 사실 자체가 근거였던 것들, 예를 들어 달 키·화면 없는 함수·구글 버튼·테마·스위치 그림자), 정본에 없던 건 그 문서의 「아직 안 정한 것」 절로 옮겼고(`components.md`에 스켈레톤·통신 없음 띠 등 절 신설, `login.md`에 위치 서술과 브랜드 색), 할 일은 backlog 후보로, 훅·테스트·CI 상시 주의는 `4-test/README.md`·`5-deploy/README.md`로, 정책 마찰은 관찰 013(integration 사용자 미정리 vs service role 금지)으로 보냈다. CLAUDE.md가 이미 말하는 것(PUBLIC, hooksPath, Docker, domain 먼저)은 그대로 지웠다. `session-recorder` 정의문에도 handoff 절이 서서, 넷 밖의 절을 만들지 않고 열린 결정을 셋으로 나눠 보내는 규칙을 박았다.

`architecture/README.md`에 「목표 설계다」 한 문단을 더하고, `api/README.md`(타입 생성)·`runtime/account.md`(게이트)·`data-model/account.md`(신원·개인정보 표)에 지금 코드가 실제로 어떤 상태인지와 이를 옮기는 backlog 행을 적었다 — architecture 문서가 목표만 그리고 있어서 지금 코드와의 간극이 안 보이는 문제였다.

## 값이 드러난 자리

`design-map` 검사와 `changelog` 검사 둘 다 원래 계획서는 「검사를 안 단다」고 적었던 자리다. 실제로 페이지 문서 일곱이 지도에서 빠져 있었고 CHANGELOG가 50개 가까운 PR만큼 밀려 있었다는 사실이 드러나면서, 이미 상처가 난 자리에 기계가 대신할 수 있는 검사를 다는 쪽으로 계획을 뒤집었다. 증축 규칙의 판정 기준("기계가 대신할 수 있나")이 계획 문서를 쓸 때의 판단과 실행 시점의 판단을 다르게 만든 경우다.

## 남은 것
