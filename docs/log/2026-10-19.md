# 2026-10-19 — 통계 다시 시도가 신분을 되살리고 테스트 인프라 세 행이 한 PR로 닫힌다

PR 둘(#617·#618)이 돈 회차다. 어제 candidate로 나온 네 행이 닫혔다 — `stats-retry-profile-key`와 `orphan-profiles-legacy`·`default-wage-rate-tests-in-lock`·`fixture-blocked-user-shape`. 앱 쪽은 통계 화면의 「다시 시도」가 세션과 프로필도 다시 읽게 됐고, 도구 쪽은 `user_id` 빈 옛 profile 238행이 치워지고 기본 시급에 닿는 테스트 여덟이 잠금 안으로 들어가고 차단 픽스처가 실제 `block_member`의 꼴이 됐다. 단위·lint·타입·integration 전체와 번들은 초록이다. 닫으면서 candidate 셋이 새로 나왔다.

## 신분이 failed에서 돌아오지 못하던 길

신분(`identity`)이 `failed`가 되는 길은 세션 읽기 실패와 프로필 읽기 실패 둘인데, 통계 화면의 다시 시도가 무효화하는 `RETRY_KEYS`에 두 키가 없었다. 한 번 넘어지면 화면이 `failed`에서 돌아오지 못했다. 세션이 실패하면 프로필 쿼리는 `skipToken`이라 아예 안 돌므로 키 순서가 뜻을 가진다 — 세션 키를 맨 앞에 두어야 세션이 회복돼 `userId`가 선 뒤에 프로필이 읽힌다. 프로필 키만 넣으면 세션 실패 쪽이 여전히 안 풀린다.

범위는 통계 화면 하나로 잡았다. 관리자 통계에는 신분 실패 경로가 없다는 것을 test writer가 확인했고, 그래서 다른 화면의 다시 시도는 건드리지 않았다. 앞서 받아 둔 실패 테스트 둘(프로필 실패 뒤·세션 실패 뒤 다시 시도하면 `ready`로 돌아온다)이 단언 수정 없이 통과했다. DB에 닿는 코드가 없어 integration은 돌리지 않았다.

## 표식 없는 옛 profile은 판정 조건으로 찾는다

`user_id`가 빈 profile 238행은 이메일 표식도 등록부 id도 없어 어떤 정리도 닿지 못했다. 238행이 전부 같은 꼴이라는 것을 로컬 DB에서 확인했다 — `approved_at`은 있고 `submitted_at`은 비었고, 개인정보 행이 있는 행도 `email`이 비었다. 실제 경로로는 이 꼴이 서지 않는다. `approve_member`가 `submitted_at`을 요구하고, 그것을 비우는 `unblock_member`의 대상은 승인 전 차단자라 `approved_at`이 없다. 이 꼴을 만든 것은 #614 전의 `approveProfile` 헬퍼다. 238행의 생성 시각이 모두 #614 이전인 것이 그 증거다.

그래서 판정 조건을 넓히지 않았다. `user_id`가 비었고, 만든 지 6시간이 넘었고, 승인됐고, 제출 시각이 없고, 제출이 남기는 이메일도 없는 profile만 고른다. 규칙은 순수 함수 `staleOrphanProfileIds`가 들고 지우는 일은 이미 있는 `purgeTestUsers`가 한다. 지울 때 `user_id is null`을 한 번 더 확인해, 판정과 삭제 사이에 사용자가 붙은 행을 안 지운다. 238행을 가리키던 `wage_rates` 273행과 `notifications` 3행은 cascade로, `assignments.profile_id` 1행은 `PROFILE_REFERENCES` 순서로 지워진다. `pnpm test:purge` 전 238행이 후 0행이 됐고 integration 전체를 한 번 돌린 뒤에도 0행이다.

자동 리뷰가 하나 짚었다. 새 경로가 이메일 패턴 없이 `profileIds`만으로 지우므로 시작 가드가 거기까지 닿는지는 diff에 안 보인다. 가드는 기존 스크립트 상단에 있고 이번에 바뀌지 않았다.

## 기본 시급 테스트는 헬퍼 밖에서도 같은 잠금을 쓴다

`withNoDefaultWageRates` 잠금이 그 헬퍼를 쓰는 테스트끼리만 직렬화해서, 헬퍼 밖에서 오늘 기본 시급을 심거나 단언하는 테스트가 다른 worktree의 실행과 섞였다. 대상은 센 것으로 정했다. `default_wage`가 걸린 integration 다섯 파일 가운데 헬퍼 밖에 있던 여덟 건을 `withDbLock(DEFAULT_WAGE_RATES_LOCK, …)` 안으로 넣었다. `setWage`·`eraseProfiles`·`getPayrollMonth`·`approveMember`·`memberDecisionRace`는 `default_wage_rates`에 행을 넣지 않고 그 결과도 단언하지 않아 뺐다. 본문은 들여쓰기만 바뀌어 `git diff -w`에는 잠금 두 줄씩만 남는다.

잠금이 못 막는 것이 하나 남았다. `set_default_wage`가 시급 이력이 없는 승인자 전원에게 오늘 행을 넣으므로, 잠금 밖에서 행 수를 정확히 세는 테스트(`getWageRates`의 「3행」「0행」「1100행」, `getPayrollMonth`의 「1100행」, `payrollRls`의 단일 행)는 동시 회차에서 여전히 흔들릴 수 있다. 이 PR의 범위를 넘겨 `default-wage-side-effect-lock` candidate로 올렸다.

## 차단 픽스처는 submit_profile 위에 선다

`createBlockedUser`는 승인과 차단이 동시에 찍힌 실제로 없는 상태를 만들었다. `block_member`는 제출됐고 승인·거절·차단 전인 사람에게 `blocked_at`만 찍는다. 헬퍼를 `createApprovedUser` 대신 `createSubmittedUser` 위에 세웠고 `BlockedUser`는 `SubmittedUser & { blockedAt }`이 됐다. 사용처 열 파일을 전수로 읽었다. 「차단된 사람이면 already_decided」는 전에 `approved_at`만으로도 막혔던 것이 이제 `blocked_at` 하나로 막혀 의미가 더 강해졌고, 알림·푸시·목록 쪽은 같다.

비용이 둘 있다. `profilesRead`의 「차단되면 남의 프로필을 다시 못 읽는다」는 이제 `approved_at`이 없어 `is_approved()`의 `blocked_at` 조건이 없어도 통과한다. `payrollFunctions`의 「승인받지 않았거나 차단됐거나 퇴사한 사람에게는 안 선다」도 차단자가 `approved_at is not null`에서 먼저 빠져 `set_default_wage`의 `blocked_at is null` 갈래를 못 지킨다. 승인된 사람이 차단될 길이 실제로 없으니 두 테스트는 「차단된 사람은 못 읽는다」「오늘 행이 안 선다」는 의미로는 맞고, 두 조건 자체를 지키는 테스트는 `blocked-guard-coverage`로 넘겼다. 같은 이유로 `members-pending.yaml` 머리말이 옛 헬퍼 꼴을 적고 있어 `e2e-comment-blocked-user`를 더했다. Maestro가 없어 e2e는 못 돌렸고 바뀐 플로우도 없다.
