# 2026-10-17 — 어제 남긴 후속 셋이 닫히고 스켈레톤 빛 줄이 흐르기 시작한다

PR 셋(#595~#597)이 돈 회차다. 어제 candidate로 남은 `now-receives-date-string`·`push-claim-limit`·`skeleton-shimmer-animation`이 모두 닫혔다. 마감 문장의 입력 이름이 값과 맞아졌고, 푸시 대기열이 한 번에 잡는 행에 상한이 생겼고, 스켈레톤의 빛 줄이 멈춰 선 막대에서 흐르는 줄이 됐다. 단위·lint·타입은 초록이다. 빛 줄은 실기기로 못 봤고, 닫으면서 candidate 둘이 새로 나왔다.

## 마감 문장은 시각 대신 날짜를 받는다

`deadlineLine`의 입력이 `{ applicationDeadline, now }`에서 `{ applicationDeadline, today }`로 바뀌었다(#595). 마감까지 남은 날은 날짜끼리의 셈인데, 함수가 시각을 받아 안에서 `kstDateOf`로 다시 날짜로 자르고 있었다. 호출부 셋(`useScheduleWorkerScreen`·`useScheduleAdminScreen`·`scripts/e2eSeedServer.mts`)은 이미 KST 날짜 `today`를 들고 있었다. 날짜 문자열을 `now`에 넘기는 꼴은 UTC 자정이 KST 09시라 우연히 맞던 것이어서, 이름을 값에 맞추면 그 우연이 없어진다. 본문은 `daysUntil(today, applicationDeadline)` 한 줄이 됐고 `kstDateOf` import가 빠졌다.

영향 범위는 호출부 셋뿐이다. `grep -rl deadlineLine`에 더 걸리는 파일은 화면 상태의 `deadlineLine` 필드 이름이라 함수와 무관하다. 출력 문장 세 꼴(「3일 남았어요」·「오늘까지예요」·「마감됐어요」)은 그대로고 `checkSourcesImpact`도 추적 중인 spec·plan의 입력이 안 바뀌었다고 냈다.

## 푸시 대기열은 오래된 것부터 500행씩 잡는다

`internal.claim_notifications`가 조건에 맞는 행을 전부 update해서, 대기가 1000을 넘으면 rpc 응답이 PostgREST `max_rows`에서 잘렸다. 잘린 행은 `push_attempts`만 오르고 안 나갔다(#596). `order by created_at, id limit 500 for update skip locked`로 묶었다. `send-push`의 `sendClaimed`는 한 번 잡고 끝나지만 500을 넘는 대기는 매분 `retry_push` 회차가 나눠 잡으므로 호출부는 안 바뀐다.

마이그레이션은 `create or replace`에 반환 열·`security invoker`·`search_path`를 그대로 두고 `revoke execute ... from public`을 한 줄 더했다. `internalGrants` integration이 PUBLIC·anon·authenticated 실행 권한이 없음을 집행해서 통과를 확인했다. 정본 `notification/design.md` 「푸시 보내기」에 상한을 한 문장 더했다. 잡기 질의를 적은 `notification-push.md`는 완료된 plan이라 기록으로 뒀다.

integration 테스트는 상한 둘을 세웠다(1100행 중 오래된 500, 둘째 호출이 다음 500). 같은 파일의 기존 테스트가 서로 행을 건드려서 격리를 보강했다(자기 profile 정리, AC-02 행을 1999년으로). 파일 전체를 두 번 연속 돌려 26/26을 확인했다.

브랜치 이력의 `06afa0a6`은 마이그레이션과 문서를 잘못 지웠다가 `eb2e3b21`이 되돌린 것이다. squash로 합쳐져 main에는 안 남는다.

## 스켈레톤 빛 줄은 훅이 폭을 재서 흐른다

빛 줄이 덩이 왼쪽 1/3에 멈춰 있었다. 정본(`components.md` 「Skeleton」, `tokens.md`의 `--interval-shimmer` 1.6s linear)은 「shimmer는 흐른다」고 적는다(#597). 이제 왼쪽 밖에서 오른쪽 밖으로 1.6초에 한 번 linear로 끝없이 지나간다. 걸리는 꼴은 `withRepeat(withTiming(덩이 폭, { duration: 1600, easing: Easing.linear }), -1, false)`고 빛 줄 폭은 덩이의 1/3, 시작은 `-빛 줄 폭`이다.

상태를 `.tsx`가 아니라 `shared/hooks/useSkeletonShimmer.ts`로 뺀 까닭은 `house/dumb-ui`다. 이 규칙이 `useReduceMotion`을 당긴 `.tsx`의 `useState`·`useEffect`를 막는다. `Skeleton.tsx`는 훅이 돌려준 것만 그리고 호출자의 `onLayout`도 그대로 부른다. `SHIMMER_INTERVAL_MS = 1600`은 `shared/consts/motion.const.ts`에 두고 `tests/lint/motionTokens.ts`의 대조 목록에 `--interval-shimmer`와 짝으로 넣어 짝이 여섯이 됐다. 쓰는 자리는 직접 import 12곳과 `SkeletonRows`를 거치는 10곳, 모두 22곳인데 props 꼴이 그대로라 호출부는 안 바뀌었다.

동작 줄이기가 켜지면 빛 줄이 없고 애니메이션도 안 걸고 `onLayout`도 안 단다. 켜지는 순간 `cancelAnimation`이 돌고, 꺼지면 잰 폭으로 다시 흐른다. 한계가 하나 있다. 켜진 채 마운트되어 떠 있는 동안 설정이 꺼지면, 폭을 못 쟀으니 덩이 크기가 바뀔 때까지 빛 줄이 서 있다. 앱 첫 진입은 `trackReduceMotion`을 기다린 뒤 라우팅하므로 이 경우는 스켈레톤이 떠 있는 몇 초 사이에 OS 설정을 바꿀 때뿐이다. `onLayout`을 늘 달면 풀리지만, 기존 `SkeletonRows.test.tsx`가 트리를 `toEqual`로 비교해서 덩이마다 다른 핸들러를 달면 깨진다. 그래서 reduce motion일 때 `onLayout`을 안 다는 꼴이 골라졌고, 한계는 `skeleton-shimmer-reduce-motion-off` candidate로 남았다.

테스트 쪽 손댐은 하나다. `useSkeletonShimmer.test.ts`에서 대상이 없을 때 달아둔 `@ts-expect-error` 한 줄을 뗐고 prettier가 import 줄을 한 줄로 접었다. 단언은 그대로다.

## 검증과 남은 것

세 PR 모두 lint·typecheck가 통과했고 #595의 `pnpm test`는 logic 4033건·components 111건, #597은 logic 4049건·components 122건이다. #596만 integration을 돌렸고 #595·#597은 DB에 안 닿아 생략했다. `pnpm e2e`는 기기 빌드가 없어 못 돌렸다.

사람 손이 남은 것은 어제 목록에 더해진다. 스켈레톤 빛 줄이 끊김 없이 흐르고 한 바퀴 돌아 다시 시작할 때 튀지 않는지(이음새), 동작 줄이기를 켜고 끌 때 멈췄다 다시 흐르는지, `absolute`로 띄운 빛 줄이 둥근 모서리(`rounded-xl`·`rounded-sm`) 안에서 잘려 보이는지, 카드 여럿이 한 화면에 설 때 깜빡임으로 읽히지 않는지다.

## 새 candidate 둘

`skeleton-shimmer-reduce-motion-off`는 위 한계다. `claim-notifications-concurrency-test`는 #596 자동 리뷰가 짚었다. `for update skip locked`가 동시 호출에서 서로 다른 행을 잡는지 integration이 단일 연결로만 본다. 상한 테스트 둘도 순차 호출이라 잠금이 겹치는 경우는 증명하지 못한다.
