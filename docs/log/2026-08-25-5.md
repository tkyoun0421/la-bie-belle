# 2026-08-25 (5) — 계획과 작성을 구현에서 떼어내고, 회차 마감을 기록자에게 넘긴다

PR 다섯 개(#171~#175)가 들어간 회차다. 구현자에게 판단 기준을 주는 작업 하나, 테스트 계획과 작성을 구현에서 분리하는 작업 하나, 그 여파로 CLAUDE.md를 덜어내고 회차 마감 자체를 subagent에 넘기는 작업 둘로 이어졌다. 코드 생산 subagent는 이번 회차에 한 번도 돌지 않았다. 다섯 PR 전부 구조 작업이라 총괄이 직접 썼다.

## 구현자에게 판단 기준을 준다 (#171)

`implementer.md`에 "무엇을 하지 마라"만 있고 "어떻게 고를까"가 없었다. 원칙이 부딪힐 때의 순서(정확성, 계약과 불변식, 기존 관행, 단순함, 최소 변경, 검증), 코드를 쓰기 전에 확인할 것, 깊은 모듈과 얕은 래퍼 금지 같은 설계 원칙, 무관 리팩터와 투기적 추상화를 막는 범위 제한 넷을 넣었다.

우선순위 목록 자체에 함정이 있다. "단순함"과 "최소 변경"이 테스트를 건너뛸 핑계가 될 수 있어서, TDD는 이 순서 밖에 두고 어느 항목과도 흥정하지 않는다고 명시했다.

## 테스트 계획과 작성을 구현에서 뗀다 (#172)

`test-planner`·`unit-test-writer`·`e2e-test-writer` 셋을 새로 만들고 `implementer`와 `test-triage`를 고쳤다. implementer는 이제 테스트를 쓰지 않는다. 받은 빨간불을 초록불로 바꿀 뿐 테스트의 기대값과 단언은 못 건드리고, 테스트가 없으면 시작하지 않고 멈춘다. test-triage에는 실패 분류 여섯(`PRODUCT_BUG`·`TEST_BUG`·`TEST_DATA_OR_ENVIRONMENT`·`FLAKY_OR_RACE`·`UNRELATED_EXISTING_FAILURE`·`UNCERTAIN`)과 실패 숨기기 금지 다섯을 얹었다.

가르는 이유는 자기 확인이다. 구현자가 쓴 테스트는 구현에 맞춰지니 버그를 잡는 게 아니라 이미 내린 결정을 확인만 한다. `CLAUDE.md`가 진작 경고하던 위험인데 손이 하나였으니 막을 길이 없었다. 계획을 따로 세우는 이유는 다른 데 있다. 무엇을 테스트할지보다 무엇을 일부러 안 덮을지가 어렵고, 그 판단이 기록으로 안 남으면 나중에 구멍인지 결정인지 구분이 안 된다.

planner는 훅이 강제하는 최소선 위에서만 더하도록 정의문에 박았다. `src/` 아래 실행 코드를 export하는 `.ts`는 짝 unit이 필요하고 screens와 라우트는 `tests/e2e/`가 필요하다는 최소선을 빼는 계획은 애초에 못 쓴다. 훅이 파일 쓰기 자체를 거부해서 구현이 막히기 때문이다. 작성이 구현보다 먼저 오니 이 순서는 훅과 맞아떨어진다. writer가 테스트를 남긴 뒤에야 implementer의 파일 쓰기가 열린다.

`integration-test-writer`는 만들지 않았다. `src/` 파일 아홉 개 중 실행 코드는 `shared/lib/utils.ts` 하나뿐이고 의존성 열두 개가 전부 프론트다. DB도 ORM도 auth도 server action도 없어서 그 writer가 검증할 대상이 저장소에 하나도 없다. `test-triager`도 새로 만들지 않았다. `test-triage`가 이미 그 자리라 실패 분류와 숨기기 금지 규칙만 얹었다.

**원래 가져온 제안과 부딪힌 지점.** 사람이 test-planner + unit/integration/e2e writer 셋 + test-triager 구조와 조율 문서를 통째로 가져왔고, 그중 둘이 우리와 정면으로 부딪혔다. 제안의 planner는 "current diff"를 분석하고 triager는 "implementation changes are complete" 뒤에 부른다. 우리는 TDD라 계획과 작성이 구현보다 먼저이고, `tdd-guard-unit.py`가 짝 테스트 없이는 구현 파일 쓰기 자체를 거부하니 test-after는 물리적으로 불가능하다. 제안은 또 "리스크에 따라 선택적으로 돌리고 매번 다 돌리지 마라"고 하는데 우리 훅은 무조건이다. 리스크로 층을 고를 여지가 없어서 planner는 훅이 정한 최소선 위에서만 더하도록 정의문에 못 박았다.

## CLAUDE.md에서 다른 데 정본이 있는 것을 뺀다 (#173)

100줄 7,485바이트에서 85줄 5,939바이트로 줄였다. subagent 갈래를 소개하는 문장 7줄을 지웠는데, `.claude/agents/*.md`의 `description`이 세션 시작 때 자동으로 전부 로드되기 때문이다. 남긴 건 설명이 알려줄 수 없는 것뿐이다 — 부르는 순서(`test-planner` → writer 둘 → `implementer` → `pr-diff`)와 `docs-researcher`를 `web-researcher`보다 먼저 부르는 규칙. TDD 경로 규칙도 지웠다. 테스트가 어디 사는지는 ADR-001에 있고 어기면 훅이 정확한 경로를 찍어 막으니 CLAUDE.md에 사본을 둘 이유가 없다.

계기는 바로 앞 PR #172에서 총괄이 subagent 셋을 소개하는 3줄을 더한 것이다. 그 3줄이 정의문 `description`과 완전히 같은 말이었다. 자동으로 들어오는 걸 손으로 다시 적고 있었다는 걸 그때 알았다. 문서 지도 절이 "다른 문서는 지도를 옮겨 적지 않는다"는 한 방향만 막고 있어서 역방향 규칙을 박았다. `CLAUDE.md`는 세션마다 통째로 로드되니 어디를 볼지와 무엇을 먼저 부를지만 담고, 다른 곳에 정본이 있는 내용은 옮겨 적지 않는다.

## 회차 마감을 기록자에게 넘긴다 (#174)

`session-recorder`(sonnet)를 만들었다. 회차가 끝나면 회차 로그, plan.md의 task 상태, handoff.md 셋을 갱신하고 PR을 연다 — 이 로그 자체가 그 산출물의 첫 사례다.

전에는 회차 로그를 총괄만 썼다. 근거가 대화에만 있고 저장소엔 없다고 봤기 때문이다. 그러면 스폰 프롬프트에 대화 요약을 통째로 실어야 하는데, `CLAUDE.md`의 판정 질문 — "스폰 프롬프트에 넣을 말이 대화 요약뿐인가? 그렇다면 총괄이 직접 쓰는 쪽이 싸다" — 이 정확히 그걸 막는다. 그 전제가 틀렸다는 걸 이번에 확인했다. 우리 PR 본문은 무엇을·왜 구조로 쓰니 근거가 이미 저장소 안에 있다. 기록자는 `gh pr view --json body`로 merge된 PR을 읽어 로그를 쓰고, 총괄이 실어주는 건 PR에 안 남은 것뿐이다 — 회차 중에 오갔지만 어느 PR 본문에도 안 들어간 판단, 다음 첫 수, 열린 결정.

이 설계에는 부수 효과가 하나 있다. PR 본문을 성의 있게 쓸 유인이 생긴다. 얇게 쓰면 로그가 얇아지고, 기록자가 "어느 PR이 얇았는지"를 리턴에 적어 온다.

기록자에게는 결정하지 않는다, `CLAUDE.md`·`docs/prd.md`·`docs/adr/`를 건드리지 않는다, 지난 회차 로그를 고치지 않는다, 스스로 task를 만들지 않는다, `src/`와 테스트를 건드리지 않는다는 다섯을 못 박았다. 문체는 `docs/log/`의 기존 파일을 읽어 맞추게 했고, 목록으로 도망가지 말라는 것과 "성공적으로 완료했다" 같은 아무것도 나르지 않는 문장을 금지하는 것을 명시했다.

## test-planner를 sonnet으로 내린다 (#175)

처음 opus로 만들었다가 haiku로 내릴지 논의했다. 안 내린 이유는 planner의 오류가 아래로 증폭되기 때문이다. 산출물이 writer 둘의 입력인데 writer는 배정받은 것만 쓰도록 묶여 있어서 계획이 틀려도 못 잡고, 그다음 implementer는 그 테스트를 통과시킬 뿐이다. 계획 오류를 잡는 그물이 아래에 없다. 다만 planner는 task마다 한 번 돌고 코드를 안 써서 출력이 짧으니 opus까지는 과했다. writer 둘이 sonnet이니 계층도 맞아서 sonnet으로 정했다.

## 남은 것

이번 회차에 생산 subagent를 실제로 돌린 적은 없다. 다섯 PR 전부 협업 구조 자체를 고치는 작업이라 총괄이 직접 썼다. 다음 회차부터 `test-planner` → writer 둘 → `implementer` → `pr-diff` 흐름이 처음 실전으로 돈다.
