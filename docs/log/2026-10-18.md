# 2026-10-18 — 설정값이 빠진 빌드가 한 장을 그리고 훅이 Bash 쓰기를 보고 integration이 자기 데이터를 치운다

PR 열넷(#602~#615)이 돈 회차다. 아홉 행이 닫혔다 — `error-screen`·`sheet-handle`·`identity-threading-into-features`·`hook-bash-writes`·`test-planner-ground-truth`·`logo-e2e`·`test-seed-transaction`·`integration-seed-canon`, 그리고 네 묶음으로 나눈 `test-data-isolation`. 앱 쪽은 설정값이 빈 채 번들돼도 죽지 않고, 바텀시트 맨 위에 손잡이가 서고, 통계·급여 조각이 신분을 화면에서 받는다. 도구 쪽은 TDD·spec 훅이 Bash로 쓰는 길을 보고, integration이 로컬 DB에만 붙고 자기가 만든 사용자와 행만 지운다. 단위·lint·타입은 초록이고 새 화면 둘(앱을 열 수 없어요 · 시트 손잡이)은 기기로 못 봤다. 닫으면서 candidate 일곱이 새로 나왔다.

## 설정값이 빠진 빌드는 죽지 않고 한 장을 그린다

`EXPO_PUBLIC_SUPABASE_URL`·`EXPO_PUBLIC_SUPABASE_ANON_KEY` 중 하나가 빈 채 번들된 앱은 `supabase.ts`가 모듈 로드에서 던져 루트 레이아웃 import에서 죽었다. 화면을 그릴 자리가 없었다. 정본(`runtime.md` 「설정값이 빠진 빌드」)을 먼저 올리고(#602) 구현이 뒤따랐다(#606). 값은 빌드 시점에 번들에 박히므로 다시 시도도 로그인 화면도 답이 아니다 — 새 빌드만 고친다. 그래서 화면에 버튼이 없고, 값이 있는데 틀린 빌드는 여기 걸리지 않고 전처럼 첫 요청이 실패해 `/retry`로 간다.

클라이언트 모듈은 던지지 않고 값이 비면 `.invalid` 자리표시 주소(절대 풀리지 않는 예약 도메인)로 클라이언트를 만들며 `supabaseConfigured`를 내보낸다. 루트는 폰트·테마를 든 채 `rootGateOf({ configured })`로 갈라, `unavailable`이면 스플래시를 내리고 `AppUnavailable`만 그린다. 세션 복원·자동 갱신·서버 시각·입장 판정·`Stack`은 `ConfiguredRoot`로 옮겨 설정된 빌드에서만 돈다. 훅 규칙 때문에 컴포넌트를 갈랐고, 설정된 빌드에서는 같은 훅이 같은 순서로 돈다.

생김새는 임시다. 기존 조각(`Screen`·`Illustration`·`Text`)만 써서 `RetryScreen` 짜임을 빌렸고, 마지막에 사람이 정한다. env를 비운 빌드에서 한 장이 뜨는지, 값이 찬 빌드가 전처럼 입장 판정대로 가는지는 기기로 안 봤다.

## 손잡이는 정본에 올랐지만 쓰는 시트가 없다

페이지 문서 넷(check-in·excuse·stats·approvals)이 바텀시트 손잡이를 그리라 하고 앞 둘은 토큰까지 적었는데, 조각의 정본(`components.md`)에 그 줄이 없어 `DraggableSheet`가 `handleComponent={null}`로 지웠다(관찰 028). 정본에 먼저 올렸다(#604). 색 `stroke.neutral-muted`, 크기 `w-8` `h-1` `rounded-full`은 페이지 문서 값 그대로고, 위 8px·아래 12px 여백은 페이지 문서에 없던 값이라 새로 정했다.

구현(#607)은 손잡이를 gorhom의 `handleComponent`로 넘기지 않고 `BottomSheet` 면 안에 그렸다. `DraggableSheet`는 gorhom 쪽 배경을 투명하게 두고 면을 `BottomSheet`가 그려서, `handleComponent`로 넘기면 손잡이가 면 밖 스크림 위에 뜬다. 면의 `p-5`를 그대로 두면 손잡이 위가 28px이 되므로 `pt-0`으로 위만 비웠다.

그런데 `DraggableSheet`를 쓰는 시트가 0이다. 화면 시트 열다섯은 끌어 닫기가 없는 `SheetLayer`를 쓴다. 정본은 「끌어 닫기가 되는 시트에는 손잡이」인데 끌어 닫는 시트가 화면에 없으니 손잡이가 화면에서 안 보인다. 시트를 끌어 닫게 바꿀지 손잡이만 그릴지는 정해지지 않아 `sheets-not-draggable`로 남았다. 관찰 028은 이 결정이 서야 닫혀서 open으로 둔다.

## 통계·급여 조각이 신분을 화면에서 받는다

`house/no-cross-slice-import`가 `features/stats` → `features/auth`를 막아 `useStatsAttendance`·`useStatsPositions`·`useMyPayrollViewDaysQuery`가 세션과 프로필 질의를 각자 따로 들고 있었다(#608). 「내가 누구인가」는 화면이 드는 맥락이라, 이제 화면 controller가 `useMyStanding`으로 한 번 읽어 `profileId`를 인자로 아래에 심는다. 조각 훅 일곱과 ui 일곱이 `profileId: string`을 받고, 화면 controller가 `profileId: string | null`을 낸다. 통계 화면은 `identity`(`pending`·`failed`·`absent`·`ready`)를 더 내서 자리를 가른다.

첫 커밋에서 회귀 둘이 생겼다 — 프로필 읽기가 실패해도, 프로필 행이 없어도 근태·포지션 탭이 같은 스켈레톤을 그렸다. 되돌려서 실패면 `StatsFailed`, 행이 없으면 `StatsEmpty`를 그린다. 급여 탭은 이 두 경우에 전에는 `listState`의 empty를 거쳐 `StatsEmpty`를 그렸고 이제 실패면 `StatsFailed`를 그린다.

`StatsFailed`의 다시 시도가 무효화하는 `RETRY_KEYS`에 프로필 키가 없다는 것은 전과 같아 손대지 않았다. 프로필 읽기가 실패한 화면은 다시 시도를 눌러도 프로필을 다시 읽지 않는다. `stats-retry-profile-key`로 남았다.

## 훅이 Bash로 쓰는 길도 본다

TDD·spec 훅 matcher가 `Write|Edit`뿐이어서 heredoc·리다이렉션·`sed -i`로 `src/`를 쓰면 훅 셋을 그냥 지나갔다. 같은 task에서 writer 하나는 막히고 하나는 안 막힌 일이 있었다(관찰 023). 같은 규칙이 도구에 따라 다르게 걸리면 규칙이 아니라 우연이라 matcher에 `Bash`를 더했다(#609). 그 대가는 명령 문자열에서 쓰기 대상을 읽어내는 일이다.

`shlex`를 쓰지 않고 작은 lexer를 세웠다. posix 모드는 따옴표를 벗겨 `grep ">" f`의 `">"`와 진짜 리다이렉션 `>`를 가를 수 없고, non-posix 모드는 이스케이프와 붙은 따옴표를 잘못 쪼갠다. 둘 다 시험해서 확인했다. heredoc 본문을 먼저 걷어내서 `git commit -m "$(cat <<'EOF' … EOF)"`의 본문이 대상에서 빠진다.

Bash는 쓰려는 내용을 안 넘겨 준다. `tdd-guard-unit`은 내용에서 실행 코드를 내보내는지와 새 export 이름을 짝이 부르는지를 읽는데, 빈 내용으로 판정하면 새 파일이 전부 통과해 이 task가 막으려던 구멍이 그대로 남는다. 그래서 새 파일은 경로 기준으로 짝 테스트를 요구하고, 있던 파일은 저장된 내용으로 판정한다. 타입만 든 파일을 `sed -i`로 고치는 걸음을 막지 않으려는 것이다. 새 파일을 막을 때는 「타입·상수만 담을 파일이면 Write로 써라」를 같이 알린다. `tdd-guard-e2e`는 내용에 든 `@/screens/<슬라이스>` import로 짝을 찾고, 새 라우트는 슬라이스를 알 수 없어 막으면서 Write로 쓰라고 알린다.

못 보는 꼴은 그대로 execution.md 「훅」에 적었다 — 인터프리터가 쓰는 파일(`python3 - <<EOF`·`node -e`), 프로세스 치환, `find -exec sed -i`, `cp -r`, `ln`, `dd of=`, 따옴표가 안 닫힌 명령. 이 task의 구현자가 ADR-001 55줄과 ADR-015 359줄이 이제 사실과 다르다고 짚었고 총괄 문서라 손대지 않았다. 따로 올린 PR이 두 문장을 고쳤다(#610). ADR-015 쪽은 `git mv`가 여전히 훅이 보는 꼴 밖이라 결론은 그대로고 근거 문장만 바뀌었다.

## test-planner가 판정에 확인 방법을 싣는다

`test-planner`가 「없다」「N개다」를 돌려줄 때 어떻게 확인했는지가 같이 안 실려 온 자리가 다섯 번이었다(관찰 020·037·039·042·075). 정의문 「지키는 것」에 넷을 더했다(#605). 「없다」에는 검색어와 범위를 붙이고, `.ts`를 e2e에만 배정하지 않고 기기 없이 볼 조각은 unit으로 같이 배정하고, plan에 든 숫자는 정본의 같은 축 숫자와 나란히 재고, 센 수에는 센 명령을 붙이되 줄 단위 grep은 하한이라고 밝힌다. 020은 고침이 이미 정의문에 있었고 그 줄의 경로가 옛 꼴이라 지금 세그먼트로 고쳤다. 관찰 다섯은 archive로 갔다.

## 로고 파일이 지워져도 초록이던 구멍

구글 로그인 버튼은 `require.context`로 `assets/google/`을 열고 파일을 못 찾으면 `catch`로 삼켜 빈 그림을 그린다. 로고 SVG를 지워도 화면 테스트와 e2e가 초록이었다(#611). Maestro는 화면의 글자로 조각을 잡고 그림이 그려졌는지는 안 보니 e2e로 올리지 않고 `tests/lint/assetReferences.ts`로 내렸다. `src/` 코드가 `require`·`import`로 가리키는 그림·서체 파일과 `require.context`가 여는 폴더가 있는지, 버튼이 이름으로 고르는 로고 넷이 있는지를 본다. `Illustration.tsx`가 여는 `assets/illustrations/`는 사람이 아직 안 넣은 폴더라 면제 목록에 있고, 폴더가 생기면 면제를 빼라고 테스트가 빨개진다. 가짜 파일 트리로 무는 것을 확인했고 실제 자산은 건드리지 않았다.

## integration이 자기 데이터만 만들고 치운다

`test-data-isolation`을 네 묶음(A~D)으로 나누고 씨앗 묶음(#603)을 곁에 뒀다. 공통 원인은 같은 로컬 DB에 앞 회차와 다른 worktree가 남긴 행이 쌓여 거짓 초록과 거짓 빨강을 다 만든다는 것이다. 이 브랜치에서 돌리기 전에 로컬 DB에 `auth.users` 1907행이 있었고 전부 옛 꼴 테스트 사용자였다.

**씨앗을 한 트랜잭션으로(#603).** `seedWorkRequest`가 요청 행을, `seedRequestCandidate`가 갈래 행을 따로 넣는 사이에 pg_cron의 `expire_requests`가 들어와 요청을 닫는 경주가 있었다(관찰 024). `seedWorkRequestWithCandidates`가 둘을 `begin`·`commit` 한 호출로 묶어, 다른 연결에는 요청과 갈래가 같이 보이거나 둘 다 안 보인다. 함수에 유예를 두는 길은 운영 동작을 테스트 사정으로 바꾸는 것이라 고르지 않았다. 헬퍼 하나를 세우고 둘(`seedRequestCandidate`·`reopenRequest`)을 뺐고 호출부 22곳을 바꿨다. 경주 자체는 매 분 틱이 틈에 떨어져야 걸려서 재현하지 못했다. execution.md의 cron 문장은 이 헬퍼를 가리키게 고쳤다.

**붙을 곳을 먼저 확인한다(A, #612).** 여러 로컬 프로젝트가 떠 있으면 psql 헬퍼가 엉뚱한 DB에 SQL을 꽂을 수 있었고 API 쪽은 호스트를 아예 안 봤다. 확인하는 곳은 시드 서버 하나뿐이었다. globalSetup이 `supabase_db_<project_id>` 컨테이너, 그 DB가 `[db]` 포트의 `postgres`인지, `supabase status`의 `API_URL`과 env의 `EXPO_PUBLIC_SUPABASE_URL`이 loopback인지 본다. 하나라도 어긋나면 이유를 찍고 테스트를 하나도 안 돌린다.

포트는 `inet_server_port()`로 비교하지 않는다 — `docker exec … psql`은 컨테이너 안에서 붙어서 소켓 연결이면 비고 TCP여도 내부 포트 5432가 나오고, 54322는 호스트 쪽 매핑이다. 그래서 DB가 쓰는 내부 포트를 읽고 `docker port`로 그 포트의 호스트 매핑을 읽어 config.toml과 맞춘다. jest의 globalSetup은 `moduleNameMapper`를 안 거쳐 `@tests/` 별칭이 `Cannot find module`로 죽고 상대 경로 import는 lint 규칙 1이 `tests/**`에서도 막는다. 그래서 `e2e:seed`와 같은 방식으로 `scripts/checkIntegrationTarget.mts`를 Node로 띄우고 그 스크립트가 헬퍼의 확인 함수를 부른다. 기기용으로 LAN 주소를 넣어 둔 셸이면 가드가 막으므로 `EXPO_PUBLIC_SUPABASE_URL`을 비우고 돌린다. CI의 `db` 컨테이너 이름이 `supabase_db_la-bie-belle`이 맞는지는 로그에 안 나와서 이 PR의 CI 첫 실행이 확인한다.

**만든 사용자를 회차 끝에 지운다(B, #613).** 95파일 중 88이 사용자를 만들었는데 지우는 파일은 둘뿐이었다(관찰 013). 가입 헬퍼가 이메일을 `test+<runId>-<uuid>@example.test`로 만들고, 만든 userId를 등록부에 자동으로 올린다. `afterAll`이 등록부를, `afterEach`가 `trackUser`한 사람을 지운다. 지우는 순서는 profiles를 cascade 없이 가리키는 13곳 → profiles → `auth.users`이고 한 트랜잭션이며, delete마다 넘어온 id와 이 회차 이메일 패턴을 둘 다 조건으로 건다 — id가 잘못 넘어와도 다른 회차나 실제 계정은 안 지워진다. 정리가 실패하면 그 suite가 빨개지고, 새 FK가 생기면 DB의 FK 목록과 `PROFILE_REFERENCES`를 대조하는 테스트가 먼저 깨진다. 임시로 `schedules.created_by`를 빼고 근무표를 만드는 테스트를 돌려 `schedules_created_by_fkey` 위반으로 suite가 실패하는 것을 확인하고 사본으로 되돌렸다.

`pnpm test:purge`는 수동 치우기다. 옛 꼴 사용자에도 6시간 나이 조건을 붙였다 — 첫 회차 중에 다른 worktree가 옛 코드로 돌린 흔적(05:11에 만든 옛 꼴 사용자)이 보였고, 나이 조건이 없으면 남이 돌리고 있는 회차를 중간에 지운다. 옛 꼴 이메일에는 시각이 없어서 `auth.users.created_at`으로 잰다. `isApprovedIsAdmin`의 자체 가입 함수가 옛 꼴 이메일로 직접 가입해 등록부를 비켜 가서 헬퍼로 바꿨다. 단언은 그대로다.

**빈 달을 세어 보고 고른다(C, #614).** `freshHolidayYear`라는 이름이 비어 있는 연도를 약속하는데 확인을 안 했다(관찰 044). `freshMonth`·`freshYear`가 후보를 뽑은 뒤 그 표의 날짜 열에 행이 있는지 세고, 비었을 때만 돌려주며 스무 번 뽑아도 없으면 표·열 이름을 넣은 오류로 멈춘다. `Math.random`으로 달·연도를 뽑던 23파일이 5파일로 줄었고 남은 자리는 달·연도 고르기가 아니다 — 테스트마다 새로 만든 사람의 `wage_rates` 날짜(키가 안 겹친다), 시급 금액, 「다음 해」 안의 날이다. 센 명령은 `find src tests -name '*.integration.test.ts' -print0 | xargs -0 grep -l 'Math.random'`이다.

관찰 038은 승인·퇴사·거절 픽스처가 제출을 거치지 않은 사람을 만들어 멤버 목록에 안 뜨는 문제였다. `approveProfile`가 `approved_at`과 함께 `submitted_at = coalesce(submitted_at, approved_at)`을 채운다. null에 기대는 테스트가 있는지 먼저 grep했고, 대기 목록 테스트는 승인·거절·차단된 사람을 결정 열로 걸러 내니 결과가 같았다. 「이미 승인된 사람을 차단·거절하면 already_decided」는 전에는 `submitted_at`이 비어서도 막혔고 이제는 `approved_at` 때문에 막혀 이름대로의 것을 본다.

진짜 날짜여야 하는 씨앗(`seedDayEndedHoursAgo`·`seedPastDay`, 취소·요청 보내기 테스트의 씨앗)은 달을 못 바꾼다. 그날 `days` 행 중 이 회차 표식 사용자가 연 것만 `deleteThisRunDay`로 지운다. 기준을 「그 관리자」로 잡았다가 `attendanceFunctions`에서 describe마다 다른 관리자가 같은 날(200시간 전)을 심어 `days_work_date_key`로 빨개져 「이 회차」로 넓혔다. 「자기가 만든 schedule」 기준도 안 맞는다 — 그 달 근무표를 `on conflict do nothing`으로 만들어서 남의 근무표일 수 있다. 등록부는 profile id도 들게 해서 `eraseProfiles`가 `user_id`를 직접 비운 profile 한 행이 남던 것도 이제 지워진다.

**단언이 자기 행을 본다(D, #615).** 「오늘 날짜는 date_past로 거부되지 않는다」가 `open_day`의 반환을 안 보고 행 존재만 단언해서, 앞 회차가 남긴 그날 행이 있으면 함수가 거절해도 초록이었다. 이제 반환된 `error`를 단언하고 `already_open`만 허용한다. `getWageRates`의 천 행 테스트는 `max_rows = 1000`에 잘리는 쪽이 아니라 「심은 날짜가 전부 받은 쪽에 있다」로 좁혔다. 조건 없는 `delete from public.default_wage_rates;` 둘은 없앴다 — 기본 시급 행은 전역 하나라 `withNoDefaultWageRates`가 advisory lock을 잡고 있던 행을 읽어 그 날짜만 지운 뒤 끝에 되돌린다. 잠금은 세션이 끝나면 풀리니 프로세스가 죽어도 안 남는다. `tests/lint/unscopedDelete.ts`가 `src/`와 `tests/`에서 where 없는 삭제를 문다.

## 검증과 남은 것

코드를 바꾼 PR은 모두 lint·typecheck가 통과했다. 정본·정의문·ADR만 바꾼 PR 넷(#602·#604·#605·#610)은 영향 확인 절을 근거로 들고 #605는 `docLinks` 통과도 적는다. 마지막 PR의 `pnpm test`가 logic 486 스위트 4202건이다. integration 전체는 #615에서 97 스위트 661건이고 #614에서 연속 두 회차 초록이었다. `pnpm bundle`은 #606·#608·#612~#614에서 통과했다. `pnpm e2e`는 기기 빌드가 없어 못 돌렸다.

사람 손이 남은 것은 어제 목록에 더해진다. env 두 값을 비운 빌드에서 스플래시가 내려가고 「앱을 열 수 없어요」가 뜨는지, 값이 찬 빌드가 전처럼 입장 판정대로 가는지, 시트 손잡이는 `DraggableSheet`가 안 쓰여 화면에서 안 보이는 것을 확인하는 일이다. 에러 화면의 생김새는 디자인 결정이다.

바뀐 실행 방법은 셋이다. integration은 로컬 가드가 원격·LAN URL을 거부하므로 `EXPO_PUBLIC_SUPABASE_URL`을 비우고 돌린다. `pnpm test:purge`가 중단한 회차의 사용자를 치운다. 훅이 Bash 쓰기도 막는다.

## 값이 드러난 자리

**#606의 integration 1건 실패가 main에 이미 있었다.** `setApplicationDeadline.api.integration.test.ts`의 「그 달 근무표가 없으면 no_schedule」이 졌다. 그 PR이 고친 파일은 이 테스트의 import 그래프에 없었고 main 상태에서 이미 깨져 있는 것으로 보고 따로 봤다. 같은 부류(남은 근무표가 달 고르기를 막는 것)를 B의 2회차 실패가 다시 보였고(`getMonthAttendance`의 앞뒤 달 `already_exists`) C가 `freshMonth({ neighbours: true })`로 고쳤다.

**#613이 `profiles`가 회차마다 한 행씩 느는 것을 숫자로 잡았다.** 회차 앞뒤 행 수 표에서 `profiles`만 2136 → 2137 → 2138 → 2139로 늘었다. 원인이 `eraseProfiles`의 「user_id가 널이면 다시 쏘지 않는다」가 profile의 `user_id`를 직접 비워 이메일 표식으로 닿지 못하는 것이라는 점도 거기서 나왔고 C의 등록부 profile id로 이어졌다. 행 수를 안 셌으면 정리가 된다고 믿고 지나갔을 자리다.

**#615의 mutation 확인 넷.** 오늘도 `date_past`로 거절하게 바꾼 `open_day`, `no_default_wage` 대신 `bad_amount`를 내는 `reset_wage_to_default`, 첫 1000행만 읽는 `getWageRates`(사본), 가장 오래된 기본 시급을 고르는 `getWageRates`(사본)가 각각 해당 테스트를 빨갛게 했고 되돌린 뒤 초록이었다. 좁힌 단언이 무는지 확인한 것이다.

**#607 자동 리뷰가 단언 빈틈을 짚었다.** `DraggableSheet.test.tsx`가 `BottomSheet`를 mock했고 mock이 `className`을 버려서, 핵심 변경인 `pt-0`이 빠져도 테스트가 통과한다. 위 여백 28px 회귀를 못 잡는다. 행으로 만들지 않고 사실로만 남긴다. 같은 리뷰가 본문의 「동적 import를 정적 import로 바꿨다」가 diff에서는 새 파일로 보인다고도 짚었다.

**#609의 구현자가 ADR 두 문장이 사실과 달라졌음을 짚었다.** 총괄 문서라 손대지 않고 올린 덕에 #610이 고쳤다. 안 올렸으면 ADR-001이 「Bash로 쓰는 것은 보지 않는다」를 계속 적고 있었을 것이다.
