# 2026-08-28 (2) — 테스트가 개발을 막은 자리 셋을 규율은 지키며 푼다

PR 하나(#211)가 들어간 회차다. 저장소의 첫 기능 task 「세션 기반을 깐다」의 완료 조건 여섯과 예외 규칙 셋을 채웠다. `docs/spec/session-foundation.md`가 그 명세다. 로그인한 사람을 서버에서 읽는 함수, 토큰을 갱신하는 미들웨어, `POST /auth/logout`, 그 사람의 이메일을 그리는 `/`가 실제로 생겼다. 테스트 계획이 명세의 빈자리에 걸려 명세에 커밋 둘이 먼저 얹혔고, 구현이 시작된 뒤에는 TDD 규율이 실제 개발을 세 자리에서 막아 각 자리를 다르게 풀었다.

## "테스트가 개발을 막으면 안되지"

이번 회차의 축이 된 한 문장이다. TDD로 가면 테스트가 구현보다 먼저 생기는데, 그 순서 자체가 세 군데에서 손을 묶었다. 셋 다 규율을 통째로 느슨하게 풀지 않고, 막힌 게 규율 자체인지 규율을 잘못 놓은 자리인지를 갈라 풀었다.

**빌드가 red 단계에서 통째로 깨졌다.** `tsconfig.json`이 `**/*.ts`를 그대로 포함하고 있어서, `next build`의 타입 검사가 아직 구현되지 않은 모듈(`@/middleware`, `@/shared/lib/get-current-user`)을 import한 테스트 파일까지 같이 봤다. 테스트만 먼저 들어온 red 단계에서는 그 import가 실제로 안 풀리니 빌드가 프로젝트 전체를 실패로 떨어뜨렸고, e2e는 빌드가 있어야 도니 TDD의 첫 단계에 들어서는 순간 손이 묶였다. `tsconfig.build.json`을 새로 만들어 `tests`와 `__tests__`, `*.test.ts(x)`, `*.spec.ts(x)`를 빼고, `next.config.ts`의 `typescript.tsconfigPath`로 그걸 물렸다. 빌드의 타입 검사가 앱 코드만 보게 되면서 테스트까지 보는 검사가 하나 빠지므로, `pnpm typecheck`를 CI에 새로 넣었다. 이 단계는 그전까지 CI에 아예 없었다 — `next build`가 유일한 타입 게이트였다. 규율을 푼 게 아니라 게이트를 옮기고 하나 더 세운 셈이다.

**lint 규칙 번호 불변식과 부딪혔다.** 서버에서 `getSession()`을 금지하는 걸 하우스 lint 규칙 no:18로 넣으려 했더니, `tests/lint/rules.ts`의 `DOCUMENTED_LINT_RULE_COUNT`(14)를 지키는 카탈로그 테스트가 걸렸다. 이 상한은 [2026-08-26 (5)](2026-08-26-5.md)에서 나왔다. 카탈로그가 lint 밖의 강제 수단(TDD 가드 둘, pre-commit의 시크릿 검사)에 15·16·17을 스스로 붙이면서, 그 번호들이 문서에서 온 열넷과 섞이지 않게 "lint가 집행하는 마지막 번호는 열넷"을 못박은 것이다. 새 lint 규칙에 no:18을 주면 카탈로그가 지어낸 번호와 문서에서 온 번호의 경계가 흐려진다. 대신 `tests/lint/no-get-session.test.ts`를 ESLint 규칙이 아니라 소스 스캔 테스트로 썼다. `src/` 아래를 재귀로 훑어 `.getSession(` 호출을 찾되 `__tests__`와 `"use client"`가 붙은 파일은 뺀다. 막는 효과는 같고 불변식은 그대로다.

**TDD 훅이 클라이언트 팩토리를 막았다.** `src/shared/lib/`는 `tdd-guard-unit.py`가 짝 테스트를 면제해주는 `SKIP_PREFIXES`(`src/app/`, `src/shared/ui/`)에 들지 않아서, 테스트 없이는 파일을 못 쓴다. 쿠키 저장소를 잇는 `create-supabase-server-client.ts`가 이 자리였다. 처음엔 팩토리 테스트가 동어반복이 될 거라 보고 작성자에게 쓰지 말라고 했다가, 훅 예외를 넓히는 대신 다시 들여다봤다. 이 어댑터는 동어반복이 아니라 계약이다. Next의 쿠키 모양과 `@supabase/ssr`이 요구하는 `getAll`·`setAll` 모양이 다르고, Server Component에서 쿠키 쓰기가 실패할 때 그걸 삼키고 넘어가는 분기가 따로 있다. 훅은 그대로 두고 그 계약을 실제로 확인하는 테스트를 쓰게 했다.

## test-planner가 명세의 구멍을 잡았다

명세 초안에는 완료 조건이 다섯이었다. `test-planner`가 조건 넷에 테스트를 못 짝지었다 — 로그아웃을 무엇으로 부르는지가 안 정해져 있어서 검증할 통로가 없었다. 화면 없이 e2e가 직접 부를 수 있어야 하니 Route Handler로 내기로 정했고, 그게 지금의 완료 조건 4(`POST /auth/logout`)다. 계획하는 손이 구현하기 전에 명세 자체의 빈자리를 잡아낸 사례다.

## `/`가 이메일을 그대로 드러내는 이유

완료 조건 6은 로그인한 사람의 이메일 주소를 화면에 그대로 쓰라고 못박는다. "로그인됨" 같은 문구만 띄우면 아무 쿠키나 심어도 e2e가 통과한다. 그 세션에만 있는 값이 화면까지 나와야 쿠키가 서버까지 닿아 진짜로 검증됐다는 증거가 된다. 실제로 이메일을 노출하는 화면을 만들겠다는 뜻이 아니라 발판이고, 로그인 화면 task에서 걷어낸다. 그 발판 위에서 `src/app/page.tsx`가 직접 통신을 하게 됐는데, 이건 `.tsx`는 더미 UI라는 ADR-001 규칙과 어긋난다. 같은 이유로 로그인 화면 task까지만 사는 코드다.

## `pr-diff`가 캐시 헤더 배선의 구멍을 잡았다

미들웨어는 `@supabase/ssr`이 쿠키와 같이 돌려주는 캐시 금지 헤더를 응답에 옮긴다. 토큰이 실린 응답이 중간 캐시에 남으면 한 사람의 세션이 다른 사람에게 나갈 수 있어서다. 그런데 `setAll(cookiesToSet, headers)`의 둘째 인자로 넘기는 이 경로에 단언이 없었다. 모의가 헤더를 늘 빈 객체로 넘겨서 통과해버렸기 때문이다. `pr-diff`가 `node_modules/@supabase/ssr/dist/main/types.d.ts`를 읽어 그 둘째 인자가 실제 API 계약임을 확인하고 작성자를 돌려보냈다. 작성자가 `src/middleware.ts`에서 그 한 줄을 지워보니 8개 단언 중 정확히 1개만 빨개지는 걸 확인한 뒤 되돌렸다 — 새로 더한 테스트가 그 배선 하나만 잡는다는 뜻이다.

## e2e가 병렬에서 흔들렸다

정적 자원 예외를 확인하는 테스트는 GoTrue 컨테이너 로그에 찍힌 `GET /user` 호출 횟수를 센다. 이 로그는 워커 전체가 공유하는데, `setSession`이 내부에서 `getUser`를 부르기 때문에 다른 워커가 그사이 세션을 심으면 남의 호출이 내 카운트에 섞인다(`Expected 20, Received 21`). 구현자가 단언을 고치는 대신 `playwright.config.ts`에 `workers: 1`을 넣어 워커 간 간섭 자체를 없앴다. 판단은 맞지만 e2e 전체가 직렬로 도는 비용이 이 시점부터 붙는다.

## 포매터를 두 번째로 잊었다

CI가 `pnpm format:check`에서 죽었다. 방금 더한 테스트 파일에 Prettier를 돌리지 않았기 때문이다. 앞선 회차에서도 구현자가 받은 테스트 파일에 포매터를 돌려야 했던 적이 있어 이번이 두 번째다. `CLAUDE.md`의 증축 규칙은 같은 자리를 세 번째 두드리면 구조를 짓는다고 정해뒀다. 다음에 같은 일이 한 번 더 생기면 작성자 정의문에 `pnpm format:check`를 박아 넣을 자리다.
