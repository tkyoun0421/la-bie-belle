# 2026-08-26 — Supabase 바탕이 서고 TDD 흐름이 처음 코드 위에서 돈다

PR 다섯 개(#179~#183)가 들어간 회차다. #179는 지난 회차 기록을 남겼고, #180은 영속과 인증을 Supabase로 정한 ADR-003을 세웠고, #181과 #182는 그 위에서 흐름 자체를 손봤고, #183이 실제로 Supabase 바탕과 integration 테스트 층을 코드로 깔았다. `test-planner` → writer 셋 → `implementer` → `pr-diff`로 이어지는 흐름이 지금까지는 문서만 만들었는데 이번에 처음 코드 위에서 한 바퀴 돌았다. 도는 동안 구조의 빈자리 셋이 드러났고, 그 자리에 바로 지었다.

## 지난 회차 기록 (#179)

PR 176부터 178까지를 기록했다. 다섯 번째 회차 기록, ADR-002, PRD와 도메인 용어 확정이다. `docs/log/2026-08-25-6.md`로 남았다.

## 영속과 인증을 Supabase로 정한다 (#180)

PRD가 근무표와 계정과 급여를 요구로 확정해 영속을 더 미룰 수 없었다. ADR-003으로 Supabase(Postgres + 인증, 구글 OAuth), 웹 표준 Web Push, RLS로 DB에서 권한을 막는 방향, `dals` 세그먼트 하나로 DB 접근을 모으는 방향, 그 층을 integration 테스트로 검증하는 방향, CI에 lint → test → integration → build → e2e 순서를 얹는 방향을 정했다.

`dals` 경로를 훅의 `SKIP_PREFIXES`에 넣어 예외로 두는 길이 더 쌌지만 버렸다. ADR-001의 "탈출구를 두지 않는다"와 "훅은 세그먼트 이름을 모른다"를 둘 다 깨고, 급여 계산이 사는 자리에 무검증 구멍을 판다. 그래서 예외가 아니라 다른 증거를 받는 쪽으로 갔다. 짝 테스트가 없으면 여전히 못 쓰고, unit이 안 맞는 층에 integration을 요구할 뿐이다. mock으로 채우는 길도 버렸다. 가짜 DB로는 RLS 정책이 맞는지도, 실제 Postgres에서 급여 집계가 맞는지도 알 수 없다.

RLS를 고른 이유는 하나다. 앱 코드에 버그가 있어도 남의 급여가 안 나가야 한다. 돈과 개인정보라 판정을 한 군데서 빼먹으면 그대로 뚫린다. 다만 service role key는 모든 정책을 우회하니 서버에서도 사용자 세션으로 붙어야 RLS가 산다는 함정을 문서에 박아뒀다.

## integration 층에 손과 계획을 붙인다 (#181)

ADR-003이 층을 열었는데 쓸 손이 없었다. 증축 규칙은 "같은 스폰 프롬프트를 세 번째 쓰게 되면 그때 추출한다"이고 이때는 0번이었다. 규칙과 부딪히는 걸 알고도 `integration-test-writer`를 만들었다. 지난 회차에 이 에이전트를 안 만든 근거가 "검증할 대상이 저장소에 없다"였는데 ADR-003이 그 조건을 바꿔놨다. 손이 없는 채로 계획을 태우면 배정된 리스크가 unit으로 밀려나고, 그게 ADR-003이 버린 mock 범벅 테스트다.

`test-planner`를 이 task에 태웠더니 처음엔 어긋난 계획이 돌아왔다. `INTEGRATION` 절은 만들었는데 writer는 `unit-test-writer`가 두 몫을 다 맡으라고 했다. 원인은 계획자 정의문에 있었다. "integration 층은 아직 이 저장소에 없다. 층을 배정하지 말고 막힌 것에 적는다"는 문장과 `UNIT`·`E2E` 둘뿐인 리턴 템플릿이 남아 있었다. 계획자는 스폰 프롬프트가 시키니 절은 억지로 만들었지만 판단은 낡은 정의문 쪽으로 끌려갔다. 계획자가 스스로 나열한 근거 넷도 같은 자리에서 나왔다. 실패 확인 명령이 다르고, 사전에 `supabase start`가 떠 있어야 하고, 파일명 확장자가 다르고, mock 원칙이 반대로 뒤집힌다는 것이다. 매번 프롬프트에 실어야 하는 차이가 넷이면 그게 정의문으로 뺄 신호고, 특히 마지막이 결정적이다. `unit-test-writer` 정의문의 "mock은 진짜 경계에만 쓴다"가 integration 배정과 매번 부딪혀, 프롬프트로 정의문을 뒤집으라 지시하는 구조가 됐을 것이다. 정의문을 고치고 계획자를 다시 돌리니 배정이 제대로 나왔다.

## 구현자에게 integration 검증을 요구한다 (#182)

`implementer` 정의문의 검증 명령에 `pnpm test:integration`이 빠져 있었다. ADR-003의 "남는 위험"에 이미 적어둔 사안인데 정작 정의문을 안 고쳤고, 계획자가 이 task를 계획하다 짚어 올렸다. 이게 없으면 구현자가 로컬에서 integration을 안 돌리고 PR을 열고, 완료 조건의 "CI의 integration 단계가 돈다"가 CI에서야 처음 드러나 빨간불을 보고 나서 고치는 왕복이 생긴다. 로컬 Supabase 전제(`supabase status`로 확인하고 안 뜨면 `supabase start`), Docker가 없으면 리턴에 적고 멈추는 것, `pnpm test`만 초록불인 건 확인이 아니라는 것도 같이 박았다.

## Supabase 바탕과 integration 테스트 층을 세운다 (#183)

훅과 스키마와 러너를 실제로 깠다. `tdd-guard-unit.py`가 짝 후보를 `__tests__/<이름>.integration.test.ts`까지 둘로 늘렸고, `SKIP_PREFIXES`는 그대로 둬 경로 예외를 안 만들었다.

스키마는 `profiles` 테이블 하나다. 여기서 승인 경계를 다시 그었다. 총괄이 인터뷰에서 "`display_name`은 가입 이후 정보 입력 화면에서 받는다"는 답을 이미 받아뒀는데, 그게 RLS 정책과 부딪혔다. 이름을 넣는 화면이 자기 행을 읽어야 하는데, 승인 전에는 못 보게 정책을 짜면 이름 없는 프로필만 쌓이고 관리자는 누구를 승인할지 모르게 된다. 조용히 조정하지 않고 그대로 드러내 선택을 받았고, "자기 프로필은 항상 보인다"로 정했다. select 정책은 `id = auth.uid()` 하나만 보고 승인은 여기 없다. 승인이 막는 건 자기 프로필 바깥이고 그건 근무표와 급여 테이블이 생길 때 그쪽 정책이 맡는다. ADR-003 본문과 `docs/domain.md`를 이 결정에 맞춰 고쳤다.

이 결정에는 대가가 붙는다. 프로필에서 승인 조건이 빠지니 이 task에서 "승인 전 차단"을 증명할 대상이 사라졌다. 근무표 테이블이 없어서다. 최소 뼈대 원칙대로 그 증명은 근무표 task로 미뤘다.

프로필은 가입 트리거로 자동 생성한다. 앱이 명시적으로 insert하는 길도, 테스트 픽스처만 두는 길도 있었지만 트리거를 골랐다. 관리자가 승인하려면 승인 대기 목록이 있어야 하는데 그건 `approved_at`이 빈 프로필들이다. 가입해도 행이 안 생기면 관리자는 누구를 승인할지 모른다.

승인 여부는 참거짓 컬럼이 아니라 `approved_at` 하나로 판정한다. 플래그와 시각을 따로 두면 둘이 어긋나는 상태가 생기고, 애초에 표현할 수 없게 만드는 편이 낫다.

승인 자가발급은 컬럼 권한으로 막았다. 구현자가 낸 판단인데 근거가 정확해 그대로 받았다. RLS의 `with check`는 새 행만 보고 이전 행을 못 봐서 "이 컬럼은 그대로여야 한다"를 표현할 수 없다. `with check (approved_at is null)`로 쓰면 승인된 사람이 자기 이름도 못 고치게 된다. 그래서 `revoke update on public.profiles from authenticated` 뒤 `grant update (display_name)` 하나만 열었다. 승인을 실제로 찍는 자리는 관리자 task 몫으로 남겼다. grant는 역할 단위라 `authenticated`에 `approved_at`을 열면 관리자든 아니든 다 열리기 때문에, 그쪽은 권한을 확인하는 `security definer` 함수로 가야 한다.

integration 테스트 여섯이 처음부터 빨간불 없이 초록불이었다. TDD 위반으로 보지 않았다. 검증 대상이 앱 코드가 아니라 DB 정책이고, 정책은 마이그레이션 없이는 존재하지 않는다. 계획자가 순서를 마이그레이션 먼저로 짠 이유이기도 하다. 그래야 실패가 "dals 함수가 없다"는 정상 빨간불이 되지, "DB가 없다"는 미준비 신호가 되지 않는다.

`--passWithNoTests`는 일부러 뗐다. 떼는 순간 테스트가 0개라 CI가 빨간불이 되는 걸 알고 그대로 push했다. 남겨두면 나중에 include 글롭이 깨져도 CI가 조용히 초록불이 되는데, 그게 ADR-001이 말한 탈출구다. 다음 스폰의 첫 integration 테스트가 이 빨간불을 풀었다.

## 운영에서 겪은 것

`integration-test-writer`를 만든 바로 그 회차에 그 에이전트를 못 불렀다. main에 merge됐는데 세션이 시작할 때 로드된 목록에는 없었다. `handoff.md`의 "새 subagent 정의문은 main에 merge된 뒤에야 호출할 수 있게 등록된다"가 실제로 물었다. 범용 에이전트에 정의문 파일을 읽혀 그대로 따르게 하는 다리를 놨다. `unit-test-writer`로 대신하지 않은 이유는 그쪽 정의문의 "mock은 진짜 경계에만"이 이 층과 정면으로 부딪히기 때문이다.

작업 중 Orca worktree 둘이 사라졌다. 총괄이 쓰던 `adr-003-persistence`와 구현자가 쓰던 `supabase-impl`이 같은 시각에 `.orca-worktree-trash`로 치워졌다. 총괄 명령도 구현자 명령도 아니다. 커밋은 전부 push돼 있어 잃은 것은 없고 각자 새 worktree에서 이어갔다.

리셋 이전 프로젝트의 Supabase 스택이 6일째 떠 있었다. 포트 54321~54324를 잡고 있어 새 스택을 못 띄웠다. `assignments`·`ceremonies`·`profile_roles` 같은 pre-reset 스키마와 마이그레이션 18개가 들어 있었고, 그걸 만든 `supabase/` 디렉터리는 저장소 어디에도 없었다. 2026-08-20 리셋 이전의 고아로 판단해 내렸다. 구현자가 내리기 전에 통째로 백업했고, 사람이 확인한 뒤 백업도 지웠다.
