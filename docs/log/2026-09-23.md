# 2026-09-23 — spec 양식에 상태 격자를 박고 화면 task 스물의 spec을 세워 승인한다

PR 둘(#391·#392)로 spec 게이트를 실제로 연다. 양식에 「상태 격자」와 AC별 「검증 층」을 더하고, 화면이 있는 task 전부에 spec을 세우고 승인했다. 그 과정에서 기능 plan 열둘이 완료 조건을 중복으로 품던 자리 문제를 고쳤고, 승인이 격자 검사 자체의 구멍 하나를 드러냈다.

## spec 양식에 상태 격자가 들어갔다

지금까지 양식은 「요구·설계 참조·완료 조건·범위 밖」 넷이었다. 완료 조건은 해피 패스를 적기 쉬운 자리라 빈 상태·실패·동시 변경 같은 것이 조용히 빠졌다. `test-planner`의 입력이 spec이라, spec이 안 적은 상태는 테스트도 안 본다.

널리 쓰이는 에이전트 하네스 여섯(Claude Code `SKILL.md`, Anthropic tool use, OpenAI function calling, MCP, LangChain Tool, Cursor rules)을 훑어 가져올 것을 찾았다. 가져올 축은 하나뿐이었다 — 입출력 계약이 산문이 아니라 따로 선 구조 필드에 산다는 것. 나머지는 우리 양식이 이미 갖고 있었고, 「무엇을 안 하나」를 적는 칸은 여섯 중 어디에도 없었다 — 우리 「범위 밖」이 그만큼 앞서 있었다는 것도 이 조사의 결과다.

더한 것은 둘이다. `## 상태 격자` 절은 여덟 줄이 고정이다 — 빈 상태 · 로딩 · 실패 · 권한 없음 · 경계 · 재진입 · 동시 변경 · 성공 직후. 줄마다 「무엇이 뜨나」와 그것을 덮는 AC를 적는다. 해당이 없으면 「해당 없음」만으로 안 되고 이유를 붙인다 — 가리킬 AC가 없으면 그건 AC가 모자란 것이다. AC마다는 「검증 층」 한 줄이 붙는다 — unit·integration·e2e·수동 중 어디서 보는지와 왜 거기인지. `test-planner`가 뒤집을 수 있고 그 판정이 정본이다. 여기 적는 목적은 정답을 정하는 것이 아니라 아무 층도 안 적힌 AC를 눈에 띄게 하는 것이다.

검사는 `tests/lint/spec-grid.ts`, 단언 16개다. 절이 빠짐·줄이 빠짐·칸이 빔·이유 없는 「해당 없음」·AC 칸이 빔·없는 AC를 가리킴을 잡는다. 회귀 단언은 「위반 0건」이 아니라 「검사가 실제로 spec을 훑는다」로 썼다 — 0건으로 쓰면 옛 형식인 `login-screens.md`를 다시 쓸 때까지 계속 빨갛고, 그 빨강이 길어지면 사람이 검사를 꺼버린다.

## 격자가 실제로 찾아낸 빈 자리

새 양식으로 profile-form 넷을 먼저 쓰며 걸린 것과, 화면 task 스물을 마저 쓰며 걸린 것을 합치면 다음과 같다.

- `profile-form` — 보내는 사이에 관리자가 차단하면? 화면 문서에 없었고 `submit_profile`의 `not_allowed`가 답이었다. AC-05·AC-06으로 이었다.
- `members` — 마지막 관리자인지를 누르는 그 순간에 서버가 다시 센다. 버튼을 미리 끄지만 그 사이 다른 관리자가 퇴사할 수 있다. 같은 자리에서 `mark_leave`의 남은 배정 검사([schedule-data plan AC-11](../3-build/plans/schedule-data.md))도 여기 붙었다 — `assignments`는 섰는데 함수가 없어 떠돌던 것이다.
- `attendance-qr` — 관리자 둘이 잇따라 새로 뽑으면 먼저 뽑은 사람이 인쇄한 종이가 그 순간 죽는데 앱은 그것을 모른다.
- `notification-settings` — 권한 상태를 읽는 동안 스위치를 꺼진 모양으로 두면 끈 것처럼 보인다.
- `rehearsal` — 리허설 구간을 배정된 근무 시간과는 안 견준다.
- `schedule-worker` — 「열어둔 화면을 실시간으로 갱신하지 않는다」를 흩어 적지 않고 한 줄로 세웠다.
- `stats-admin` — 열두 달 중 일부만 읽기가 실패하면 그 달이 값 없는 달과 모양이 같아 갈리지 않는다.
- `payroll-view`·`stats-worker`·`stats-admin` — 「성공 직후」가 「해당 없음」이다. 쓰기가 없는 화면이라 끝나는 행위가 없고, 그 사실이 이제 명시됐다.
- `members-pending` — 「경계」가 「해당 없음」인데 이유가 값진다. 판정 넷이 전부 한 번 누르면 끝이고 되돌리는 건 차단 풀기뿐이라 이 화면에는 상한도 마감도 없다.

## 자리 문제 — 완료 조건이 plan과 spec 둘에 살고 있었다

`3-build/README.md`가 「완료 조건과 업무 규칙은 spec과 `2-design/`이 정본이라 여기 다시 적지 않는다」고 이미 적었는데, 지키는지 볼 수 있는 문장이 아니었다. 살아 있는 기능 plan 열둘(`schedule-admin`·`schedule-worker`·`schedule-assign`·`schedule-requests`·`attendance-excuse`·`rehearsal`·`stats-admin`·`payroll-view`·`payroll-wages`·`payroll-adjust`·`notification-list`·`stats-worker`)이 완료 조건 104개를 그대로 품고 있었다.

판정을 절 이름으로 풀었다 — 기능 plan에 `## 완료 조건` 절이 있으면 그 기능의 spec이 없다는 뜻이다. 그 절 이름은 비기능 task 문서(cron·Edge Function)의 것이고, 기능 쪽은 `## 구현 산출물`이 파일·함수·계산을 든다. 열둘을 그 꼴로 바꿨고 AC 번호와 본문은 안 건드렸다 — `attendance-excuse`가 무는 `schedule-worker.md#ac-09`가 그대로 산다.

## 승인 스물과 격자 검사의 구멍

스물을 `status: approved`로 올렸다. 승인 판정은 총괄이 이 세션에 위임했다. spec마다 「승인 근거」 절에 기준점 커밋과 이 PR의 고정 diff, 승인 범위(AC 번호 구간과 격자 여덟 줄), 그리고 그 spec이 스스로 든 제한이 적힌다 — 제한은 보일러플레이트가 아니라 spec마다 다르다. `stats-admin`은 실패한 달과 값 없는 달이 안 갈리는 것을, `payroll-wages`는 퇴사자의 지난 시급을 화면에서 확인할 길이 없는 것을, `attendance-checkin`은 [navigation Q-03](../2-design/system/navigation.md#q-03)이 아직 열려 있는 것을 든다.

`spec-grid.ts`가 처음에는 `status: approved`를 검사 밖으로 뒀었다. 스물을 승인하는 순간 검사 대상이 하나도 안 남는다 — 저장소 회귀 단언이 0건을 훑고도 초록이 되는 자리였다. 검사를 `### AC-NN`으로 조건을 나눈 spec이면 승인 여부와 무관하게 격자를 재게 고쳤다. 면제는 AC를 안 나눈 옛 명세 `login-screens.md` 하나뿐이고, 그것이 원래 면제하려던 대상이었다.

`spec-gate.py`도 이 회차로 실제 동작이 바뀐다. `feat/<슬러그>` 브랜치의 `src/` 쓰기를 `docs/2-design/spec/<슬러그>.md`의 `approved`로 통과시키는 게이트인데, 화면 task 열넷에 그 파일이 없어 전부 막혀 있었다. 스물이 서고 승인되면서 이제 읽을 것이 생겼다.

## 마찰

`docs/observations/016-rerun-reads-stale-pr-body.md`가 이 회차에 섰다. `sources` 영향 검사가 PR 본문을 `github.event.pull_request.body`에서 받는데, 재실행은 원래 이벤트 payload를 다시 튼다 — 본문을 고치고 재실행해도 옛 본문을 읽는다. 같은 빨강을 이 회차 안에서 두 번 봤다. 고치는 습관은 「본문을 먼저 고친 뒤 push한다」로 잡았고, 검사 자체는 첫 번째라 아직 손대지 않았다.

PR #392의 브랜치 base가 #391 merge 전에 갈라져서, 뒤에 rebase가 두 spec 동시 추가 자리에서 add/add 충돌을 냈다. 최종 트리가 main의 상위집합인 것을 확인하고 `origin/main` 위에 두 커밋으로 다시 쌓아 풀었다.

## PR #394~#398 — 기계만으로 닫히는 task 다섯을 마저 닫는다

`claimed-guards-audit`이 사실로만 남기고 넘긴 자리 셋(타입 생성, Edge Function import, 라우트 타입)과 앞서 미룬 서체 서브셋, 그 김에 드러난 파일 이름 규약까지 다섯이 이번 묶음이다. 다섯 다 화면 확인이 필요 없어 `expo-scaffold`의 실기기 병목 앞에서 먼저 닫혔다.

### 라우트 타입이 CI에서만 꺼져 있었다 (#394)

`app.json`이 `typedRoutes: true`를 켰지만 `.expo/`가 `.gitignore` 안이라 CI에는 라우트 타입이 없었다. 없으면 `expo-router`의 `Href`가 `string`으로 떨어져 `router.replace("/없는경로")`가 `tsc`를 그냥 통과한다 — 로컬에서만 켜진 타입 안전이었다. 만드는 명령을 찾는 데 후보 여섯을 실물로 갈랐다: `expo export`는 타입을 안 만들고, `expo` CLI에 타입 전용 서브커맨드가 없고, `@expo/router-server`를 직접 부르는 건 되지만 pnpm이 안 풀어주는 비직접 의존이고, `.expo/types/`를 커밋하면 라우트를 고치고 안 돌렸을 때 옛 타입으로 통과하는 문제를 모양만 바꾼 것이고, `expo start`를 띄웠다 죽이는 건 Metro 부팅 비용을 CI마다 문다. 남은 `expo customize tsconfig.json`이 Metro 없이 도는 유일한 진입점이었다.

생성이 조용히 절반만 되는 상태와 정상 상태가 종료 코드로는 안 갈린다. 그래서 `pnpm routes:types`가 생성물을 다시 읽어 `declare module "expo-router"` 보강·`ExpoRouter.__routes` 인터페이스·`href` 멤버·경로 리터럴 존재 넷을 본다(`tests/lint/route-types.ts`). `decide-entry.ts`의 실제 경로를 없는 경로로 바꿔 `tsc`가 무는 것까지 확인했다.

### 서체 서브셋이 정본과 실물의 어긋남을 메웠다 (#395)

`tokens.md`가 「넷 다 서브셋을 거쳐 들어간다」고 이미 적어뒀는데 실물은 원본이 들어가고 있었다. Wanted Sans 넷 합계를 9,256KB에서 1,753KB로 줄여 7.3MB를 뺐다. 글자 집합은 상용 2,350자(EUC-KR 완성형 영역을 디코더로 풀어 낸 것이지 표로 관리하지 않는다) 위에 시안·소스에서 긁은 기호 열아홉을 더한 2,527자다. 음절 전체를 넣는 대안은 실측으로 기각했다 — 9%만 줄어 상용 2,350자(81% 절감)와 비교가 안 됐다.

만들어진 `.ttf`의 `cmap`을 직접 읽어 필요한 집합이 다 들었는지 `pnpm test`가 본다 — 글자가 빠지면 그 자리만 시스템 서체로 조용히 떨어지고 앱은 안 죽어서 다른 검사가 못 잡는 자리라서다. 처음 돌렸을 때 다섯 자가 원본에 없어 빨갰고, 그중 시안이 닫기에 쓰는 「✕」(U+2715)는 원본 서체 자체에 없어 서브셋 여부와 무관하게 이미 시스템 서체로 떨어지고 있었다 — 대체 기호로 바꾸는 것은 `sian-sync`가 받았다.

### Edge Function은 `src/`를 못 읽는다 (#396)

스파이크로 실물을 갈랐다. edge-runtime 컨테이너가 `supabase/functions` 하나만 마운트해서(`docker inspect`로 확인) `deno.json`의 맵핑이나 심볼릭 링크로도 `src/`를 못 들여온다 — 맵핑 자체는 도는데 파일이 컨테이너 안에 없다. 복사도 `cp`만으로는 안 됐다. Deno가 import에 `.ts` 확장자를 요구하는데 `src/`는 안 적어서 `Maybe add a '.ts' extension`으로 부팅이 깨졌고, 확장자를 붙여 옮기니 전이 import까지 타고 실제로 동작했다. 결론은 `notification/design.md`에 이미 있던 컨테이너 마운트 문장에 「복사 단계가 import 지정자를 고쳐야 한다」를 더했고, 그 복사 단계 자체는 `notification-push`의 plan 몫으로 남겼다. 스파이크 파일(`supabase/functions/`)은 지웠다.

### 생성 타입 절이 스스로를 부정하고 있었다 (#397)

`data-access.md` 「생성 타입」이 한 절 안에서 「CI가 diff 0을 본다」와 「아직 없음 — `pnpm types`도 CI 검사도 없다」를 동시에 적고 있었다. `pnpm types`가 `supabase gen types`(스키마 `public`·`internal`)와 prettier를 한 덩이로 묶어 `src/shared/api/database-types.ts`를 만든다 — 두 단계가 갈리면 CI가 다시 뽑을 때마다 세미콜론 차이로 헛빨간불이 난다. 검사는 두 층이다: Docker 없이 도는 `tests/lint/database-types.ts`(마이그레이션의 표·뷰·함수 이름 대조, `SupabaseClient` 직접 import 금지)와 CI의 `git diff --exit-code`.

클라이언트를 받는 자리 스물아홉을 `Db = SupabaseClient<Database>`로 물리자 integration 테스트에서 오류 스물아홉이 드러났다 — 함수 이름을 `string`으로 받는 헬퍼, 인자 없는 함수에 빈 객체, RLS가 막을 것을 아는 insert가 필수 열을 안 채운 자리, 그리고 생성기의 한계 하나. `pg_proc`에 nullable 정보가 없어서 NULL을 받는 인자도 non-null로 나오는데, `check_in`·`decide_excuse`의 인자 넷에 SQL `default null`을 적어 선택 인자로 내리는 쪽으로 풀었다 — 캐스트로 덮으면 검사가 그 자리에서 꺼져서다. 자동 리뷰가 `checkIn` dal의 인자 꼴 변경(`?? null` → `?? undefined`)을 아무 테스트도 안 본다는 것을 잡아 단언을 더했다.

### 파일 이름 규약 — 정하면서 그 위험을 직접 밟았다 (#398)

저장소에 파일 이름 규약을 적은 정본이 없었다. 부르는 이름이 있으면 그 이름을 쓴다 — 컴포넌트(`.tsx`)는 PascalCase, 훅은 그 훅 이름과 같은 camelCase, 나머지는 kebab-case다. 판정은 이름 꼴이 아니라 파일이 무엇을 담았는지로 한다. 바뀐 파일은 다섯뿐이었다 — 저장소 143개는 이미 kebab이었고 어긋난 것은 컴포넌트 하나와 앞 PR에서 camelCase로 만든 넷뿐이다.

PascalCase를 고르면 대소문자 차원이 들어온다. macOS·윈도우는 대소문자를 안 구별해서 `Foo.ts`와 `foo.ts`가 OS에는 한 파일, git에는 두 파일이 된다. 그 검사(`caseCollisions`)가 실제로 무는지 확인하려다 `rm`이 추적 중인 파일(`NotBuiltYet.tsx`)을 지웠다 — `cp`가 대소문자만 다른 이름을 「동일 파일이라 복사 안 함」으로 건너뛰고, 그다음 `rm`이 원본을 지운 것이다. `git checkout`으로 되돌렸고 알아챈 것은 바로 다음 명령이 그 파일을 읽어서였다. [관찰 017](../observations/017-case-insensitive-rm-deleted-a-tracked-file.md)에 남겼다 — macOS에서는 케이스 충돌 자체를 실물로 재현할 수 없어 이 검사는 리눅스 CI에서만 문다.

`src/app/`은 규약 밖으로 뒀다 — Expo Router가 그 디렉터리를 라우팅 뿌리로 읽고 파일 이름이 그대로 URL이 된다(`.expo/types/router.d.ts`의 경로 유니언으로 확인). `src/app/check-in.tsx`를 옮기면 종이 QR에 실린 `/check-in?c=<코드>` 주소가 죽는다.

## PR #400 — e2e 러너를 Maestro로 정하고 게이트를 다시 문다

`e2e-runner` task를 닫는다. ADR-011이 「Maestro 또는 Detox」로 열어둔 자리를 [ADR-013](../2-design/adr/ADR-013-e2e-runner-maestro.md)이 닫는다.

### 왜 Maestro인가

근거 셋이다. Expo가 자기 Detox 템플릿을 지우고 공식 e2e 문서로 Maestro를 든다 — SDK를 올릴 때마다 러너가 못 따라오면 그 비용을 전부 우리가 진다. Detox는 `expo prebuild`로 네이티브 디렉터리를 저장소에 꺼내라고 해서, ADR-011이 고른 관리 흐름의 이점을 e2e 하나 때문에 되돌리는 거래가 된다. Detox의 딥링크에는 안드로이드·iOS 양쪽에 열린 버그가 있는데, 우리 여정의 시작점이 종이 QR과 OAuth 콜백이라 둘 다 딥링크를 탄다.

뒤집을 수 있었던 자리 하나는 확인하고 닫았다. 앱을 죽이고 상태를 남긴 채 다시 띄우는 동작이 관건이었다 — 「앱을 다시 연 뒤 상태가 끊긴다」가 e2e로 배정되는 리스크의 절반이다. Maestro의 `stopApp`·`killApp`이 있고, `launchApp`에 `clearState`를 안 주면 상태를 지우지 않는 차가운 시작이라고 공식 문서가 적는다.

받아들인 비용도 셋이다. YAML은 타입 검사를 안 받는다(spec 스물에 걸쳐 「검증 층: e2e」가 95개다). 앱 내부를 못 봐서 세션을 코드로 심을 수 없다. CLI가 pnpm 밖이라 버전이 `pnpm-lock.yaml`에 안 박힌다.

### 게이트가 다시 무는 방식

`tdd-guard-e2e.py`를 셋 고쳤다. 찾는 짝이 `.yaml`로 바뀐다(`tests/e2e/<이름>.spec.ts` → `tests/e2e/<이름>.yaml`). 「`tests/e2e/`가 없으면 아무것도 안 막는다」는 면제를 지웠다 — 러너를 안 고른 동안의 임시 조치였고, 남겨두면 디렉터리를 지워 게이트를 끄는 자리가 된다. `.tsx` 판정을 `spec_name()` 맨 앞으로 올려 `.tsx`만 화면으로 본다 — 관찰 006이다. `src/screens/`와 `src/app/` 두 분기가 이제 같이 물려받고, 슬라이스 이름은 디렉터리일 때만 뽑아서 `src/screens/<이름>/model/*.ts`와 그 unit 테스트가 통과한다. 짝 테스트는 24개에서 27개로 늘었다 — 「찾는 짝은 YAML이다」, 「screens 아래 순수 `.ts`는 화면이 아니다」, 그리고 자동 리뷰가 잡은 것 하나가 더해졌다.

자동 리뷰가 게이트를 빠져나가는 자리 하나를 잡았다. 슬라이스 이름을 `len(parts) > 3`일 때만 뽑게 좁히는 과정에서 `src/screens/Cart.tsx`처럼 디렉터리를 안 끼고 바로 선 화면이 `None`으로 떨어져 게이트 밖으로 나갔다. 면제를 지운 이유와 같은 종류의 구멍이라 그대로 둘 수 없었다. 그런 자리는 `src/app/` 분기처럼 제 파일명을 이름으로 써서 `tests/e2e/Cart.yaml`을 요구하게 고쳤다. FSD에서 화면은 `src/screens/<슬라이스>/` 디렉터리라 실제로 그런 파일이 설 자리는 아니지만, 서면 조용히 통과하는 것보다 무는 쪽을 골랐다.

### 첫 플로우는 하나고, 한 번도 안 돌렸다

`tests/e2e/login.yaml` — 세션 없는 차가운 시작이 로그인 화면에 서는지 본다. `clearState`가 안드로이드 앱 데이터를, `clearKeychain`이 iOS 키체인을 지운다 — expo-secure-store가 iOS에서 키체인에 세션을 넣으니 둘 다 필요하다. 나머지 라우트는 플로우가 없어서 고치려 들면 훅이 막는다. 그것이 이 task가 세운 압력이고, 막히면 그 화면의 플로우를 먼저 쓰는 것이 답이다.

이 플로우는 실제로 돈 적이 없다. Maestro는 기기·시뮬레이터에 올라간 설치 가능한 앱을 `appId`로 찾아 띄우는데 그 EAS 빌드가 없다. `pnpm e2e`는 명령으로만 서 있고, CI도 같은 이유로 e2e 단계를 못 세웠다 — 빌드 단계가 EAS 설정과 같이 서고 e2e는 그 뒤에 붙는다. 세션을 심는 방법도 안 정했다. Maestro가 앱 내부를 안 봐서 코드로 넣을 수 없고 웹 시절 쿠키 헬퍼는 같이 걷혔다 — 딥링크·화면 조작·테스트용 경로 중에서, 로그인 뒤 화면에 처음 닿는 task가 고른다.

### 영향 확인이 plan을 붙들었다

`expo-scaffold.md`가 `sources`로 ADR-011을 들고 있어서, 이 PR이 그 ADR의 러너 줄을 고치자 영향 확인 게이트가 막았다. 같은 PR에서 잇는 쪽을 골랐다 — plan이 e2e를 두 자리에서 「러너를 안 정한다」로 적고 있었고, 그대로 두면 이미 닫힌 결정을 열린 것처럼 읽게 된다. 「검사판이 Jest로 옮겨진다」의 `tests/e2e/` 줄과 AC-12 뒤 「e2e가 한동안 없다」를 과거형으로 고치고 무엇이 그 자리를 닫았는지 적었다. AC와 완료 조건은 안 건드렸다 — `expo-scaffold`는 여전히 `active`고 남은 것은 실기기 확인이다.

### 검증

`pnpm lint`·`pnpm typecheck`·`pnpm test`(61 suites · 723 tests)·`pnpm format:check`가 초록이다. `pnpm e2e`는 못 돌렸다 — 올릴 앱이 없다. `doc-links` 테스트가 ADR-013의 끊긴 앵커(`execution.md#e2e`)를 한 번 잡았다 — 절 이름이 `pnpm e2e`로 바뀐 것을 문서가 안 따라간 자리였고 고쳐서 초록이 됐다.

## PR #404 — lint 규칙 표를 저장소로 들이고 검사가 그 표를 읽게 한다

## PR #405 — 승인 대기 넷째 줄을 1차에서 뺀다

승인 대기 화면의 넷째 도는 문구 「못 가는 날은 교대를 부탁해요」를 닫았다. 그 줄이 소개하는 교대는 2차([roadmap](../1-plan/roadmap.md#릴리스-목록))고, 1차 기능 중 그 자리에 세울 것이 없다 — 근무 취소 요청이 있지만 앱을 처음 보는 사람에게 첫 화면에서 「취소」를 먼저 말하는 것이 어긋난다. 소개 문구가 셋이면 짧아 보인다는 이유로 없는 기능을 넣거나 말을 늘리는 쪽이 더 나빴다. 1차에는 다른 문구로 메우지 않고 셋만 돌린다.

## PR #407 — 관리자 홈 시안을 갈라 문서 옆에 세운다

관리자 홈의 짝 시안이 문서 옆에 섰다 — [`admin-home.sian.html`](../2-design/system/screens/admin-home.sian.html)이 목업 여섯이고, 원본 `schedule-admin.sian.html`에서 01절을 빼고 02~10을 01~09로 내렸다. 잘라내지 않은 이유는 #406과 같다 — 열 절이 CSS 한 덩이를 나눠 써서 마크업만 들어내면 `.tile`·`.todaystat`·`.vacancy`·`.minical` 같은 규칙이 어느 쪽에 남아야 하는지가 안 정해진다. `sian-writer`가 새 문서를 읽어 새로 그렸고, 원본에서는 쓰는 곳이 없어진 규칙 서른다섯 줄을 걷었다.

감사가 문서에 없는 조합을 잡았다. 확정 전 목업에 빈 자리 카드와 오늘 현황 실값이 같이 서 있었는데, 문서 상태 표는 카드의 조건을 「확정 뒤 예식이 사흘 안인데 빈 자리가 남았다」로 못박고 문안 표는 오늘 현황이 확정 전에는 「–」라고 적는다 — 두 조항을 같이 읽으면 근무표 상태 하나가 그 목업의 나머지를 다 정한다. 미니뷰의 「오늘」 표식까지다(확정 전 시나리오가 9월 29일이라 10월 미니뷰에는 오늘이 없다). 목업을 상태별로 다시 짜서 여섯이 됐다 — 정상 · 빈 자리 둘 · 만드는 중 · 아직 없음 · 오늘 근무가 없다 · 기본값 시트. 「오늘 근무가 없다」는 처음 「아직 없음」에 흡수돼 있었는데, 문서의 조건은 「그날 배정이 없다」뿐이라 확정 뒤인 달에도 선다는 것이 드러나 따로 뺐다. 재감사에서 어긋남이 없었다.

문서가 안 정한 자리 셋을 시안이 메웠고 캡션에 판단이라고 밝혔다 — 열째 가는 선의 위아래 여백(첫째 선과 대칭), 확정 전 오늘 현황에서 보조 줄과 띠를 통째로 뺀 것, 「오늘 근무가 없다」 목업의 날짜(10월 6일 — 문서가 고정한 날은 9월 29일과 10월 8일뿐이다).

`admin-home.md`를 `sources`로 드는 문서 둘(`attendance-qr.md`·`schedule-admin.md` plan)은 판정이 영향 없음이다 — 이 PR이 고친 것은 본문 한 문장(「움직이는 모습은 옆의 시안을 열어 본다」가 가리키는 곳)뿐이고, 두 문서가 인용하는 절은 안 바뀌었다.

`pnpm test`(61 suites, 724 tests) · `pnpm format:check` 통과. 시안 태그 균형은 `tests/lint/sian-html.ts`가 본다.

이 PR에 handoff.md 갱신도 같이 실렸다 — 회차 중간이라도 작업이 끝나면 총괄이 「다음 작업」을 갱신한다는 규칙대로, 시안을 그리는 동안 밀린 #404~#406을 같이 적었다.
