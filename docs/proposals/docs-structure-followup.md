# docs 구조 후속 개선 제안

**채택됐다.** 8개 항목 전부다. 갈림길이 있던 둘은 이렇게 정했다 — 2번은 `profiles.photo_url`을 유지하고 본인 수정은 `update_my_photo()` 함수로(직접 쓰기 예외는 `profile_private` 하나 그대로), 3번은 「다음」의 정의를 유지하고 행을 갈라 옮기는 쪽으로. 8번은 지금 쓰지 않고 첫 출시 준비 task에 건다. 실행은 아래 [적용 순서](#적용-순서)의 네 묶음이 PR 하나씩이고, 갱신된 정본은 각 PR이 링크한다.

최초 검토는 2026-09-14 기준이다. 검토 대상은 `a570f17`의 `docs/`와 문서를 읽거나 갱신하는 검사·에이전트 정의문이다. 최초 제안서 추가 전 파일은 146개다 — Markdown 131개, 시안 HTML 12개, `.gitkeep` 3개. 전체 파일 구성과 안내 문서, 작업 보드, 최근 개편 계획을 확인하고 관련 본문을 대조했다. 모든 화면의 시각 설계나 업무 규칙을 전수 감사한 결과는 아니다.

**제안 상태다.** 이 문서는 후속 수정 후보와 완료 기준을 담는다. 제안서의 보관 위치는 [ADR-008](../2-design/adr/ADR-008-proposals-and-implementation-plans.md)로 정했고, 아래 8개 항목은 별도 검토 대상이다. 각 항목의 구현 착수나 제품 정책 변경을 확정하지 않는다. 이전 [문서 구조 계획](../3-build/plans/docs-structure.md)은 완료된 기록으로 보존한다.

## 판단

**SDLC 단계 구성을 유지하고, 문서 사이의 내용 불일치와 작업 연결을 먼저 고치는 것을 권한다.** 단계별 구분과 설계의 세 갈래는 역할이 분명하다. 최근 개편으로 루트 진입점, 디자인 색인, 긴 문서 목차, 목표 설계 표시, CHANGELOG 갱신도 갖춰졌다. 같은 개편을 다시 제안할 필요는 없다.

지금 남은 큰 문제는 파일의 위치보다 읽은 뒤의 판단이다. 1차 작업이 2차 미정에 묶이고, 같은 사진 필드의 저장 위치와 수정 방법이 다르며, 바로 착수할 수 있다는 목록에 준비가 덜 된 작업이 있다. 기존 문서 검사가 모두 통과해도 이런 문제는 남는다.

## 유지할 구조

```text
docs/
  handoff.md       현재 상태와 다음 첫 수
  backlog.md       작업 상태와 순서
  CHANGELOG.md     변경 색인
  log/            회차 기록
  observations/   작업 규칙·도구의 마찰 기록
  proposals/      여러 단계에 걸친 변경 방향의 검토 제안
  1-plan/         제품 범위, 릴리스, intent
  2-design/       domain, architecture, design-system, ADR, spec
  3-build/plans/  기능 구현 계획과 비기능 task 문서
  4-test/         검증 기준과 실행 안내
  5-deploy/       배포 준비와 절차
  6-maintain/     운영 절차와 지표
```

문서의 전체 지도는 [CLAUDE.md](../../CLAUDE.md#문서-지도)에 두고, 각 폴더의 README는 자기 갈래를 안내한다. 별도 문서 사이트는 필요하지 않다. 여러 단계에 걸친 검토 제안은 [proposals](README.md)에 두고, 채택된 변경의 실행 계획을 `3-build/plans/`에 둔다.

## 1. 릴리스 범위와 선행 조건을 맞춘다

**근거.** [로드맵의 릴리스 목록](../1-plan/roadmap.md#릴리스-목록)은 교대와 관리자 공지를 2차로 미룬다. 그런데 [backlog의 대기](../backlog.md#대기)는 알림 작업에 교대 승인 화면의 미정을 붙이고, [handoff의 막는 결정](../handoff.md#막는-결정)은 이를 알림 task 전에 닫으라고 한다. [알림 이동 경로](../2-design/modules/notification/design.md#ui-연결)도 여러 릴리스의 알림을 한 표에 둔다. 현재 알림 task가 1차만인지 전체인지 불명확하다.

**제안.** 기존 로드맵을 기준으로 알림 작업의 범위를 표시한다. 1차 알림과 공통 전송 기반, 2차 교대·공지 작업을 구별하고, 교대 승인 화면의 미정은 교대 알림 작업에 연결한다. 공통 기반 때문에 선행 설계가 실제로 필요하다면 그 이유를 plan에 적는다. 화면 목적지가 미정이라는 이유만으로 알림 전체를 대기시키지 않는다. 릴리스 범위를 바꾸기로 했다면 로드맵을 먼저 갱신한다.

화면에도 같은 경계가 필요하다. [로그인 페이지 문서](../2-design/modules/account/screens/login.md)는 승인 대기 소개 문구에 「못 가는 날은 교대를 부탁해요」를 넣는다. 1차에서 보여줄 문구와 후속 릴리스용 문구를 구별하고, 변경 시 [로그인 시안](../2-design/modules/account/screens/login.sian.html)도 맞춘다. 이미 구현된 문구의 변경은 해당 화면 task에 연결한다.

**수정 대상.** `docs/backlog.md`, `docs/handoff.md`, `docs/2-design/architecture/flows/notification.md`, `docs/2-design/design-system/pages/login.md`와 짝 시안. 릴리스 범위를 변경할 때만 `docs/1-plan/roadmap.md`도 수정한다.

**완료 기준.** 알림 작업을 읽으면 어느 릴리스까지 구현하는지 알 수 있다. 교대 승인 화면이 미정이어도 1차 알림의 착수 가능 여부를 별도로 판단할 수 있다. 1차 화면은 아직 제공하지 않는 기능을 이용할 수 있다고 소개하지 않는다.

## 2. 사진 필드의 저장 위치와 수정 경로를 맞춘다

**근거.** [계정 데이터 모델](../2-design/modules/account/design.md)의 13행은 `photo_url`을 `profiles`에 둔다. 바로 아래 15행은 연락처·사진을 `profile_private`에서 직접 갱신한다고 한다. [계정 API](../2-design/modules/account/design.md#행위별-구현-계약)도 같은 갱신 방법을 적지만, 제시된 `profile_private(profile_id, phone, birth_date, gender)`에는 사진 필드가 없다. [system/data-access.md](../2-design/system/data-access.md#네-원칙) 역시 직접 쓰기 예외를 연락처·사진으로 설명한다.

**제안.** 사진 URL이 속하는 표와 본인 수정 경로를 먼저 확정한다. 현재 모델대로 `profiles.photo_url`을 유지한다면 사진을 수정하는 함수 또는 제한된 쓰기 권한을 명시하고, 「직접 쓰기는 `profile_private` 하나뿐」이라는 규칙과 맞춘다. 사진을 다른 표로 옮긴다면 이름·사진을 읽는 조회와 공개 범위도 함께 설명한다. 이미지 파일의 저장소 선택과 URL 컬럼의 소유 표는 별개 질문으로 다룬다.

**수정 대상.** `docs/2-design/architecture/data-model/account.md`, `docs/2-design/architecture/data-model/README.md`, `docs/2-design/architecture/api/account.md`. 확정된 계약은 계정 데이터 구조 전환 plan이 참조한다.

**완료 기준.** 사진을 읽는 표, 쓰는 경로, 수정 가능한 사람이 문서마다 같다. 후속 구현에서는 본인의 사진 변경 성공과 다른 사람의 변경 거부를 integration 테스트로 확인한다. 이 제안서에서 DB나 권한을 변경하지는 않는다.

## 3. 준비된 작업과 준비할 작업을 구별한다

**근거.** [backlog](../backlog.md)는 「다음」을 바로 잡을 수 있는 목록으로 정의한다. 실제 목록에는 「plan을 쓴 뒤 잡는다」, 「계정 데이터 구조 뒤」인 작업이 함께 있고, 네 항목 모두 spec이나 plan 링크가 없다. 같은 파일은 완료 조건의 정본을 spec·plan으로 정한다. 현재 목록은 착수 가능한 보드보다 앞으로 할 일의 순서에 가깝다.

**제안.** 현재 정의를 유지한다면 계획 작성부터 작업으로 드러낸다. 당장 할 수 있는 스파이크는 결과 기록 위치와 판정 기준을 담은 작은 plan을 연결한다. 계정 데이터 구조 전환처럼 준비가 필요한 구현은 plan과 완료 조건을 만든 뒤 「다음」으로 올린다. 선행 작업이 남은 항목은 「대기」에 두고 선행 작업을 링크한다. 단순히 순서 목록으로 운영하려면 「다음」의 정의를 바꾸고 각 행에 착수 조건을 명시해야 한다. 둘 중 하나로 통일한다.

`handoff.md`는 선택된 첫 작업만 가리키고, 전체 순서를 다시 나열하지 않는다. 새 기능은 기존 spec 승인 절차를 따르고, 비기능은 plan에 완료 조건을 둔다.

**수정 대상.** `docs/backlog.md`, `docs/handoff.md`, [구현 안내](../3-build/README.md). 새로운 plan은 작업 범위를 정할 때 만든다. 지금 빈 파일을 일괄 생성할 필요는 없다.

**완료 기준.** 「다음」의 첫 항목에서 완료 조건과 결과를 남길 곳으로 이동할 수 있다. 선행 작업 때문에 시작할 수 없는 구현을 착수 가능한 작업으로 표시하지 않는다. handoff와 backlog가 같은 첫 작업을 가리킨다.

## 4. 디자인 진행 규칙과 완료 표현을 맞춘다

**근거.** [로드맵의 순서 규칙](../1-plan/roadmap.md#순서-규칙)은 1차 화면 디자인을 전부 끝낸 뒤 구현한다고 정했다. 반면 [디자인 시스템의 순서](../2-design/design-system/README.md#순서)는 기능 개발과 디자인을 병렬로 진행한다고 한다. 두 문서가 적용 시기나 예외를 설명하지 않아 착수 기준이 다르게 읽힌다.

[handoff](../handoff.md#지금-상태)는 「설계가 다 섰다」고 요약하지만, [login.md의 미정](../2-design/modules/account/screens/login.md#아직-안-정한-것)에는 차단 화면의 모습과 생년월일 시트 등이 남아 있다. 1차 포함 여부와 차단 조건을 함께 읽어야 완료를 판단할 수 있다. 수량 표현도 점검할 필요가 있다. handoff는 화면 열한 개라고 쓰고 페이지 문서와 시안은 각각 12개다. 파일 하나가 여러 화면을 담으므로 파일 수와 화면 수를 혼용하지 않아야 한다. [system/navigation.md의 세 층](../2-design/system/navigation.md#세-층)은 게이트를 「셋」이라고 쓰고 경로 네 개를 나열한다.

**제안.** 진행 순서는 로드맵을 정본으로 삼고 디자인 안내가 링크한다. 병렬 진행을 허용하는 적용 범위가 있다면 그 범위만 적는다. 완료 요약은 「주요 설계 문서 작성 완료, 관련 미정은 각 작업 착수 전 해결」처럼 실제 상태를 나타낸다. 미정마다 관련 릴리스와 막는 작업을 연결하되, handoff에 전체 미정 목록을 복제하지 않는다. 수량은 필요한 경우에만 단위를 붙여 쓴다.

**수정 대상.** `docs/2-design/design-system/README.md`, `docs/handoff.md`, `docs/2-design/architecture/flows/README.md`. 개별 미정의 작업 연결이 필요하면 해당 페이지 문서와 backlog도 함께 수정한다.

**완료 기준.** 어느 문서를 먼저 열어도 같은 구현 시작 기준을 얻는다. 「설계 완료」와 「화면 상태 일부 미정」이 설명 없이 공존하지 않는다. 게이트 경로 수가 본문과 일치한다.

## 5. 현재 문서와 완료된 계획을 구별한다

**근거.** [대시보드 spec](../2-design/spec/dashboard.md#완료-조건)은 선행 작업 넷이 「아직 보드에 없다」고 적는다. 지금은 [backlog의 대기](../backlog.md#대기)에 모두 있다. spec의 형식 개편은 대시보드 착수 시점으로 미뤘지만, 이 상태 설명은 이미 낡았다.

완료된 plan도 현재 지시처럼 읽힐 수 있다. [세션 기반 계획](../3-build/plans/session-foundation.md)은 ADR-002의 옛 spec 승격 기준을 설명하지만, [ADR-005의 사슬](../2-design/adr/ADR-005-sdlc-stage-folders-and-artifact-chain.md#사슬)은 그 기준을 대체했다. [서버 클라이언트 정리 계획](../3-build/plans/supabase-client-entry.md)의 서버 승인 게이트는 이후 클라이언트로 이동하는 [목표 설계](../2-design/modules/account/design.md)와 구별해야 한다.

**제안.** 대시보드 spec의 낡은 한 문장만 현재 backlog 링크로 바꾸고, 전체 형식 개편은 기존 결정대로 착수 때 한다. 완료 plan의 본문은 당시 기록으로 보존한다. 상단에 「완료된 작업의 당시 계획이며, 현재 규칙은 연결된 정본을 따른다」는 짧은 안내와 완료 기록 링크를 붙인다. 구현 상태는 계속 backlog가 맡고, 모든 문서에 별도의 진행률·상태 필드를 만들지 않는다.

**수정 대상.** `docs/2-design/spec/dashboard.md`, `docs/3-build/README.md`, 현재 지시로 오해할 수 있는 완료 plan부터. 시작 후보는 `session-foundation.md`, `supabase-client-entry.md`, 기존 `docs-structure.md`다.

**완료 기준.** 대시보드 선행 작업의 존재 여부가 보드와 일치한다. 완료 plan에서 현재 정본과 완료 기록으로 이동할 수 있다. 과거 intent·plan을 소급 작성하거나 역사 본문을 새 설계로 덮어쓰지 않는다.

## 6. 관찰 집계와 handoff 작성 규칙을 맞춘다

**근거.** [관찰 로그의 상태와 마감](../observations/README.md#상태와-마감)은 같은 target의 열린 관찰 3건을 handoff의 「열린 결정」에 올리라고 한다. [session-recorder](../../.claude/agents/session-recorder.md)의 「관찰 로그」도 같다. 그러나 같은 정의문의 「handoff.md」는 절을 넷으로 제한하고, 「막는 결정」에는 다음 첫 수를 막는 것만 넣으라고 한다. 이전 handoff 작성 방식이 관찰 집계 지시에 남아 있다.

**제안.** 관찰 원문과 상태는 `observations/`에 유지한다. 3건이 모이면 기록자가 결과에 판정 후보와 관찰 링크를 보고하고, 지속적으로 추적할 후보는 backlog의 「후보」에 한 번만 연결한다. 다음 작업을 실제로 막는 경우에만 handoff의 「막는 결정」에 적는다. 기록자가 개선안 채택 여부까지 결정하지 않는 경계는 유지한다.

**수정 대상.** `docs/observations/README.md`, `.claude/agents/session-recorder.md`. 두 지시를 같은 변경에서 맞춘다.

**완료 기준.** 다음 첫 수와 무관한 동일 target 관찰 3건이 생겨도 handoff에 새 절을 만들지 않는다. 후보는 유실되지 않고 반복 마감에도 중복 등록되지 않는다. 관찰 판정의 주체가 바뀌지 않는다.

## 7. 문서 간 이동을 링크로 만들고 검사와 함께 바꾼다

**근거.** [CLAUDE.md의 지도](../../CLAUDE.md#문서-지도)와 [기획 안내](../1-plan/README.md), [설계 안내](../2-design/README.md)는 상당수 경로를 인라인 코드로 적는다. 검색은 가능하지만 클릭해서 이동할 수 없다. [system/architecture.md](../2-design/system/architecture.md)는 한 도메인을 보려면 네 폴더를 오간다는 비용을 이미 인정한다. 하위 README는 각 관심사를 안내하지만, 계정 하나의 도메인·데이터·API·런타임·흐름을 한 줄로 연결하는 입구는 없다.

**제안.** 파일을 이동하지 않고 안내 문서의 실존 경로를 상대 링크로 바꾼다. 아키텍처 README에는 도메인 여섯 × 관심사 네 갈래의 링크 표를 둔다. 예를 들어 계정 행은 [domain](../2-design/modules/account/README.md) · [data-model](../2-design/modules/account/design.md) · [api](../2-design/modules/account/design.md) · [runtime](../2-design/modules/account/design.md) · [flows](../2-design/modules/account/design.md)로 이동한다. 표에는 규칙이나 구현 상태를 복제하지 않는다. 다른 README에 같은 표를 다시 만들지 않는다.

**검사도 같이 수정해야 한다.** [doc-map.ts](../../tests/lint/doc-map.ts)는 「문서 지도」 불릿의 코드스팬에서 `docs/` 경로를 추출한다. 일반 링크로만 바꾸면 검사 대상이 사라져 잘못된 지도도 통과할 수 있다. 링크 목적지를 읽도록 검사와 짝 테스트를 같은 변경에 포함한다. [doc-links.ts](../../tests/lint/doc-links.ts)는 `docs/`와 루트 README만 검사하므로, 지도를 링크로 바꾸면 `CLAUDE.md`도 범위에 넣는다.

존재하지 않는 링크 검사와 지도에서 빠진 항목 검사는 다르다. 누락 검사 확대가 필요하면 우선 지도에 명시하기로 한 단계 폴더와 아키텍처 도메인 파일에 한정한다. 로그와 모든 plan까지 전역 목록에 올리도록 강제하지 않는다. 기존 [design-map.ts](../../tests/lint/design-map.ts)는 페이지 목록 누락을 이미 잡으므로 같은 검사를 다시 만들 필요가 없다.

**수정 대상.** `CLAUDE.md`, `docs/1-plan/README.md`, `docs/2-design/README.md`, `docs/2-design/architecture/README.md`, `tests/lint/doc-map.ts`·짝 테스트, `tests/lint/doc-links.ts`·짝 테스트.

**완료 기준.** 지도에서 실제 파일과 폴더로 이동할 수 있다. 링크 형식으로 작성한 잘못된 경로도 검사에 걸린다. 도메인 하나의 네 설계 문서를 한 입구에서 열 수 있다.

## 8. 출시 전에 필요한 운영 문서의 작성 시점을 정한다

**근거.** [배포 안내](../5-deploy/README.md)는 배포가 다가오면 채우도록 정해 적절한 시점을 둔다. 반면 [운영 안내](../6-maintain/README.md)는 운영이 시작되면 채운다고 한다. 이 순서라면 첫 배포 장애를 확인하거나 되돌릴 방법을 정하지 않은 채 운영을 시작할 수 있다. [성공 지표](../1-plan/metrics.md)는 의미와 목표 결정 시점을 정했지만, 분모·집계 기간·자료 출처가 아직 구체적이지 않다.

**제안.** 첫 출시 준비 작업의 완료 조건에 최소 운영 안내를 포함한다. 배포 문서는 적용·확인·되돌리기 순서와 환경별 설정 위치를 다루고, 운영 문서는 장애 확인 위치, 대응 담당, 복구 후 확인 방법을 다룬다. 실제 배포 환경을 정한 뒤 작성하고, 지금 플랫폼이나 상세 운영 체계를 미리 확정하지 않는다.

지표는 측정 구현 전에 집계 기준을 정한다. 출근 인증률은 어떤 배정을 분모로 세는지, 어느 기간인지, 취소·미확정 배정을 어떻게 다루는지 필요하다. 알림은 전송 성공과 기기 수신·사용자 열람 중 무엇을 측정하는지 구별해야 한다. [알림 API](../2-design/modules/notification/design.md)가 기록하는 `pushed_at`을 사용자 도달로 간주할 수 있는지는 별도 확인 대상이다. 관리자 시간 절감에 필요한 도입 전 측정도 첫 사용 전에 해야 한다.

**수정 대상.** `docs/5-deploy/README.md`, `docs/6-maintain/README.md`, `docs/1-plan/metrics.md`. 상세 절차가 커질 때만 해당 폴더에 별도 문서를 만든다.

**완료 기준.** 첫 운영 전에 배포 실패 시 되돌릴 방법과 확인 담당을 찾을 수 있다. 같은 자료를 받은 두 사람이 같은 지표 값을 계산할 수 있다. 아직 수집하지 못하는 값은 측정 가능하다고 쓰지 않는다.

## 적용 순서

1. **구현 전 정합성:** 1~3번을 먼저 다룬다. 릴리스 범위와 계정 계약을 정리한 뒤, 각 작업의 완료 조건과 착수 순서를 보드에 연결한다.
2. **문서 운영:** 4~6번을 한 묶음으로 정리한다. 정본과 이를 요약·갱신하는 문서를 같은 변경에서 맞춘다.
3. **탐색과 검사:** 7번은 링크 변환과 검사 수정을 같은 변경에 담는다. 테스트 입력 형식을 바꾸므로 문서만 먼저 바꾸지 않는다.
4. **출시 준비:** 8번은 첫 배포 준비 작업에 연결한다. 다음 데이터 작업의 선행 조건으로 올리지 않는다.

기존 backlog의 디자인 값·시안 불일치, WebKit 추가, 캔버스 소스 보관 등은 이미 이름이 있는 후보다. 이번 제안에 별도 작업으로 중복 등록하지 않는다. 긴 페이지 문서는 최근 추가한 내부 목차를 유지하고, 파일 분할은 별도 필요가 확인될 때 검토한다.

## 검증과 한계

검토 시작 시 저장소의 기존 검사 함수 다섯을 실행했고 모두 위반 0건이었다. 상대 링크·앵커, CLAUDE 문서 지도 경로, 이전 경로 잔존, 디자인 페이지 색인 누락, 로그에서 언급한 PR의 CHANGELOG 누락을 확인했다. 이는 각 검사가 다루는 범위의 결과이며, 문서의 의미 일치나 전체 이력의 완전성을 보장하지 않는다.

최초 검토 당시에는 작업 폴더에 의존성이 설치되어 있지 않아, Node 22의 TypeScript 실행 기능으로 기존 검사 모듈을 임시 폴더에 복사해 실행했다. 검사 로직은 그대로 사용하고 내부 경로 별칭만 로컬 import로 치환했다. 새 정규식이나 별도 Markdown 파서로 대체하지 않았다. `pnpm test` 전체, 앱 빌드, integration·e2e는 실행하지 않았다. 외부 서비스 사양, 외부 링크 접속, 실제 시안 화면도 검증 범위에 포함하지 않았다.

최초 문서 추가 후에도 같은 다섯 검사에서 위반 0건을 확인했다. 제안서를 `proposals/`로 옮기는 변경에서는 상대 링크를 새 위치에 맞추고, 정식 검사 결과를 해당 PR에 기록한다. 후속 수정에서는 의미 정합성을 해당 정본과 대조하고, 지도 검사 코드를 변경할 때는 관련 Vitest 테스트와 저장소의 필수 CI 검사를 실행한다.
