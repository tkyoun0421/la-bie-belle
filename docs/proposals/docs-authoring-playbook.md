# SDLC 문서의 템플릿과 절별 작성 방법을 정한다

## 결정 기록

2026-09-14에 전부 채택했다. 「판단할 항목」 다섯은 모두 추천안대로다 — 작성법은 단계 README가 소유하고 틀은 그 안의 코드 블록이며, 새 문서와 활성 문서부터 적용하고, `sources`와 고정 ID로 참조하며, 문제·판정 사례·행위 계약·화면 상태·실행 결과를 구별하고, 계정을 시범으로 전개한다. 근거는 [ADR-010](../2-design/adr/ADR-010-authoring-guides-in-stage-readmes.md), 실행은 [plan](../3-build/plans/docs-authoring-playbook.md)이다.

채택하며 달리 정한 것은 넷이다. 알림 규칙의 접두는 `NOT`이 아니라 `NTF`다 — [상위 제안](docs-sdlc-coherence.md)의 실행이 먼저 박았다. `evidence/`·`releases/`·`incidents/` 폴더는 첫 기록이 생길 때 만들고 그 전에는 단계 README의 문서 지도가 자리만 든다 — 빈 파일을 미리 만들지 않는다는 2.2절을 따른다. 상위 제안 plan의 묶음 D(대시보드 추출)·E(검증·배포·운영과 상태 소유권)·F(검사와 전파 확인)는 이 plan이 이어 나른다 — 옮긴 문서를 틀에 맞춰 다시 쓰는 일과 한 번에 하기 위해서다. 활성 설계 문서를 틀에 맞춰 다시 쓸 때 문장은 재구성해도 결정 내용은 바꾸지 않고, 판정 예시·상태 전이·계약 표처럼 규칙에서 도출하는 표는 총괄이 한 줄씩 확인한다 — 규칙 문서와 design은 총괄이 쓴다는 ADR-004의 조항을 지키는 방식이다. `modules/README.md`·`design.md`의 마지막 절 이름은 기존 문서와 링크가 쓰는 「아직 안 정한 것」을 유지한다.

아래 본문은 검토 당시 그대로다. 본문이 든 경로 중 상위 제안의 실행으로 옮겨진 것은 링크만 새 자리로 고쳤다.

2026-09-14, `55c85a5` 기준 제안이다. [SDLC 문서 구조 제안](docs-sdlc-coherence.md)이 정한 파일별 책임과 절 순서를 바탕으로, 각 절을 실제로 채우는 방법을 구체화한다. 여섯 단계, 업무별 설계, 동일 작업 슬러그의 intent→spec→plan, spec 승인, TDD를 유지한다.

**문서 종류마다 「언제 쓰는가 → 복사할 틀 → 절을 채우는 질문 → 검토 기준」을 제공한다.** 아래 경로는 상위 제안의 목표 경로다. 아직 없는 경로는 코드로 표기하고, 현재 근거만 실제 링크로 연결했다. 템플릿 안의 `&lt;…&gt;`는 작성할 값이며 실제 제품 결정·승인·검증 결과가 아니다. 이 문서의 작성으로 기존 문서 형식이나 도구가 바뀌지는 않는다.

## 1. 작성 기준을 둘 곳

현재 [2-design 안내](../2-design/README.md#spec)는 spec의 네 요소를, [화면 작성 안내](../2-design/README.md#화면-문서)는 화면 내부 틀을 설명한다. [3-build 안내](../3-build/README.md)는 기능 계획과 비기능 task를 구별한다. 하지만 이 안내들을 읽어도 규칙 한 줄을 판정 예시로 바꾸거나, 완료 조건을 검증에 연결하는 방법은 작성자가 다시 정해야 한다. [테스트 전략](../4-test/strategy.md)의 세부 기준도 아직 에이전트 정의문에 나뉘어 있다.

추천은 **단계 README가 자기 문서의 작성법을 소유하고, 템플릿은 그 안의 코드 블록으로 제공하는 방식**이다. 긴 공통 설명은 `docs/README.md`에 한 번만 두고 각 작성법에서 링크한다.

| 작성 기준의 자리 | 소유할 내용 |
| --- | --- |
| `docs/README.md` | 문서 소유권·참조·미정·변경 전파의 공통 작성법, backlog·handoff·log·CHANGELOG의 틀 |
| `1-plan/README.md` | PRD·로드맵·시나리오·지표·intent의 틀과 작성법 |
| `2-design/README.md` | system·modules·화면·spec·ADR의 틀과 작성법 |
| `2-design/design-system/README.md` | 토큰·foundation·컴포넌트·문안 기준의 작성법 |
| `3-build/README.md` | 기능 plan과 비기능 plan의 틀과 작성법 |
| `4-test/README.md` | strategy·execution·evidence의 틀과 작성법 |
| `5-deploy/README.md` | environments·procedure·release의 틀과 작성법 |
| `6-maintain/README.md` | monitoring·response·metrics·incident의 틀과 작성법 |
| `proposals/README.md`·`observations/README.md` | 각 기록의 기존 작성법과 상태 규칙 |

각 작성법은 **용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준** 순서로 둔다. 단계 README에서는 「입력과 산출물」 아래에 배치한다. 업무 README는 업무 규칙만 담고 이 작성법을 다시 싣지 않는다. 에이전트 정의문은 읽을 작성법과 맡은 역할을 링크한다.

| 대안 | 얻는 것 | 비용 | 제안 |
| --- | --- | --- | --- |
| 단계 README에 틀과 작성법을 함께 둠 | 문서를 고르는 곳에서 작성까지 이어짐 | README가 길어짐 | 목차와 문서 종류별 하위 절로 시작 |
| 별도 `templates/`와 작성 가이드 폴더 | 원본 파일을 바로 복사하기 쉬움 | 단계 안내·틀·작성법이 다시 갈라짐 | 반복 복사 오류가 확인될 때 재검토 |
| 생성기·문서 스키마로 강제 | 일괄 생성·검사 가능 | 형식과 도구를 함께 유지해야 함 | 초기 범위 밖 |

이 제안서는 검토 근거로 보존한다. 채택한 내용은 위 소유 문서로 옮기고 제안서에는 목적지를 링크한다. 이후 작성법 변경은 소유 문서에서 한다.

## 2. 모든 문서에 적용할 작성 방법

### 2.1 문장을 쓰기 전에 소유 문서를 고른다

1. 이번에 답할 질문을 한 문장으로 적는다. 「누구의 문제인가」는 intent, 「항상 어떤 판정을 하나」는 업무 규칙, 「이번에 어디까지 만드나」는 spec이다.
2. 현재 소유 문서와 결정 근거를 읽는다. 코드에서 확인한 동작과 합의된 목표를 구별한다.
3. 기존 결정은 원문을 링크한다. 새로 결정할 내용만 해당 소유 문서에 쓴다.
4. 초안을 실제 사례로 읽는다. 같은 입력에서 서로 다른 답이 나오면 표현이나 결정이 덜 된 것이다.
5. 변경된 조항을 참조하는 활성 문서와 테스트를 확인한다. 영향 처리 결과는 해당 PR에 남긴다.

규칙 본문, 입력 예시, 검증 결과는 역할이 다르다. 「번호는 이 형식만 허용한다」는 규칙 한 곳이 소유한다. spec과 테스트에는 그 규칙에서 도출한 입력·기대 결과를 쓸 수 있다. 예시가 규칙을 바꾸거나 다른 예외를 추가해서는 안 된다.

### 2.2 사실·결정·제안·미정을 구별한다

| 종류 | 쓰는 방법 | 필요한 근거 |
| --- | --- | --- |
| 확인 사실 | 「기준 커밋에서 이 호출이 이 데이터를 쓴다」 | 코드 위치·실행 결과·관찰 일시 |
| 합의된 결정 | 조건과 결과를 단정문으로 쓴다 | 사용자 결정·채택된 문서·ADR 등 결정 근거 |
| 제안 | 「제안: …」으로 시작하고 대안과 비용을 적는다 | 해결할 문제와 판단할 차이 |
| 미정 | 질문·영향·결정할 사람 또는 역할·필요한 자료·결정 시점을 적는다 | 미정을 소유한 절과 막히는 작업 |
| 해당 없음 | 적용되지 않는 이유를 한 문장으로 쓴다 | 검토한 범위 |

`미정`은 `해당 없음`으로 대체하지 않는다. 해당 절이 실제로 없으면 이유를 적고, 아직 모르면 아래 틀을 쓴다. 빈 파일을 미리 만들지는 않는다.

```markdown
### Q-01

- 질문: &lt;무엇을 정해야 하나&gt;
- 영향: &lt;어떤 판정·화면·작업을 막나&gt;
- 결정 담당과 시점: &lt;누가, 어떤 작업 전에 정하나&gt;
- 필요한 근거와 대안: &lt;확인할 자료, 선택지의 차이&gt;
```

질문은 한 소유 문서에만 둔다. 다른 문서와 backlog에서는 그 절을 링크한다. 결정 뒤에는 규칙을 소유 절에 반영하고 질문 절에는 결정 근거와 목적지를 남긴다. 이미 링크된 질문 앵커는 바로 없애지 않는다.

### 2.3 참조와 식별자는 필요한 곳에만 둔다

- `sources`는 기능 spec의 intent·적용 설계, plan의 spec 또는 비기능 작업의 입력 문서에 사용한다. 그 입력의 변경이 산출물 재검토를 요구한다는 뜻이다. 단순 참고 자료는 본문 링크로 구별한다.
- 경로는 **실제로 작성될 파일 기준의 상대 경로**다. README의 템플릿을 복사한 뒤 목적지에서 확인한다. 코드 블록 속 예시 링크는 실제 파일의 링크 검사 통과를 보장하지 않는다.
- 작업 ID는 파일 슬러그에서 얻는다. 기능의 intent·spec·구현 plan은 같게 하고 frontmatter에 ID를 다시 적지 않는다.
- 중요한 규칙은 `### ACC-001`, 완료 조건은 `### AC-01`처럼 제목 자체를 ID로 둔다. 이름은 그 아래 문장에 적는다. AC와 질문 번호는 파일 안에서만 유일하면 된다.
- 업무 규칙 접두사는 `ACC / SCH / ATT / PAY / SWP / NOT`을 제안한다. 번호는 해당 업무 규칙 문서에서 발급하고 재사용하지 않는다. 공통 설계에도 고정 참조가 필요할 때만 `SYS-…`를 쓴다. 모든 설명 문장에 ID를 붙이지 않는다.
- 규칙을 나누거나 없애면 기존 ID에 대체 조항을 연결한다. 숫자를 다시 매겨 참조를 깨뜨리지 않는다.
- spec·proposal·observation 외 문서에 일괄 `status`를 붙이지 않는다. 작업 진행 상태는 backlog, 기능 승인은 spec, 제안 판단은 proposal이 소유한다.

이 선언으로 직접 의존 문서를 계산하고, 일반 본문 링크로 추가 영향을 찾는다. 간접 영향과 의미 변화까지 참조 선언만으로 알아낼 수 있다고 가정하지 않는다.

### 2.4 작성자가 마지막에 확인할 질문

**근거가 있는가, 이 문서의 책임인가, 입력과 결과가 분명한가, 실패·경계 조건을 보았는가, 바뀌면 어디를 다시 읽어야 하는가.** 다섯 질문을 공통 기준으로 두고 문서별 검토에서는 그 문서만의 질문을 추가한다. 승인되지 않은 정책을 템플릿 예시나 테스트 기대값으로 확정하지 않는다.

문서끼리 충돌하면 양쪽 조항·결정 근거·현재 코드·영향 작업을 함께 비교한다. 최근 수정일이나 더 상세한 문서라는 이유로 승자를 고르지 않는다. 근거가 충분하면 소유 문서를 바로잡고, 제품 판단이 남으면 그 문서의 미정에 둔다.

## 3. 문서 지도와 단계 README

`docs/README.md`의 틀은 「문서 지도 / 기준의 소유권 / 참조와 작성 규칙 / 변경 전파 / 협업 기록 작성법」이다. 전역 경로와 문서 종류를 찾게 하고 각 단계의 세부 목록은 해당 README로 보낸다.

단계 README 여섯은 아래 틀을 공통으로 쓴다.

```markdown
# &lt;단계&gt; — &lt;이름&gt;

## 역할
&lt;이 단계에서 답하는 질문과 결정할 범위&gt;

## 문서 지도
| 문서 | 답하는 질문 |
| --- | --- |
| &lt;실제 상대 링크&gt; | &lt;한 문장&gt; |

## 입력과 산출물
### &lt;문서 종류&gt;
&lt;용도·작성 시점 / 필요한 입력 / 복사용 틀 / 절별 질문 / 검토 기준&gt;

## 다음 단계로 넘기는 조건
&lt;필요한 결정·근거·산출물. 미정이 막는 범위와 처리 방법&gt;
```

넘기는 조건은 단계별로 다르다. 기획은 사용자 문제·범위와 미정의 영향을, 설계는 해당 기능 spec의 승인 근거를, 구현은 완료 조건의 검증 근거를 확인한다. 검증은 출시 대상으로 삼을 수 있는 결과와 남은 제한을, 배포는 운영에서 확인할 릴리스·복구 정보를 넘긴다. 운영은 발견한 제품 문제를 다음 intent로 넘긴다. 모든 단계에 새 승인 절차를 만들지는 않는다.

`modules/README.md`는 예외적으로 「영역 지도 / 공통 용어 / 영역 사이의 책임과 의존 / 경계의 미정」을 쓴다. 영역별 규칙을 요약해 복사하지 않고, 공유 데이터나 행위의 소유 영역과 참조 방향을 적는다.

## 4. 기획 문서

### 4.1 PRD·로드맵·시나리오·지표

아래 순서를 문서별 최소 틀로 삼는다. 전부 새로 만들 필요는 없고 기존 파일에서 이번에 바뀌는 제품 판단을 갱신한다.

| 문서 | 본문 틀 | 그 아래에 쓸 내용과 작성 방법 | 검토 기준 |
| --- | --- | --- | --- |
| `prd.md` | 제품 목적 → 대상 사용자 → 현재 문제와 근거 → 제품 범위 → 범위 밖 → 제약·미정 | 사용자별 현재 수단과 손실을 먼저 적는다. 기능 묶음은 해결할 문제와 연결하고 계산·권한 상세는 설계를 링크한다 | 기능마다 누구의 문제인지 말할 수 있고, 목표와 비범위가 충돌하지 않는가 |
| `roadmap.md` | 릴리스 목록 → 순서의 이유 → 재검토 조건 | `릴리스 / 담는 묶음 / 미루는 묶음과 이유 / 출시 판정의 참조` 표. 순서는 사용자 가치·의존 관계로 설명한다. 개별 task 상태는 backlog로 보낸다 | 릴리스 범위가 PRD와 맞고, 선행 관계를 설명할 수 있는가 |
| `scenarios.md` | 장면별 누가 → 언제·계기 → 하려는 일 → 현재 어려움 → 성공·실패 뒤 모습 → 관련 설계 | 가상 인물의 구체 장면으로 쓴다. 사용자가 결과를 확인하는 순간까지 적고 상세 버튼 배치는 화면 문서로 보낸다 | 화면 이름을 몰라도 사용자의 목적과 끝나는 상태가 이해되는가 |
| `metrics.md` | 지표별 정의 → 측정 이유 → 집계 기준 → 목표선과 근거 → 결정할 항목 | 아래 측정 틀로 분모·분자·기간·제외 대상을 정한다. 수집 쿼리는 운영 metrics로 보낸다 | 같은 원자료를 두 사람이 집계해 같은 값이 나오는가 |

장면 번호처럼 이미 참조되는 식별자는 보존한다. 새 표기법을 위해 기존 번호를 바꾸지 않는다. 숫자 정책이 필요하면 원문을 링크하고 장면의 숫자는 그 규칙의 사례임을 밝힌다.

```markdown
### &lt;지표 이름&gt;

- 정의와 이유: &lt;무엇을 세며 어떤 제품 판단에 쓰나&gt;
- 집계 단위: &lt;사람·근무·요청 중 무엇인가&gt;
- 분자 / 분모: &lt;비율일 때 각각의 포함 조건. 비율이 아니면 집계식&gt;
- 기간과 시각 기준: &lt;기간 경계·시간대·어느 사건 시각인가&gt;
- 제외·중복·누락: &lt;취소·재시도·데이터 없음의 처리&gt;
- 목표선과 근거: &lt;합의된 값, 또는 미정과 결정 시점&gt;
- 측정 방법: &lt;운영 metrics의 해당 절 링크, 아직 없으면 준비 작업&gt;
```

현재 [성공 지표](../1-plan/metrics.md)의 목표선은 운영 첫 달 이후 결정하기로 되어 있다. 템플릿에 빈칸이 있다는 이유로 목표 숫자를 채우지 않는다.

### 4.2 intent

새 기능·이슈의 사용자 문제를 확인할 때 쓴다. 인터뷰·관찰·시나리오가 입력이며 기술 구현안부터 고르지 않는다.

```markdown
# &lt;사용자가 해결하려는 일&gt;

## 사용자 문제
&lt;누가 어떤 상황에서 무엇을 못 하는가. 확인한 근거와 날짜&gt;

## 사용자 장면
&lt;계기 → 현재 행동과 어려움 → 원하는 끝. 기존 장면은 링크&gt;

## 기대 결과
&lt;사용자가 확인할 변화와 그 변화가 필요한 이유&gt;

## 제약·범위 밖
&lt;기기·운영·일정 등 확인된 제약 / 이번에 풀지 않을 문제&gt;

## 열린 질문
&lt;문제·범위의 미정. 설계 미정은 그 소유 문서를 링크&gt;

## 연결 설계
&lt;관련 업무·공통·화면 설계 링크와 이번에 결정이 필요한 부분&gt;
```

**작성 방법:** 사용자가 말한 해결안에서 그 이유를 확인해 문제와 기대 결과를 분리한다. 인터뷰 사실과 작성자의 가설을 구별하고, 화면·업무 결정이 확정되면 설계에 올린 뒤 링크한다. 기존 [관리자 근무표 intent](../1-plan/intent/schedule-admin.md)의 상세 화면 결정처럼 이미 기록된 내용은 결정 근거로 보존하되 현재 화면 계약의 원천으로 중복 사용하지 않는다.

**검토:** 설계자가 무엇을 결정해야 하는지 알 수 있는가. 문제를 「화면을 만든다」로만 적지는 않았는가. 결과를 바꿀 열린 질문은 승인 전에 답하거나 범위에서 명시적으로 제외할 수 있는가.

## 5. 업무 규칙과 기술 설계

### 5.1 `modules/&lt;영역&gt;/README.md`

업무 용어·판정·책임이 생기거나 바뀔 때 쓴다. 제품 요구와 사용자 결정이 입력이다.

```markdown
# &lt;업무 영역&gt;

## 책임과 범위
&lt;이 영역이 판정하는 것. 다른 영역이 판정하는 것은 소유 링크&gt;

## 용어
| 용어 | 업무에서의 뜻 | 혼동하는 개념과의 차이 |
| --- | --- | --- |
| &lt;용어&gt; | &lt;정의&gt; | &lt;구별 기준&gt; |

## 업무 규칙
### &lt;규칙 ID&gt;
&lt;규칙 이름. 누가 어떤 조건에서 무엇을 할 수 있거나 해야 하나&gt;

- 예외와 경계: &lt;허용·거부·보류가 갈리는 조건&gt;
- 이유와 근거: &lt;이 판정이 필요한 이유와 결정 근거&gt;

## 상태 전이
| 이전 상태 | 사건·행위자 | 허용 조건·규칙 참조 | 다음 상태 | 거부 시 결과 |
| --- | --- | --- | --- | --- |

## 판정 예시
| 규칙 | 입력·이전 상태 | 사건 | 기대 판정·이후 상태 | 사례의 이유 |
| --- | --- | --- | --- | --- |

## 다른 영역과의 계약
| 상대 영역 | 제공·기대하는 사실 | 소유 조항 | 바뀔 때 확인할 곳 |
| --- | --- | --- | --- |

## 미정
&lt;질문별 영향·담당·필요 근거·결정 시점&gt;
```

**규칙 문장 쓰기:** 행위자 → 전제 → 행위 → 판정 → 예외 순으로 확인한다. 「적절히 막는다」 대신 무엇을 막고 기존 상태가 어떻게 남는지 쓴다. 보존 기간·시각 경계·권한은 근거를 확인하며 DDL이나 함수 이름으로 업무 정의를 대신하지 않는다.

**판정 예시 만들기:** 정상 사례를 하나 고른 뒤 결과가 뒤집히는 축을 찾는다. 수치가 있으면 경계 직전·동일·직후, 권한이면 본인·타인과 허용·금지 역할, 상태면 허용 전이·금지 전이·중복 사건을 검토한다. 실제로 판정이 달라지는 사례만 표에 남긴다. 모르는 기대값은 테스트로 고정하지 않고 미정으로 돌린다.

**검토:** 같은 입력에 판정 하나가 나오는가. 상태 전이가 규칙과 모순되지 않는가. 다른 영역이 내부 테이블을 알아야 업무 계약을 이해하는 구조는 아닌가.

### 5.2 `modules/&lt;영역&gt;/design.md`

합의한 업무 규칙을 데이터·호출·실행 동작으로 연결할 때 쓴다. 업무 규칙, 공통 설계, 실제 마이그레이션·타입·코드가 입력이다.

```markdown
# &lt;업무 영역&gt; 기술 설계

## 참조 규칙
&lt;적용 업무 규칙과 system 조항 링크. 영역별 예외가 있으면 해당 절&gt;

## 소유 데이터
&lt;소유 테이블·관계·제약의 의미, 실제 스키마·생성 타입 위치&gt;
&lt;자기 캐시 키와 읽기 범위. 공유 데이터는 소유 영역 링크&gt;

## 행위별 구현 계약
### &lt;행위 이름&gt;

- 규칙: &lt;이 행위가 실현하는 업무 규칙 링크&gt;
- 입력·전제: &lt;진입점·인자·필요 상태·시각 기준&gt;
- 읽고 쓰는 데이터: &lt;대상·변경 필드·원자적으로 처리할 범위&gt;
- 권한: &lt;인증·행 단위 접근·서버 측 강제 위치&gt;
- 처리와 경쟁: &lt;순서·중복 호출·동시 변경·재시도 처리&gt;
- 결과와 실패: &lt;반환·오류·저장 여부·부분 성공 또는 복구&gt;
- 캐시 갱신: &lt;성공·실패 때의 무효화·직접 갱신·복원 대상&gt;

## UI 연결
&lt;행위가 시작되는 화면과 결과를 보여주는 화면·상태 링크&gt;

## 코드와의 차이
| 목표 조항 | 확인한 코드와 Git 기준점 | 차이 | 전환 작업·검증 근거 |
| --- | --- | --- | --- |

## 미정
&lt;기술 선택의 질문. 업무 판단이면 업무 규칙의 질문 링크&gt;
```

**행위별로 쓰기:** 화면의 사용자 행동 또는 시스템 사건 하나를 고른다. 입력부터 저장·응답·화면 갱신까지 따라가며 위 여섯 항목을 채운다. 데이터·API·런타임별로 같은 행위를 다시 나누지 않는다. 실패에는 「요청 실패」만 쓰지 말고 서버 저장 여부를 알 수 있는지, 재호출하면 중복되는지도 구별한다.

**소유권 쓰기:** 스키마 전체를 복사하지 않고 제약이 업무 규칙을 어떻게 보장하는지 설명한다. `requests`·`request_candidates`의 공통 계약은 상위 제안대로 schedule이 소유하고 swap은 추가 조건만 쓴다. 다른 영역 캐시까지 갱신하는 행위는 그 행위의 계약에 전체 갱신 대상을 적고 캐시 정의는 소유 영역을 링크한다.

**검토:** 허용 UI를 우회한 요청도 권한이 지켜지는가. 두 요청이 겹치거나 응답이 끊겼을 때 결과를 설명할 수 있는가. 설계 목표와 현재 코드의 차이를 진행 상태와 혼동하지 않았는가. 「코드와의 차이」를 절 이름으로 통일한다.

## 6. 공통 설계와 디자인 시스템

### 6.1 system 네 문서

여러 영역이 함께 따라야 하는 결정이 있을 때 갱신한다. 공통 문서를 만들기 위해 영역별 사례를 일반화하지 않는다. 한 영역만의 예외는 영역 design에 쓰고 공통 조항에는 예외의 대상·이유·링크를 남긴다.

| 문서 | 본문 틀 | 절별 작성 방법 | 검토 기준 |
| --- | --- | --- | --- |
| `system/architecture.md` | 구성과 경계 → 구성 요소의 책임 → 업무 영역 관계 → 주요 데이터 흐름 → 선택 근거·미정 | 브라우저·Next·Supabase·Edge Function을 실제 책임으로 연결한다. 관계도 화살표에는 호출·읽기·쓰기의 뜻을 붙인다. 대표 흐름에는 영역 design을 링크한다 | 어느 구성 요소가 인증·판정·저장을 맡는지 추적되는가 |
| `system/data-access.md` | 공유 데이터 → 스키마·타입 규약 → 읽기·쓰기 경계 → 인증·권한 → 결과·오류 계약 → 예외·미정 | 공유 halls와 영역 소유 데이터를 구별한다. DAL·auth·서비스 키의 경계를 정하고, 공통 오류는 의미·반환 위치·호출자 책임을 적는다 | 모든 업무에 적용할 규칙과 특정 업무 예외를 구별했는가 |
| `system/runtime.md` | 캐시·수명 → 오프라인 → 시각 → 경쟁·재시도 → 로딩·낙관적 처리 → 예외·미정 | 기본값마다 적용 조건과 이유를 적는다. 시각은 발생·보고·수신·판정 중 무엇인지 구별한다. 상수의 코드 원천을 링크하고 영역별 키·무효화 목록은 복사하지 않는다 | 영역 design이 어떤 기본값을 상속하며 언제 예외를 써야 하는가 |
| `system/navigation.md` | 진입과 역할 → 경로 → 탐색·뒤로 가기 → 딥링크 → 예외·미정 | `경로 / 진입 조건의 참조 / 소유 화면` 표를 둔다. 직접 URL 진입·역할 전환·재진입을 확인한다. 화면 안 버튼별 이동은 소유 화면에 둔다 | 같은 진입 조건이 화면 문서와 충돌하지 않는가 |

공통 조항 하나의 틀은 다음과 같다. 기본값의 실제 수치나 정책은 기존 근거로 채운다.

```markdown
### &lt;공통 조항 이름 또는 고정 ID&gt;

- 적용 범위: &lt;어느 호출·데이터·화면에 적용하나&gt;
- 기본 계약: &lt;조건과 결과, 호출자와 제공자의 책임&gt;
- 이유: &lt;해결하는 문제와 선택 근거&gt;
- 예외: &lt;영역·이유·예외 계약 링크, 없으면 해당 없음&gt;
- 구현 참조: &lt;코드·설정의 원천. 아직 없으면 전환 작업&gt;
```

### 6.2 design-system 문서

화면에 공통으로 적용할 시각·문안 기준이 생기거나 바뀔 때 갱신한다. 값과 사용법의 소유권은 [현재 디자인 시스템](../2-design/design-system/README.md#두-축)을 유지한다.

| 문서 | 본문 틀 | 세부 작성 방법 |
| --- | --- | --- |
| `tokens.md` | 기존 표·절·생성기 입력 형식 유지 | 값은 여기서만 바꾼다. 토큰의 의미·용도·테마 대응과 검증 근거를 확인한다. 템플릿 통일을 위해 파서가 읽는 표를 재구성하지 않는다 |
| `foundation/color.md` | 사용 목적 → 선택 기준 → 조합 예시 → 제약·예외 | 배경·글자·강조의 역할 조합과 대비 확인 방법을 쓴다. 실제 색값은 토큰 참조로 둔다 |
| `foundation/typography.md` | 정보 위계 → 역할별 사용 → 숫자·줄바꿈 → 예외 | 제목·본문·보조 정보의 토큰과 선택 이유를 적고 실제 화면 길이로 점검한다 |
| `foundation/spacing-shape.md` | 묶음과 간격 → 면·경계 → 크기·형태 → 예외 | 같은 그룹과 다른 그룹의 구분, 터치 영역, 라운딩·그림자 적용 조건을 토큰으로 설명한다 |
| `foundation/motion.md` | 목적 → 시작·종료 조건 → 사용 토큰 → 움직임 축소·예외 | 무엇이 바뀌었음을 알리는 모션인지부터 적는다. 시간·이징 값은 토큰을 참조한다 |
| `components.md` | 컴포넌트별 용도 → 변형·상태 → 구성·역할 토큰 → 입력·접근성 → 사용 예·예외 | 정상·비활성·로딩·실패 상태를 대조한다. 화면마다 새 조합을 만들기 전에 기존 컴포넌트로 표현 가능한지 본다 |
| `writing.md` | 문체·용어 → 상황별 문장 구조 → 좋은 예·고칠 예 → 금지·예외 | 행동·성공·실패·권한 제한을 구별한다. 실패 문장은 현재 상황과 가능한 다음 행동을 알려준다. 화면별 최종 문구는 화면 문서가 소유한다 |

**검토:** 새 기준을 실제 화면에 적용해 판정할 수 있는가. 토큰 값이 여러 문서에 생기지 않았는가. 화면만의 예외를 공통 기본값으로 넓히지 않았는가. 현재 규칙과 부딪힌 자리는 적용 범위와 결정 근거를 남긴다.

## 7. 화면 문서와 시안

화면 동작·구성·문안·모션이 새로 생기거나 바뀔 때 문서와 짝 시안을 함께 갱신한다. 업무 규칙, 행위별 기술 계약, 전역 탐색, 디자인 시스템이 입력이다.

```markdown
# &lt;화면 또는 흐름 이름&gt;

## 목적과 진입
&lt;사용자 목적·진입 계기·나갈 때의 결과. 경로·역할 조건은 navigation 링크&gt;

## 참조 기준
&lt;업무 규칙 / design의 행위 / navigation / 공통 시각·문안 조항&gt;

## 화면 상태와 흐름
| 상태 | 진입 조건·계기 | 보이는 내용 | 가능한 행동 | 다음 상태·목적지 |
| --- | --- | --- | --- | --- |

## 짜임과 토큰
&lt;위에서 아래의 정보 순서, 컴포넌트·역할 토큰, 작은 화면·키보드·포커스 처리&gt;

## 문안
| 상태·위치 | 최종 문구 | 가변값·표기 조건 |
| --- | --- | --- |

## 모션
&lt;시작·종료 상태 / 공통 토큰 / 움직임 축소 시 표현&gt;

## 예외와 미정
&lt;범위 밖 / 공통 기준과의 충돌·판단 / 아직 결정하지 않은 상태&gt;
```

**상태 표 채우기:** 정상·빈 상태·로딩·실패·권한 제한·성공 직후를 한 번씩 검토한다. 각 상태에서 사용자가 할 수 있는 행동을 따라 다음 상태를 쓴다. 입력 보존·중복 누름·닫기·뒤로 가기·재진입 때문에 결과가 달라지는 경우도 추가한다. 한 표에 모든 상태 조합을 늘어놓지 말고 실제로 다른 표현이나 행동이 필요한 경우를 남긴다.

**문안 쓰기:** 상태 표가 쓰는 최종 문구는 문안 절에서 소유한다. 상태 표는 그 문구를 위치나 항목명으로 가리킨다. 실패 원인마다 다음 행동이 다르면 문구도 구별한다. 아직 행동 정책이 없으면 임의로 「다시 시도」를 넣지 않는다. 읽기·재시도 시점은 design, 기다리는 동안 보이는 모습은 화면 문서가 정한다.

**시안 만들기:** `&lt;화면&gt;.md`와 `&lt;화면&gt;.sian.html`을 같은 폴더에 둔다. 파일 첫 주석에는 문서 경로와 토큰이 정본이라는 점을 적는다. 화면 상태 표와 비교할 수 있도록 시안에도 상태 이름을 표시한다. 확정되지 않은 표현은 「제안」으로 구별한다. 문서에서 변경한 상태를 시안에서도 확인하고 문서에 없는 동작이 나타나면 소유 문서로 돌린다. 시안 CSS를 앱 구현 코드로 복사하지 않는 기존 규칙을 유지한다.

**검토:** 버튼을 누른 뒤 성공·실패의 끝까지 그려졌는가. 적용되는 라이트·다크와 작은 화면에서 글자·터치·포커스를 확인할 수 있는가. 지적마다 근거 조항을 연결할 수 있는가. 새 시안 메타데이터 형식이나 HTML 생성기를 이번 제안으로 추가하지 않는다.

## 8. 기능 명세와 결정 기록

### 8.1 spec

사용자 문제와 적용할 설계가 정리되어 이번 기능의 범위를 승인받을 때 쓴다. 설계가 덜 된 곳을 spec 안의 별도 정책으로 채우지 않는다. 상위 제안의 참조 형식을 다음처럼 구체화한다.

```markdown
---
status: draft
sources:
  - ../../1-plan/intent/&lt;task&gt;.md
  - ../modules/&lt;영역&gt;/README.md#&lt;규칙-id&gt;
  - ../modules/&lt;영역&gt;/design.md#&lt;행위-앵커&gt;
  - ../modules/&lt;영역&gt;/screens/&lt;화면&gt;.md
---

# &lt;이번 기능에서 바뀌는 사용자 동작&gt;

## 요구
&lt;intent의 문제와 연결한 이번 구현 범위&gt;

## 설계 참조
&lt;각 입력에서 이번에 적용하는 부분과 제외하는 부분. 규칙 본문은 링크&gt;

## 완료 조건
### AC-01

- 전제: &lt;사용자·상태·입력&gt;
- 행동: &lt;사용자 또는 시스템이 하는 일&gt;
- 관찰 결과: &lt;화면·반환·저장 상태로 확인할 결과&gt;
- 근거: &lt;적용 설계 조항 링크&gt;

## 범위 밖
&lt;인접 기능 중 이번 승인에 포함하지 않는 것&gt;

## 승인 근거
&lt;승인 전에는 승인 기록 없음&gt;
```

**완료 조건 쓰기:** 요구 하나마다 어떤 결과를 보면 끝인지 묻는다. 「잘 동작한다」「설계대로 만든다」로 끝내지 않는다. 하나의 조건이 하나의 판정으로 통과·실패할 수 있게 나누고 정상·거부·경계 사례를 필요한 만큼 적는다. 파일 변경 목록과 테스트 명령은 plan으로 보낸다. 테스트가 참조할 때는 spec 경로와 `#ac-01`을 함께 쓴다.

**승인 기록 쓰기:** 승인한 사람, 날짜, 실제 승인 메시지·리뷰·기록의 참조, 검토한 Git 기준점, 승인 범위와 제한을 적는다. 대상 spec뿐 아니라 `sources`의 내용을 그 시점에 재현할 수 있어야 한다. 커밋 전 승인이라면 기준 커밋과 검토한 고정 diff·PR revision을 함께 연결한다. 움직이는 브랜치 이름이나 `HEAD`만 쓰지 않는다. 승인 근거가 없는 상태에서 `approved`로 채우지 않는다.

**입력 변경 검토:** 승인 이후 요구나 입력 설계가 달라지면 이전 승인 기준과의 차이·영향 AC·기존 승인 범위 충족 여부를 남긴다. 기존 사용자 결정이 충분하면 그 근거를 연결하고, 범위가 새로 넓어지면 필요한 승인을 받는다. 단순 링크 이동과 제품 요구 변경을 같은 것으로 처리하지 않는다. 완료된 과거 spec의 승인 내용은 현재 템플릿에 맞춰 다시 쓰지 않는다.

### 8.2 ADR

영역 경계·플랫폼·접근 방식처럼 중요한 선택을 확정했을 때 쓴다. 검토 중인 대안은 proposal이나 해당 설계의 미정에 둔다.

```markdown
# ADR-&lt;번호&gt; — &lt;선택을 드러내는 제목&gt;

&lt;결정 날짜와 근거. 이전 결정을 바꾸면 해당 ADR 링크&gt;

## 배경과 제약
&lt;무엇이 문제였고 어떤 조건을 지켜야 했나&gt;

## 대안과 선택
&lt;검토한 대안 / 비교 기준 / 선택 / 받아들이는 비용&gt;

## 적용과 결과
&lt;영향받는 정본·작업 링크 / 얻는 것 / 남는 제약&gt;

## 재검토 조건
&lt;어떤 사실이 바뀌면 다시 판단할 것인가&gt;
```

선택의 이유와 비용이 핵심이다. 상세 현재 정책은 소유 설계로 보내고 ADR에는 이유를 보존한다. 이후 결정이 바뀌면 새 ADR에서 이전 것을 참조하고 이전 문서에 후속 결정 링크를 추가한다. 이미 확정된 결정의 역사를 최신 설명으로 덮어쓰지 않는다.

## 9. 구현 계획

승인된 기능 spec 또는 방향이 정해진 비기능 task를 실제 변경 순서로 전개할 때 쓴다. 저장소에서 기존 구현·테스트·설정을 확인하고 나서 파일과 명령을 적는다.

```markdown
---
sources:
  - ../../2-design/spec/&lt;task&gt;.md
---

# &lt;작업 이름&gt; — 구현 계획

## 입력 명세·기준
&lt;승인된 spec / 관련 설계 / 확인한 코드와 Git 기준점&gt;

## 변경 파일
| 파일·영역 | 바꿀 책임 | 참조 완료 조건·규칙 |
| --- | --- | --- |

## 구현 순서
1. &lt;관련 실패 테스트와 실패 확인&gt;
2. &lt;그 테스트를 통과시킬 구현&gt;
3. &lt;영향받는 문서·생성물·주변 동작 확인&gt;

## 리스크·전환·되돌리기
&lt;영향받는 사용자·데이터 / 전환 전제·순서 / 실패 시 되돌리는 단위와 한계&gt;

## 검증 방법
| 완료 조건·규칙 참조 | 테스트 층·위치 또는 수동 시나리오 | 명령·환경 | 확인할 결과 |
| --- | --- | --- | --- |
```

**비기능 plan:** `sources`에는 실제 입력 정본·채택된 제안 항목을 넣는다. spec과 intent를 억지로 만들지 않는다. 「입력 명세·기준」 뒤에 「완료 조건」을 추가하고 `AC-01` 같은 식별자로 직접 판정 가능하게 쓴다. 기능 plan은 spec의 AC를 참조하며 복사하지 않는다.

**구현 순서 쓰기:** 변경 파일을 나열하는 데서 끝내지 않고 선행 이유를 적는다. 규칙·동작이 달라지면 실패 테스트→구현 순서를 유지한다. 문서만 고치는 작업은 관련 기존 문서 검사로 확인하며 형식만 베끼는 새 테스트를 만들지 않는다. 구조 전환이면 읽기·쓰기의 호환 기간과 되돌릴 수 없는 지점을 따로 확인한다.

**검토 방법 쓰기:** 먼저 AC별 실패 위험을 찾고 그 위험을 관찰할 수 있는 테스트 층을 고른다. 테스트 경로가 아직 없으면 예정임을 밝힌다. 실제 실행 결과는 CI·PR·특수 evidence로 연결하며 계획한 명령을 실행한 것처럼 적지 않는다.

**검토:** 구현자가 계획과 참조 문서로 착수할 수 있는가. 기술 선택이 새 사용자 동작을 만들면 설계·spec으로 돌렸는가. 비기능 task의 완료 조건과 준비 작업의 산출물이 분명한가. 준비 task가 다른 작업의 plan을 산출하는 경우 그 경로를 그대로 링크한다.

## 10. 검증 문서

### 10.1 strategy와 execution

검증 기준을 바꿀 때는 `strategy.md`, 실행 환경·명령·문제 해결이 바뀔 때는 `execution.md`를 갱신한다. 개별 기능마다 전략 문서를 만들지 않는다.

| 문서 | 본문 틀 | 절별 작성 방법 |
| --- | --- | --- |
| `strategy.md` | 리스크와 층 배정 → 대역·실제 의존성 경계 → 판정 예시와 AC 연결 → 수동 검증 조건 → 완료 판정 | `리스크 / 이를 관찰할 층 / 실제로 통과해야 하는 경계 / 이유` 표. 계산·규칙은 unit, RLS·DB 제약·트랜잭션은 integration, 사용자 흐름은 e2e라는 현재 기준을 연결한다. 같은 위험의 중복 테스트는 별도 이유가 있을 때만 둔다 |
| `execution.md` | 실행 전제 → 명령·환경 → 훅·문서 검사 → 실패 진단 → 결과 찾기 | 아래 실행 항목 틀로 로컬·CI의 차이, 필요한 서비스·빌드 순서, 통과 기준, 결과 위치를 적는다. 실패한 명령의 증상·확인 위치·복구 순서를 묶는다 |

```markdown
### &lt;검증 명령 또는 절차 이름&gt;

- 전제: &lt;작업 위치·도구·서비스·데이터 상태&gt;
- 실행: &lt;저장소에서 확인한 실제 명령&gt;
- 정상 결과: &lt;종료 코드와 확인할 산출물·검사 내용&gt;
- 실패할 때: &lt;증상 → 확인 위치 → 조치 → 재검증&gt;
- 근거 위치: &lt;CI 실행 결과·리포트 등&gt;
```

테스트 층 선택은 `test-planner`와 strategy에서 따로 유지하지 않는다. ADR-003은 선택의 이유를 보존하고 현재 배정 기준은 strategy에 모은다. 테스트 코드의 위치와 TDD는 ADR-001을 유지한다. 형식이 맞는 것과 동작이 맞는 것은 각각 문서 검사와 실제 테스트로 확인한다.

### 10.2 evidence

실기기·외부 서비스 등 CI 결과만으로 근거가 남지 않는 검증을 실행했을 때 쓴다. 실행 전 계획은 plan에 두고 사건 없는 evidence는 생성하지 않는다.

```markdown
# &lt;task&gt; — 검증 기록

## 검증 대상과 Git 기준점
&lt;spec AC 또는 비기능 plan AC 링크 / 검증한 커밋·변경분 / 실행 일시·검증자&gt;

## 환경·기기
&lt;로컬·스테이징 등 / OS·브라우저·기기 / 설치·권한·연결 상태&gt;

## 명령·시나리오
&lt;초기 데이터·이전 상태 → 실행 단계 → 기대 결과. 사용한 실제 명령&gt;

## 결과·증거
| AC·시나리오 | 실제 결과 | 판정 | 증거 위치 |
| --- | --- | --- | --- |

## 미해결 항목
&lt;실패·미실행의 이유 / 차단되는 범위 / 후속 작업&gt;
```

**작성 방법:** 기대 결과와 실제 결과를 분리한다. 환경이 없어 못 했다면 `미실행`으로 기록한다. 결과 표의 판정은 `통과 / 실패 / 미실행`으로 충분하며 작업 상태와 구별한다. 스크린샷·녹화·로그는 어떤 AC를 뒷받침하는지 연결하고 공개 저장소에 필요한 가짜 데이터 기준을 따른다.

**검토:** 다른 사람이 같은 기준점과 환경에서 재현할 수 있는가. 이미지 한 장으로 확인하지 못하는 저장·권한·재시도까지 통과로 넓히지 않았는가. 코드가 바뀌었다면 이전 evidence가 이번 변경에도 유효한지 영향 범위를 확인했는가.

## 11. 배포 문서

### 11.1 environments와 procedure

첫 출시 준비에서 실제 환경을 확인해 작성하고 환경·절차가 바뀔 때 갱신한다. 현재 [배포 안내](../5-deploy/README.md)는 플랫폼이 미정임을 밝히고 있다. 아래 틀로 플랫폼·설정값·운영 명령을 임의로 확정하지 않는다.

```markdown
# 배포 환경

## 환경별 구성
| 환경 | 용도 | 앱·DB·외부 서비스 | 관리 위치·담당 역할 |
| --- | --- | --- | --- |

## 설정
| 설정 이름 | 필요한 환경 | 설정 위치 | 읽히는 시점 | 누락 확인 방법 |
| --- | --- | --- | --- | --- |

## 데이터와 외부 의존성
&lt;환경 분리·초기 데이터·서비스 제약·확인 근거와 날짜&gt;

## 미정
&lt;출시 전에 정할 항목과 준비 작업&gt;
```

설정에는 이름과 보관 위치를 적고 실제 시크릿 값은 쓰지 않는다. 빌드 시점과 실행 시점을 구별한다. 구독 플랜·외부 제약은 실제 환경을 조사할 때 확인한 날짜와 근거를 남긴다.

```markdown
# 배포·확인·되돌리기 절차

## 진입 조건
&lt;릴리스 범위·검증 근거·환경 준비·실행 담당&gt;

## 실행 순서
| 단계 | 전제 | 명령·행동 | 정상 확인 | 실패 시 중단·복구 |
| --- | --- | --- | --- | --- |
| &lt;빌드·데이터 전환·배포·배포 후 확인의 각 단계&gt; | &lt;조건&gt; | &lt;확인된 방법&gt; | &lt;관찰 결과&gt; | &lt;행동&gt; |

## 되돌리기
&lt;판단 조건 / 앱·데이터별 복구 방법 / 복구 불가능한 구간 / 복구 후 확인&gt;

## 기록과 운영 인계
&lt;release에 남길 결과 / monitoring·response 참조&gt;
```

**작성 방법:** 정상 배포 순서를 먼저 쓰고 각 단계가 실패했다고 가정해 중단·복구 경로를 채운다. 데이터 변경을 앱 버전 되돌리기로 복구할 수 있는지 따로 확인한다. 확인하지 않은 복구 가능성을 단정하지 않는다. 명령 설명은 procedure, 실제로 실행한 사실은 release에 둔다.

**검토:** 다음 단계로 넘어갈 조건과 멈출 조건이 있는가. 앱·데이터·설정의 적용 순서를 재현할 수 있는가. 배포 전 환경값 주입처럼 실행 결과에 영향을 주는 전제를 빠뜨리지 않았는가.

### 11.2 release

구체적인 출시 대상을 구성할 때 만들고 실제 실행마다 결과를 덧붙인다. task 슬러그 대신 릴리스 식별자를 파일명으로 쓰며, 아직 실행하지 않은 항목은 `미실행`으로 구별한다.

```markdown
# &lt;release&gt; — 출시 기록

## 포함 작업·Git 기준점
&lt;포함 task와 산출물 링크 / 배포할 커밋·빌드 산출물 / 마이그레이션&gt;

## 사전 검증 근거
&lt;CI 실행 결과·필요한 evidence / 적용한 procedure의 버전·절 / 남은 제한&gt;

## 배포 기록
| 시각·실행자 | 환경·적용 대상 | 실행한 단계 | 결과·근거 |
| --- | --- | --- | --- |

## 배포 후 확인
&lt;procedure가 요구하는 확인 항목별 실제 관찰 결과&gt;

## 되돌리기 이력·후속 작업
&lt;되돌린 대상·시각·이유·복구 확인, 또는 실행하지 않았음 / 후속 작업 링크&gt;
```

릴리스에 묶인 작업의 완료 조건이나 상태를 다시 적지 않는다. 검증한 커밋과 배포할 대상이 다르면 차이를 확인하고 필요한 검증을 연결한다. 배포 명령 성공과 사용자 동작 확인을 각각 기록한다.

## 12. 운영 문서

### 12.1 monitoring·response·metrics

첫 운영 전에 관측·대응·측정 방법을 작성한다. 실제 담당·도구·경보 기준은 출시 준비 작업에서 확인한다. 사건 기록을 채우기 위해 가상의 운영 사건을 만들지 않는다.

| 문서 | 본문 틀 | 절별 작성 방법 | 검토 기준 |
| --- | --- | --- | --- |
| `monitoring.md` | 관측 대상 → 확인 위치·방법 → 신호 해석 → 담당·주기 → 누락·미정 | `신호 / 확인 위치·질의 / 정상 기준의 근거 / 대응을 시작할 조건 / response 링크` 표. 앱·DB·푸시 같은 의존성별로 사용자가 겪는 문제와 신호를 연결한다 | 담당자가 이상 여부를 판단하고 필요한 로그를 찾을 수 있는가 |
| `response.md` | 분류와 담당 → 초기 확인 → 완화 → 복구 확인 → 기록·후속 | 영향 파악·담당 연결·완화·복구 확인을 실제 순서로 쓴다. 각 단계에 전제·행동·확인 결과·다음 분기를 둔다. 되돌리는 명령은 deploy/procedure를 링크한다 | 담당·중단 조건·지원 요청 경로가 있고, 복구를 사용자 동작으로 확인하는가 |
| `metrics.md` | 기획 지표 참조 → 수집 원천 → 집계 구현 → 검증 → 측정 주기·담당 → 한계 | 아래 틀로 이벤트·쿼리·작업을 기획의 정의에 대응한다. 정의를 다시 만들지 않는다 | 분모·기간·누락 처리가 기획 정의와 같고, 수집하지 않는 값을 측정한 것처럼 쓰지 않았는가 |

```markdown
### &lt;기획 지표의 이름&gt;

- 정의: &lt;1-plan/metrics.md의 해당 절 링크&gt;
- 수집 원천: &lt;이벤트·테이블·수기 기록, 발생·수집 시각&gt;
- 집계 구현: &lt;쿼리·스크립트 위치, 매개변수, 실행 방법&gt;
- 정의와의 대응: &lt;분자·분모·기간·제외 조건을 구현한 위치&gt;
- 검증: &lt;알려진 작은 표본의 기대 집계와 실제 값&gt;
- 주기와 담당: &lt;언제 누가 실행·검토하고 결과를 어디에 두나&gt;
- 한계: &lt;누락·중복·지연·관측 불가능한 항목과 보완 작업&gt;
```

**측정 방법 쓰기:** 먼저 기획의 집계 정의가 결정되었는지 본다. 그다음 결과를 손으로 셀 수 있는 작은 가짜 표본을 만들고 쿼리 결과와 비교한다. 푸시를 보냈다는 기록이 사용자의 수신을 뜻하는지처럼 관찰한 사실과 추정도 구별한다. 관찰할 수 없는 지표를 다른 지표로 조용히 대체하지 않는다.

### 12.2 incident

장애가 발생했을 때 확인한 사실부터 적고 대응 중에 보완한다. `&lt;date&gt;-&lt;incident&gt;.md`는 작업 ID·릴리스 ID와 별개이며 관련 기록을 링크한다.

```markdown
# &lt;발생일&gt; — &lt;장애 이름&gt;

## 영향과 발생 시각
&lt;영향 사용자·기능 / 최초 영향·발견 시각과 시간대 / 아직 모르는 범위&gt;

## 관련 릴리스
&lt;릴리스·커밋·변경 사항. 관련성이 미확인이라면 그 사실&gt;

## 확인 사실
| 시각 | 관찰한 사실 | 근거 | 남은 가설·확인 방법 |
| --- | --- | --- | --- |

## 대응·복구 확인
| 시각·담당 | 실행한 조치 | 실제 결과·근거 | 다음 판단 |
| --- | --- | --- | --- |

## 원인과 후속 작업
&lt;확인한 원인과 근거, 또는 미확인 / 재발 조건 / 후속 task·정본 변경 링크&gt;
```

장애 중에는 사실·가설·조치를 시간순으로 쓴다. 복구 후 원인을 설명하고 미확인 추정을 확정 원인으로 바꾸지 않는다. 제품 요구 변경은 intent, 절차 문제는 해당 운영 문서와 비기능 plan, 작업 방식의 반복 마찰은 observation으로 연결한다. incident 본문에서 이후의 진행 상태를 별도로 관리하지 않는다.

## 13. 단계 밖의 협업 문서

### 13.1 proposal과 observation

제안의 상태와 채택 절차는 [proposals 안내](README.md)를 유지한다. 제안 내용이 구체적이라는 이유로 채택 상태로 바꾸지 않는다.

```markdown
---
status: proposed
---

# &lt;바꾸려는 방향&gt;

&lt;검토 날짜·Git 기준점·범위&gt;

## 문제와 근거
&lt;확인 사실·원문 링크·영향&gt;

## 추천과 대안
&lt;권고 / 비교 기준 / 대안별 이익·비용 / 선택 이유&gt;

## 적용 범위
&lt;영향받는 정본·파일·도구 / 범위 밖 / 미정&gt;

## 이행과 완료 기준
&lt;채택 후 적용 순서·검증·되돌릴 단위&gt;

## 판단할 항목
&lt;각 항목에서 무엇을 채택·보류·기각할지&gt;

## 결정 기록
&lt;실제 판단이 있을 때 날짜·항목별 결과·이유·정본·ADR·task 링크&gt;
```

문제에는 불편하다는 평가만 쓰지 말고 실제 충돌이나 반복 비용을 연결한다. 대안에는 현행 유지 또는 더 작은 변경을 포함해 비용을 비교한다. 부분 채택의 상태 집계는 기존 proposals 안내를 따른다.

observation의 복사용 틀은 [현재 안내](../observations/README.md#파일)를 그대로 쓴다. `status / target / date / resolved`와 「일 / 고침 / 원칙」을 유지한다. 이 제안에서 새 필드를 만들지 않는다.

| 항목 | 구체적으로 쓰는 방법 |
| --- | --- |
| 일 | 계기 → 기대한 동작 → 실제 마찰 → 근거 위치 순으로 쓴다. 개인 평가나 추정 원인은 분리한다 |
| 고침 | 정의문·훅의 어느 책임을 어떻게 고칠지 적는다. 대안 검토가 필요하면 proposal로 연결한다 |
| 원칙 | 다음에도 같은 종류의 문제인지 판정할 수 있는 문장으로 쓴다. 일회성 우회로를 전역 규칙으로 만들지 않는다 |

기존 번호·상태·집계·archive 규칙을 유지한다. 관찰을 기록하는 것과 해결안을 채택하는 것을 구별한다.

### 13.2 backlog와 handoff

상위 제안의 단일 표를 다음 복사용 틀로 구체화한다. 현재 보드에 바로 적용하는 변경은 아니다.

```markdown
# backlog

| 작업 ID | 작업 | 상태 | 선행 작업 ID | spec 또는 plan | 검증·완료 근거 |
| --- | --- | --- | --- | --- | --- |
| &lt;task&gt; | &lt;완료할 변화&gt; | candidate | &lt;없음 또는 작업 ID&gt; | &lt;문서 링크 또는 미작성과 이유&gt; | &lt;실제 결과 링크 또는 없음&gt; |
```

| 상태 | 행을 작성·변경할 때 확인할 것 |
| --- | --- |
| `candidate` | 검토할 문제나 개선 후보가 있는가. 아직 방향·착수 조건이 없어도 된다 |
| `blocked` | 선행 작업 또는 소유 문서의 미정이 무엇인지 링크했는가 |
| `ready` | 선행 조건과 plan이 준비되었는가. 기능이면 승인된 spec이 있는가 |
| `active` | 실제로 착수한 작업인가 |
| `done` | spec 또는 비기능 plan의 완료 조건을 충족하는 실제 근거가 있는가 |

`ready` 행은 위에서부터 착수하므로 행 순서가 우선순위를 나타낸다. 상태별 목록을 따로 만들지 않는다. 후보가 실행 작업이 될 때는 plan 또는 기능 사슬을 갖춘다. 준비 task의 완료는 구현 완료와 구별하고, 산출물 파일명이 준비 task ID와 다를 수 있다는 상위 제안의 예외를 유지한다.

```markdown
# Handoff

## 다음 작업
&lt;backlog의 작업 ID와 링크&gt;

## 재개 맥락
&lt;해당 작업 재개에 필요한 회차별 정보. 없으면 없음&gt;
```

문제가 다음 회차에도 필요한 상시 규칙이면 소유 문서로 옮긴다. 열린 제품 질문·전체 완료 목록·복제한 작업 상태를 넣지 않는다. 작업 ID의 구체 행 링크 방식은 보드 검사와 함께 정하고, 그전에는 backlog 파일 링크와 ID를 함께 쓴다. 상태별 절 앵커를 새 보드에도 있는 것처럼 쓰지 않는다. 이 형식의 실제 적용은 `session-recorder`의 입력·출력 정의와 함께 한다.

### 13.3 log와 CHANGELOG

```markdown
# &lt;날짜&gt; — &lt;회차의 주요 판단&gt;

## 판단과 근거
&lt;무엇을 왜 정했나 / 실제 사용자 결정·검증·PR 근거&gt;

## 확인한 결과
&lt;merge된 PR·CI·evidence 링크와 그 결과의 의미&gt;

## 남긴 질문과 후속 작업
&lt;소유 문서·backlog 링크. 현재 상태를 복제하지 않음&gt;
```

log는 도구 호출을 전부 옮기는 일지가 아니다. 선택 이유·실패에서 배운 사실·다음 판단에 필요한 근거를 남긴다. 미완료 작업은 완료 결과와 구별하고 실제 없는 PR 번호나 merge 사실을 만들지 않는다.

CHANGELOG는 현재의 `날짜 / 변경 / PR` 표를 유지한다. merge 날짜와 최종 변경 효과를 한 행으로 쓰고 이유는 PR·log로 보낸다. 작성법은 전역 안내에서 소유하고 파일 머리에는 용도와 안내 링크만 둔다. 과거 log·CHANGELOG를 새 틀로 소급 작성하지 않는다.

## 14. 한 변경을 문서로 전개하는 예

상위 제안이 발견한 **연락처 수정 경로의 불일치**를 시범 사례로 삼는다. [계정 업무 규칙](../2-design/modules/account/README.md#연락처)은 본인 연락처의 형식을, [API](../2-design/modules/account/design.md#프로필-제출연락처사진)는 본인 행 직접 갱신을, [runtime](../2-design/modules/account/design.md#프로필-제출연락처사진)은 `submit_profile` 호출을 적고 있다. 이 사례의 목적은 두 기술 설명이 일치하도록 작성 방법을 검증하는 것이다. 여기서 최종 호출 경로를 선택하지 않는다.

| 순서 | 작성자가 할 일 | 남길 내용 |
| --- | --- | --- |
| 1. 근거 비교 | 두 조항·결정 기록·현재 구현을 확인한다 | 확정된 사실, 서로 다른 설명, 추가 판단 필요 여부 |
| 2. 업무 규칙 확인 | 자기 연락처 수정 권한과 입력 형식의 근거를 확인한다 | account 업무 규칙의 고정 ID와 판정 예시. 템플릿만을 이유로 새 정책을 추가하지 않음 |
| 3. 기술 계약 정리 | 결정 근거에 따라 호출·쓰기·권한·실패·캐시를 한 행위로 묶는다 | `account/design.md`의 연락처 수정 계약. 미합의 내용은 미정에 둠 |
| 4. 화면 연결 | 입력·제출·실패·성공 직후의 모습을 해당 계약에 맞춘다 | profile 화면 상태·문안·짝 시안 |
| 5. 작업 범위 구별 | 문서 정정만인지 사용자 동작 변경까지인지 확인한다 | 정정은 비기능 plan. 기능 변화가 있으면 같은 슬러그의 intent→spec→plan과 승인 |
| 6. 검증 연결 | 실제 저장 경계와 사용자 흐름의 위험을 확인한다 | 규칙·AC 참조를 가진 필요한 테스트와 실행 근거. 수동 검증이 필요할 때만 evidence |
| 7. 변경 영향 마감 | 참조하는 활성 문서와 과거 기록을 구별해 확인한다 | 현재 계약의 모순 해소, 구현 차이·전환 작업, 보존한 과거 승인 기록 |

기존 연락처 형식에서 도출할 수 있는 판정 예시는 다음과 같다. 번호는 가짜다. 규칙 ID는 채택 후 해당 소유 문서에서 발급하며 이 표가 별도 규칙의 원천이 되지는 않는다.

| 입력 | 기대 판정 | 확인하는 경계 |
| --- | --- | --- |
| `01000000001` | 형식 검증 통과 | 010으로 시작하는 11자리 |
| `0100000000` | 형식 검증 거부 | 한 자리 부족 |
| `01100000001` | 형식 검증 거부 | 길이는 같지만 접두사가 다름 |

권한·저장·동시 수정·낙관적 복원은 위 형식 검사와 별도로 관련 설계 근거를 확인한다. 알려진 숫자 예시 세 개가 기술 계약 전체를 검증했다고 보지 않는다.

출근의 통신 지연도 같은 절차로 검토한다. 보고 시각·수신 시각·판정 시각을 명시하고, 상위 제안이 지적한 6분 지연 사례를 확정된 규칙과 대조한다. 10분 초과 지연의 처리처럼 아직 합의되지 않은 내용은 템플릿이나 테스트로 대신 결정하지 않는다.

## 15. 적용 순서와 완료 기준

### 15.1 판단할 항목

| 항목 | 추천 | 채택할 때의 범위 |
| --- | --- | --- |
| 작성법의 위치 | 단계 README에 틀·절별 질문·검토 기준을 함께 둔다 | 별도 가이드 폴더·생성기는 추가하지 않음 |
| 틀의 강제 수준 | 새 문서와 활성 문서의 해당 변경부터 적용한다 | 과거 승인·완료 기록은 보존, 빈 미래 기록은 만들지 않음 |
| 참조 방법 | spec·plan의 `sources`, 중요한 규칙·AC의 고정 ID를 쓴다 | 본문 링크·현재 승인 게이트와 함께 검증 |
| 작성 방법 | 문제·판정 사례·행위 계약·화면 상태·실행 결과를 구별한다 | 문서마다 자기 결정과 근거만 소유 |
| 초기 검증 | 계정 사례를 처음부터 끝까지 전개해 검토한다 | 미합의 제품 정책은 별도 판단으로 남김 |

상위 제안의 구조 변경과 이 제안의 작성법은 항목별로 판단할 수 있다. 새 경로를 쓰는 템플릿의 적용은 해당 구조 이관과 함께 한다. 현행 경로를 유지하는 동안에는 그 경로에 맞는 입력 참조를 사용한다.

### 15.2 적용 순서

1. 채택 항목과 상위 구조 제안의 관계를 기록한다. 중요한 소유권 결정은 후속 ADR에, 실제 이행 순서·완료 조건은 비기능 plan에 둔다.
2. `docs/README.md`와 단계 README에 해당 작성법을 옮긴다. 기존 작성 규칙과 다른 부분은 근거를 확인해 통합하고 제안서에만 현행 규칙이 남지 않게 한다.
3. 계정 설계를 시범 이관할 때 규칙·행위·화면 틀을 채운다. 실제 작업 성격에 따라 spec·plan·검증의 연결을 확인한다. 없는 기능 작업을 예시용 승인 문서로 만들지 않는다.
4. 시범 과정에서 답하기 어렵거나 중복되는 항목을 고친 뒤 나머지 활성 설계에 적용한다. 완료 spec·plan·ADR·log의 역사적 본문은 유지한다.
5. 작성법을 읽는 `.claude/agents/`와 `REVIEW.md`, 문서·시안 경로 검사, 기존 승인 게이트와의 연결을 같은 이행 작업에서 맞춘다. 테스트 전략의 세부 기준도 정의문에서 소유 문서로 옮긴다.
6. 첫 출시 준비에서 배포·운영 템플릿을 실제 환경으로 채워 실행 가능성을 확인한다. release·incident·evidence는 해당 사건과 필요가 있을 때만 쓴다.

### 15.3 자동 검사와 사람 검토

| 대상 | 자동으로 확인할 것 | 사람이 확인할 것 |
| --- | --- | --- |
| 문서 참조 | 실제 링크·앵커·`sources` 경로 존재, ID 중복 | 참조한 조항이 이번 결정을 실제로 뒷받침하는가 |
| 기능 사슬 | 적용 대상의 동일 슬러그, intent/spec/plan 연결, 기존 승인 게이트 보존 | 요구·설계·AC·검증의 의미가 이어지는가 |
| 승인 이후 변경 | 기준점·변경 검토 기록의 존재와 연결 | 기존 승인으로 충분한지, 범위가 바뀌었는지 |
| 화면·시안 | 소유 위치·짝 파일·기존 토큰 검사 | 상태·문안·접근성·성공 직후가 같은가 |
| 실행 기록 | 대상·근거 링크의 존재 | 실제로 실행했고 그 결과로 완료를 판정할 수 있는가 |

기존 [문서 검사](../4-test/execution.md#pnpm-test에-끼는-문서-검사)는 링크·지도 등을 확인한다. `sources`·고정 ID·승인 변경 기록의 추가 검사는 상위 제안과 함께 구현할 후속 범위이며 현재 이미 작동하는 것으로 안내하지 않는다. 검사 도입 때 새 문서·활성 작업·과거 완료 작업의 적용 대상을 명시하고, 모든 산출물을 소급 필수화하지 않는다. 제목 개수나 글자 수를 품질 기준으로 강제하지 않는다.

### 15.4 완료 기준

- 상위 제안에 나열된 문서 종류마다 작성 시점·입력·최소 틀·절별 작성 방법·검토 기준을 소유 안내에서 찾을 수 있다.
- 작성자가 같은 결정 본문을 여러 단계에 복사하지 않고 문제→규칙→행위→화면→완료 조건→검증을 연결할 수 있다.
- 계정 시범 사례의 기술 계약 불일치가 결정 근거에 따라 처리되고, 미정은 확정 내용과 구별된다.
- 템플릿을 실제 목적지에 복사해 채운 문서의 상대 링크와 규칙·AC 참조가 유효하다.
- 기능 승인과 작업 진행 상태를 구별하며, 비기능 task·준비 작업·완료 기록의 예외가 유지된다.
- 문서와 경로 소비자의 검사가 통과하고 lint·format·typecheck·단위 테스트가 통과한다. 토큰 파일을 재구성하지 않은 경우에도 이관이 생성 결과를 바꾸지 않았는지 확인한다.
- 배포·운영의 미정, 실행하지 않은 검증, 미래의 장애 기록을 사실처럼 채우지 않는다.

이 제안 자체의 산출물은 작성법을 검토할 수 있는 템플릿과 세부 방법이다. 실제 파일 이동·승인 상태 변경·새 검사 구현·문서 사이트 구축은 채택 후 이행 작업의 범위다.
