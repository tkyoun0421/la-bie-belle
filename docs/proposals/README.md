# proposals — 변경 제안

제품·설계·작업 방식의 변경 방향을 여러 단계에 걸쳐 검토하는 곳이다. 무엇을 바꾸고 왜 바꿀지 판단하기 전에 쓴다. 구분의 근거는 [ADR-008](../2-design/adr/ADR-008-proposals-and-implementation-plans.md)이다.

## 다른 문서와의 경계

| 자리 | 담는 것 |
| --- | --- |
| `1-plan/intent/` | 제품 기능·이슈의 사용자 문제와 디스커버리 결과. spec의 입력 |
| `proposals/` | 변경의 근거, 대안, 영향 범위, 판단할 항목 |
| `2-design/adr/` | 확정한 중요한 선택과 근거 |
| `3-build/plans/` | 실행 방향이 정해진 task의 구현 순서와 검증 방법. 비기능 task의 완료 조건 |

방향이 분명한 작은 수정은 별도 제안서 없이 task 문서로 간다. 정의문·훅에서 본 마찰은 [observations](../observations/README.md)에 기록하고, 대안을 검토할 필요가 있을 때 여기와 연결한다. 제안서를 모든 작업의 필수 관문으로 삼지 않는다.

## 파일과 작성 형식

제안 하나가 `<슬러그>.md` 한 파일이다. 소문자 kebab-case를 쓰고 같은 주제의 실행 plan과는 별개로 보관한다.

첫머리에 `status`를 적는다. 본문에는 검토 기준일과 범위, 확인한 문제와 근거 링크, 제안과 검토한 대안, 영향을 받는 파일, 채택 시 확인할 완료 기준을 담는다. 채택·보류·기각을 정한 뒤에는 결정 날짜와 이유, 연결된 정본·ADR·task를 덧붙인다. 제안별 상태는 각 파일이 정본이고, 아래 목록에는 상태를 복제하지 않는다.

```yaml
---
status: proposed
---
```

## 상태와 후속 작업

| status | 뜻 |
| --- | --- |
| `proposed` | 제안. 아직 판단할 항목이 있다 |
| `accepted` | 채택. 검토가 끝났고 채택한 변경을 정했다. 구현 완료라는 뜻은 아니다 |
| `deferred` | 보류. 다시 검토할 조건을 본문에 적는다 |
| `rejected` | 기각. 반영하지 않기로 한 이유를 본문에 적는다 |

판단은 총괄이 사용자와 정하고, 기록만으로 채택을 추정하지 않는다. 항목이 여럿이면 각 항목의 결과를 본문에 남긴다. 일부를 채택했어도 판단할 항목이 남으면 파일은 `proposed`다. 검토를 마쳤을 때 채택 항목이 있으면 `accepted`, 채택 없이 다시 볼 항목이 있으면 `deferred`, 전부 기각이면 `rejected`다. 후속 검토를 다시 열면 `proposed`로 바꾸고 이전 결정 기록은 남긴다.

채택한 항목은 영향을 받는 기획·설계 정본을 먼저 갱신하고, 필요한 구현 계획과 backlog 작업을 연결한다. 중요한 결정의 이유는 ADR로 남긴다. 제안서는 근거로 보존하고 새 정본을 링크한다. 기능은 기존 spec 승인 관문을 그대로 거친다. `accepted`는 spec의 `approved`를 대신하지 않으며, 제안 상태를 읽는 별도 구현 게이트도 만들지 않는다.
