# 시안의 정보 위계와 사용성을 다듬고 디자인 시스템의 빈자리를 채운다

2026-09-16, Git 기준점 `52de1f04c5d36d2f010756ac81f2fc0f8ed76295`에서 검토했다. 화면 시안과 디자인 시스템을 확인한 뒤 개선 사항과 추가 콘텐츠를 제안해 달라는 요청을 문서로 정리한 것이다.

머지 준비 중 main의 `fa3606d` 변경도 문서·CSS 차이로 확인했다. 달력 달 기준, 사람 픽커, 라운딩 변경은 이미 반영된 결정으로 취급한다. 서체 선언과 작은 알림 버튼의 높이, 관리자 홈 순서, 공통 상태의 미정은 해당 변경 후에도 남아 있다. 위 기준점에서 본 화면을 최신 라운딩으로 다시 렌더링해 전수 검증한 것은 아니다.

**추천 방향은 현재의 브라운 포인트·절제된 색상·여백을 유지하면서, 근무 정보의 강조 순서와 조작 편의부터 개선하는 것이다.** 서체와 터치 영역을 먼저 정리하고, 홈 화면의 정보 위계, 공통 상태, 추가 콘텐츠 순으로 검토한다.

이 문서의 작성과 main 반영은 제안 내용의 채택을 뜻하지 않는다. 아래 항목은 모두 검토 후보이며, 실제 화면·업무 규칙·기능 spec의 변경은 채택한 범위에 따라 진행한다. 상태의 의미는 [제안 안내](README.md#상태와-후속-작업)를 따른다.

### 이번 검토의 한계

- 대상은 설계용 HTML 시안이다. 실제 앱에 같은 문제가 구현돼 있다고 단정하지 않는다.
- 대표적인 고정 폭 모바일 목업을 중심으로 봤다. 모든 상태, 실제 휴대전화의 터치, 화면 읽기 프로그램, 글자 확대, 반응형 레이아웃을 전수 검증한 결과는 아니다.
- 사용자 관찰이나 업무 처리 시간 측정은 하지 않았다. 정보 위계와 메뉴 순서의 효과는 가설이며, 비교 시안과 사용자 확인이 필요하다.
- 서체 차이·버튼 크기·문서에 남은 미정은 확인 사실이다. 불편의 빈도나 개선 효과를 수치로 추정하지 않는다.
- 이 문서의 숫자는 관찰값·예시·검증 조건이다. 디자인 값의 정본은 계속 [tokens.md](../2-design/design-system/tokens.md)이며, 새 값을 채택하면 그곳에만 정의한다.

## 문제와 근거

### 유지할 부분

브랜드 색을 주요 행동에 아끼는 방식, 목록과 여백으로 정보를 나누는 방식, 급여 금액의 강조, 짧은 한국어 문안이 화면 전반에서 일관된다. 특히 출근 인증은 주요 버튼이 분명하고, 실패 시 위치 재확인과 QR 대안이 이미 마련돼 있다. 이를 개선안의 출발점으로 삼는다.

라이트·다크 팔레트, 역할별 색 토큰, 숫자 정렬, 문안 규칙, 빈 상태와 실패 상태도 이미 설계돼 있다. 이 항목들이 없다는 전제로 새 체계를 만들지 않는다. 근거는 [디자인 시스템 안내](../2-design/design-system/README.md), [색 원칙](../2-design/design-system/foundation/color.md), [컴포넌트](../2-design/design-system/components.md), [문안](../2-design/design-system/writing.md)이다.

### D-01

**시안과 구현의 서체를 맞춘다.**

- 추천: 앱 목업 안에서는 지정 서체를 먼저 사용한다. 시안 바깥의 설명·캡션 서체는 별개로 유지할 수 있다.
- 이유: 지금 보는 자간과 줄바꿈을 승인해도 구현에서 다른 서체가 나오면 다시 판단해야 한다. 먼저 서체를 맞춰 이후 정보 위계 비교의 조건을 통일한다.
- 적용 방법: [서체 연결](../2-design/design-system/tokens.md#서체-연결)을 따르고, 실제 폰트 로딩 여부와 fallback 상태를 구별해서 확인한다. CSS에 이름만 적힌 상태를 완료로 보지 않는다.
- 대안: 시스템 서체를 제품의 정식 서체로 채택할 수도 있다. 이 경우 시안만 유지하는 것으로 끝나지 않고 타이포그래피 정본과 앱의 서체 연결까지 재검토해야 한다. 현재 결정과 일치시키는 추천안보다 범위가 크다.
- 완료 기준: 대시보드의 시각·알림, 근무표의 달 제목·명단, 급여 금액, 긴 이름이 지정 서체에서 잘리지 않는다. 폰트가 늦게 로딩되는 경우에도 주요 버튼을 찾을 수 있다.

### D-02

**작게 보이는 버튼도 충분히 누를 수 있게 한다.**

- 추천: 알림 CTA의 시각적 크기와 보조 행동의 무게는 유지하되, 실제 터치 영역은 기존 기준을 충족시킨다.
- 적용 방법: 버튼 바깥 투명 영역 또는 레이아웃의 여백으로 누를 수 있는 면을 확보한다. 수락·거절이 나란히 있는 경우 두 버튼의 확장 영역이 겹치지 않아야 한다. 필요한 경우 버튼 사이 간격이나 알림의 보조 줄 높이를 함께 조정한다.
- 확인 대상: 알림의 수락·거절·근무표 보기부터 시작한다. 달 이동 화살표·사진 수정 아이콘·시트 닫기 등도 실제 영역을 측정하되, 작아 보인다는 이유만으로 모두 결함으로 기록하지 않는다.
- 대안: 버튼 외형 자체를 키우면 구현은 단순해진다. 대신 대시보드의 출근 인증 버튼과 시각적으로 경쟁할 수 있어 두 안을 함께 비교한다.
- 완료 기준: 버튼 중앙과 가장자리를 눌렀을 때 의도한 행동이 실행된다. 인접 버튼의 영역이 겹치지 않고, 부모의 잘라내기 설정이 확장 영역을 없애지 않는다. 키보드 포커스도 구분된다.

### D-03

**대시보드에서 근무 시각과 포지션을 먼저 읽히게 한다.**

현재 화면은 오늘 근무 덩이에 무게를 주고 주간 근무·예상 급여를 아래로 내리는 구조다. 그 구조는 유지하고 덩이 안의 강조 순서만 비교한다.

| 자리 | 현행 | 비교할 추천안 |
| --- | --- | --- |
| 오늘 근무 머리 | 「오늘 근무가 있어요」가 가장 큼 | 「오늘 근무」를 맥락으로 두고 시각을 강조 |
| 핵심 정보 | 띠 양끝에 시각, 아래에 포지션 | `10:00–19:00`과 `안내 · 9시간`을 가까이 배치 |
| 진행 정보 | 진행률·남은 시간·띠 | 근무 정보 아래에서 보조 정보로 유지 |
| 행동 | 본문 안의 출근 인증 버튼 | 같은 근무 덩이 안에 유지 |

- 추천: 현행과 비교안 두 장을 같은 서체·같은 데이터로 만든다. 근무 시각을 바로 찾는지, 인증 가능 여부와 인증 완료를 구별하는지 확인한 뒤 고른다.
- 상태별 처리: 확정 전에는 모르는 시각을 채우지 않는다. 근무 없는 날은 다음 근무 안내를 유지한다. 인증 완료·인증 누락·사유 제출 후에도 결과 안내가 시각 아래에서 사라지지 않게 한다.
- 대안: 현행을 유지하고 시각·포지션의 크기와 대비만 한 단계 높이는 작은 변경도 비교한다. 제목을 바꾸지 않고 문제를 풀 수 있으면 그쪽을 택한다.
- 완료 기준: 사용자가 오늘의 시작·종료 시각, 포지션, 지금 가능한 행동을 구별할 수 있다. 같은 내용을 불필요하게 반복하지 않고 긴 포지션 이름에서도 인증 버튼이 밀려 가려지지 않는다.

### D-04

**관리자 홈에서 처리할 일을 설정 앞에 놓는다.**

- 추천 순서: 근무표 관리 타일 → 승인할 일 → 가입 대기 → 근무 시간 기본값 → 기존 관리 도구 묶음.
- 유지할 부분: 근무표 관리 타일의 상태 요약과 임박한 빈 자리 경고는 이미 설계돼 있으므로 그대로 활용한다. 대기 건수·대기 인원 수도 기존 의미를 유지한다.
- 이유: 기본값은 설정이고 승인·가입은 처리해야 줄어드는 일이다. 기존 문서도 승인할 일이 가입보다 잦다고 설명한다. 그 판단을 설정과의 순서에도 적용해 볼 만하다.
- 대안: 근무표를 처음 만드는 시기에는 기본값 설정이 먼저 필요할 수 있으므로 현행 유지도 가능하다. 다만 대기 수에 따라 메뉴가 계속 이동하는 자동 정렬은 첫 제안에 포함하지 않는다. 익숙한 위치를 유지하기 위해서다.
- 완료 기준: 대기가 있는 경우와 없는 경우 모두 메뉴 위치가 일정하다. 설정 변경이 이미 열린 날에 소급 적용되지 않는다는 기존 안내가 남고, 기본값 설정으로 가는 길도 쉽게 찾을 수 있다.

### S-01

**공통 컴포넌트의 조작 상태를 한 표로 완성한다.**

- 추천: Button부터 기본·마우스 올림·누르는 중·키보드 포커스·비활성·처리 중을 나란히 정의한다. Input의 오류·포커스 조합, 선택 목록의 선택·비선택도 이어서 확인한다.
- 역할 분담: 상태의 모양과 조합은 [components.md](../2-design/design-system/components.md), 값은 [tokens.md](../2-design/design-system/tokens.md), 처리 시점과 재시도는 [runtime.md](../2-design/system/runtime.md)가 소유한다.
- 주의: disabled 색과 일부 pressed 값은 이미 있다. 모든 상태에 새 토큰을 늘리지 않고 기존 역할 토큰으로 표현되는지 먼저 본다. 마우스 올림이 없어도 누를 수 있는 곳을 알아야 한다.
- 처리 중: 현재 실행 규칙은 버튼 글자 자리에 스피너를 두는 것이다. 버튼 폭을 유지하고, 접근 가능한 이름으로 어떤 작업을 처리 중인지 전달하는 방법을 함께 정한다.
- 대안: shadcn 기본 상태를 유지할 수 있다. 이 경우에도 우리 토큰과의 연결을 확인하고 기본값을 따르는 범위를 명시해야 한다. 화면마다 별도로 고르는 방식은 반복 검수 비용이 크다.
- 완료 기준: 같은 역할의 버튼은 화면이 달라도 같은 상태를 보인다. 포커스·선택·비활성을 구분할 수 있고, 실패 뒤 재시도 가능 상태가 해당 화면의 계약과 일치한다.

### S-02

**로딩과 통신 실패의 공통 모양을 정한다.**

실행 규칙은 이미 [로딩](../2-design/system/runtime.md#로딩)과 [오프라인](../2-design/system/runtime.md#오프라인)에 있다. 이번 제안은 그 규칙에 대응하는 시각 요소를 완성하는 것이다.

| 상황 | 기존 계약에 맞춰 그릴 내용 | 구별할 점 |
| --- | --- | --- |
| 첫 진입, 데이터 없음 | 최종 정보 배치에 가까운 스켈레톤 | 실제 빈 목록처럼 보이지 않게 함 |
| 캐시를 보이며 재조회 | 기존 값을 유지 | 이미 읽던 내용을 전면 로딩으로 가리지 않음 |
| 메모리에 화면이 있고 통신 실패 | 기존 화면 + 통신 없음 띠, 쓰기 제한 | 저장됐다는 인상을 주지 않음 |
| 새로 실행했는데 통신 없음 | 공통 통신 없음 화면 | 빈 상태와 구별하고 가능한 복구 행동 제시 |
| 보내기 실패 | 입력을 유지하고 실패·다음 행동 표시 | 다시 보내야 하는지, 기다려야 하는지 구별 |

- 추천: ListRow·금액 요약·근무표에 필요한 최소 스켈레톤과 중립적인 통신 안내부터 정한다. 화면 전체가 회색으로 바뀌는 모션을 기본으로 추가하지 않는다.
- 문안 예시: 「연결을 확인하고 다시 시도해주세요」처럼 현재 상황과 다음 행동을 짝짓는다. 저장되지 않았다는 문장은 저장 실패가 확인된 경우에만 사용한다.
- 예외: 출근 인증의 화면 내 재시도 등 영역별 계약은 [출근 기술 설계](../2-design/modules/attendance/design.md)를 따른다. 공통 디자인을 만들면서 모든 쓰기를 자동 재시도로 바꾸지 않는다.
- 대안: 화면별 안내만 둘 수도 있다. 하지만 동일한 통신 실패가 서로 다른 의미로 보일 수 있으므로 공통 부분과 영역별 예외를 분리하는 안을 추천한다.
- 완료 기준: 로딩·빈 상태·읽기 실패·쓰기 실패가 구별된다. 재연결 후 안내가 사라지는 시점과 잠긴 행동이 풀리는 시점이 실행 계약과 맞는다.

### S-03

**자주 쓰는 컴포넌트를 한곳에서 비교한다.**

- 추천: Button, ListRow, Input, Badge, 알림 블록, BottomCTA, Dialog·바텀시트부터 작은 미리보기 페이지를 만든다. S-01·S-02에서 정한 상태와 실제 사용 사례를 같은 자리에서 본다.
- 담을 내용: 라이트·다크, 긴 이름과 문장, 큰 금액, 긴 포지션, 처리 중·실패, 시트 안의 키보드 표시와 하단 버튼 관계.
- 화면 조건: 폭 320·375·430 CSS px와 글자 확대 200%를 검토 사례로 둔다. 이는 이번 검토에서 통과한 결과나 새 반응형 기준의 선언이 아니다. 실제 적용 범위는 채택 시 정한다.
- 구성 원칙: 정본의 토큰과 컴포넌트를 참조하고 미리보기 안에 별도 팔레트·규칙을 복제하지 않는다. 이후 실제 컴포넌트가 구현되면 가능한 한 그것을 렌더링해 차이를 줄인다.
- 대안: 초기에는 대표 시안의 비교 모음만으로 시작할 수 있다. 별도 Storybook 도입이나 모든 화면의 전시까지는 필요하지 않다. 유지할 예제가 많아지는 비용을 먼저 본다.
- 완료 기준: 지정한 사례를 반복해서 볼 수 있고, 문서와 화면의 차이가 어느 컴포넌트에서 발생했는지 찾을 수 있다. 예제 데이터는 가짜 값만 사용한다.

### C-01

**근무가 바뀌었을 때 바뀐 항목을 요약한다.**

- 추천: 근무표 변경 안내에 날짜, 변경 항목, 가능한 경우 변경 전후 값을 제공한다. 예를 들면 「9월 12일 근무 시간이 바뀌었어요」 아래에 `10:00–19:00 → 11:00–20:00`을 두는 방식이다. 예시 값은 가짜이며 실제로 지원할 변경 유형은 별도 확인한다.
- 해결할 문제: 현재 값만 보여주면 사용자가 기억에 의존해 무엇이 달라졌는지 비교해야 한다. 근무에서 빠진 사람은 현재 명단에서 자기 줄을 찾을 수도 없다.
- 데이터 전제: [알림 행](../2-design/modules/notification/design.md#알림-행)은 `kind`와 `payload`를 저장하지만 이것만으로 모든 이전 값이 보존된다고 볼 수는 없다. 변경 시점의 이전 값·새 값·대상자·시각을 어떤 계약으로 남길지 확인한다. 보존하지 않은 과거 값을 현재 근무표에서 추정하지 않는다.
- 대상과 노출: [알림 대상](../2-design/modules/notification/README.md#ntf-014)을 임의로 넓히지 않는다. 시간이 바뀌는 경우의 대상도 기존 근무표·알림 계약과 대조한다. 동료의 개인 정보나 사유가 요약에 들어가지 않게 한다.
- 노출 위치: 대시보드의 한 건 요약이 지나치게 길어지면 자세한 비교는 근무표 진입 후 보여주는 안을 검토한다. 읽음·닫기 동작은 기존 규칙을 따른다.
- 대안: 이전 값이 없거나 저장 비용이 크면 변경된 항목 이름과 현재 값만 표시한다. 전후 비교가 없는 알림에도 근무표로 가는 길을 남긴다.
- 완료 기준: 추가 배정·배정 해제·지원하는 시간 또는 포지션 변경·연속 변경을 구별한다. 오래된 알림의 당시 변경 내용과 현재 근무표를 혼동시키지 않는다. 이전 값이 없는 경우에는 비교를 만들어내지 않는다.

### C-02

**급여 계산 근거를 보여줄지 기존 결정을 재검토한다.**

현재 급여 화면은 예상 금액, 근무 횟수·시간, 날짜별 내역과 연장 정보를 제공한다. 내역이나 예상치 안내가 빠져 있다는 제안은 아니다. 문제는 사용자가 그 금액을 직접 검산할 때 적용 시급을 알 수 있느냐이다.

[급여 화면의 기존 결정](../2-design/modules/payroll/screens/payroll.md#규칙과-부딪힌-자리)은 시급을 노출하지 않고, 검산이 실제로 막히면 프로필의 「내 시급」을 검토하는 것이다. 따라서 계산 근거 추가를 단순한 디자인 보완으로 바로 반영하지 않는다.

| 대안 | 이익 | 비용·한계 |
| --- | --- | --- |
| 현행 유지 | 화면과 공개 범위가 단순함 | 적용 시급을 모르면 검산하기 어려움 |
| 프로필에 현재 시급만 표시 | 기존 문서의 재검토 방향과 가까움 | 과거 근무에 적용한 값이나 조정 근거는 설명하지 못함 |
| 급여에서 날짜별 계산 근거 펼침 | 금액을 보는 자리에서 적용 시간·시급·연장·조정을 확인 | 과거 적용값, 공개 항목, 화면 상호작용의 설계가 필요함 |

- 추천: 먼저 사용자가 어떤 내역을 이해하지 못하는지 확인하고 공개 범위를 결정한다. 추가한다면 전체 급여 화면을 복잡하게 만들기보다 날짜별로 필요한 근거를 펼쳐 보는 안을 우선 비교한다.
- 계산 원칙: [급여 업무 규칙](../2-design/modules/payroll/README.md)을 참조한다. 예시 산식이 새 급여 규칙이 되지 않도록 하고, 현재 시급으로 과거 내역을 단순 재계산하지 않는다. 표시한 근거의 합이 해당 내역 금액과 맞아야 한다.
- 범위: 예상치 표시는 유지한다. 실제 지급 확정, 세금·보험 계산, 지급일 약속을 이 제안에 추가하지 않는다. 타인의 시급 공개도 포함하지 않는다.
- 완료 기준: 일반·연장·교육·결근·출근 인정·관리자 조정 등 적용 가능한 내역에서 표시 근거와 결과가 일치한다. 시급 변경 전후 내역도 혼동하지 않는다. 공개하지 않는 항목이나 근거가 없는 내역의 안내를 정한다.

### C-03

**처음 출근하는 사람이 인증과 복구 방법을 찾게 한다.**

- 추천: 기존 기능을 설명하는 짧은 안내를 제공한다. 위치 인증, 위치가 안 잡힐 때의 QR 인증, 인증을 놓쳤을 때의 사유 제출을 상황별로 나눈다.
- 진입 위치: 출근 인증 화면의 보조 도움말 또는 「나」의 도움말 진입을 비교한다. 먼저 기존 화면 안의 짧은 설명으로 충분한지 본다. 앱을 열자마자 전면 안내를 강제하는 방식은 [문안 원칙](../2-design/design-system/writing.md#다크패턴을-쓰지-않는다)과 맞지 않는다.
- 콘텐츠 초안: 「위치 권한을 허용하고 홀에서 인증해요」, 「위치가 안 잡히면 현장 QR로 인증할 수 있어요」, 「인증을 놓쳤다면 사유를 남겨주세요」. 실제 노출 문구는 화면 문서가 소유한다.
- 조건: [인증 가능 시간](../2-design/modules/attendance/README.md#att-008)과 [사유 제출 기한](../2-design/modules/attendance/README.md#att-011)을 적용한다. 시간이 지난 뒤에도 인증할 수 있는 것처럼 안내하지 않고, 사유 제출을 승인 완료처럼 표현하지 않는다.
- 확인이 필요한 정보: QR이 실제로 비치된 위치와 권한 설정 안내 대상 기기. 운영자가 제공하지 않은 위치·연락처를 지어내지 않는다. 기기별 설정 절차는 게시 시 실제 화면에서 확인한다.
- 대안: 기존 QR 링크와 오류 안내만 유지할 수 있다. 사용자가 복구 방법을 충분히 찾는다면 별도 도움말 화면을 추가할 필요가 없다.
- 완료 기준: 사용자가 자신의 상황에 맞는 인증 또는 복구 방법을 찾는다. 위치 거부·카메라 거부·만료된 QR·인증 시간 종료·사유 기한 종료에서 불가능한 행동을 권하지 않는다.

### 범위 밖과 의존 관계

- 현재 브랜드를 전면 교체하거나 팔레트를 늘리는 작업은 포함하지 않는다. 공식 브랜드 색 확인 문제는 [토큰의 기존 미정](../2-design/design-system/tokens.md#아직-안-정한-것)에서 계속 다룬다.
- 시안 CSS를 앱 코드로 복사하는 작업은 포함하지 않는다. 실제 구현은 [퍼블리싱 원칙](../2-design/design-system/README.md#퍼블리싱)을 따른다.
- 차트·직원 순위·광고·자동 메시지·실제 급여 지급 기능을 추가하지 않는다.
- 근무표의 달력 달 기준과 사람 픽커, 버튼·배지의 라운딩은 `fa3606d`에서 이미 결정·반영됐다. 이 제안으로 다시 미정으로 돌리거나 이전 형태를 복원하지 않는다. 관련 작업의 재개 맥락은 [handoff](../handoff.md)에 있다.
- 작은 화면·글자 확대 사례를 더하는 것은 검토 범위 확대다. 기존 시안이 이미 모든 기기에서 실패한다는 판단이 아니다.
- 기능 동작이 추가되는 항목은 채택 후 intent·spec·plan으로 연결한다. 문서·토큰·시안 정합성만 맞추는 비기능 작업은 해당 실행 계획으로 연결한다. 제안 채택과 기능 spec 승인은 구별한다.

| 4 | S-03으로 대표 조각을 반복 확인 | 실제로 자주 확인할 사례와 유지 범위가 정해짐 | 미리보기 산출물과 안내 링크 |

서체를 먼저 맞추는 이유는 뒤의 화면 비교에서 줄바꿈과 글자 폭을 같은 조건으로 보기 위해서다. 콘텐츠는 그 뒤에 검토해 현재 화면의 문제를 새 기능으로 덮지 않는다. 전 영역 설계 후 구현한다는 기존 진행 순서는 이 제안으로 변경하지 않는다.

### 채택 후 검증할 사례

아래는 앞으로 실행할 검증 계획이다. 이번 시안 검토에서 모두 통과했다는 기록이 아니다.

| 축 | 사례 | 확인할 결과 |
| --- | --- | --- |
| 근무 상태 | 확정 전·근무 없음·인증 전·인증 후·미인증·사유 제출 후 | 모르는 값을 만들지 않고 현재 상태와 가능한 행동을 구별 |
| 글자와 숫자 | 긴 이름·긴 포지션·여러 줄 알림·큰 금액·여러 자리 건수 | 핵심 정보를 잘라내거나 버튼을 가리지 않음 |
| 화면과 테마 | 좁은 폭·일반 폭·넓은 모바일 폭, 라이트·다크 | 같은 정보 위계와 읽을 수 있는 대비 유지 |
| 입력 방식 | 터치·키보드·글자 확대·모션 축소 | 버튼 영역이 겹치지 않고 포커스와 상태가 드러남 |
| 통신 | 최초 로딩·캐시 재조회·읽기 실패·쓰기 실패·복구 | 입력 보존·재시도·쓰기 제한이 해당 계약과 일치 |
| 변경 알림 | 이전 값 있음·없음·배정에서 빠짐·연속 변경 | 변경 당시 사실과 현재 상태를 구별 |
| 급여 근거 | 과거 시급·연장·교육·조정·근거 없음 | 공개하기로 정한 근거와 표시 금액이 일치 |
| 출근 도움말 | 권한 거부·QR 문제·시간 종료·기한 종료 | 실제로 가능한 다음 행동만 안내 |

문서 검증은 링크·앵커·문서 지도와 정본의 참조를 확인한다. 시안 검증은 렌더링된 화면과 실제 누를 수 있는 영역을 확인한다. 기능 구현 후에는 해당 spec의 관찰 결과에 맞는 테스트를 실행한다. 사진이나 모양이 같다는 이유만으로 저장·재시도·권한 동작까지 통과한 것으로 보지 않는다.

### AC-01

채택한 항목마다 근거와 목적지가 연결돼 있고, 제안·확정된 기준·실제 구현을 구별할 수 있다. 바뀐 기준을 참조하는 활성 문서와 테스트의 영향이 확인된다.

### AC-02

D-01·D-02를 채택한 경우, 지정 서체와 fallback을 구별해 확인하고 터치 영역은 기존 기준을 충족한다. 주변 버튼과의 겹침이나 잘림이 없다.

### AC-03

D-03·D-04를 채택한 경우, 현행과 비교한 화면 및 선택 근거가 남고 선택한 상태·메뉴 순서가 화면 문서와 시안에 일치한다.

### AC-04

S-01·S-02·S-03 중 채택한 항목은 대표 화면에서 다시 확인할 수 있다. 값은 토큰 정본에서 관리하며, 미리보기가 별도 디자인 규칙을 만들지 않는다.

### AC-05

C-01·C-02·C-03 중 채택한 항목은 필요한 데이터·공개 범위·행동 조건과 기능 범위가 정해져 있다. 존재하지 않는 과거 값·운영 정보·지급 약속을 표시하지 않는다.
