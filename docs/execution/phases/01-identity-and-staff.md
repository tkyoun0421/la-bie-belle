# P1. 인증, 승인, 역할, 근무자 관리

## 목표

Google OAuth 가입부터 관리자 승인, 역할, 개인정보, 시급, 가능 포지션 관리까지 안전하게 제공한다.

## 진입 조건

- P0 완료.
- 관련 spec: [PRD](../../product/PRD.md) `AC-12`, `AC-13`, [Domain](../../product/DOMAIN.md) `DOMAIN:IDENTITY`, [ADR-0002](../../standards/adr/0002-authorization-boundaries.md), [ADR-0007](../../standards/adr/0007-offboarding-and-history-recovery.md), [ADR-0010](../../standards/adr/0010-dormancy-and-automatic-account-lifecycle.md).

## 작업

### P1-T01. Google OAuth와 세션

- Supabase Google provider와 PKCE callback을 연결한다.
- 로그인, 로그아웃, 세션 갱신, 보호 라우트를 구현한다.
- OAuth 성공 후 profile 존재 여부에 따라 온보딩 또는 상태 화면으로 이동한다.

기획 확정 사항(2026-08-06 인터뷰):

- Google OAuth 클라이언트는 사용자가 발급 완료했고 값은 로컬 `.env`에만 둔다. `supabase/config.toml`의 `[auth.external.google]`은 env 치환으로 secret을 주입한다.
- 로그인 화면은 [Worker flows](../../product/design/WORKER-FLOWS.md)의 로그인 절이 정본이다 — 제품명, 용도 한 문장, `Google로 계속하기` 한 화면.
- 보호 범위는 기존 탭 라우트 전체다. 미로그인 접근은 로그인 화면으로 리다이렉트한다. dev 전용 `/preview`는 프로덕션 라우트가 아니므로 대상 밖이다.
- profile 없는 사용자는 `/onboarding` 자리표시 화면으로 보낸다(사용자 결정) — 리다이렉트 분기 로직은 이번에 완성되고 P1-T02가 화면만 교체한다. profile 있는 사용자는 홈으로 보내며 상태별 세분화는 P1-T02 이후가 소유한다.
- E2E는 실물 Google 로그인 대신 로컬 Supabase 테스트 사용자 세션 주입으로 보호 라우트를 검증하고, Google 버튼은 리다이렉트 시작까지만 단언한다.
- 파생 결정: push 절차의 `.env` 취급을 "이미 존재하면 보존"으로 바꾼다(실물 secret 보호) — ci-finisher 정의를 별도 메타 커밋으로 갱신한다.

인수 조건:

- 신규·기존 사용자가 Google로 로그인할 수 있다.
- 미인증 사용자는 보호 화면과 API에 접근할 수 없다.

기획 승인: user, 2026-08-06.

### P1-T02. 가입 프로필과 승인 대기

- 이름, 휴대폰, 성별, 생년월일 폼을 구현한다.
- 필수값과 형식을 서버에서 검증한다.
- 신규 프로필 상태를 `pending`으로 생성한다.
- 승인 전에는 신청·스케줄·개인정보 API를 차단한다.

인수 조건:

- 가입 완료 후 승인 대기 화면만 접근 가능하다.
- 브라우저 요청을 조작해도 활성 사용자 기능을 호출할 수 없다.

### P1-T03. 관리자 가입 승인

- 관리자가 pending 목록과 제출 정보를 조회한다.
- 승인과 거절, 처리자, 처리 시각을 기록한다.
- 승인 시 안내·매니저·축가 기본 가능 포지션을 부여한다.
- 안내의 남성 조건은 배정 시 별도로 강제한다.

인수 조건:

- 승인된 사용자만 근무자 홈에 진입한다.
- 승인·거절은 감사 로그에 남는다.

### P1-T04. 역할과 최초 슈퍼 관리자

- `worker`, `admin`, `super_admin` 다중 역할 모델을 구현한다.
- 환경변수 이메일과 일치하는 최초 로그인 사용자에게 슈퍼 관리자 역할을 멱등 부여한다.
- 슈퍼 관리자만 일반 관리자를 임명·해제한다.
- 관리자도 근무자 기능을 사용할 수 있게 한다.

인수 조건:

- 일반 관리자는 다른 관리자를 임명할 수 없다.
- 역할 변경 후 세션과 RLS 결과가 일치한다.

### P1-T05. 근무자 관리

- 관리자용 근무자 목록, 검색, 상태 필터를 만든다.
- 개인정보, 개인 시급, 가능 포지션을 조회·수정한다.
- 가능 포지션 수정은 관리자만 허용한다.
- 시급과 개인정보는 일반 근무자 목록 응답에 포함하지 않는다.

`worker_position_eligibilities`가 `positions`를 참조하는 첫 테이블이다. [ARCHITECTURE](../../standards/ARCHITECTURE.md)의 `ON DELETE RESTRICT` 규약을 여기서 처음 적용하고, P0-T03이 걸 상대가 없어 이월한 삭제 차단 검증도 함께 맡는다.

인수 조건:

- 관리자가 개인 시급과 가능 포지션을 저장할 수 있다.
- 근무자는 본인 시급만 읽을 수 있다.
- 가능 포지션에 쓰인 포지션의 삭제가 DB에서 차단되고 비활성화만 가능하다(P0-T03에서 이월).

### P1-T06. 휴면 계정 상태와 접근 차단

목표:

- `pending`, `active`, `rejected`, `dormant`, `departed` 상태와 서버 권한 경계를 구현한다.
- 본인과 관리자의 휴면 해제, 관리자의 수동 휴면 command와 감사 이력을 구현한다.

범위:

- `일시 정지` 상태를 만들지 않고 `dormant`를 사용한다.
- 휴면 사용자는 상태·자동 탈퇴 예정일 화면과 본인 재활성화만 접근할 수 있고 다른 업무 mutation은 데이터 계층에서 차단한다.
- 본인 또는 관리자 재활성화는 서버 시각으로 인정 활동 시각을 갱신하고, 사유 없이 변경 전후 상태·행위자·시각을 감사한다.
- 관리자의 수동 휴면은 인정 활동 시각을 바꾸지 않는다.
- 비활성 사용자의 새 신청과 배정을 데이터 계층에서 차단하고 기존 이력은 삭제하지 않는다.

비목표:

- 3개월·1년 예약 작업, 신청·배정 차단 조건과 탈퇴 연쇄 처리는 P7-T01에서 구현한다.
- 탈퇴 후 진행 중 근무의 체크아웃 예외는 출퇴근 결정에서 별도로 다룬다.

인수 조건:

- 휴면 사용자는 로그인 상태여도 재활성화 외의 업무 mutation을 수행하지 못한다.
- 본인과 관리자가 휴면을 해제하면 인정 활동 시각과 3개월·1년 기준이 같은 서버 시각으로 초기화된다.
- 관리자의 수동 휴면은 인정 활동 시각을 바꾸지 않는다.
- 상태 변경에 사유 입력을 요구하지 않고 변경 전후 상태·행위자·시각을 조회할 수 있다.
- 동시 재활성화 요청은 멱등하며 권한 우회가 차단된다.

### P1-T07. 권한 회귀 테스트

- PRD와 Architecture의 권한 매트릭스를 SQL과 API 통합 테스트로 구현한다.
- 본인, 다른 근무자, 팀장 후보, 관리자, 슈퍼 관리자 fixture를 둔다.

인수 조건:

- 개인정보·시급·역할에 대한 허용과 거부 케이스가 모두 자동화되어 있다.
- service role 없이도 사용자 경로가 필요한 작업을 수행한다.

## 종료 조건

- 승인된 근무자와 관리자가 각자 허용된 화면만 사용한다.
- 개인정보와 역할 우회 테스트가 통과한다.

## 제외

- 자동 휴면·탈퇴, 신청·배정 연쇄 처리와 재가입 이력 복구는 P7.
- 스케줄 기능은 P2 이후.
