# P4. 변경 요청과 PWA 푸시

## 목표

확정 후 취소·교대·관리자 변경을 감사 가능하게 처리하고 앱 내 알림과 PWA 푸시로 전달한다.

## 진입 조건

- P3 완료.
- 관련 spec: [PRD](../../product/PRD.md) `AC-06`, `AC-11`, [Domain](../../product/DOMAIN.md) `DOMAIN:SCHEDULING`, `DOMAIN:NOTIFICATIONS`, [ADR-0005](../../standards/adr/0005-transactional-notification-outbox.md).

## 작업

### P4-T01. 알림과 outbox 기반

2026-08-16 기획 승인. 스키마·읽음·알림함 실데이터·시범 사건 1종의 수직 완결이다.

- notifications, notification_outbox, push_subscriptions 스키마를 만든다.
- 멱등성 키(`event_type + aggregate_id + recipient_id + revision`, ADR-0005), 재시도 상태, 읽음 시각을 구현한다.
- 알림함 화면을 mock에서 실데이터로 연결한다 — 목록 조회, 읽음 처리(개별·스와이프·모두 읽음)의 서버 반영(2026-08-16 기획).
- 시범 사건 1종: 스케줄 확정 시 배정자 전원에게 앱 내 알림을 확정과 같은 트랜잭션에 기록한다 — P4-T03에서 이관(2026-08-16 기획).
- 알림함 오늘/이번 주 그룹 경계는 Asia/Seoul 고정이다(2026-08-16 기획).
- 알림은 무제한 보존한다 — 정리 로직 없음, 보관 만료는 P7 재검토(2026-08-16 기획).

비목표:

- 푸시 실발송 — 구독은 P4-T02, 소비자·재시도 실행은 P4-T08. 이 task는 outbox 행과 상태 모델까지다.
- 확정 외 알림 생성(모집 오픈·변경·요청 계열)은 P4-T03.
- 문자·카카오톡(PRD 제외).

인수 조건:

- 같은 outbox를 반복 처리해도 중복 알림이 생기지 않는다(멱등성 키).
- 푸시 경로(outbox 상태)와 무관하게 앱 내 알림 행이 유지된다 — 분리 기록.
- 확정 트랜잭션이 실패하면 알림·outbox 행도 함께 롤백된다.
- 알림함이 실데이터로 그룹·읽음을 표시하고 읽음 시각이 서버에 남는다.

### P4-T02. PWA 설치와 Web Push 구독

- Service Worker와 VAPID 구독·해지 흐름을 구현한다.
- 권한을 사용자 행동 후 요청하고 거부·미지원 상태를 안내한다.
- 한 사용자의 여러 기기 구독을 지원한다.
- 알림 클릭 시 관련 화면으로 이동한다.

인수 조건:

- Android와 홈 화면 설치 iPhone에서 테스트 알림을 수신한다.
- 만료된 구독을 안전하게 비활성화한다.

### P4-T03. 모집·확정·변경 알림

- 모집 오픈 대상에게 알림을 생성한다.
- 스케줄 확정 알림은 P4-T01로 이관됐다(2026-08-16 P4-T01 기획) — 이 task는 확정 알림의 푸시 링크 연결(상세 화면 이동)만 확인한다.
- 확정 후 시간·예식·배정 변경은 영향받는 사용자에게 revision 기반 알림을 보낸다.
- 변경 전후를 감사 로그에 남긴다.

인수 조건:

- 관리자 재시도로 같은 revision 알림이 중복 발송되지 않는다.
- 관련 없는 근무자에게 변경 알림이 가지 않는다.

### P4-T04. 근무 취소 요청

- 취소 신청 흐름을 마감 후~확정 전 구간(신청 철회 요청)까지 확장할지 P4 기획 인터뷰에서 결정한다(2026-08-07 P2-T04 기획에서 이월 — 해당 구간의 임시 해결책은 재오픈).
- 확정 근무자가 선택 사유로 취소를 요청한다.
- 승인 전 기존 배정이 유지된다.
- 관리자가 승인·거절하고 요청자에게 알린다.
- 승인 시 배정은 삭제하지 않고 취소 상태와 이력을 남긴다.

인수 조건:

- pending 요청 중 중복 취소 요청을 만들 수 없다.
- 요청자와 관리자 외에는 상세 사유를 볼 수 없다.

### P4-T05. 특정 근무자 교대

- 기존 근무자가 교대 상대를 선택한다.
- 후보는 기존 정식 포지션을 모두 수행할 수 있어야 한다.
- 상대에게 알림을 보내고 읽음 여부를 관리자에게 표시한다.
- 상대의 응답 없이도 관리자가 승인할 수 있다.
- 승인 트랜잭션에서 자격과 현재 배정을 다시 검사한다.

인수 조건:

- 오래 열린 화면에서 자격이 바뀐 경우 승인 시 안전하게 실패한다.
- 승인 전 기존 근무자의 책임이 유지된다.

### P4-T06. 전체 공개 교대

- 관리자가 특정 교대 요청을 전체 공개로 전환하거나 공개 요청을 만든다.
- 수행 가능한 근무자만 참여할 수 있다.
- 관리자가 한 명을 선택해 승인하고 나머지 후보를 닫는다.
- 공개·참여·선택 결과를 관련 사용자에게 알린다.

인수 조건:

- 자격 없는 근무자가 API로 참여할 수 없다.
- 두 관리자의 동시 승인에서 한 명만 최종 선택된다.

### P4-T07. 당일 포지션 교환과 감사

- 관리자가 같은 날짜에 배정된 근무자들의 포지션을 직접 교환한다.
- 근무자용 포지션 변경 요청 API는 만들지 않는다.
- 교환 후 requirement 충족과 자격을 다시 계산한다.
- 영향받는 근무자에게 알리고 변경 전후를 기록한다.

인수 조건:

- 부분 교환이나 자격 불충족 상태가 저장되지 않는다.

### P4-T08. 예약 발송과 변경 E2E

- Supabase Cron/Edge Function outbox 소비자를 구현한다.
- 재시도, 만료 구독, 발송 로그를 구현한다.
- 취소, 특정 교대, 공개 교대, 관리자 변경을 모바일 E2E로 검증한다.

인수 조건:

- 일시적 발송 실패를 재시도하고 영구 실패는 중단한다.
- 핵심 변경 흐름과 읽음 상태가 자동 테스트된다.

## 종료 조건

- 확정 후 운영 대화를 앱의 요청·알림으로 대체할 수 있다.

## 제외

- 문자·카카오톡.
- 자동 교대자 추천.
