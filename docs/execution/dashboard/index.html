  • F-01테스트

    RLS 쓰기 축 UPDATE 거부 단언이 실제 무변경을 증명하지 못하고 주체×테이블 조합도 불완전하다

    쓰기 축 테스트(728·732·765행 등)는 UPDATE가 RLS 행 필터로 0행 처리되는 동작을 lives_ok와 자기대입(set status = status)으로만 확인한다. 정책이 SELECT에서 FOR ALL로 넓어져 UPDATE가 실제 실행되는 회귀에서도 같은 단언이 통과하고, set_updated_at이 시각을 바꿔도 검출할 행 수·전후 값 단언이 없다. 또한 active 근무자는 schedules만, admin은 감사 테이블만 UPDATE를 시도해 3주체×3테이블 조합이 채워지지 않았다. 현재 정책 구현은 SELECT 전용으로 올바르므로 정정 방향은 코드가 아니라 단언 강화다. 두 리뷰어가 독립적으로 같은 결함을 발견했다.

  • F-02테스트

    applications의 두 외래 키를 결합 위반 하나로만 검증해 개별 FK 회귀를 잡지 못한다

    FK 위반 테스트(75~81행)는 schedule_id와 profile_id를 모두 존재하지 않는 값으로 넣고 SQLSTATE 23503 하나만 확인한다. 먼저 검사되는 schedule_id FK가 남아 있는 한 profile_id FK가 제거돼도 계속 통과하므로, RADIO 기술 인수 조건 1이 요구한 두 FK의 회귀 보호가 완성되지 않는다. 현재 마이그레이션에는 두 FK가 모두 존재해 실동작 결함은 아니다. 중요도 갈림: opus low(제약 자체는 존재), codex medium(인수 조건의 회귀 안전망 불이행) — 계약에 따라 높은 쪽을 택했다.

  • F-03테스트

    본인 명의 직접 INSERT 거부를 주장하는 단언이 실제로는 타인 명의만 시도한다

    741~756행에서 authenticated 주체는 근무자 A인데 삽입하는 applications.profile_id는 근무자 B다. 단언 문구와 달리 본인 명의 직접 INSERT 거부는 검증되지 않는다. applications 정책 수 1개 단언이 별도 INSERT 정책 추가는 잡지만, 기존 정책이 own-or-admin FOR ALL로 잘못 확대되는 회귀는 본인 명의 시도만이 잡을 수 있어 실질적인 권한 테스트 공백이다. 중요도 갈림: opus low(문구 정확도 문제로 판단), codex medium(권한 확대 회귀 미방어) — 계약에 따라 높은 쪽을 택했다.
