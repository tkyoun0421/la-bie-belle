# 회고 저장소

task를 닫을 때마다 무엇이 통했고 무엇이 걸렸는지 한 줄로 남기는 곳이다. `retrospector` 에이전트가 5단계 종료 시점, 마무리 커밋 **전에** 쓴다. 사람이 직접 써도 되지만 형식은 같다.

## 왜 gate로 막는가

회고는 "시간 나면 하는 일"이 되면 아무도 안 한다. 그래서 `gate:retro`가 강제한다 — `index.jsonl`에서 `done`인 task 중 면제 목록에 없는 ID는 [`cases.md`](cases.md)에 자기 줄이 있어야 하고, 없으면 커밋이 막힌다.

게이트는 **task ID가 그 파일에 있는지만** 기계로 본다. 내용이 쓸모 있는지는 사람과 교차 검증이 판단한다.

## 파일 넷

| 파일 | 담는 것 | 쓰는 주체 |
| --- | --- | --- |
| [`cases.md`](cases.md) | task별 회고 한 줄. 누적만 하고 지우지 않는다 | retrospector |
| [`proposals.md`](proposals.md) | 회고에서 나온 개선 제안. 체크박스 목록 | retrospector |
| `exempt.json` | 게이트 시행 시점에 이미 `done`이던 task 전수 | P0-T46 구현 시 1회 생성, 이후 불변 |
| 이 파일 | 형식 계약 | 사람 |

## `cases.md` 한 줄 형식

```
- <task-id> | 성공|실패 | <한 줄 요약> | <근거 경로>
```

예시:

```
- P0-T46 | 성공 | 게이트를 먼저 세우고 자기 자신에게 적용해 첫 실전 통과까지 한 번에 확인했다 | docs/execution/runs/P0-T46/
```

- **성공·실패는 task의 성패가 아니라 진행 방식의 성패다.** 결과물이 나왔어도 되돌림이 잦았으면 실패로 적는다.
- 요약은 한 문장. 다음에 같은 상황을 만난 사람이 판단을 바꿀 만한 내용을 쓴다. "잘 끝냈다" 같은 줄은 쓰지 않는다.
- 근거 경로는 `runs/<id>/`, `reviews/<id>-review.json`, 커밋 SHA 중 확인 가능한 것.

한 task가 두 줄 이상을 가져도 된다. 성공 하나와 실패 하나가 같이 나오는 경우가 흔하다.

## `proposals.md` 한 줄 형식

```
- [ ] <제안 요약> | 출처 <task-id> | <근거 경로>
```

**제안을 task로 만드는 것은 사용자 승인이 있을 때만 한다.** 여기 쌓아두는 것 자체는 승인이 아니다 — [backlog](../reviews/backlog.md)와 같은 규칙이다. 채택되면 `[x]`로 바꾸고 뒤에 task ID를 적는다.

## 면제

`exempt.json`은 게이트를 세운 시점에 이미 `done`이던 task를 담는다. 그 시점 이전 task에 회고를 소급해 쓰는 것은 [WORKFLOW](../../workflow/WORKFLOW.md)의 "done task의 history를 소급 편집하지 않는다" 규칙과 부딪히기 때문이다.

```json
{ "generated_at": "2026-08-16T14:30:00Z", "task_ids": ["P0-T00", "..."] }
```

P4-T02는 `done` 표기가 이 게이트보다 아주 조금 앞서지만, 전 과정이 회고 에이전트 없던 절차로 진행됐으므로 같은 이유에서 면제에 넣었다.

**이 파일은 한 번 만든 뒤 늘리지 않는다.** 회고를 쓰기 싫어서 면제 목록에 ID를 더하는 순간 게이트가 무의미해진다. 정말 면제가 필요한 예외가 생기면 그건 승인 사안이다.
