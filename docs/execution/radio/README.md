# task별 RADIO 개발 설계

이 디렉터리는 설계 단계에서 승인한 task별 기술 설계의 정본이다. 공통 규칙은 [개발 컨벤션](../../standards/DEVELOPMENT.md)을 참조하고 반복하지 않는다.

## 파일과 상태

- 파일명은 `<task-id>-radio.md`를 사용한다.
- 문서에 1부터 시작하는 `revision`과 `Draft | Approved | Superseded` 상태를 기록한다.
- task가 `design_pending`일 때 초안을 작성한다.
- 사용자 승인 후 정확한 파일 전체의 SHA-256과 revision을 `development_approval`, 경로를 `radio_ref`에 기록하고 `planned`로 바꾼다.
- 승인 후 의미가 바뀌면 고정 경로에서 revision을 증가시키고 `Draft`로 바꾼 뒤 설계 단계에서 재승인한다. 이전 revision은 Git 이력으로 보존한다.
- 상위 결정 변경으로 설계 전제가 무너져 개발 승인이 철회되면 문서를 `Superseded`로 표시하고 무효 사유를 적는다. 본문은 역사 기록으로 보존하고 `index.jsonl`에서 `development_approval`과 `radio_ref`를 제거한다. 새 설계는 같은 경로에 새 revision으로 작성한다.
- 여러 task에 영향을 주거나 되돌리기 어려운 결정은 ADR로 승격한다.
- `docs/execution/runs/<task-id>/radio.md`는 이 문서의 대체물이 아니라 실행 결과와 차이 증거다.

## 변경 허용 경로

코드 구현 task의 RADIO는 `## 변경 허용 경로` 절의 첫 코드블록에 구현 중 변경이 허용되는 경로를 glob 한 줄씩 선언한다. 커밋 범위 게이트가 이 목록을 기계 판독하며, 목록은 승인 SHA-256에 함께 봉인되어 승인 후 변조할 수 없다. (P0-T31부터 적용)

## 위험 기반 테스트

코드를 바꾸는 task의 RADIO는 `### 위험 기반 테스트` 절의 첫 번째 표에서 인수 조건마다 위험 6렌즈(Happy Path·주요 실패·경계값·권한·중복 요청·동시성)를 점검한 증거를 남긴다. `gate:radio`가 형식을 기계 판독해 강제한다. (P0-T36부터 적용)

- 헤더는 `| 인수 조건 | Happy Path | 주요 실패 | 경계값 | 권한 | 중복 요청 | 동시성 |`이며 이름과 순서를 그대로 쓴다.
- 행은 기술 인수 조건마다 하나 이상 필요하다. 행이 하나도 없으면 차단된다.
- 칸 값은 두 형식만 허용한다: `테스트함`으로 시작(뒤에 무엇을 어떻게 테스트했는지 이어 써도 된다), 또는 `해당 없음 — <사유>`. `해당 없음` 뒤 사유가 비어 있으면 차단된다.
- 여섯 렌즈로 표현되지 않는 서술형 위험은 표 아래 불릿 목록으로 적는다. 이 보충 행은 검사 대상이 아니다.
- 변경 허용 경로가 `docs/**`·`.claude/**`뿐인 문서 전용 task는 표 없이 통과한다.
- P0-T36 시행 이전에 개발 설계 승인을 받은 task는 이후 재봉인이 있어도 소급 요구 대상이 아니다. 대상 목록은 `config/radio-lens.json`의 고정 스냅숏이 소유하며 시행 이후 항목을 추가하지 않는다.

예시:

| 인수 조건 | Happy Path | 주요 실패 | 경계값 | 권한 | 중복 요청 | 동시성 |
| --- | --- | --- | --- | --- | --- | --- |
| 출근 체크인이 GPS 반경 안에서 성공한다 | 테스트함 | 테스트함(반경 밖 거부) | 테스트함(반경 경계값 100m) | 해당 없음 — 인증된 근무자 전용 화면이라 별도 권한 분기가 없다 | 테스트함(같은 근무의 중복 체크인 거부) | 해당 없음 — 근무자 1인 1세션 조작이라 동시 요청 경합이 없다 |

## 적용 상태

각 관련 `DEV-*` 규칙은 다음 상태 중 하나를 가진다.

- `기본 적용`: 공통 규칙을 그대로 따른다.
- `해당 없음`: 작업 범위에 적용되지 않는다.
- `추가 결정`: 작업별 기술 선택과 근거를 기록한다.
- `예외`: `SHOULD` 규칙의 예외와 위험·보완책·되돌림 조건을 기록한다.

`MUST` 규칙은 task에서 예외 처리할 수 없다.
