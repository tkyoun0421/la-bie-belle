## 확정된 사실 (사용자 답변·요약본 승인)

- **개발 설계 승인(user, 2026-08-10).** RADIO revision 1을 봉인했다. SHA-256 `3a5a54a5430067e0b38ff55eed31960b3e52390149a615d03a10c14aac3e0009`.
- 테이블 모양: `assignments`(사람 단위 참여, `(schedule_id, profile_id)` 유니크) + `assignment_positions`(담당 포지션) 두 층. DOMAIN 언어를 그대로 따르며, 확정 시점 시급 스냅샷·탈퇴자 `change_required`·교육생 여부가 붙을 자리를 윗층에 남긴다.
- 빈 배정 처리: 마지막 담당 포지션이 제거되면 `assignments` 행도 같은 트랜잭션에서 삭제한다. 담당 포지션 없는 배정 행은 존재하지 않는다.
- 판정 위치: 후보 조회 함수가 신청 여부와 자격 판정(`eligible`·이유)을 붙여 반환한다. 넣을 때 막는 규칙과 목록에서 접는 규칙이 같은 SQL 한 곳에 있다. 화면은 받은 판정을 그리기만 하고 다시 계산하지 않는다.
- 화면 배치: P3-T02 필요 인원 표의 행에 `필요 N / 배정 M`을 붙이고 행 탭으로 후보 시트를 연다. 별도 페이지를 만들지 않는다.
- 저장 흐름: 포지션 단위 batch. 여러 명을 고르고 해제한 뒤 저장 1회로 교체하며 `N개 변경` 표시와 되돌리기를 붙인다(P2-T03 근무자 달력과 같은 모양).

## 인터뷰 중 바로잡힌 것

- 조정자가 기획 인터뷰에서 확정 전 스케줄 상태를 `OPEN`·`CLOSED` 둘로 말했으나 실제 enum은 `OPEN`·`CLOSED`·`PREPARING`·`CONFIRMED`·`CANCELLED` 다섯이다. `PREPARING`은 마감과 확정 사이 단계이며 배정을 짜는 자리 그 자체다. 사용자가 고른 "확정 전이면 허용"과 P3-T02 복사 함수의 판정(`CONFIRMED`·`CANCELLED`만 거부)에 맞춰 세 상태 모두 허용으로 반영하고 PRD 7장·결정 대장·기획 handoff를 정정했다.
- 봉인 전 구조 대조에서 두 가지를 고쳤다. `04-rls-default-deny.test.sql`은 `positions`·`venue_settings`·`check_in_rules`를 이름으로 지목해 단언하므로 새 테이블 추가로 갱신할 필요가 없다(P3-T02 때와 상황이 다르다). `config/fsd.json`이 `api`·`hooks`·`model`에 unit 테스트를 필수로 걸어두므로 신설 파일마다 `__tests__/` 짝이 필요하다는 점을 Architecture에 명시했다.

## 해석 (요약본에 명시 후 승인으로 함께 확정)

- 쓰기 경로: 두 테이블 RLS는 admin `select`만 열고 insert·update·delete 정책을 두지 않는다. 직접 DML은 42501(insert) 또는 0건 적용(update·delete)이 된다. 쓰기는 정의자 권한 함수 하나만 지난다.
- 거부 코드: 확정·취소 스케줄은 기존 `LB020` 재사용, 자격 미달은 신규 `LB023`. 화면 코드는 `SCHEDULING_ASSIGNMENT_NOT_ELIGIBLE` 1개 신설.
- 불가 이유는 `GENDER_MISMATCH`·`NOT_ELIGIBLE` 두 종류다. 활성이 아닌 계정은 이유 없이 후보에서 제외한다.
- 감사는 교체 1회당 1행(`assignment_positions_replaced`), detail에 수치만 담고 PII를 담지 않는다. 변경 없으면 0행.
- E2E 픽스처는 `tests/e2e/support/work-date-band.ts`에 겹치지 않는 새 구간을 추가해 받는다.
