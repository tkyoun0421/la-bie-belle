## 확인된 사실 (사용자 답변·요약본 승인)

- **개발 설계 승인(user, 2026-08-11).** RADIO revision 1을 SHA-256 `12e3f2fa…`로 봉인했다.
- **겸직 e2e는 기존 `assignment-eligibility.spec.ts`에 붙인다.** 시딩 헬퍼 셋과 `assignmentEligibility` 밴드를 그대로 쓴다. 새 spec으로 떼려면 헬퍼를 `tests/e2e/support/`로 추출하며 기존 spec을 고쳐야 해서 멀쩡한 테스트가 깨질 위험이 생긴다는 쪽이 이겼다.
- **테스트가 드러낸 불일치는 화면·집계 코드까지만 이 task에서 고친다.** 문구·정렬 같은 표시 문제는 backlog로 보낸다.
- **DB 함수 쪽 불일치는 고치지 않고 멈춰 반환한다.** 이미 배포된 스키마에 마이그레이션을 새로 올리는 일이라 검증 task 안에서 조용히 지나갈 변경이 아니라는 판단이다. `supabase/migrations/**`와 `src/features/assignment/api/**`를 「변경 허용 경로」에서 빼 그 판단을 경로로 강제했다.

## 조사에서 정해진 것 (선택지가 아니었던 것)

인터뷰에서 물으려다 코드 확인으로 답이 정해져 묻지 않은 항목들이다.

- **실인원의 출처는 하나뿐이다.** `listScheduleRequirements`만 `assignments` 행을 쥐고 있고, view model은 집계된 `Record`만 받아 사람 수를 복원할 수 없다. 그래서 스칼라를 읽기 응답에 더하는 것 외의 길이 없다. 조회는 늘지 않는다 — `(schedule_id, profile_id)` 유일이라 행 배열의 길이가 곧 사람 수다.
- **테스트 층 분배도 정해진다.** 단위 테스트가 Supabase를 전부 mock하므로(`replace-position-assignments.test.ts`가 `rpc`를 `vi.fn()`으로 갈아끼움) 겸직 추가·제거·자격 검사는 실DB e2e로만 검증된다. 단위로 덮이는 것은 순수 계산뿐이다.
- **표시 판정의 자리도 정해진다.** 화면 로직은 UI가 아니라 `model`이 갖는다는 저장소 취향에 따라 `views/admin-schedule/model/`에 순수 함수를 둔다.

## 봉인 전 체크리스트 결과

P0-T45에서 세 번 뚫린 자리를 이번에는 봉인 전에 돌렸다.

- **세그먼트 대조.** `api`는 `requireServerOnly`이자 단위 필수 — 대상 파일에 `import "server-only"`가 이미 있고 테스트도 있다. `model`은 `react` import 금지에 단위 필수 — 새 순수 함수가 타입만 import한다. `ui`는 단위 면제이며 `**/api/**` import 금지 — 화면은 prop만 받는다.
- **인수 조건별 출발지 파일 대조.** 인수 조건 5(실인원 줄)의 출발지가 네 파일(엔티티 API·view model·화면·페이지 어댑터)에 걸쳐 있음을 확인하고 넷 다 허용 경로에 넣었다.
- **glob 매처 실측.** 경로에 `[id]`와 `(protected)`가 들어가 문자 클래스·그룹으로 오독될 위험이 있어 `matchesAnyGlob`을 직접 돌려 확인했다. `escapeRegExpChar`가 `[`·`]`·`(`·`)`를 escape하므로 문자 그대로 잡힌다. 허용해야 할 7개가 허용되고, 막아야 할 `layout.tsx`·다른 spec·`features/assignment/api`·`supabase/migrations`가 모두 차단되는 것을 실행으로 확인했다.
- **스키마 대조에서 한 건 걸렸다.** `spec_refs`의 `DOCS:` 접두는 `SDD`·`DDD`만 받는다. `DOCS:ADMIN-FLOWS`로 적었다가 `gate:index`가 잡아 `DOCS:SDD`로 고쳤다 — 기존 49건이 설계 문서를 그렇게 참조한다. RADIO의 관련 spec 줄도 함께 고치고 해시를 다시 계산했다.

## 남는 위험

- **"이미 돌아간다"는 코드를 읽은 판단이지 실행해 본 것이 아니다.** 인수 조건 1~4가 이 task에서 처음 실행 검증을 받는다. 깨지면 정지 조건대로 갈린다.
- **겸직 시딩이 두 포지션의 자격을 모두 통과해야 한다.** 한 근무자에게 두 포지션의 `worker_position_eligibilities`와 성별 조건을 함께 맞춰야 하고, 기존 헬퍼가 못 받으면 그 spec 안에서 넓힌다(파일 밖으로 빼지 않는다).
- **`assignment-eligibility.spec.ts`가 400줄을 넘긴다.** 테스트 1개짜리 파일에 하나가 더 붙는다. 가르는 일은 backlog.

## 미결 사항

- 겸직자의 급여를 한 번 세는가 두 번 세는가 — P6 소유.
- 겸직자의 출퇴근 기록이 하나인가 둘인가 — P5 소유.
- `assignment_positions_replaced` 감사 로그가 개수만 남겨 "누가 들어갔나"를 못 되짚는다 — P3-T03이 봉인한 형식 전체의 성질이라 후속 제안.
- `assignment-eligibility.spec.ts`를 언제 가를지 — 헬퍼를 `support/`로 빼는 시점의 별도 제안.
