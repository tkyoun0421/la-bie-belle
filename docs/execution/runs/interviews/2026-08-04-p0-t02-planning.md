### 확정된 사실

- **기획 승인(user, 2026-08-04)**. `docs/execution/phases/index.jsonl`의 P0-T02가 `design_pending`이고 `product_approval`이 기록됐다. 범위 정본은 `docs/execution/phases/00-foundation.md`의 P0-T02 절이다.

- **Playwright 모바일 E2E를 이 task에 포함한다.** P0-T35로 미루면 P0-T05가 의존할 단일 검증 명령을 나중에 한 번 더 고쳐야 한다. 검증 대상이 부트스트랩 화면 한 장뿐이라 얻는 것은 얕지만, 이후 task는 테스트를 추가하기만 하면 된다.

- **검사 배치**: pre-commit은 harness 게이트 4종 + lint-staged(변경 파일만) + `tsc --incremental` + 단위 테스트 전체, pre-push는 `pnpm build`, CI(P0-T05)는 그 전부와 Playwright E2E·type-aware 린트·`pnpm gate:all`.
  - 조정자가 처음 "RED 테스트를 커밋해야 하는 순간이 정상 흐름에 있으므로 pre-commit에서 테스트를 강제하면 안 된다"고 주장했으나 **사실이 아니었다**. `harness/lib/tdd-gate.ts`를 읽어 확인한 결과 게이트는 테스트를 실행하지 않고 `tdd.json`의 RED→GREEN **기록**만 검사하며, task당 단일 commit 계약상 커밋 시점은 이미 GREEN이다. 사용자 지적으로 근거가 정정되어 테스트를 pre-commit으로 앞당겼다.
  - 실측(현재 `src/` 6파일 기준): harness 게이트 4종 0.09s, `tsc --noEmit` 0.46s, `pnpm typecheck` 0.73s, `pnpm build` 캐시 있음 2.79s / clean 5.03s.
  - 타입 검사와 build는 변경 파일만 검사할 수 없다. TypeScript는 프로그램 단위로 검사하고 파일 목록을 직접 주면 `tsconfig.json` 옵션이 무시된다. 증분 캐시로 실제 작업량만 줄인다.

- **FSD 구조 계약을 `config/fsd.json` 하나로 통합한다.** ESLint와 `.claude/hooks/tdd-guard.sh`가 같은 파일을 읽는다.
  - 발견한 문제: 같은 구조 지식이 훅의 셸 패턴(`tdd-guard.sh:59,66,77`)과 앞으로 만들 ESLint 설정 두 곳에 하드코딩되어 `DEV-SSOT-01`을 어긴다. 실제로 이미 어긋나 있다 — 훅은 `*/types/*`, `*/components/*`, `*/generated/*`를 예외 처리하는데 이 이름들은 세그먼트 목록에 없다.
  - 훅이 이미 `jq`를 요구하므로 새 의존성은 없다.

- **세그먼트 7종과 각각의 규칙**: `ui`(단위 테스트 면제·컴포넌트/E2E로 위임), `hooks`(필수), `model`(필수·React import 금지), `api`(필수·`server-only` 필수), `lib`(필수), `config`(면제·런타임 export 금지), `types`(면제·런타임 export 금지).
  - **면제 구역에 잠금을 건다.** 단위 테스트 면제는 "여기엔 로직이 없다"는 가정 위에 서 있는데 지금은 그 가정을 강제하는 것이 없어, `types/`에 함수를 넣으면 TDD 가드를 그냥 통과한다. `config`·`types`의 런타임 export를 금지해 면제가 우회 통로가 되지 않게 한다.
  - **`hooks` 분리가 `model`의 React 금지를 가능하게 한다.** 그 결과 `DEV-CODE-02`가 기계 검사 대상이 되고, `model`은 jsdom 없이 Node에서 돌아 단위 테스트가 빨라진다. `hooks`가 없으면 query 훅이 `model`에 남아 React 금지를 걸 수 없다.
  - `ui`의 면제는 검증 포기가 아니라 위임이다. `verifiedBy`에 검증 계층을 명시해 비어 있으면 검증 계획 없는 면제 구역으로 드러나게 한다(`DEV-TEST-01`).
  - 코드 생성물(Supabase DB 타입)은 세그먼트가 아니라 `api/generated/`에 두고 `exemptPaths`로 처리한다.

- **barrel(`index.ts`)을 쓰지 않는다.** Next.js에서 빌드 성능 문제를 만들고 순환 의존의 주 통로다. 면제 구역이 하나 줄어드는 부수 효과도 있다. 기존 `src/views/bootstrap/index.ts`를 제거하고 `tdd-guard.sh`의 `*/index.ts` 예외도 없앤다. FSD의 슬라이스 public API 대신 직접 경로 import를 쓰며, 지켜야 할 계층 방향은 ESLint가 직접 강제한다.

- **네이밍 컨벤션**: 폴더·일반 파일 kebab-case, React 컴포넌트 파일과 export는 PascalCase, 훅은 파일 `use-*.ts`/export `useXxx`, 타입 PascalCase, 테스트 `*.test.ts(x)` 형제 배치. 예외는 Next.js 예약 파일명과 shadcn 관리 구역 `shared/ui/**`.
  - 규칙 자체가 어느 문서에도 없었다. 코드는 이미 kebab-case였으나 명문화되지 않은 관행이었다.
  - `MUST` 규칙 변경은 설계 단계가 아니라 L3에서 먼저 처리한다([ADR-0013](../../../standards/adr/0013-project-layer-structure.md)). 따라서 규칙 내용은 기획에서 합의하고, 실행 시 `DEVELOPMENT.md`에 `DEV-NAME-*`로 신설한 뒤 ESLint로 강제한다.
  - shadcn CLI는 레지스트리 파일명(`button.tsx`)을 그대로 쓰고 `components.json`에 파일명 옵션이 없다. 개명해도 재설치 때 원래 이름으로 다시 생긴다.

- **ESLint 규칙 채택 범위**: 구조 강제(FSD 단방향·UI의 서버 모듈 금지·`server-only` 선언·세그먼트 제약), 규칙 기계화(주석 금지 `DEV-CODE-07`·`process.env` 차단 `DEV-SEC-02`·`no-console`·`import/no-cycle`), 정확성(`@next/eslint-plugin-next`·`react-hooks`·`consistent-type-imports`). type-aware 규칙(`no-floating-promises` 등)은 **CI 전용 설정으로 분리**한다 — 타입 정보를 요구해 린트가 타입 검사만큼 느려지고 변경 파일만 검사하는 방식과 상성이 나쁘다.
  - 넣지 않는 것: 스타일 프리셋(취향 규칙이라 formatter와 충돌), 함수 줄 수·복잡도 제한(`DEV-CODE-06`이 명시적으로 반대).
  - 주석 금지는 기성 ESLint 규칙이 없다. 주석은 AST 노드가 아니라 토큰이라 로컬 커스텀 규칙이 필요하다. P0-T01에서 실제로 한 번 어겼다가 전부 걷어낸 이력이 있어 기계화 가치가 있다.
