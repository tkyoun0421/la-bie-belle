### 확정된 사실

- **기획 승인(user, 2026-08-05)**. `docs/execution/phases/index.jsonl`의 P0-T37이 `design_pending`이고 `product_approval`이 기록됐다. 범위 정본은 `docs/execution/phases/00-foundation.md`의 P0-T37 절이다.

- **실행 순서: P0-T37 → P0-T04** (사용자 결정). P0-T04의 오류·접근 거절 화면이 오류 계약의 첫 소비자인데 두 task 사이에 의존성이 없어 게이트가 순서를 강제하지 못했다. 재작업 없는 쪽을 택해 P0-T37을 먼저 확정하고, 결정을 index의 의존성으로 인코딩했다 — P0-T04의 `depends_on`에 P0-T37을 추가했다.

- **산출물 범위: 표준 문서 + 정본 레지스트리 파일 + ESLint 강제** (사용자 결정). 세 안(문서만 / 문서+파일 / 문서+파일+린트) 중 가장 넓은 안을 택했다. "짧은 문서 task"라는 재정렬 당시 전제는 깨졌고, task 성격이 코드+도구로 격상됐다. 조정자 추천(문서만)과 다른 선택이며, 정본 밖 코드를 사람 리뷰가 아니라 기계가 막는 쪽을 우선했다.

- **명명 구조: 도메인 접두 + 의미 슬러그** (사용자 결정). 접두는 DOMAIN의 5개 경계(IDENTITY·SCHEDULING·ATTENDANCE·NOTIFICATIONS·PAY)와 공통용 COMMON. HTTP 상태는 이름에서 유도하지 않고 레지스트리에서 코드별로 선언한다. 근거: `DEV-ERR-01`이 "UI는 안정적인 code 기준 표현"을 이미 정해 업무별 코드 분화가 필요하고, 문의용 식별자는 correlation ID가 담당하므로 코드는 짧기보다 자기 설명적인 게 유리하다.

- **메시지 정본: 중앙 기본 + 화면 재정의** (사용자 결정). 레지스트리가 코드별 기본 한국어 문구를 보관하고 화면은 예외적으로만 재정의한다. 서버 응답에 문구를 넣는 안은 구버전 PWA 캐시에 옛 문구가 박히는 문제와 `DEV-ERR-01` 마찰로 제외했다.

### 다시 열지 않은 것

- **Server Action 오류 형식** — `DEVELOPMENT.md:161`과 `DEV-ERR-01`/`DEV-ERR-02`가 이미 소유(`{ ok: false, code, fieldErrors? }`). P0-T37은 `code` 값의 문법만 정하고 형식은 건드리지 않는다. 인터뷰 시작 시점에 이 사실을 확인해 범위 질문에서 제외했다.
- **사용자 노출 원칙** — "안전한 오류 코드와 문의용 식별자만 제공"(`DEVELOPMENT.md:206`). read Route Handler 응답에 correlation ID를 담는 것은 이 규칙의 함의로 처리했다.

### 조정자가 판단해 기록한 것

인터뷰 질문으로 올리지 않고 가정으로 명시한 뒤 승인 요약에 포함해 확정했다.

- **린트 적용 범위는 `src/` 전체, 위반은 pre-commit·CI 차단.** 현행 `pnpm lint`가 `src/`만 보는 구조 그대로이고, 오류 코드가 아직 0개라 기존 위반이 생길 수 없어 실질 분기가 없다.
- **COMMON 최소 세트 시드**(인증 필요, 권한 없음, 찾을 수 없음, 예상 밖 실패). P0-T04가 코드를 발명하지 않게 하는 이 task의 존재 이유에서 따라온다. 도메인 코드는 각 기능 task가 추가한다.
