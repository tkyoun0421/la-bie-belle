### 확인된 사실

상위 문서가 이미 정해 둔 것이며 이 인터뷰에서 다시 열지 않았다.

- `venue_settings`는 단일 행 설정 테이블이다(좌표·GPS 반경·정확도 한도·기본 시급). ARCHITECTURE 주요 테이블 절이 소유한다.
- `check_in_rules`는 첫 예식 시작 시각과 추천 출근 시각의 규칙표다. Phase 문서가 말한 "기본 출근 규칙"이 이것이다.
- 시간은 `timestamptz`, 날짜·마감 계산은 `Asia/Seoul`. RLS로 행 단위 권한 강제. 출퇴근 원본과 감사 로그는 UPDATE·DELETE 금지.
- ARCHITECTURE §15가 무엇을 테스트할지(RLS 권한 매트릭스, append-only 제약 등)는 정했으나 무엇으로 돌릴지는 정하지 않았다. `DEV-TEST-02`는 실제 PostgreSQL 경계만 요구한다.

### 이 인터뷰에서 결정한 것

**1. 테이블 범위는 참조 데이터와 공통 규약까지** (사용자 결정)

`positions`·`venue_settings`·`check_in_rules`와 공통 enum·`timestamptz` 규칙·감사 컬럼 규약만 만든다. `audit_log` 테이블은 P1-T04로 넘긴다. 감사 레코드의 형태는 무엇을 감사하는지가 정해져야 제대로 정할 수 있고, 쓰는 곳 없이 굳히면 P1에서 되돌려야 한다. Phase 문서가 "감사 기반 타입"이라고 쓴 것과도 맞는다.

**2. 삭제 차단은 규약만 세우고 검증은 P1-T05로 이월** (사용자 결정)

기획에서 "사용 중인 포지션의 삭제가 DB에서 차단"을 인수 조건으로 넣었으나, P0-T03 시점에는 `positions`를 참조하는 테이블이 하나도 없어 FK를 걸 상대가 없다. `worker_position_eligibilities`는 P1, `assignment_positions`는 P3다.

- P0-T03은 `is_active` 컬럼과 "`positions`를 참조하는 모든 FK는 `ON DELETE RESTRICT`" 규약을 ARCHITECTURE에 세운다.
- 실제 차단 검증은 첫 참조 테이블이 생기는 P1-T05의 인수 조건으로 옮겼다.
- 트리거로 흉내내는 안은 버렸다. 삭제 규칙의 정본이 FK와 트리거 두 곳으로 나뉘고, 새 참조 테이블을 트리거에 등록하는 걸 잊으면 조용히 뚫린다. P0-T02에서 방금 고친 판정 불일치와 같은 종류다.

**3. 팀장 포지션 보호 — 불변 code** (사용자 결정, 기획 갱신)

설계에 들어가면서 **승인된 제품 규칙 두 개가 충돌하는 것을 발견했다.** PRD 67행은 당일 팀장을 "해당 날짜에 `팀장` 포지션으로 배정된 근무자"로 정의해 권한을 포지션 이름에서 파생시킨다. 그런데 같은 날 기획에서 관리자 포지션 CRUD를 승인했다. 관리자가 `팀장`을 `팀리더`로 고치면 당일 팀장 권한이 아무 오류 없이 사라진다. 권한 경계를 편집 가능한 표시명에 묶어둔 상태이며 `DEV-SEC-01`이 막으려는 형태다.

- 이것은 기술 판단이 아니라 제품 판단이라 1단계로 반환할 성격이었고, 사용자가 그 자리에서 결정해 기획을 갱신했다.
- `positions`에 관리자가 못 고치는 `code` 컬럼을 두고 `팀장`을 `team_lead`로 고정한다. 권한 파생과 RLS는 표시명이 아니라 code로 판정한다.
- code가 있는 시스템 포지션은 삭제도 비활성화도 못 한다. 표시명 변경은 허용한다.
- "어떤 포지션이 당일 팀장 권한을 갖는지 관리자가 정한다"는 선택지는 제시하지 않았다. 권한 부여 자체를 데이터로 여는 결정이라 PRD 67행을 다시 여는 일이고 설계 인터뷰에서 곁다리로 정할 성격이 아니다.

**4. DB 테스트는 pgTAP과 Vitest 역할 분담** (사용자 결정)

pgTAP이 스키마·제약·RLS 같은 DB 내부 불변을, Vitest가 애플리케이션 통합을 맡는다. P0-T03은 애플리케이션 코드가 0줄이라 이번 task의 실체는 pgTAP뿐이다. Vitest DB 통합 하네스는 검증할 코드가 없어 소비자 없는 선행 추상화가 되므로 첫 DB 접근 코드가 생기는 P1이 세운다.

### 조정자가 판단해 RADIO에 넣은 것

인터뷰 질문으로 올리지 않고 결정했다. 실질적 트레이드오프가 없거나 상위 문서가 이미 정한 것들이다.

- **RLS는 켜고 정책 0개.** `DEV-SEC-01`과 ARCHITECTURE가 RLS를 이미 강제하므로 켜는 것 자체는 선택지가 아니다. 역할이 없는 지금 정책을 쓰면 P1에서 지워야 하고 그 사이 잘못 열려 있을 위험이 크다. Postgres는 RLS가 켜지고 정책이 없으면 전부 거부한다.
- **`code`는 nullable.** 값이 있으면 시스템 포지션, `NULL`이면 관리자가 만든 일반 포지션이다.
- **시스템 포지션 보호는 트리거.** `CHECK` 제약은 삭제 연산과 다른 행을 볼 수 없어 이 규칙을 표현할 수 없다.
- **`gender`와 `gender_requirement`를 별개 enum으로 분리.** 성별은 사람의 속성이고 성별 조건은 포지션의 제약이라 값 집합이 다르다(`any`). 하나로 합치면 한쪽이 늘 때 다른 쪽이 끌려간다.
- **`venue_settings` 단일 행을 `UNIQUE INDEX ON ((true))`로 강제.** "첫 행을 고른다"는 애플리케이션 관례에 기대지 않는다.
- **`check_in_rules` 구간 겹침을 `EXCLUDE USING gist`로 차단.** 겹치면 같은 예식 시각에 추천 출근이 둘이 되어 규칙표가 함수가 아니게 된다.
- **참조 데이터는 seed가 아니라 migration.** 기획 결정(seed는 로컬 전용)의 구현이다. Supabase CLI가 `db push`에서 migration만 적용하고 `seed.sql`은 `db reset`에서만 실행하므로 도구 기본 동작이 이미 이를 보장한다.
- **`pnpm verify`에 DB 테스트를 넣지 않는다.** Docker와 로컬 Supabase 기동이 필요해 의존성 없는 환경에서 깨진다. CI 통합은 P0-T05가 소유한다.
- **인덱스는 제약이 만드는 것 외에 추가하지 않는다.** 행이 수십 개이고 조회 패턴이 아직 없다.
- **오탐 대조군을 인수 조건에 명시.** 일반 포지션은 삭제와 비활성화가 성공해야 한다. 없으면 "전부 막는" 구현도 통과한다.

### 절차 기록

- 인터뷰 초반에 venue 저장 형태와 RLS 도입 시점을 "설계에서 정할 것"이라고 예고했으나, 확인해 보니 둘 다 상위 문서에 이미 결정돼 있었다. 질문으로 올렸다면 승인된 결정을 다시 여는 셈이라 기본 적용으로만 기록했다.
