# P3-T03 기획 인터뷰 handoff

- 작업 식별자: P3-T03 (배정 후보와 자격 검사)
- 현재 단계: 기획 승인 종료 → 다음 설계(RADIO) 인터뷰
- 기준 시각: 2026-08-10

## 확인된 사실 (사용자 답변·요약본 승인)

- **기획 승인(user, 2026-08-10).** 결정용 요약본을 승인 형식으로 확인받았다.
- 범위 경계: T03이 배정 테이블과 쓰기 경로, 자격 강제까지 가진다. 한 포지션에 대해 넣기와 빼기가 온전히 동작하는 상태로 끝낸다. 한 사람에게 여러 포지션을 함께 붙이는 일과 모바일 흐름 다듬기는 T04가 가진다.
- 후보 목록: `신청함`·`신청 안 함` 두 묶음으로 나눈다.
- 조건 미달자: 기본은 접어두고, 펼치면 각자의 이유와 함께 보여준다.
- 자격 검사 시점: 배정을 만드는 순간에만 검사한다. 이후 가능 포지션 회수나 성별 조건 변경은 이미 만들어진 배정을 바꾸지 않고 표시도 하지 않는다.
- 확정 스케줄: T03 범위 밖이다. 확정 전 상태에서는 모두 배정할 수 있다. 조정자가 인터뷰에서 확정 전을 `OPEN`·`CLOSED` 둘로 잘못 말했으나 실제로는 `PREPARING`을 포함한 셋이며, 사용자가 고른 "확정 전이면 허용"과 P3-T02 복사 함수의 판정(`CONFIRMED`·`CANCELLED`만 거부)에 맞춰 세 상태 모두 허용으로 반영했다.
- 중복 배정: 이미 다른 포지션에 배정된 근무자도 제자리에 두고 배지로만 표시한다.
- 초과 배정: 필요 인원을 넘겨 배정할 수 있고 경고도 확인창도 없다.
- 필요 인원 0명 포지션: 그대로 배정할 수 있다.
- 감사 기록: 확정 전부터 남긴다.

## 인터뷰 중 드러난 승인 충돌과 처리

- 사용자가 감사 기록을 "확정 뒤에만"으로 답한 뒤, P3-T02가 만든 필요 인원 함수 3종과 새 포지션 트리거가 이미 확정 전 변경을 `scheduling_audit_logs`에 남기고 있음을 소스로 확인해(`supabase/migrations/20260809000000_position_requirements.sql` 80·139·159·218·259행) 조정자가 그 사실을 제시했다. 사용자가 "배정도 확정 전부터"로 다시 결정해 두 동작의 규칙을 맞췄다.

## 해석 (요약본에 명시 후 승인으로 함께 확정)

- 진입점은 P3-T02가 만든 스케줄 준비 화면의 필요 인원 표이며, 포지션 행을 눌러 후보 목록을 연다. 각 행에 `필요 N / 배정 M`을 표시한다.
- 정식 담당자 조건은 넷이다: 계정이 활성, 포지션 성별 조건과 근무자 성별 일치, 기본 포지션이거나 개인별 가능 포지션 보유, 같은 스케줄 같은 포지션에 중복 아님. 비활성 포지션에는 새로 배정할 수 없다(PRD 4장 기존 확정).
- 불가 이유는 성별 조건 불일치와 가능 포지션 없음 두 종류다. 활성이 아닌 계정은 이유를 붙이지 않고 후보에서 아예 제외한다.
- 강제는 서버 액션과 DB 함수 두 곳에 두고, 테이블 RLS는 관리자 select만 열며 쓰기는 정의자 권한 함수만 지난다(P3-T02 교차 검증에서 확정된 저장소 구조).
- 배정 데이터는 DOMAIN이 이미 정한 `assignment`(근무자 한 명의 하루 참여)와 `assignment_position`(그 배정이 채우는 포지션) 언어를 따른다. 실제 테이블 형태는 설계 결정이다.

## 미결 사항

- 확정 시점에 자격을 다시 검사할지 — 결정 주체: 사용자, 반환할 단계: P3-T06 기획·설계. 자격을 만드는 순간에만 본다는 이번 결정의 귀결로, 자격이 사라진 사람이 배정에 남은 채 확정이 통과한다.
- 교육생(P3-T05)이 배정 구조에 붙는 방식 — 결정 주체: AI, 반환할 단계: 설계. T03에서 자리를 비워둘지 T05에서 테이블을 고칠지 RADIO 인터뷰에서 정한다.
- 후보 조회의 행 수 상한 — 결정 주체: AI, 반환할 단계: 설계. PostgREST 기본 1000행 절단을 넘지 않는지 확인한다.
