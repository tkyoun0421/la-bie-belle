# P0-T03 기획 인터뷰 handoff

## 2026-08-04 · 기획 종료

- 작업 식별자: P0-T03 (Supabase 로컬 개발과 초기 스키마)
- 현재 단계: 기획 종료 → 다음 설계(RADIO)
- 기준 시각: 2026-08-04
- 상태 전이: `proposed` → `design_pending`

### 확인된 사실

승인된 문서에서 그대로 가져온 것이며 이 인터뷰에서 다시 열지 않았다.

- Phase 문서가 범위를 이미 정했다. Supabase CLI·마이그레이션 디렉터리, 공통 enum·timestamp·audit 규약, 포지션 9종, 단일 venue 기본 설정.
- 스케줄·신청·배정 테이블은 P2-T01이, append-only 출퇴근 테이블은 P5-T02가 가져간다. P0-T03은 기반과 참조 데이터만 다룬다.
- 단일 근무 장소·단일 예식홀은 승인된 결정이고 다중 장소·다중 홀은 PRD가 명시한 비목표다(PRD 5·33·349행).
- seed 값은 전부 PRD에 이미 있다. 포지션 9종의 이름·기본 필요 인원·성별 조건(PRD 4장), GPS 반경 100m와 위치 정확도 100m(PRD 277~281행), 지각은 예정 출근 시각 1분 초과(PRD 299행).
- `INV-STAFF-02`(교육생은 필요 인원에 포함하지 않는다)가 seed와 이후 필요 인원 계산의 정본이다.

### 이 인터뷰에서 새로 결정한 것

**1. 포지션은 관리자 CRUD 대상이다** (사용자 결정)

- 고정 9종 참조 데이터가 아니다. 관리자가 포지션을 추가·수정·삭제할 수 있다.
- PRD가 원래 명시한 관리자 수정 권한은 기본 필요 인원과 성별 조건 둘뿐이었고, 포지션 집합 자체를 바꿀 수 있는지는 공백이었다. 그 공백을 CRUD 허용으로 메웠다.
- 성별 조건의 값 집합(제한 없음·남성·여성)은 고정이며 관리자가 새 조건 종류를 만들지 않는다.
- 대가: 배정 자격 검사·기본 포지션 자동 부여·개인별 가능 포지션이 닫힌 9종이 아니라 열린 집합을 가정해야 한다.

**2. 사용된 포지션은 삭제 대신 비활성화** (사용자 결정)

- 배정이나 개인별 가능 포지션에 한 번이라도 쓰인 포지션은 삭제할 수 없다. 비활성화만 할 수 있고 과거 기록은 그대로 남는다.
- 한 번도 쓰이지 않은 포지션만 하드 삭제한다. 오타로 만든 포지션을 지울 수 있게 하되 이력은 지키기 위한 절충이다.
- **UI가 아니라 DB 참조 제약으로 강제한다.** 화면이 뚫려도 과거 배정·예상 급여가 가리키는 대상이 사라지지 않는다.
- PRD의 다른 이력 보존 원칙(출퇴근 원본 불변, 탈퇴해도 확정 배정은 `change_required` 표시)과 같은 방향이다.

**3. seed는 로컬 개발 전용** (사용자 결정)

- seed는 `supabase db reset` 흐름에서만 동작하고 운영 DB에는 실행하지 않는다.
- 운영의 초기 포지션과 venue 설정은 1회성 데이터 migration으로 넣는다. 그 뒤 정본은 DB다.
- 포지션을 관리자 CRUD로 연 이상 seed가 운영 정본이면 두 정본이 싸운다. 관리자가 안내를 3명으로 바꿔둔 상태에서 seed를 재실행하면 2명으로 되돌아가는 데이터 손실 경로를 막는다.
- 기존 인수 조건이 이미 "빈 로컬 DB에서"라고 못 박은 것과도 맞는다.

### 해석과 가정

- 해석: `positions`는 관리 대상 테이블이 되고 배정 자격 검사는 열린 집합을 가정한다. 스키마 자체는 크게 달라지지 않지만 삭제가 새 문제를 만들며, 그것이 결정 2로 닫혔다.
- 가정(사용자가 명시 확인함): 성별 조건 값 집합은 고정이다.

### 다루지 않기로 한 것

- venue의 저장 형태(테이블 대 단일 설정 행)는 제품 판단이 아니라 기술 판단이므로 2단계(설계)로 넘긴다. 단일 장소는 이미 승인된 제품 결정이다.
- RLS를 켜는 시점(P0-T03 대 P1 인증 도입 시)도 기술 판단이라 RADIO에서 정한다. 권한을 DB 정책에서 강제한다는 규칙 자체는 이미 승인돼 있다.

### 미결 사항

- **새 포지션의 기본 포지션 지정이 소급되는가** — 결정 주체: 사용자, 반환할 단계: 기획(P1-T05 또는 P3-T03). PRD는 안내·매니저·축가를 기본 포지션으로 두고 승인된 근무자에게 자동으로 가능 상태를 적용한다. 관리자가 새 포지션을 기본으로 지정하면 이미 승인된 전원에게 소급 적용되는지, 이후 승인자부터인지가 정해지지 않았다. 대량 권한 부여라 가볍지 않다. P0-T03의 스키마를 바꾸지 않으므로 이 task를 막지 않는다.
- **P3-T02의 범위가 넓어진다** — 결정 주체: 사용자, 반환할 단계: 기획(P3-T02). 지금 요약이 "9개 포지션 설정"인데 CRUD(추가·삭제·비활성화)가 붙어야 한다. P3-T02는 아직 `proposed`라 자체 기획 승인 때 확정한다. 결정을 잃지 않도록 PRD와 P3-T02 phase 절에 기록했다.

### 인계 — 정합화한 문서

승인 후 PRD → DOMAIN → phase 순서로 반영했다.

- `docs/product/PRD.md` 4장 — 포지션 표가 고정 목록이 아니라 시작 시점 값임을 명시하고, CRUD 권한·성별 조건 값 고정·삭제 대 비활성화 규칙을 추가했다.
- `docs/product/DOMAIN.md` — 공통 언어에 `position`과 `position.is_active = false`를 추가하고, `DOMAIN:SCHEDULING`의 책임과 소유 데이터에 포지션 목록을 넣었다.
- `docs/execution/phases/00-foundation.md` P0-T03 절 — 목표·비목표·인수 조건 5종·기획 승인·이월 미결 사항을 기록했다.
- `docs/execution/phases/03-assignment-and-confirmation.md` P3-T02 절 — CRUD로 범위가 넓어진 사실과 인수 조건 2건을 추가하고, 기획 승인이 아직 없다는 점을 명시했다.
- `docs/execution/phases/index.jsonl` — P0-T03을 `design_pending`으로 두고 `product_approval`, 갱신한 `summary`와 `verification` 5종을 기록했다.

ADR은 만들지 않았다. 포지션 CRUD는 제품 범위 결정이라 PRD가 소유하고, seed 정책은 P0-T03 RADIO가 다룰 수준이다. 이후 다른 phase에서도 같은 seed 판단이 반복되면 그때 ADR로 승격한다.
